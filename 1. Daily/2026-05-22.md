### Keycloak 동기화 메모

- **로컬 KC** (`localhost:8180`) ≠ **194 KC** (`192.168.10.194:8080`) — 별도 인스턴스, 별도 DB
- 로컬 KC DB = 로컬 Postgres 컨테이너(`db_postgres:5432/keycloak`)
- 194 KC = 194 서버 자체 DB
- 매칭 우선순위 (`account_service.py:209-365`): UUID → code → 신규 생성
- 그룹명 = DB `code` (path leaf name)
- `keycloak_group_id` NULL이면 로그인 시 자동 backfill 가능하나 수동 선반영이 안전
- Keycloak 테이블:
  - `user_entity` (id, username, email, first/last_name, realm_id)
  - `user_group_membership` (group_id, user_id)
  - `credential` (해시 비밀번호)
  - `spx_accounts.sub` = Keycloak `user_entity.id`

### web-ui Keycloak 연결 사전 분석 18항 (오늘 협의)

> 데모 = LLM 데모 사이트(`web-ui` 프로젝트, 옛날 만든 거). 로그인 화면 UI만 있고 실제 기능 미구현 → spx-agent의 Spelix realm + 194 Keycloak 인프라 재활용해서 실제 동작 붙이는 작업.

**web-ui 프로젝트 현황**
1. 위치/스택 확인 (Next.js/React/Vue, 라우팅)
2. 현재 로그인 화면 구현 수준 (form UI만 vs submit 핸들러 stub)
3. 백엔드 유무 — LLM 직접 호출 vs API 게이트웨이
4. 세션/상태 관리 패턴 + 라우팅 가드

**spx-agent Keycloak 패턴 재활용**
5. spx-agent의 Keycloak 통합 코드 위치 (OIDC 흐름 / 토큰 발급·저장·리프레시)
6. 사용 라이브러리 (keycloak-js / next-auth / 자체 PKCE)
7. api 측 토큰 검증 미들웨어 필요 여부 — 프론트 검증으로 충분한지

**Spelix realm 데모용 분리**
8. Keycloak client 신설 vs 공유 (redirect URI 다르면 신설 필수)
9. 데모 접근용 계정 발급 방식 (별도 `DEMO` 그룹 신설 vs 단일 계정 공유)
10. redirect URI 사전 등록 (dev/배포 URL 모두)

**인증 흐름 설계**
11. 토큰 보관 — localStorage vs httpOnly cookie (web-ui 백엔드 유무에 따라)
12. LLM 호출에 토큰 첨부 여부 + 검증 위치
13. 로그아웃 흐름 — Keycloak `/logout` + 로컬 정리
14. 토큰 만료/리프레시 (silent refresh vs 재로그인)

**운영**
15. 환경 변수 — `KEYCLOAK_URL` / `REALM=spelix` / `CLIENT_ID` / `REDIRECT_URI` (dev/배포 분기)
16. CORS — 194 Keycloak이 web-ui origin 허용

**리스크**
17. 승랑님 패턴이 spx-agent 전용이라 web-ui SSR 차이/API route 유무로 부정합 가능
18. web-ui가 옛 코드라 라이브러리 버전 충돌 (keycloak-js ↔ React 버전)

→ 우선순위 톱 4: **1 → 3 → 5~7 → 8**. 4개 확정되면 통합 전략(SPA-only PKCE vs SSR+httpOnly cookie) 결정 자동.
