## 배운 것

### 결함 처리에는 두 가지 경로가 있다 — 방어 vs 회피
오늘 spec 작성 중 가설 결함 3개(`DRILL-LAYOUT-DRIFT`, `DRILL-ESC-PROPAGATION`, `DRILL-STATE-RESIDUAL`)를 식별했는데, 처리 방식이 셋 다 달랐음. 여기서 새로운 패턴 학습:

1. **방어 가능 결함** → `defect-catalog.md`에 Harness ID로 등록 → AI 구현 시 "이걸 방어해" 지시 가능
   - 예: H-DASH-01 (ADVANCED_CHAT 토큰 이중 카운트) — 코드를 잘 짜면 회피 가능, 안 지키면 결함
2. **회피 가능 결함** → 마운트 환경 규칙(`CLAUDE.md`)이나 conventions로 흡수 → 애초에 결함 발생 코드를 안 씀
   - 예: ESC 핸들링 — 모달 환경에서는 ESC가 항상 모달 닫기 계약. 가로채는 코드 자체를 금지하는 게 깔끔
3. **그냥 일반 위생** → 결함 카탈로그에 안 들어감 (catalog 신뢰도 보호)
   - 예: ~~DRILL-STATE-RESIDUAL~~ — 일반 React state 위생, 도메인 함정 아님

→ **catalog는 "방어 코드 패턴" 모음**이고, **마운트 환경 규칙은 "이 환경에서 안 해야 할 행동" 모음**. 둘은 다른 도구.

### 가설 결함을 catalog에 박지 마라
spec 작성 중 떠오른 가설을 그대로 catalog에 등록하면 catalog 신호 대 잡음비가 흐려짐. **검증 절차**:
- spec 단계: `harness_candidates` 후보로만 표시 (frontmatter 분리, 정식 `harness: []`와 구별)
- 검증: (a) 소스 분석으로 입증 (b) 구현/테스트로 실제 발생 확인
- 검증 통과한 것만 정식 ID 부여 + catalog 등록

### 소스 분석은 spec 단계의 가설 검증 도구다
- `DRILL-ESC-PROPAGATION`은 spec 작성 단계에서 "모달 환경 가설"이었음
- `account-setting/menu-dialog.tsx` + `index.tsx:212` 소스 분석 5분 → **"ESC = 모달 닫기" 명시 UX 계약** 발견 → 가설 입증 + 회피 결정 도출
- spec 검증을 구현 단계까지 미루지 말고, **저비용으로 끝낼 수 있으면 spec 단계에서 처리** → 1단계 구현 후 발견하는 비용보다 훨씬 저렴

### Mount와 drift — Docker dev 환경의 본질
오늘 mount 관련 이슈로 헤맸음. 끝에 가서 멘탈 모델이 풀림. 정리:

**1. 컨테이너 ≠ 호스트 코드 띄운 것**
- 컨테이너는 **이미지(Dify팀이 만든 박제 스냅샷)에서 띄워짐**
- 호스트 코드는 사용자가 git에서 별도로 pull한 것
- **둘은 처음부터 별개 코드베이스**

**2. Mount = 호스트 폴더 ↔ 컨테이너 경로를 같은 곳으로 연결하는 트릭**
- `../api:/app/api` = 컨테이너가 `/app/api` 보면 사실은 호스트의 `~/projects/spx-agent/api/` 직접 보고 있음
- 코드 변경 즉시 반영 → dev 속도 ↑
- 부수 효과: 호스트의 모든 파일이 컨테이너에 노출됨

**3. Drift = 호스트와 컨테이너 환경의 시간 간격**
- 호스트 환경 = 사용자가 setup 시점에 한 번 정함 (Node 20, Python 버전 등)
- 이미지 환경 = Dify가 빌드 시점에 박음
- **Dify는 살아있는 프로젝트** → 시간 지나며 의존성/코드/환경 요구사항이 진화
- 사용자 환경은 자동 따라가지지 않음 → drift 누적

**4. 오늘 발견한 drift 3건**
| 영역 | 사용자 setup 시점 | Dify 현재 | 노출 |
|---|---|---|---|
| Python 의존성 | 옛 .venv | graphon 추가됨 | 이미지 재빌드 필요 |
| Python 코드 | 옛 Dify 코드 | 호스트 신 코드 (SQLAlchemy 안티패턴) | mount로 노출 (plugin/DSL) |
| Node 버전 | 호스트 20 | vinext가 22 요구 | vitest 부팅 불가 |

→ **셋 다 같은 본질**: "사용자가 이전에 결정한 환경 ↔ 현재 Dify 요구사항" 사이의 시간 간격.

**5. 운영 원칙 — 주기적 동기화**
- drift는 자연스러운 현상. 막을 수 없음.
- **주기적으로 환경 체크 + 업데이트**가 dev 운영의 일부.
  - Node 버전 (호스트)
  - Python 의존성 (컨테이너 .venv 재빌드)
  - 이미지 버전 (registry pull)
- 발견 시점은 보통 "갑자기 뭐가 안 됨" → 그때마다 drift 한 조각 메움.

**6. Mount 트레이드오프 (내일 검토 섹션 참조)**
- mount 사용 → 빠른 dev + drift 노출
- mount 제거 → 느린 dev + drift 잠복 (운영 시 노출)
- 우리 선택: mount + 발견 버그 case-by-case patch

### 내일 검토 — Mount 트레이드오프 결정 (보류)

**문제**: docker-compose.override.yaml의 통째 mount(`../api:/app/api`)가 호스트 신코드의 잠복 버그를 컨테이너에 노출
- 오늘 2건 발견: plugin auto-upgrade DetachedInstanceError + DSL import expire_on_commit 누락
- 둘 다 같은 SQLAlchemy 안티패턴 (`with sessionmaker.begin() as session: return obj`)
- mount 안 했으면 → 컨테이너는 이미지의 옛 Dify 코드 사용 → 버그 잠복 (안 보임)
- mount 후 → 호스트 신 Dify 코드 사용 → 버그 활성화

**왜 mount했었나** (히스토리):
1. 처음엔 individual mount (몇 파일만) — 사용자 기존 패턴
2. admin/dashboard.py 추가 후 admin/__init__.py 못 찾음
3. 부분 mount(`admin/` 폴더) 시도 → `ImportError: LangContentDict` (admin/__init__.py가 호스트 신 billing_service.py 의존)
4. 통째 mount로 전환 — graphon, LangContentDict 등 의존 체인 한 번에 해결
5. 부수 효과: **모든 호스트 파일 노출 → 잠복 버그 활성화**

**옵션 A. 현재 유지 (mount + 버그 patch)**
- 비용: 발견되는 버그마다 patch (오늘 2건 = 그리 많지 않음)
- 장점: 빠른 dev, refactor 없음
- 같은 안티패턴 grep으로 한번에 일괄 patch 가능 (5분)
- Dify upstream이 fix하면 자동 해소

**옵션 B. mount 제거 + refactor**
- admin/__init__.py가 LangContentDict 의존 제거 (Dify 기능 일부 잘림 가능)
- graphon 등 다른 import 체인도 정리
- 1~2시간 작업
- 장점: 호스트 신코드 노출 없음, 깔끔
- 단점: refactor 비용

**옵션 C. mount 빼고 build만 사용**
- ❌ 의미 없음 — Dockerfile이 호스트 코드를 이미지에 박으므로 같은 버그 그대로

**오늘 결정**: **A 유지** (실용적). 내일 다시 볼 때 옵션 B 무게가 더 크다면 전환 검토.

**내일 검토 시 고려할 것**:
- 같은 안티패턴이 더 발견되면 일괄 patch (`grep "with sessionmaker"`)
- DSL import fix 동작 확인
- 2번 더 같은 패턴 발견되면 옵션 B 진지하게 재검토 — 패턴이 너무 흔하면 patch보다 mount 제거가 낫다
