사용자가 업로드한 n8n 워크플로우처럼 복잡한 SQL 쿼리 실행과 이메일 전송 로직을 구현할 때 매우 중요한 선택 기준이 됩니다.

---

## 1. Function Calling (함수 호출 방식)

모델 자체가 특정 도구를 언제, 어떤 파라미터로 호출해야 하는지 구조화된 데이터(JSON)로 직접 출력하도록 훈련된 방식입니다.

- **동작 원리**: LLM이 사용자의 질문을 분석한 뒤, "지금 `execute_sql` 도구가 필요하고 파라미터는 `{"sql": "SELECT..."}`이다"라고 명확히 짚어줍니다.
    
- **장점**:
    
    - **속도와 정확도**: 도구 호출 판단이 빠르고 파라미터 형식이 정확합니다.
        
    - **안정성**: 최신 모델(GPT-4o, Claude 3.5 Sonnet 등)은 이 방식에 최적화되어 있어 오류가 적습니다.
        
- **단점**: 모델이 Function Calling 기능을 공식적으로 지원해야만 사용할 수 있습니다.
    

## 2. ReAct (Reason + Act 방식)

"생각(Reasoning)하고 행동(Acting)한다"는 뜻으로, 모델이 스스로 추론 과정을 텍스트로 써 내려가며 도구를 사용하는 방식입니다.

- **동작 원리**: `Thought(생각) -> Action(도구 선택) -> Observation(도구 결과 확인) -> Thought...` 단계를 반복합니다.
    
- **장점**:
    
    - **추론 과정 투명성**: AI가 왜 이 도구를 썼는지 논리적인 흐름을 확인할 수 있어 디버깅에 유리합니다.
        
    - **범용성**: Function Calling 전용 인터페이스가 없는 오픈소스 모델(Llama 3 등)에서도 프롬프트만으로 구현 가능합니다.
        
- **단점**: 추론 과정이 길어지면 답변 속도가 느려지고, 가끔 엉뚱한 단계에서 루프에 빠질 위험이 있습니다.

|**적합한 모델**|GPT-4, Claude 3, Gemini 등 최신 상용 모델|오픈소스 모델 또는 추론 과정이 중요한 경우|

|**응답 속도**|상대적으로 빠름|추론 과정을 생성해야 하므로 상대적으로 느림|

## 💡 결론: 어떤 것을 선택해야 할까요?

사용자의 n8n 워크플로우처럼 **데이터베이스 스키마를 확인하고, 컬럼을 조회한 뒤, 최종 SQL을 실행하는 '여러 단계의 도구 활용'**이 필요한 경우 다음과 같이 선택하시는 것을 추천합니다.

1. **GPT-4o나 Claude 3.5 Sonnet 같은 고성능 모델**을 사용하신다면: **Function Calling**을 선택하세요. 훨씬 깔끔하고 빠르게 작동합니다.
    
2. **직접 구축한 sLLM(Ollama 등)**을 Dify에 연결해 사용하신다면: 모델이 Function Calling을 완벽히 지원하지 않을 수 있으므로 **ReAct** 방식이 더 안정적일 수 있습니다.
    

특히 사용자가 관심 있어 하시는 **sLLM(Small Language Model) 기반의 프로젝트**라면, 모델의 체급에 따라 ReAct 방식이 도구 사용의 논리를 잡는 데 더 도움이 될 것입니다.

|**모델 계열**|**추천 방식**|**이유**|
|---|---|---|
|**qwen3-30b**|**Function Calling**|Qwen 시리즈(30B 이상)는 오픈소스 중에서도 Function Calling 성능이 매우 뛰어납니다. 복잡한 SQL 생성 시 구조화된 출력을 가장 잘 내보낼 모델입니다.|
|**gpt-oss-20b / latest**|**ReAct**|해당 모델들이 특정 Task에 특화된 sLLM이라면, 명시적인 추론 단계(Thought)를 거치는 ReAct 방식이 도구 사용 오류를 줄이는 데 도움이 됩니다.|
|**qwen3-vl-32b**|**Function Calling**|시각 지능(VL) 모델이지만 언어 모델 체급이 32B로 커서 복잡한 로직 처리에 능숙합니다.|

각 모델이 **'도구 호출(Tool Calling)' 기능을 공식적으로 지원하느냐**에 따라 Dify가 자동으로 필터링해주기 때문에 발생합니다.

## 1. Function Calling 전략에서 모델이 적게 뜨는 이유

**Function Calling**은 모델 학습 단계에서부터 "도구를 사용할 때는 이런 JSON 형식을 내뱉어라"라고 특수 훈련된 모델만 사용할 수 있는 기능입니다.

- **gpt-oss 시리즈**: 이름에서 알 수 있듯이 GPT 계열(또는 해당 구조를 모방한 모델)로, Dify 시스템이 '이 모델은 API 수준에서 Function Calling 출력을 지원한다'고 판단하여 목록에 노출되는 것입니다.
    
- **나머지 모델 (Qwen 등)**: Qwen3 같은 훌륭한 모델도 내부적으로는 도구를 잘 쓰지만, Ollama나 Vllm 설정을 통해 연결할 때 **표준화된 Function Calling 인터페이스**가 활성화되어 있지 않으면 이 목록에서 제외됩니다.
    

## 2. ReAct 전략에서 모델이 더 많이 뜨는 이유

**ReAct**는 모델의 특수 기능이 아니라 **'프롬프트 기법'**입니다.

- **작동 방식**: "너는 도구를 쓸 수 있어. 생각하고(Thought), 행동하고(Action), 관찰해(Observation). 자, 이제 시작해!"라는 긴 지시문을 모델에게 전달하는 방식입니다.
    
- **범용성**: 일반적인 대화가 가능한 텍스트 생성 모델이라면 이론상 모두 가능합니다. 따라서 Dify는 사용자가 보유한 **`qwen3-30b`**, **`qwen3-vl-32b`** 등의 모델도 "프롬프트로 가르치면 도구를 쓸 수 있다"고 보고 목록에 모두 띄워주는 것입니다.
