## 배운 것
- spx-agent Keycloak 소스 분석 4 Phase 완료 → 이식 대상/생략 대상 분류 ([[0. Inbox/2026-05-28 web-ui Keycloak Phase 1 — 핵심 흐름 분석]] ~ Phase 4)
- spx-agent 1,000줄+ → web-ui ~320줄로 경량화 가능 (Flask-Login 제거, JIT provisioning 생략, PKCE/force-login 미이식)
- PyJWKClient 싱글턴 + threading.Lock 패턴: gevent 환경에서 매 요청마다 생성하면 HTTPS 핸드셰이크 충돌 발생 → 모듈 레벨 싱글턴 필수
- httpOnly cookie + SameSite=Lax 조합이면 CSRF 토큰 없이도 단일 도메인 데모 수준의 방어 충분
- Next.js rewrite 프록시는 same-origin이므로 기존 fetch 호출에 `credentials` 미지정이어도 cookie 자동 전송됨 (기본값 `same-origin`)
- gunicorn 뒤에서 `request.is_secure`가 `X-Forwarded-Proto` 누락 시 False 반환 → `COOKIE_SECURE` 환경변수로 명시 통제
- `.gitignore`에 `.env` 포함된 상태에서 `.env`를 새로 만들면 기존 설정(DB URL, API 키 등) 유실 위험 — 항상 기존 파일 확인 먼저
- **Keycloak ROPC 토큰 발급 시 "Account is not fully set up" 에러** — Required Actions가 비어있어도 발생. User Profile 정책의 First/Last name/Email 필수 필드 미입력이 원인. [[4. 지식노트/Keycloak - User Profile 정책으로 ROPC 토큰 발급 실패하는 함정]]
- **authFetch 래퍼 패턴** — access 만료 시 단순 redirect 금지, 401 intercept → refresh → 재시도. in-flight promise 공유로 동시 호출 race 회피. [[4. 지식노트/웹 인증 - authFetch 래퍼 패턴 (401 intercept + auto refresh)]]
- **JWT lifespan 정합 확인** — IdP 설정값을 코드/문서로만 믿지 말고 토큰 받아서 `exp - iat`로 실측. 5/28 refresh token 2시간 발견 (설계 30일과 큰 차이). [[4. 지식노트/JWT - 토큰 lifespan 정합 확인 (exp - iat)]]
