### 2단계 레이어별 측정 — 마트 가치 판정 뒤집힘 ⭐
- **방법**: nginx `log_format`에 `$request_time` + `$upstream_response_time` + `$upstream_header_time` 추가 → 모든 요청의 백엔드 시간 자동 수집. Flask 미들웨어 박을 필요 없음.
- **DB는 무죄**: messages 375 / workflow_runs 75 양에서 EXPLAIN ANALYZE 결과 모든 쿼리 < 2ms. 9-CTE 최복잡 쿼리도 1.5ms.
- **백엔드 non-DB가 99.9%**: Phase 1 엔드포인트 2.4~2.7s 중 DB는 1.5ms. 차이 약 1800배.
- **마트화 결정**: 현재 데이터 양에서는 마트 만들어도 효과 0. 운영 데이터 양 확보 후 재측정 필요.
- **5/8 예상이 뒤집힌 이유**: 화면 wall clock 10초 = 백엔드+프론트+토스트 retry 누적. DB 가설은 mock 데이터 양 미체크였음.
- **부수 발견 (보류)**: 1요청당 JWT 검증 + account/tenant 조회가 **59번 redundant 실행** → [[4. 지식노트/Dify - 대시보드 API 백엔드 2.7초 병목 분석 (Flask-Login 캐시 미작동).md]]. 원인 추적은 옵션 C(보류) — Dify upstream + keycloak patch + ssp RBAC 결합 영역. 신입 단독 fix 영역 아님. 김이사님/팀 공유 후 결정 필요.

### 측정 산출 — Phase 1 vs Phase 2 패턴
- Phase 1 4개 동시 진입: 거의 동일하게 ~2.7초 (쿼리 복잡도 무관, 공통 오버헤드)

### PM/김이사님 확인 항목 — 마트 fact 설계 정합성 (12종 추론에서 도출)

**자체 결정 완료 (확인만 받으면 됨):**
- ✅ "활성 사용자" 정의: `messages` UNION `workflow_runs` 로 통일 → dept-dau 코드 수정 필요
- ✅ ⑱ 부서별 에러 테이블 "주원인" 표시: 정규화 라벨 사용 → 단 처리 방식은 audit collector 동작 확인 후 결정
- ✅ Silver fact_event 안 만들기: audit이 이미 80% 역할 함, 우리 ETL 추가 부담 피함

**결정 필요 4개:**

1. **"부서별" 차트의 부서 기준** ⭐ 가장 큰 영향
   - 현재 코드: ⑮⑯⑰⑱ = 앱 소유 부서 / ⑫⑬ = 사용자 소속 부서 (혼재)
   - 의미 차이: 마케팅 직원이 재무 앱 호출 100회 → 앱 소유 관점은 재무에, 사용자 소속 관점은 마케팅에
   - 선택지: (a) 앱 소유 — 거버넌스 / (b) 사용자 소속 — 활용도 / (c) 토글 (마트에 양쪽 다 박음, 추천)

2. **신규/이탈 정의** (가벼움 — yes/no)
   - 현재 코드: 활동 기반 (처음 메시지 / 활동 끊김)
   - 활동 기반이 자연스러운데 계정 기반(입사/퇴사) 의도였는지 확인만

3. **top-error-types 차트 범위** (옵션 C/D/E 결정에 영향)
   - (a) 호출 중 에러만 (model_timeout, rate_limit 등) → 옵션 D(OLTP 정규식) 가능
   - (b) 보안 이벤트 포함 (auth_failed 등) → 옵션 C(audit) 필수, OLTP에 행 없음
   - (c) 둘 다 → 옵션 E(절충: 호출은 OLTP, 보안은 audit)

4. **운영 환경 `messages.from_end_user_id` 값 패턴** — VSCode Claude 조사 완료
   - **mock 잘못된 패턴 확정**: mock에선 88%가 `account.id`이지만 실제 운영은 `end_user.id` (별도 UUID)
   - Dify는 두 컬럼이 배타적: 외부(웹앱/API) → `from_end_user_id`, 콘솔(어드민/직원) → `from_account_id`
   - Keycloak 패치는 이 로직 영향 없음
   - **마트 시사점**:
     - `fact_user_activity_daily.user_id` = `COALESCE(from_end_user_id, from_account_id)` UNION
     - 사용자 소속 부서(`actor_dept_id`)는 `from_account_id`만 매핑 가능. 외부 사용자는 `is_external=TRUE` 플래그로 박음
     - 앱 소유 부서(`owner_dept_id`)는 `app_id → resource_ownership` 매핑이라 사용자 유형 무관
   - **결정 완료** (사용자): 외부 사용자는 부서별 차트에서 "외부" 라벨로 별도 표시 (H-DASH-04 "미배정"과 의미 분리)
   - PM 확인 항목: 비즈니스 측면 "외부 고객 챗봇 발급 정책 있나?" (있으면 외부 트래픽 비중 가늠)
