## 배운 것

### 1. 부하 측정의 본질 — 단독 vs 동시 분리
- 약식 측정(EXPLAIN ANALYZE) = DB 단독 = 운영 환경 일부만 보여줌
- 정식 측정(k6) = 전 스택 + 동시성 효과 = 진짜 운영 환경
- 둘 사이의 격차가 진짜 진단의 시작점
- 오늘: DB 단독 7ms vs 단일 호출 1.9s = **DB 위 레이어(Flask-Login) 0.4s + 측정 환경(work_mem) 1초** 분리됨

### 2. work_mem과 external merge sort
- `work_mem 4MB` (Dify 환경변수 기본) → 정렬 작업이 한도 초과 시 디스크 임시 파일
- 증거 = `Sort Method: external merge Disk: 4496kB` + `temp read/written` 1,600+
- 16MB로 늘리면 디스크 sort → 인메모리 sort = 1.48s → 484ms (3배)
- 진짜 해결책 = 시드 분포 정상화 (정렬 대상 행 수 자체 줄이기)
- 운영 환경에서는 자연 분포로 4MB로도 충분할 가능성 큼

### 3. N+1 패턴이 진짜 원흉이 아닐 수도 있음
- 5/19 약식 측정에서 dept-user-activity 5.8초 = N+1 7쿼리로 진단
- 5/20 단일 CTE 통합 후에도 5.9초 → N+1은 0.1초 영향에 불과
- 진짜 원인 = base CTE 437K행 정렬 (work_mem 부족)
- N+1 통합은 정답이긴 했지만 본질 원인 아니었음 — **다층 진단 필요**

### 4. 시드 데이터가 운영 환경 대표성 좌우
- 시드 카디널리티 + 시간 분포 + 분포 패턴(균등 vs power-law)이 측정값을 완전히 좌우
- 5/19 시드 = 30일 편중 + 균등 분포 = 인위적
- 5/20 시드 = 90일 균등 + power-law (Pareto) = 운영 환경 가까움
- **측정 환경이 진짜 운영처럼 되어야 측정값이 의미 있음**

### 5. spec 갱신 없이 코드만 고치면 drift 누적
- 5/14 누락 트랙 = spec은 갱신됐는데 코드 미정합
- 6일 누적 → 부하 테스트에서 옛 명세 NOT IN 쿼리가 진짜 병목 노출
- 거꾸로 5/20 KPI 1+3 정합 = 코드가 정답이라 spec 갱신 (코드 쪽으로)
- 본질 = **spec과 코드는 한 PR에서 같이 정합**, 한쪽만 박으면 잠재 부채

### 6. 5/11에 진단한 것이 5/20에 그대로 살아있음 (Flask-Login)
- 5/11 진단: 1요청당 59회 redundant load = 백엔드 2.7초 99.9%
- 5/20 현재: 데이터 양 커지면서 DB 비중 늘었지만 Flask 0.42초 잔존
- 매일 이월(5/11~5/18) 항목인데 김이사님 보고 못 함
- 데이터로 다시 확인된 상황 = 이번엔 보고 우선순위 올려야 함

### 시드 재구성 power-law 분포

위임 측이 PROMPT 범위 외 사용자 지시로 추가 적용:
- 상위 10개 앱이 호출 40% (Pareto)
- 상위 20명 사용자가 활동 35%
- 상위 5명 소유자가 25앱 소유
- 에러 9앱+ 분산 (모듈러 해시 상관관계 제거)
- 모델 threshold 0-1000 스케일 통일 (이전 0-100 vs 0-1000 혼용)
