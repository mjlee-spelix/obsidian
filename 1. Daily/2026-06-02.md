## 배운 것

### Dify Enterprise vs Community Edition 경계 인식
- 페이지 frontmatter `tag: "ENTERPRISE"`가 명시되어 있으면 **Cloud/Enterprise 한정 기능** — CE 기반 fork(spx-agent)에서는 페이지 통째 폐기 대상
- 코드 분석만으로는 헷갈리는 경우 있음 (예: WebApp access mode 3가지 backend 코드 → enterprise microservice 위임이라 실질 비노출)
- **frontmatter tag 확인이 1차 판단 도구**, 코드 분석은 보조

### "sandbox" 용어 모호성
- 같은 단어가 두 가지 다른 개념 가리킴:
  - **SaaS Sandbox 워크스페이스**: Cloud의 테스트 환경 (spx-agent엔 없음, 분기 제거 대상)
  - **보안 격리 Sandbox 컨테이너**: `langgenius/dify-sandbox` (Code 노드 실행 격리, spx-agent에 실제 존재 — 보존 대상)
- 글로서리/규칙 작성 시 동음이의어 명확화 안 하면 Phase 4 포팅 중 혼동 발생

### "관리자" 표현 모호성
- 사내 시스템에서 "관리자"는 두 층위:
  - **워크스페이스 관리자**: Dify role Owner/Admin/Editor
  - **시스템 관리자**: 인프라/배포/env var 만지는 사람
- 사용자 매뉴얼에서 무작정 "관리자" 표기하면 어느 쪽인지 안 명확 → 수집 단계에선 원문 발췌만 유지, 노출 시점에 구분

### 전역 규칙 박제의 효율
- "페이지마다 매번 판단"은 비용 큼 + 일관성 깨지기 쉬움
- 1~2개 페이지에서 발견된 패턴이 전역 규칙으로 박힐 만한지 즉시 판단 → 박으면 나머지 페이지는 자동 처리
- 오늘 5개 규칙 박은 후 검토 속도 체감상 2~3배 빨라짐

### 같은 단어, 다른 위치 — Dify docs 자체의 분류 문제
- Dify docs 페이지 제목 = "Analysis", UI label = "Monitoring" — 같은 영역인데 명칭 분리
- 한국어 번역 시 UI label 우선이 자연스러움 (사용자가 실제 보는 라벨)
- 글로서리에 매핑 박을 때 "원본 페이지 제목 → 우리 번역"이 아니라 "UI label → 우리 번역" 기준 필요

### baseline 정합 — 라이브 docs 함정
- `docs.dify.ai` 라이브는 최신 버전(1.14+) 렌더링
- 우리 baseline은 1.13.3 (`5c1c3a4c`) → 라이브에서 본 페이지가 우리 매트릭스에 없으면 1.14 신규 추가일 가능성
