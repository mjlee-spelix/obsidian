```
문의 주신 내용에 대해 답변드립니다.

현재 데모 시스템의 Multi Agent 구성은 말씀하신 대로 Agent를 도구(Tool)로 등록하여 호출하는 Tool-Use 방식으로 구현되어 있습니다.

A2A 프로토콜을 적용하지 않은 이유는, 현재 데모의 모든 Agent가 동일 플랫폼(Dify) 내에서 동작하고 있어 A2A의 핵심 이점인 이기종 프레임워크 간 통신이나 독립 서비스 배포의 필요성이 크지 않았기 때문입니다. 동일 플랫폼 내에서는 Tool-Use 방식이 구현이 간결하고 별도의 네트워크 통신 없이 플랫폼 내부에서 직접 호출이 가능하여 현 단계에서는 더 적합하다고 판단하였습니다.

다만, A2A 적용은 기술적으로 가능합니다. Dify Marketplace에서 A2A Server/Client 플러그인을 지원하고 있어, 각 Sub Agent를 독립 서비스로 분리한 뒤 A2A Server로 노출하고 Master Agent에서 A2A Client로 호출하는 구조로 전환할 수 있습니다. 향후 다른 프레임워크로 개발된 Agent와의 연동이나 독립적인 배포/확장이 필요한 경우, A2A 전환을 고려해볼 수 있을 것으로 보입니다.
```

```
Dify는 워크플로우 내 노드(LLM, Tool, Agent 등) 간 데이터 전달과 오케스트레이터-노드 간 상태 공유에 'Variables'라는 플랫폼 고유의 내부 상태 관리 메커니즘을 사용하며 서로 다른 Agent 애플리케이션 간 외부 통신에는 A2A 프로토콜 등 별도 표준으로 구현 할 수 있습니다.

|---|---|

|Dify에서 A2A 사용 가능?|플러그인으로 외부 앱 간 통신 가능|
|A2A가 내부 노드 통신에 적합?|오버헤드 과다, 상태 공유 어려움|
|A2A 도입이 가장 효과적인 시나리오?|이종 프레임워크/외부 에이전트 통합|
```
