## 배운 것

### gunicorn은 자동 reload 안 함 — endpoint 추가 후 `restart` 필수
- api 컨테이너가 override mount로 호스트 코드를 보긴 하지만, Python 프로세스는 시작 시점에 import한 모듈 트리만 들고 있음
- 신규 폴더(`controllers/console/dashboard/`) + Blueprint 등록 위치 변경은 프로세스 reload가 별개
- 증상: 프론트가 새 endpoint 호출 → 404
- 해결: `docker compose restart api worker` 한 번. destroy/recreate 불필요
- 데드라인: [[3. 프로젝트/spx-agent/conventions.md]] "신규 endpoint/service 추가 후 컨테이너 재시작 의무" 박혀 있었음 — 다음에는 endpoint 변경 시 자동 반영 기대 X

### 라우트 페이지의 카드 톤 위계 — 모달 환경과 다름
- 모달 시절엔 PROVIDER 탭 단일 톤(`bg-components-card-bg + shadow-xs`)이 자연 — 좁은 공간 + 위계 단순
- 라우트 페이지 첫 실측: 같은 단일 톤이 시각적 무게 어색 → **메인 카드(KPI) vs 컨테이너 카드(차트·표)** 위계 필요
- 결론: 스튜디오/지식 페이지가 이미 같은 패턴 — `AppCard`(콘텐츠 메인) / `NewAppCard`(섹션 컨테이너)를 그대로 차용
- 일반화: 같은 디자인 토큰이라도 *마운트 환경*(모달 vs 라우트 페이지)이 톤 위계 요구를 다르게 만듦

### Generated Column + JSONB의 마트 인터페이스 가치
- collector 14종이 각자 다른 details 구조 → 모든 collector에 컬럼 INSERT 강제 시 *스키마-collector 강결합* 발생
- DB 측 `GENERATED ALWAYS AS (details->>'X') STORED`로 추출 위임 → collector는 자유롭게 details 박고 DB가 컬럼화
- `STORED` 사유: `VIRTUAL`은 매 쿼리 계산이라 인덱스 불가
- expression index (`CREATE INDEX ON (details->>'X')`) 대안 대비 핵심 이점: audit_events 자체가 모든 소비처(마트 + 보안 + 운영)의 공용 인터페이스가 됨

### MView 사전 JOIN 옵션 B — "ID만 박고 이름은 query-time"
- 비싼 결합(audit × dept_members 만 단위)은 refresh 시 1회로 흡수
- 작은 dimension(부서명, 백 단위)은 컴포넌트 쿼리에서 query-time JOIN → 부서명 변경 *즉시 반영*
- 옵션 A(이름까지 박음)는 변경 5분 stale / C(완전 분리)는 매 쿼리 hash build 반복 → 사이에서 B가 sweet spot

### 마트 "방어 컬럼화" — 비즈니스 규칙은 마트가 흡수
- `is_debug` / `is_canonical_call` 같은 H-DASH-01/03 방어 로직을 enriched MView 컬럼으로 박음
- 컴포넌트 쿼리가 그냥 `WHERE NOT is_debug AND is_canonical_call`만 쓰면 됨 — 누락 가능성 0
- 황금 규칙: *비즈니스 규칙은 마트 안에 흡수하고 컴포넌트는 그냥 SELECT한다*

### 선행 분석 함정 — mock 데이터 분포가 코드 결론으로 둔갑
- 1차 선행 분석에서 우리 환경 mock(`messages.app_mode` 빈 문자열, audit_events 658건 분포)을 보고 "Dify가 안 채움" 결론
- 운영 환경 코드(`message_based_app_generator.py:216`)에서는 항상 세팅 → 정반대
- 교훈: 분석 위임 시 **"코드 grep 결과 + 파일·라인 인용" 명시적으로 요구**해야 함. "데이터 X건 확인"은 환경 한정 사실 → 일반화 금지
- 재조사로 정정 완료. 운영 진입 시 mock 가정과 다른 항목 list-up 박힘 (적어도 추적 가능)
