**핵심 함의**:

- 5/11 메모 § 2의 "OLTP 우세" 결론은 ETL/jsonb 비용 관점이었으나, 이사님은 **단일 SoT + 통합 활동 로그** 가치를 더 높게 평가
- 어제 옵션 D(OLTP 정규식) 결정 폐기. 단 ILIKE 분류 자체는 유효(audit details->>'error'에 적용)

**액션 4개**:
1. collector 부족 필드는 마트 만들면서 부족분 누적 → 완료 후 승랑님께 **최종 리스트 일괄** 전달

4. RBAC 데이터 다시 조사 + 오브젝트 구현 가능성 검증 (우선순위 2.5)

## 배운 것

### Dify 에러 처리 흐름 — 예외 타입 정보는 DB에서 소실 ⭐
- 출처: [[0. Inbox/Dify의 에러 처리 흐름 추적 산출물.md]] (VSCode Claude 조사)
- **3단계 변환 경로**: ① plugin daemon → `InvokeError` 서브클래스 생성 (SDK 메시지를 `description`에 보존) → ② `app_generator`에서 catch (Auth만 하드코딩 교체, 나머지는 원본 그대로) → ③ `based_generate_task_pipeline._error_to_desc()`에서 **`Exception → str` 변환 → `messages.error` 컬럼에 텍스트만 저장**
- **타입 정보 손실 지점**: `based_generate_task_pipeline.py:65-67` — `isinstance(e, InvokeRateLimitError)` 같은 분류는 이 이후 불가능. DB에는 `description` 문자열만 남음
- **함의**: 향후 누군가 `messages.error`로 에러 분류할 때 `isinstance` 흐름 기대하면 안 됨. 텍스트 매칭(ILIKE)만이 유일한 길

### SDK error code 보존 안 됨 — 옵션 3 영구 폐기 ⭐
- `messages` 테이블에 `error_code`, `error_type` 컬럼 **없음** (LongText `error` 하나뿐)
- `message_metadata`는 정상 완료 경로에서만 채워짐 (에러 시 NULL) — `_save_message()` 호출 분기
- Plugin daemon 내부에서 `error_type` 문자열(예: `"InvokeRateLimitError"`)이 `match` 문으로 InvokeError 서브클래스 선택에 소비되지만, **DB 저장 단계에는 이 정보가 전달되지 않음**
- OpenAI/Anthropic SDK `error.code` 필드도 plugin daemon에서 소비되고 버려짐
- 결론: error code 활용은 collector 보강(옵션 2) 또는 Dify upstream 변경 없이는 영구 불가

### messages.error 텍스트는 반정형 — ILIKE 5~6 룰로 90%+ 커버 ⭐
- InvokeError 서브클래스 `description` 기본값이 안정적 접두어 역할 (`"Rate Limit Error"`, `"Connection Error"` 등)
- Plugin daemon이 SDK 원문으로 덮어쓰는 경우도 키워드(`Rate limit`, `Connection`, `Incorrect API key`)는 유지
- **고정 문자열 4종** (분류 가장 안전): `"Incorrect API key provided"` (Auth), `"Your quota for Dify Hosted Model Provider has been exhausted..."` (Quota), `"Rate Limit Error"`, `"Server Unavailable Error"`
- **반정형 2종** (키워드 매칭): `Connection`, `context length`
- **자유 텍스트 1종**: 기타 — `unknown` 분류

### 옵션 결정 — 오전 D 확정 → 오후 이사님 미팅으로 마트 자체 전환 ⚠️
- 옵션 C(audit.action 활용) ❌ — 5/11 확정 (collector 분류 함수 0)
- 옵션 3(SDK error code) ❌ — 오늘 오전 확정 (DB 미보존)
- 옵션 D(OLTP 정규식 ETL) ⏸ — 오전 채택했으나 **마트 입력이 audit 단독으로 바뀌어 적용 위치 이동** (messages.error → audit_events.details->>'error')
- 옵션 E(절충) — 의미 사라짐 (마트 자체가 audit 단독이라 OLTP/audit 분리 없음)
- 옵션 2(collector 보강) — **필수 의존으로 격상** (audit 단독 마트의 진짜 차단 요소가 collector 비대칭)
- 옵션 5(외부 룰 테이블) — 마트 audit 단독 위에서도 유효, design.md § 10 미해결 유지

### 마트 설계 진화 흐름 (오늘 큰 변경 ⭐)

```
5/8  1단계: 4-fact (OLTP 3 + audit 1)
  ↓
5/11 2단계 측정: 마트 가치 뒤집힘 + ETL/jsonb 비용 관점에서 OLTP 우세
  ↓ → OLTP 3-fact 단순화
5/12 오전: 옵션 D(OLTP 정규식 ETL) 확정
  ↓
5/12 오후 이사님 미팅: 단일 SoT + 통합 활동 로그 + 보안 이벤트 통합 가치 우선
  ↓ → audit 단독 + RBAC JOIN. 오브젝트만 resource_ownership 직접.
```

**진화의 핵심 인사이트**:
- ETL 비용 관점(OLTP 우세) vs SoT 통일/통합 활동 로그(audit 우세) — 두 관점이 충돌
- 이사님은 후자(단일 SoT + 보안 이벤트 통합)를 더 가치 있게 평가
- collector 비대칭은 풀어야 할 의존성이지 차단 요소가 아니라고 해석 (보강 요청으로 해소)
- state 차트(dept-cumulative) 본질 문제는 `resource_ownership` 직접 활용으로 회피

### KPI 4종 구조 — 두 번의 이사님 미팅으로 두 번 흔들림 ⭐
오늘 하루에 KPI 구조가 두 번 큰 변화:

| 시점 | 변화 |
|---|---|
| 오전 | KPI 4종 = SaaS 4축 (Volume/Breadth/Depth/Quality) 분석 정리 |
| 오후 1차 미팅 | 마트 audit 단독 + 부서 기준 통일 + 신규/이탈 삭제 — KPI 컨텐츠 영향 |
| 오후 2차 미팅 | **KPI 자체 변경** — 활성 사용자 → 부서별 사용 / 에러율 → 앱별 통계 |

**함의**:
- SaaS 4축 패턴이 일부 깨짐 — Quality 신호가 KPI에서 빠지고 "앱별 분석"으로 대체
- KPI 4축 = Volume(자산) / 부서별 활용 / 부서별 호출 / 앱별 분석으로 재정의 가능
- 안정성 신호(이전 에러율)는 "앱별 통계 KPI" 안의 컬럼/Top 차트로 흡수 (D 작업에서 결정)
- 보안 이벤트 신호는 KPI에서 빠짐 → 감사 로그 풀뷰(`/audit`)로 미루기

### Dify 모니터링 데이터 소스 — OLTP 직접 (mart 결정과 충돌)
- Dify 앱별 모니터링 탭(`/app/[appId]/overview`)은 OLTP `messages`/`workflow_runs` 직접 사용 (`statistic.py` / `workflow_statistic.py`)
