## 배운 것

### git+docker 동시성 함정 — 컨테이너 잡힌 채 브랜치 전환 시 워킹트리 깨짐 (CAND 등록) ⭐
어제 작업 결과 보려고 localhost 들어가니 무한 로딩. API 컨테이너가 `health: starting`로 무한 재시작 중. docker logs 추적 → `flask_migrate Error: Can't locate revision identified by 'c1d2e3f4a5b6'` 무한 반복.

**증상 추적 흐름**:
1. `docker ps` → API만 5초 전 재시작 (다른 컨테이너는 20분 전 정상). nginx(80)는 살아있어 nginx → API 프록시가 무한 대기 → 브라우저 무한 로딩
2. `docker logs api` → flask_migrate가 alembic revision `c1d2e3f4a5b6`를 못 찾음
3. `psql alembic_version` → DB는 `c1d2e3f4a5b6` 정상 박혀있음 (어제 5/6 RBAC mock 적용 시 잔존)
4. 호스트 `versions/` 폴더 확인 → 그 마이그레이션 파일이 `Mode: d-----` (**빈 디렉토리**)로 깨져있음. `Get-ChildItem -Filter '*.py'`엔 잡히지만 안에 아무것도 없음
5. `git ls-tree origin/feat/rbac:api/migrations/versions/` → 그 파일은 git blob으로 정상 존재 (현재 브랜치 HEAD엔 없음)

**추정 메커니즘**: 어제 작업하면서 `feat/rbac` → `KAN-29-...` 브랜치로 checkout 했을 때 docker 컨테이너가 `api/migrations/versions/`를 bind mount로 잡고 있었음. Windows file-in-use 때문에 git이 파일을 깨끗이 삭제 못 함 → entry는 사라지지만 빈 디렉토리만 잔존. 다음 컨테이너 부팅 시 호스트의 깨진 형태(빈 디렉토리)를 그대로 마운트 → Python `.py` import 불가 → flask_migrate가 그 revision 모듈을 못 읽음.

**복구**:
```powershell
docker compose stop api worker worker_beat
Remove-Item <빈 디렉토리 2개> -Recurse -Force
git checkout origin/feat/rbac -- <마이그레이션 2개 path>
docker compose start api worker worker_beat
```

**방어 — 신설 CAND**:
- 등록: [[3. 프로젝트/spx-agent/hdd/defect-catalog.md|CAND-git-checkout-with-running-container]]
- 권장: **브랜치 전환 전 `docker compose stop api worker worker_beat`** (코드 mount 잡은 컨테이너 멈춤)
- 검증 명령: `Get-ChildItem api\migrations\versions -Directory | Where-Object Name -Match '\.py$'` → 0건
- 컨테이너 안 검증: `docker exec <api> sh -c "cd /app/api && flask db heads"` → head revision 출력

→ **1차 발생이라 정식 H-ENV-04가 아닌 CAND로 등록**. 재발 시 승격. 다른 파일 유형(.json/.yaml/.ts)에서도 재현되거나 Linux/macOS에서도 발생하면 메커니즘 보강.

### 진단 흐름의 메타 학습 — "표면 에러"와 "실제 원인" 사이 4단계
이번 디버깅에서 표면 에러(`Can't locate revision`)와 실제 원인(빈 디렉토리) 사이에 4계층이 있었음:
1. 컨테이너 안 alembic 동작 (`flask db heads`로 직접 호출 → 결과 보고 호스트로 시선 옮김)
2. DB 상태 (`alembic_version` 조회)
3. 호스트 파일 형태 (`Get-Item`으로 Mode 확인)
4. git 메타 (`git ls-tree`로 blob 존재 확인)

**교훈**: flask_migrate 에러 메시지만 보고 "마이그레이션 파일이 없네" 결론 짓지 말고, **존재 여부와 형태를 분리해서** 검증할 것. 파일이 "있다"는 보고가 사실은 "디렉토리 형태로 잘못 존재한다"일 수 있음. PowerShell `Get-ChildItem -Filter '*.py'`는 **이름만 매치**하고 종류 구분 안 함 → `Mode` 컬럼 봐야 정확.

- 정정: 이번 사건은 **결함이 아님** — hook이 제 일을 한 케이스. 다만 **AI 작성자가 lint 자체검증 안 함 + 템플릿 복제로 N배 증식**이라는 비효율 패턴.
- 사용자 의문("훅 얘기가 왜 나오지?" + "기준이 신규 컴포넌트면 괜찮으려나?")이 정정의 트리거. 어제 5/6 H-DASH-17 발견 흐름과 같은 패턴 — **사용자 의문을 진지하게 받기**가 가족 잘못 묶기를 차단.

**방어 — conventions.md § 5 작성 워크플로우 신설**:

**부가 학습 — "같은 가족" 묶기의 함정**:

### Silent fallback의 디버깅 함정 — "컨벤션 박은 것 ≠ 코드 적용된 것" ⭐

오후 service 4종 명명 정정(sp_ → 회사 표준) 작업 후 화면이 여전히 "미배정 14"만 보임. 디버깅 1시간+ 소요. 진단 흐름:
1. 컨테이너 안 service 코드 grep → sp_ 잔존 0건 (갈아끼움 OK)
2. 호스트 service 코드 grep → 잔존 0건
3. SQL 직접 실행 → 9행 정상 반환 (DB도 OK)
4. api 로그에 `sp_object|UndefinedTable|ProgrammingError` 검색 → 0건
5. 시도: gunicorn worker reload (docker compose restart) → 회복 안 됨 → stop+start clean restart → 회복
6. 그러다 nginx 로그에서 `499 Client Closed Request`로 사용자 측 반복 새로고침 패턴 발견 → 1~2분 기다리니 정상 표시

**숨은 진짜 원인**: service 4종 except 블록이 `logger.exception` 없이 silent fallback (`except Exception: return []`). 어제 conventions § 1 Fallback 패턴 예시 코드엔 `logger.exception`이 박혀있었지만 **실제 5/4 작성 시점 service들은 그 표준을 따르지 않았음**. 정작 가장 필요한 디버깅 순간에 에러 메시지가 묻혀 보이지 않음.

**메타 학습 — 컨벤션과 코드의 drift**:
- 컨벤션 문서에 표준 예시 박는 것 ≠ 그 표준이 모든 코드에 적용된 것
- 신규 컨벤션 추가 시 *"기존 코드에 적용 여부 grep 확인"* 단계가 같이 와야 함
- 자동화 후보: pre-commit hook 또는 CI lint에 silent fallback 검출 (`grep -rln 'except Exception' | xargs grep -L 'logger.exception'`)

**방어 보강**:
- conventions.md § 1 Fallback 패턴에 *"`logger.exception` 의무 — silent fallback 함정 방어"* 하위 섹션 신설. 5/7 사례 인용 + grep 검증 명령 박음.
- 백엔드 11종 프롬프트에 "Silent fallback 방어 — 의무" 섹션 추가 예정 — 신규 service 11종은 처음부터 표준 적용, 기존 service 4종도 같은 PR에서 보강.

**부가 — 진단 흐름의 메타 학습**:
- "에러가 안 보임" = 정말 에러가 없는 상태일 수도, **에러 로깅이 묻혀있는 상태**일 수도. 두 경우를 분리해서 검증.
- 첫 5분: silent fallback 가능성 의심 (logger.exception 누락 grep)
- 진짜 코드 관련 에러 검색 전에 로깅 채널 자체가 활성화되어 있는지 확인
- 오늘 1시간 디버깅의 70%는 "있는 줄 알고 찾는데 없음"의 헤매기였음 — 첫 단계에 silent fallback 점검을 박아두면 회피 가능

### docker bind mount는 호스트의 깨진 형태를 그대로 노출
이번 사건의 본질. docker bind mount는 호스트 파일시스템의 충실한 view → 호스트가 깨지면 컨테이너도 깨짐. **컨테이너 안에서 ls가 정상으로 보여도 안심 금지** (오히려 호스트 형태가 정상이 아닐 가능성을 늘 의심).
