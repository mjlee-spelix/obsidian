- 자꾸 RAG로 대책 생성할 때 40분 이상 걸리길래 확인해보니.. 코드 노드가 RAG 분기 끝나고 한 번, LLM 분기 끝나고 한 번 실행되게 되어 있었다. 이유는 LLM 분기는 노드가 2개고 RAG 분기는 노드가 3개라 RAG 마지막 노드랑 LLM 분기 끝나고 실행되는 코드 노드가 병렬로 돌아가는데 RAG 끝나기 전에 코드 노드에서 에러 나서 RAG 쪽 모델이 다 끝났는데도 계속 돌아가는 것처럼 보인 것이다.... 코드 노드는 지금 def run(input)을 해야 되는데 def run(inputs) 로 해놔서 에러가 났었고 수정해뒀는데 저장을 안해서 한 번 날아갔던 듯 암튼 아래 문제 상황 이사님께 말씀 드려서 병합용 노드 하나 만들어주셨다
```
RAG:  검색 ─▶ 프롬프트 ─▶ RAG LLM ─┐   ← 3스텝 (긴 갈래)
LLM:  프롬프트 ─▶ LLM① ───────────┴─▶ 코드(n_9n25m1s) ─▶ end   ← 2스텝 (짧은 갈래)


짧은 LLM① 분기가 먼저 도착 → code 노드 발화 → code 즉시 실패
                                          → run 전체 중단
느린 RAG LLM 분기는 아직 실행 중(span_started만) → 완료 이벤트 못 받음
                                          → UI에서 "응답 대기"로 멈춤
```
- langgraph도 노드 하나로 엣지 2개 병합할 때 분기 길이가 다르면 위와 같이 동작한다고 한다. 그래서 노드가 모두 끝나고 1번만 돌게 **deferred node execution** 라는 설정이 있고 (`python 모든 pending 태스크 끝날 때까지 대기 후 1회 실행`), 두 결과를 합치려면 리듀서를 새로 만들어야 한다고. (`defer로 1회만 돌아도, LangGraph에서 병렬 업데이트는 기본적으로 **덮어씁니다(overwrite)**. 두 LLM 결과를 모두 받으려면 state 채널에 **reducer**를 걸어야 합니다`)
```
① 브랜치 길이가 같으면 → 설정 불필요, 자동 join
A ─▶ B ─┐
A ─▶ C ─┴─▶ D     (B, C 둘 다 1스텝)

② 브랜치 길이가 다르면 → 문제 발생
A ─▶ B ─▶ B2 ─┐   (긴 갈래, 2스텝)
A ─▶ C ───────┴─▶ D   (짧은 갈래, 1스텝)

** 리듀서 reducer: "노드가 반환한 값을 기존 State에 어떻게 합칠지" 정하는 함수
```
