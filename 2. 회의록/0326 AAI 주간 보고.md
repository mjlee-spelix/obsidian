## 논의 내용

### HITL 구현 방식
- 한 번의 워크플로우가 돌았다가 memory 기반으로 저장된 기록을 가져와서 HITL처럼 보이게 구현
- Client에서 orchestrate 하는 방법 사용
- JS 라이브러리에 무관하게 JSON 형태만 맞추면 front/back 어디서든 구현 가능

### 멀티 에이전트 아키텍처
- **방법 1**: 질문 분류기로 요청 분기 후 에이전트 여러 개 운용
  - 클래스 설정 + 클래스별 설명 작성 → 자동 분기
- **방법 2**: 하나의 에이전트에 서브 에이전트들을 도구로 등록
- 마스터는 큰 카테고리(사무, 유틸 등)만 판단해서 서브를 실행하는 방향
  - 마스터에 일일이 도구 설명 X → 서브에 케이스 종속 처리
  - 메일 주소 없을 때 사용자에게 묻는 것도 서브가 처리
- 일단 지금 방향으로 만들어두고 나중에 규모/성능 등 고려해서 아키텍처 재검토

### 메일 발송
- 마스터 에이전트에서 메일 보낼 때 조건 충돌 이슈 발생
  → 나중에 **util agent**로 분리하는 것 권장 (도메인 정보 반영)
- 파일 저장 경로를 따로 지정해야 메일 첨부 가능
  - 파일 다운 경로 지정 후 메일 첨부 시 해당 경로를 전달하는 방식
  - 커스텀 노드로 저장 처리하거나, 계정 설정에 '저장' 탭 구현도 검토

### 시각화 노드
- 차트 그리는 기능을 노드로 만들어 재사용성 높이기
- matplotlib으로 이미지 Base64 생성 후 전달하는 방식
- QuickChart 같은 외부 API 대신 **내부에서 처리**하는 방향으로 최대한 외부 통신 최소화
- 플러그인 라이선스 확인 필요

### 챗봇 구성 방향
- 통합 챗봇: 인사/복지 규정 등 일반 질문 처리
- 개별 챗봇: 각 업무별 챗봇 별도 구성
- 기존 UI: 탭만 없애고 유지
- 임베디드 코파일럿이 이상적이나, 기존 애플리케이션 수정 필요한 어려움 있음

### 모델 및 인프라
- 쿼리 품질 비교 및 성능 테스트 필요 (로커스트 등 부하 테스트 툴 검토)
- 120b vs 20b 비교 테스트 진행 예정
- WatsonX 도입 검토 중 (현재 GPU 부족으로 설치 보류)
  - ollama/vLLM 서버 정리 후 WatsonX 설치 방향 논의

### DB 조회 전략
- `DISTINCT`로 row 랜덤하게 몇 개씩 가져와서 실제 값 확인
- `null` 결과는 도구 워크플로우 자체에서 "검색 결과 없습니다" 노드 추가해서 처리

### Function Calling vs ReAct
- Function Calling 미지원 시 ReAct 사용
- ReAct는 토큰 소모 매우 큼
- Agent 전략과 모델 간 상관관계는 명확하지 않은 것으로 보임

## 결정 사항
- HITL은 memory 기반 + client orchestration 방식으로 구현
- 멀티 에이전트: 일단 현재 방향 유지 후 성능 보고 재검토
- 외부 API(QuickChart 등) 최대한 배제, 내부 처리 방향
- 통합 챗봇 = 인사/복지 규정, 나머지 = 개별 챗봇
- 기존 UI 탭 제거 후 유지
