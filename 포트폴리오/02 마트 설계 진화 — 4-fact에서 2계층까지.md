## Act 1 — 1차안: 4-fact 구조 (5/8)

### 설계

```
fact_call_daily              호출/토큰        (OLTP 기반, 영구)
fact_user_activity_daily     활성 사용자      (OLTP 기반, 영구)
fact_objects_snapshot_daily  오브젝트 누적    (OLTP 기반, 영구)
fact_audit_event_daily       감사 이벤트      (audit 기반, 90일 자연 cap)
+ RBAC = dim (별도 fact 없음)
```

### 이 구조를 고른 이유 — "단일 통합 fact 금지"

> audit(90일) vs OLTP(영구) **보존 정책이 달라** 한 테이블로 못 묶음.
> 단일 fact에 합치면 audit 부분만 91일째 사라지면서 OLTP 부분만 남는 비대칭 → 카운트 부정확
> → **fact는 데이터 출처별로 분리**, 차트가 필요한 fact를 골라 쓰는 구조

→ 즉 **보존 정책의 비대칭**이 분리의 근거였다. 이건 지금 봐도 맞는 판단이다.

### 그리고 12종 전수 비교를 했다

차트 12종 각각에 대해 OLTP / audit 두 가지 쿼리를 다 써보고 비교했다. 결론은 **OLTP 11 + audit 1**.

| 판정 사유 | 해당 차트 |
|---|---|
| **workflow collector에 `triggered_from` 누락** → 디버거 필터 불가 → 카운트 부정확 | 4개 (call-count / rps / error-rate / error-table) |
| **audit 90일 보존 한계** → 누적 카운트 부정확 | 3개 (dept-cumulative / top-owners / 신규 판별) |
| jsonb 추출 + 형변환 비용 **2~5배** | messages 계열 |
| **audit이 명확히 우월** — `messages.error` 자유 텍스트 vs `audit.action` 정규화 | 1개 (top-error-types) |

**부수 발견 2건** (collector 13종 전수 점검):
- `messages.ts`는 details **14필드**로 OLTP를 거의 완벽 보존 / `workflow-runs.ts`는 **5필드만**
- 비대칭 발견: `workflow-nodes.ts`엔 `triggeredFrom`이 박혀있는데 `workflow-runs.ts`엔 빠짐 → **일관성 결함**으로 보고

> 이 비교 자체가 나중에 통째로 폐기되지만(전환 2), **"결정적 누락은 1건뿐"**이라는 실측이 남아서
> 5/12 회의에서 "collector 비대칭은 차단 요소가 아니라 풀면 되는 의존성"이라는 재해석의 근거가 됐다.

## Act 2 — ⚡전환 1: 측정이 전제를 뒤집었다 (5/11)

### 무엇을 측정했나

nginx `log_format`에 `$request_time` + `$upstream_response_time` + `$upstream_header_time`을 추가해 **Flask 미들웨어 없이** 모든 요청의 백엔드 시간을 자동 수집했다.

### 결과 — 마트의 전제가 무너졌다

| 레이어 | 비중 |
|---|---|
| Network | ~0.001초 (0.04%) |
| **DB** | **0.002초 (0.07%)** |
| **백엔드 non-DB** | **2.7초 (99.9%)** |

- 9-CTE 최복잡 쿼리도 **1.5ms**
- 즉 **DB는 무죄**. 마트를 만들어도 "8/15 엔드포인트 단축 → **0% 단축**"
- 5/8 가설이 뒤집힌 이유: 화면 wall clock 10초를 DB 탓으로 봤는데, 실은 **백엔드 + 프론트 + 토스트 retry 누적**이었고 mock 데이터 양(375건)을 체크 안 했었다

**부수 발견**: 1요청당 JWT 검증 + account/tenant 조회가 **59번 redundant 실행** (Flask-Login 캐시 미작동)

### 그런데도 마트를 만들기로 했다 — 두 트랙 분리

여기가 이 프로젝트에서 **가장 중요한 판단**이었다.

| 트랙 | 내용 |
|---|---|
| **A. 마트 (장기 보험)** | "운영 데이터 양 증가는 **기정 사실** (mockup 375건 → 운영 100만+). 운영 들어간 후 만들기 시작 = **사용자 응답시간 한참 느려진 후 fix 시작** = 피해" |
| **B. 백엔드 non-DB fix (단기)** | "DB 0.07% / non-DB 99.9%. 원인 추적은 **신입 단독 fix 영역 아님** (Dify upstream + keycloak patch + RBAC 결합) → 팀 결정 영역" |

> **두 트랙은 분리된 문제.** 한쪽이 다른 쪽을 막지 않음. 마트 가치는 데이터 양에서, 응답시간 개선은 백엔드 fix에서.

→ **"지금 안 아프다"와 "나중에 안 아프다"를 분리**한 것. 그리고 내가 할 수 있는 것과 없는 것도 분리했다.
→ **결과적으로 맞았다**: 5/19에 450K행을 넣자마자 Seq Scan 7건 / 3.3초가 터졌고, Layer 2 기반 엔드포인트는 그때도 **0.5~2ms**를 유지했다.

### 동시에 설계는 단순해졌다 — 4-fact → OLTP 3-fact

`fact_audit_event_daily`를 제거했다. 그리고 **드로어용 Silver 레이어도 안 만들기로** 했다.

처음 가설은 "드로어 한 행 그리려면 5테이블 JOIN이니 ETL로 미리 합쳐두자"였는데, 재검토에서 뒤집혔다:

| 검토 | 결론 |
|---|---|
| audit이 이미 메시지 1건 단위로 적재 중 | 사실상 **fact_event 역할의 80%를 audit이 이미 함** |
| audit에 빠진 건 메시지 본문뿐 | collector에 `queryPreview` 200자 추가 요청이면 끝 |
| 부서 매핑은 audit이 RBAC를 모름 | 화면 JOIN 2개로 처리 (드로어 LIMIT 6이라 부담 작음) |
| 우리 작업량 | Silver = **우리 ETL 코드 + 모니터링 부담** / audit 보강 = **팀 협의 한 번** |

> **있는 자원(audit) 활용 > 새 ETL 시스템 추가 운영**

## Act 3 — ⚡전환 2: 회의가 기술 결론을 뒤집었다 (5/12)

### 오전까지의 상태

에러 분류 방식을 놓고 옵션을 좁혀놓은 상태였다:

| 옵션 | 판정 | 사유 |
|---|---|---|
| C. audit `action` 활용 | ❌ | collector에 분류 함수 0 |
| 3. SDK error code 활용 | ❌ | **DB에 미보존** — `messages`에 `error_code`/`error_type` 컬럼 자체가 없음. plugin daemon이 소비하고 버림 |
| **D. OLTP 정규식 ETL** | ✅ 오전 채택 | `messages.error`는 반정형 — ILIKE **5~6룰로 90%+ 커버** |
| E. 절충 | — | |

에러 타입 정보가 어디서 사라지는지도 소스로 특정했다 — `based_generate_task_pipeline._error_to_desc()`에서 **`Exception → str` 변환**되며 타입 소실.

### 오후 회의 — 두 관점이 충돌했다

| 관점 | 우세한 쪽 |
|---|---|
| **ETL / jsonb 추출 비용** | OLTP (2~5배 저렴) |
| **단일 SoT + 통합 활동 로그 + 보안 이벤트 통합** | audit |

이사님은 **후자**를 더 가치 있게 평가했다. 그리고 collector 비대칭은 **차단 요소가 아니라 풀면 되는 의존성**으로 해석됐다(보강 요청으로 해소).

### 결과 — OLTP 3-fact 전면 폐기

```
5/8  4-fact (OLTP 3 + audit 1)
  ↓
5/11 측정: 마트 가치 뒤집힘 + ETL 비용 관점에서 OLTP 우세
  ↓ → OLTP 3-fact 단순화
5/12 오전: 옵션 D(OLTP 정규식 ETL) 확정
  ↓
5/12 오후 회의: 단일 SoT + 보안 이벤트 통합 가치 우선
  ↓ → audit 단독 + RBAC JOIN. 오브젝트만 resource_ownership 직접.
```

**이 전환에서 배운 것**: 내가 만든 비교표(OLTP 11 + audit 1)는 **비용 축에서만** 정답이었다. 조직이 중요하게 보는 축(단일 SoT, 보안 이벤트 통합)을 비교표에 안 넣었던 게 한계였다.
→ 다만 **옵션 D의 ILIKE 분류 자체는 살아남았다** — 적용 위치만 `messages.error` → `audit_events.details->>'error'`로 이동.
→ 그리고 **state 차트(dept-cumulative)의 90일 문제**는 `resource_ownership` 직접 활용으로 회피했다. audit 단독이 되어도 이 예외는 유지.

## Act 4 — 제약이 하나 더 붙었다 (5/13)

**사용자 범위가 "관리자 전용" → "로그인 사용자 전체"로 변경**됐다(이사님 "데이터 노출 OK").

이게 기술 선택을 바꿨다:
- View로 시작하면 **동시 쿼리 부하가 사용자 수에 비례**
- 전체 공개인 이상 "일단 View, 느려지면 MView" 전략은 위험
- → **MView + `REFRESH CONCURRENTLY`(UNIQUE INDEX 전제)로 다운타임 0** 전제 확정

같은 날 Generated Column 아이디어도 확정됐다 — `ALTER TABLE ... ADD COLUMN app_mode TEXT GENERATED ALWAYS AS (details->>'appMode') STORED`.

> **메타 교훈**: 기술 선택(View vs MView)의 선행 변수가 **사용자 범위 결정**이었다. 제품 결정이 아키텍처를 바꾼 사례.

## Act 5 — 최종안 확정 (5/14)

11개 섹션짜리 결정 노트를 쓰면서 구조가 확정됐다.

### 왜 2계층인가

- Layer 1만으로도 5개 컴포넌트를 다 커버할 수 있다. 하지만 **kpi-cards + drill-through는 동시 조회**라 같은 집계를 카드별로 4번 깎으면 비쌈
- Layer 2(daily roll-up)로 day 단위까지 미리 굴려두면 **카드·차트·표가 같은 mat을 다른 GROUP BY로 재사용**, 기간 필터는 `SUM` 한 번
- 역할 분리: Layer 1 = "정규화된 이벤트 스트림" / Layer 2 = "비즈니스 큐브"
- → 미래 진화(incremental fact / 분석 DB) 때 **Layer 2만 갈아끼우면 컴포넌트 코드 무수정**
- 스테이징 레이어는 안 뒀다 — `audit_events`가 이미 정규화된 이벤트 로그라 정제 단계 불필요

### Layer 1을 굳이 따로 둔 진짜 이유

옵션 C(Layer 1 없이 Layer 2에서 RBAC JOIN)도 가능했다. 그런데:
- drill-through의 **정확한 users 카운트**는 daily mat 합산이 아니라 `COUNT(DISTINCT actor_id)`가 필요 → **행 단위 데이터를 다시 봐야 함**
- 옵션 C면 매 drill 요청마다 `audit_events × RBAC JOIN`을 새로 함 (만 단위 `dept_members` hash build 반복)
- Layer 1을 분리하면 **행 단위 조회(drill)와 집계 조회(카드)가 같은 사전 JOIN 결과를 공유** → RBAC JOIN을 마트 전체에서 한 번만

### MView vs View — 3축으로 갈랐다

| 축 | View 유리 | MView 유리 |
|---|---|---|
| 원본 크기 | 작다 (수천 이하) | 크다 (수십만 이상) |
| 신선도 허용치 | 즉시 필요 | 분 단위 OK |
| 조회 빈도 | 낮음 | 높음 |

- `audit_enriched`: 900만 행 + 5분 stale OK + 5개 컴포넌트 공용 → **3축 모두 MView**
- `ownership_enriched`: 수천 행 + 즉시 반영 자연 + 빈도 적당 → **3축 모두 View**

### RBAC JOIN 옵션 B — A도 C도 각자 다르게 나빴다

| 안 | 왜 별로였나 |
|---|---|
| A. 부서명까지 마트에 박음 | 부서명 변경 시 **최대 5분간 옛 이름 노출**. 조직개편 잦은 회사에서 신뢰도 직격 |
| C. 완전 분리 | 작은 dimension인데도 **매 쿼리 hash build 반복** |
| **B. ID만 사전 JOIN** ✅ | 비싼 결합은 **refresh 1회로 흡수**, 부서명은 query-time → **즉시 반영** |

### 플래그 컬럼화 — 시간이 지나며 사고가 누적되는 구조를 차단

`is_debug` / `is_canonical_call`을 컬럼으로 안 박고 매 쿼리에서 직접 조건을 쓸 수도 있었다. 그런데:

| 시점 | 컬럼화 안 했을 때 |
|---|---|
| 지금 | 내가 H-DASH-01을 알고 정확히 씀 |
| 3개월 후 | 다른 개발자가 새 KPI 추가 → **AppMode 분기 누락 → 카운트 2배** ❌ |
| 6개월 후 | 새 컴포넌트 추가 → 또 누락 ❌ |
| 1년 후 | 한 군데만 고침 → **컴포넌트 간 숫자 불일치** ❌ |

> 컴포넌트 = N명 × N시간이 지남. 방어 코드를 매번 복사하라고 하면 **어딘가에서 빠진다.**
> **책임을 코드 한 곳에 모아 누락 가능성을 0으로 만든다**가 본질.

부수 이점 3가지: 인덱스 가능(boolean) / 자기문서화(`is_debug`는 이름에 의미가 박힘) / 정의 변경 시 **한 곳만 수정**.

### 실시간(trigger)을 안 한 이유 — 병목 분석

```
[Dify INSERT] → [collector 폴링 5분] → [chain refresh 5분] = 최악 10분
                       ↑ 진짜 병목
```

> **시스템 전체 lag = MAX(병목 단계)**. enriched만 실시간(0초)으로 만들어도 collector가 5분 폴링이라 사용자는 여전히 5분 lag.
> → 진짜 실시간이 필요하면 **collector도 함께 실시간화**해야 한다. 한쪽만 바꾸면 비용만 들고 효과 0.

여기에 incremental ETL의 멱등성/재시도/ordering 비용까지 따라온다. → **배치로 시작 → 운영 부하 보고 진화**.

그리고 mat별로 cron을 분리하면 collector 5 + enriched 5 + mat 5 = **최악 15분**. 체이닝하면 **mat 단계 추가 지연 0분** → 최악 10분.

## Act 6 — 구현하면서 또 바뀌었다 (5/15)

### pg_cron 미채택 → collector chain

설계 단계에선 pg_cron 5분 주기였는데, 구현 직전에 바꿨다:
- `postgres:15-alpine`에 pg_cron **미포함** → 이미지 교체 또는 Dockerfile 빌드 필요
- 반면 db-poller 사이클 끝에 chain refresh를 붙이면 **코드 5줄(+16줄)**
- 평균 lag도 **1~2분 짧아짐**

→ `refreshMartChain()`을 try/catch로 격리해 **마트 실패가 collector 다음 회차를 막지 않게** 처리.

### 검증

- Layer 1: `spx_v_audit_enriched` **316행 100% 매칭**
- Layer 2: `spx_mv_kpi_calls_daily` 7행 + `spx_mv_model_tokens_daily` 5행
- **정합: Layer 1 292 = Layer 2 calls 합 292 완전 일치** ✅

### 동시에 rename 사고

audit 스키마 rename 작업의 자가 검증이 거짓이었다 — trigger 함수 미교체로 **17건이 옛 테이블로 INSERT 진행 중**이었다. (→ [[포트폴리오/01 SPX-Agent 데이터마트 — 4대 역량 정리.md]] § 5-2)

## Act 7 — 표준화 정정 구간 (5/18 ~ 5/21)

구조는 확정됐지만 **이름과 물리 설계를 6일간 계속 고쳤다.**

| 날짜 | 정정 | 사유 |
|---|---|---|
| 5/18 | `tenant_id::uuid` 캐스트 | design.md엔 있는데 마이그레이션엔 미반영 → `text = uuid` 연산자 에러 |

| 5/19 | RBAC 무접두 → `spx_` 접두사 | 접두사 **2회 정정** (`sp_` → 무접두 → `spx_`) |

| 5/20 | sentinel UUID 도입 | 표현식 인덱스면 `REFRESH CONCURRENTLY` 불가 |

> **교훈**: 구조 설계보다 **네이밍·물리 설계 정정에 더 많은 날이 들었다.** 그리고 정정 대부분은 "처음에 한 번 확인했으면" 막을 수 있던 것들이었다.

## Act 8 — ⚡전환 3: 의존을 다시 끊었다 (6/10)

### 문제

모델별 토큰 차트에 **워크플로우·챗플로우가 안 나왔다.** 조사해보니:
- 챗플로우(advanced-chat)의 message는 **모델 컬럼이 NULL로 생성**됨 (`message_based_app_generator.py:140-144`)
- → **차트의 '미분류' 정체는 워크플로우가 아니라 챗플로우**였다
- 순수 워크플로우는 message 자체가 없어 **아예 누락**
- 모델 정보는 run이 아니라 **노드**에 있다 (`workflow_node_executions.process_data`), 모델 보유 노드 3종: `llm` / `question-classifier` / `parameter-extractor`

### B안 — 범위를 좁혀서 해결

| 차원 | 소스 | 이유 |
|---|---|---|
| **모델 차원 2종**만 | 노드 기반 재분류 | 워크플로/챗플로가 실제 모델로 등장 |
| 부서·앱 차원 / canonical 호출수 | `message_send` 유지 | **노드로 바꾸면 호출 수가 N배 부풀려짐** |

그리고 의존 구조 자체를 바꿨다:
```
OLD: spx_audit_events → spx_mv_audit_enriched → spx_mv_model_tokens_daily
NEW: spx_audit_events ─────────────────────────→ spx_mv_model_tokens_daily
```
> 모델 차트는 **부서 차원이 없어 RBAC JOIN이 불필요** → enriched 의존 제거, refresh chain에서 독립.

이중집계 차단: 챗플로우 `message_send`를 (1)에서 제외하고 (2) 노드에서만 집계.
검증: `node_tokens(24,000) == msg_tokens(24,000)`, 미분류 **0건**.

### 이 전환의 의미

5/20에 `get_model_call_share`에 `WHERE model_id IS NOT NULL`로 **워크플로우를 의도적으로 제외**해둔 게 있었다. B안은 그 필터를 걷어낸다.
→ 착수 전 세션 기록을 대조해서 이걸 발견했고, **"되돌리기가 아니라 상위호환"**으로 정리했다.
→ 옛 결정을 모르고 덮었으면 "왜 필터를 지웠냐"는 충돌이 났을 것.

## 회고 — 3번의 전환에서 각각 배운 것

| 전환 | 방아쇠 | 배운 것 |
|---|---|---|
| **1 (5/11)** | 측정 결과가 가설을 부정 | 내 설계 전제를 **내가 측정해서 부순** 경험. "마트 효과 0%"를 인정하면서도 **왜 여전히 필요한지**를 다른 논리(데이터 증가는 기정 사실)로 세웠다 |
| **2 (5/12)** | 조직의 가치 판단이 기술 결론을 이김 | 내 비교표는 **비용 축에서만** 정답이었다. 조직이 보는 축(단일 SoT, 보안 이벤트 통합)을 표에 안 넣은 게 한계. **의사결정 기준을 먼저 합의하고 비교해야 한다** |
| **3 (6/10)** | 실사용 데이터가 구멍을 드러냄 | 설계가 끝났다고 끝난 게 아니다. **'미분류'라는 증상 하나에서 출발해 소스 코드까지 내려가** 원인을 특정하고 의존 구조를 다시 끊었다 |

### 살아남은 것 / 버려진 것

| 1차안(5/8)에서 | 최종안까지 |
|---|---|
| 신규 fact 테이블 4개 | ❌ → **신규 테이블 0개** (MView/View) |
| OLTP 기반 3-fact | ❌ → audit 단독 + RBAC JOIN |
| RBAC = dim, ETL 시점에 dept_id 사전 박기 | ✅ **살아남음** (옵션 B로 정제 — ID만) |
| 보존 정책 비대칭 인식 | ✅ **살아남음** (audit 90일 → 기간 cap 90일 결정의 근거) |
| state 차트는 OLTP `resource_ownership` 직접 | ✅ **살아남음** (`spx_v_resource_ownership_enriched`) |
| ILIKE 에러 분류 5~6룰 | ✅ **살아남음** (적용 위치만 이동) |
| ETL 배치 (실시간 X) | ✅ **살아남음** (5분 chain refresh) |

> **1차안이 통째로 틀린 게 아니었다.** 구현 형태(테이블 vs MView)와 소스(OLTP vs audit)가 바뀌었을 뿐,
> **보존 정책 비대칭 · RBAC는 dim · state는 OLTP 직접 · 배치 우선**이라는 판단 축은 6주 내내 유지됐다.

## 면접용 3분 버전

> 대시보드 데이터 마트를 설계했는데, 최종안은 **4번째 안**이었습니다.
>
> 처음엔 신규 fact 테이블 4개를 만드는 안이었어요. 그런데 직접 측정해보니 **DB가 전체 응답의 0.07%**밖에 안 됐습니다. 마트를 만들어도 그 시점엔 개선이 0%였죠. 제 전제가 틀린 걸 제가 측정해서 확인한 셈입니다.
>
> 그럼에도 만들기로 했습니다. 운영 데이터 증가는 기정 사실이었고, 운영 들어간 뒤에 만들면 **사용자가 이미 느려진 다음에 고치기 시작**하는 거니까요. 대신 "지금 느린 문제"는 별도 트랙(백엔드 non-DB)으로 분리했습니다. 실제로 나중에 45만 행을 넣자 3.3초가 튀어나왔고, 마트 기반 엔드포인트만 0.5~2ms를 유지했습니다.
>
> 두 번째 전환은 회의에서 왔습니다. 저는 비용 기준으로 "OLTP 11 + audit 1"을 권고했는데, 조직은 **단일 SoT와 보안 이벤트 통합**을 더 중요하게 봤어요. 결과적으로 제 비교표가 **비용 축만 담고 있었다**는 게 한계였습니다. 그 뒤로는 비교표를 만들기 전에 평가 축부터 합의합니다.
>
> 최종 구조는 신규 테이블 없이 **2계층 4객체**입니다. 핵심은 비즈니스 규칙을 마트가 흡수하게 한 건데, 디버깅 데이터 제외 같은 조건을 매 쿼리에 복사하게 하면 **1년 뒤엔 누군가 반드시 빠뜨리고 컴포넌트 간 숫자가 달라집니다.** 그래서 플래그 컬럼으로 박고, 규칙 준수는 grep 게이트로 강제했습니다.
