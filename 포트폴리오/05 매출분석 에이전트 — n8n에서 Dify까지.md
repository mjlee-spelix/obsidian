## 2. 장면 ⓪ — 플랫폼 전환은 기능이 아니라 라이선스 때문이었다

### 배경
n8n으로 먼저 프로토타입을 만들었고, 기능적으로는 동작했다. 그런데 이걸 **회사 자체 솔루션으로 제품화**하려는 순간 다른 종류의 제약이 걸렸다.

### 제약
**n8n은 소스를 수정할 수 없다.** 오픈소스처럼 보이지만 라이선스상 소스 수정·재배포에 제한이 있어, 자체 솔루션에 넣고 커스터마이즈하려면 별도 에디션/라이선스가 필요했다.
`[NEEDS CLARIFICATION: 정확한 라이선스 명칭과 해당 조항 미확인 — n8n은 OSI 오픈소스가 아닌 fair-code 계열로 알려져 있으나, 당시 검토한 조항 원문을 확인해 채울 것]`

### 결정
→ **Dify로 이관.** 소스 수정이 가능한 라이선스라 자체 솔루션에 통합·커스터마이즈할 수 있었다.

### 왜 이게 포트폴리오에서 중요한가
기능 비교로 고른 게 아니라 **제품화 가능성(라이선스)이라는 비기능 요건이 기술 선택을 뒤집은 사례**다. 공고의 *"복잡한 기술/비즈니스/규제 요구사항을 이해하고 전략적으로 문제를 해결"*에 정확히 대응한다.

> 💬 면접용: "기능은 n8n으로 이미 돌고 있었습니다. 그런데 자체 솔루션에 넣으려면 소스를 고쳐야 했고, 라이선스가 그걸 막았습니다. 동작하는 프로토타입을 버리고 플랫폼을 바꾸는 결정이었습니다."

> ⚠️ 주의: 전환 후에도 **같은 종류의 문제가 반복**됐다(도구 호출 순서, 파라미터 환각, 출력 파싱). 즉 플랫폼 교체가 품질 문제를 해결해 준 게 아니다 — 이건 장면 ①~③에서 따로 풀었다. 면접에서 "플랫폼 바꿔서 해결됐다"로 말하지 말 것.

## 3. 장면 ① — 만든 게 아니라 "왜 깨지는지"를 찾았다

### 증상
20b+Ollama에서 잘 되던 function calling이, 120b+vLLM으로 올리자 무너졌다.
- 존재하지 않는 테이블명(`sales`, `salesorderheader`)을 만들어냄 → 빈 결과 → 원인 모름 → 무한 루프
- **1라운드에서만 도구 12회 이상 호출**, 유의미한 결과 0
- 도구를 `SQL Executor`(파라미터 `query` 하나)에서 `PostgresqlTool`(action/table_name/query)로 바꾼 직후 발생

### 좁히기 — 조합 매트릭스
| 조합 | 결과 |
|---|---|
| 20b + Ollama + SQL Executor | 정상 (round당 1회 순차 호출) |
| 120b + vLLM + PostgresqlTool | 병렬호출 + 환각 + 루프 |
| 20b + vLLM + PostgresqlTool | 내부 추론이 텍스트로 새어나옴 |
| 20b + Ollama + PostgresqlTool | `PluginInvokeError: KeyError` |

→ **"multi-action 도구로 바꾸면 어떤 조합이든 깨진다"**는 패턴 발견

### 근본 원인 3개
1. **chat_template 미적용** — gpt-oss는 `tokenizer_config.json`에 `chat_template` 필드가 없고 별도 jinja 파일로만 존재. vLLM이 이를 자동으로 읽지 못하면 fallback 템플릿이 적용되어 tool call 특수 토큰(`<|call|>`, `<|channel|>`)을 전혀 처리하지 못함
2. **포맷 불일치** — gpt-oss는 채널 시스템(`analysis` 내부추론 / `commentary` 도구호출 / `final` 최종응답)을 쓰는데, `--tool-call-parser openai`가 기대하는 표준 JSON과 완전히 다름. "내부 추론이 텍스트로 출력된" 증상이 여기서 나옴
3. **multi-action 도구의 취약성** — `table_name`이 자유 텍스트라 모델이 아무 값이나 넣고, 에러 없이 빈 결과만 돌아와 원인 파악 불가 → 루프

### 결정적 발견
chat_template.jinja 원문의 주석:
```
{#- We assume max 1 tool call per message #}
```
→ **템플릿이 제대로 적용되면 병렬 호출 문제까지 같은 뿌리에서 해결된다**는 걸 확인. (vLLM에는 `--max-tool-calls-per-turn` 같은 옵션이 없어 다른 해결 경로가 없었다.)

### 조치
`--chat-template` 플래그로 jinja 파일 명시 지정 + 도구 설계를 단순 파라미터로 회귀.

> 💬 면접용: "플랫폼 문서에 답이 없어서 모델의 jinja 템플릿 원문을 읽었습니다. 거기 주석 한 줄이 세 가지 증상을 하나로 묶어줬습니다."

## 4. 장면 ② — 제품 동작의 원인이 프레임워크 구현에 있었다

### 증상
"차트로 그려줘" 같은 **후속 요청에서 SQL을 다시 실행**한다. instruction에 "재호출 금지"를 박아도 소용없음.

### 규명 — 양 플랫폼 소스를 직접 비교
| 항목 | Dify (`token_buffer_memory.py`) | n8n (`memoryManagement.ts`) |
|---|---|---|
| 저장 단위 | `message.query` + `message.answer` 두 필드만 | Human + AI(tool_calls) + **ToolMessage** + AI |
| tool_result 포함 | **No** | **Yes** |
| window 제어 | 메시지 개수 (`window.size`) | 토큰 수 (`maxTokensFromMemory`) |
| 후속 턴에서 원본 데이터 | 마크다운 텍스트만 | 원본 JSON 참조 가능 |

**프롬프트 문제가 아니라 Dify가 tool_result를 애초에 저장하지 않는 구조였다.** 지시를 아무리 해도 참조할 `raw_data`가 컨텍스트에 없었던 것. (n8n에서는 이 문제가 없었는데, 이관하면서 새로 생긴 제약이었다.)

### 대응
1. instruction을 **신규 차트**(nl2sql 먼저) / **후속 차트**(chat history의 마크다운 표 재사용)로 분기
2. chart workflow가 JSON 배열뿐 아니라 **마크다운 표도 입력으로** 받게 유연화

> 💬 면접용: "'모델이 말을 안 듣는다'로 끝날 문제를 양쪽 프레임워크 소스까지 내려가서 확인했더니, 지시의 문제가 아니라 컨텍스트에 데이터가 없는 문제였습니다."

## 5. 장면 ③ — 무엇을 LLM에 맡기고 무엇을 코드에 맡길까

### 문제
에이전트 하나에 SQL 생성·실행·분석 서술·차트 데이터 구성·이메일·JSON 조립이 전부 몰려 있었다. 프롬프트는 무거워지고, 후속 요청("차트로 그려줘")에도 불필요한 로직이 섞였다.

### 재설계
```
Sales Analysis Agent  (의도 분류 · 메모리 · 호출 순서 판단 · 최종 응답)
├── NL2SQL Tool   (Workflow) — 질문 → {sql, columns, raw_data, row_count}
├── Chart Tool    (Workflow) — raw_data → matplotlib → base64 PNG
└── Email Tool    (Workflow) — {to, subject, body} → 발송
```
출력은 **JSON 모드**(Next.js UI가 렌더링) / **MD 모드**(Dify 웹앱용 마크다운+이미지) 두 가지.

### 이 프로젝트의 핵심 판단 — 경계 설정
| 판단 | 근거 (원문) |
|---|---|
| 차트 생성은 도구가 아니라 **코드 노드** | "차트 생성은 기계적 변환이지 LLM 판단이 아니므로" |
| `raw_data`는 LLM이 만들지 않고 **코드가 파싱** | "NL2SQL Agent는 SQL 생성/실행만 담당, 결과 데이터는 코드가 책임" |
| Chatflow vs Workflow **기준 명문화** | Chatflow = 대화 메모리·멀티턴·사용자 대면 / Workflow = stateless 단일 입출력 |
| 차트 첨부 메일 **미지원 결정** | Dify 메일 노드가 첨부 미지원 → UI에 위임할 이유가 없으므로 JSON에서 email 플래그 자체를 제거 |
| 메모리로 SQL 재실행 방지 | 후속 요청 시 raw_data 로드만 — 토큰 ~70% 절감 **(설계상 추정)** |

> 💬 면접용: "AI 제품에서 제일 중요한 설계 결정은 모델을 고르는 게 아니라 **어디까지를 모델에 맡길지 선을 긋는 것**이라고 생각합니다."

📎 원문: [[3. 프로젝트/Sales Analysis 에이전트 구조 설계.md]]

## 6. 장면 ④ — 평가 체계를 설계했다 (설계까지만)

> ⛔ **실행하지 않았다.** DSL 3개를 만들어 뒀지만 프롬프트·도구가 비어 있는 상태에서 중단됐다.
> 이력서·면접에서 **"실험을 설계했다"**로만 말할 것. "테스트했다/비교했다"는 거짓이 된다.

### 문제 재정의
"어떤 모델이 제일 좋냐" → **"의도분류 · 도구호출 · 쿼리작성 3능력을 각각 독립 측정"**

기존 매출분석 워크플로우에서는 능력이 섞여 있었다. NL2SQL 에이전트는 도구 호출과 쿼리 작성을 동시에, 마스터는 의도 분류와 도구 호출을 동시에 한다.

### 변수 통제
> "연결해서 하나로 만들면 앞 단계 실패가 뒤 단계를 오염시킨다. 의도 분류를 틀리면 도구 호출도 당연히 틀리고 SQL도 엉뚱하게 나오는데, 이러면 실제로는 분류만 못하는 모델을 '전부 못한다'고 잘못 평가하게 된다."

→ 워크플로우 **3개 분리**(의도분류: LLM 노드만 / 도구호출: 에이전트+더미도구 / SQL: LLM 노드만), 시나리오는 통일

### 실험 조건
- temperature 고정 (분류·도구호출 0.1, SQL 0)
- **반복 3~5회 일관성** — "한 번 맞추는 것보다 매번 안정적으로 맞추는 게 프로덕션에서는 더 중요하다"
- 동일 GPU · 동일 추론엔진(vLLM)
- 프롬프트 통일 vs 모델별 최적화 — **트레이드오프를 미결 쟁점으로 명시**

### 능력별 평가 기준
| 능력 | 지표 |
|---|---|
| 의도 분류 | 분류 정확도, 애매한 입력 시 되묻는지 vs 임의 판단하는지 |
| 도구 호출 | 성공률, hallucination, 파라미터 정확성, 병렬 호출 안정성 |
| 쿼리 작성 | 실행 정확도, 문법 유효성, JOIN 정확성 |

+ 실패 원인 분류 체계 (문법인지 결과인지 / 안 부른 건지 파라미터가 틀린 건지)

## 7. 반복해서 나온 문제들 — 같은 결의 판단 4건

> 개별로는 작지만, **"LLM 출력을 신뢰하지 않고 제약을 거는"** 하나의 일관된 태도를 보여준다.

### ① 카테고리명 환각
사용자가 "자전거"라고 치면 LLM이 DB 실제값 `Bikes` 대신 `Bicycle`을 만들어 `WHERE category = 'Bicycle'` → 결과 0건.
대안 3개를 **각각의 비용과 함께** 비교: DISTINCT 사전조회(토큰·쿼리 횟수 증가) / 용어사전 삽입(값이 고정적일 때 유효) / ILIKE 부분일치(노이즈 포함 가능).
→ **세 가지를 조합**해 프롬프트에 함께 적용.
📎 [[4. 지식노트/Dify Agent - LLM 카테고리명 환각 대응.md]]

### ② 멀티턴 출력 파싱이 깨진 이유
에이전트가 도구를 여러 번 호출하면 출력에 JSON wrapper가 여러 개 섞여 나온다(탐색 쿼리 결과 + 환각 preview + 진짜 최종답). 초기 코드는 `max(row_count)`로 골랐는데, **단일턴에서는 우연히 맞았고 멀티턴으로 바뀌는 순간 깨졌다** — 탐색 쿼리(DISTINCT)가 row가 많고 진짜 답은 집계라 1 row인 경우가 대부분이라서.
→ **`last valid` 전략**(뒤에서부터 첫 유효 wrapper)으로 교체. 에이전트의 최종 답은 항상 마지막 emit이므로.
📎 [[4. 지식노트/Dify - 멀티턴 Agent 출력 wrapper 선택 전략.md]]

### ③ UNION 쿼리 플러그인 에러
LLM이 생성한 `UNION` 쿼리가 db_client 플러그인에서 `Invalid operation type` 에러. 루트가 `Select`가 아니어서였다.
→ 집합 연산을 **서브쿼리로 감싸도록** NL2SQL instruction에 룰로 강제.
교훈: *"LLM이 생성할 수 있는 SQL 패턴을 사전 제약으로 좁히는 게 fallback 처리보다 안정적. instruction에 금지 패턴 명시가 cheap & effective."*
📎 [[4. 지식노트/Dify - db_client_node UNION 쿼리 Invalid operation type 에러.md]]

### ④ 멀티 에이전트 역할 분리 원칙
마스터 = 큰 카테고리 판단·오케스트레이션 / 서브 = 도메인 특화 로직. **마스터에 모든 도구 설명을 넣지 않는다** — 설명이 길어져 성능이 떨어지므로. 공통 유틸(메일 발송)은 util agent로 분리해 재사용.
방향: 통합 챗봇(인사·복지 규정) + 개별 챗봇(매출분석·전자결재), 최종적으로는 임베디드 코파일럿.
📎 [[4. 지식노트/Dify - 멀티 에이전트 설계 패턴.md]]

## 8. n8n 시기에 이미 같은 문제가 있었다

> 플랫폼을 바꿔도 반복됐다는 증거 — "LLM 에이전트의 구조적 문제"라는 주장의 근거가 된다.

n8n으로 AdventureWorks 매출분석을 만들던 시기의 디버깅 기록:
- `create_chart`에 `query_result` 대신 `input`이 넘어가 **모델이 임의로 차트를 생성** → 도구 description에 `Input: {{$json.query_result}}`를 명시해 해결
- **`execute_sql` 없이 `create_chart`를 먼저 호출**하는 순서 위반 → 프롬프트에 명시해도 안 고쳐짐
- `query_result`가 길면 파싱 에러 → 차트 워크플로우 안에 `execute_sql`을 넣었더니 *"이러면 그래프를 너무 이상하게 만드네"* (트레이드오프 기록)
- **quickchart 노드 한계**: binary 이미지 반환, **단일 시리즈만 지원** → 도구 선택의 제약 조건으로 확인

→ Dify 이관 후에도 **동일한 3종(도구 순서 / 파라미터 환각 / 출력 파싱)이 그대로 재현**됐다.

📎 [[1. Daily/2603/2026-03-10.md]] · [[3. 프로젝트/n8n workflow 정리.md]] · [[3. 프로젝트/Dify 차트 시각화 설계.md]]

### 차트 기능이 빠져 있던 조각
Dify 이관 후 매출분석 chatflow는 에이전트가 `chartType`/`chartData`를 JSON으로 잘 뽑아줬지만 **이걸 이미지로 바꾸는 단계가 아예 없었다.**
→ JSON 파싱 코드 노드 **바로 뒤에 차트 생성 코드 노드 1개만 추가**하는 설계. `chart=false`면 빈 문자열로 통과, `true`면 matplotlib → base64. IF/ELSE 조건에서 chart 판단을 제거하고 이메일 발송 여부만 남김.
**추가 노드 1개로 4가지 시나리오**(차트만/메일만/둘다/둘다아님)를 모두 커버하도록 최소 변경.

## 9. 이해관계자 — 기술을 남의 언어로 번역한 기록

제휴사 A의 기술 문의 3건에 직접 답변:

| 질문 | 답변 요지 |
|---|---|
| Dify 구현 부분 / n8n 구현 부분 | 챗봇 전부·업무자동화·매출분석(커스텀) = Dify / 컴플라이언스·앱 전부 = n8n |
| Master Agent는 Worker를 어디서 호출하나 | 직접 호출 안 함. 백엔드가 Master에게 task 목록을 받아 순차 호출 |
| 왜 A2A 프로토콜을 안 썼나 | 모든 Agent가 동일 플랫폼(Dify) 내 동작이라 A2A의 이점(이기종 프레임워크 통신·독립 배포) 필요성이 낮음. 기술적으로는 Marketplace의 A2A Server/Client 플러그인으로 전환 가능하며, 이종 프레임워크 연동 시 고려 |

> 💬 면접용: "기술 선택을 '안 했다'가 아니라 '이런 조건에서는 안 하는 게 맞고, 조건이 바뀌면 이렇게 전환한다'까지 문서로 답했습니다."

그 외: **3/17 제휴사 A 대상 데모 발표 직접 준비** — UI당 3~4분, 워크플로우 단계별 설명, *"기술 회사니까 기술적 측면에서 설명 보충"*처럼 청중에 맞춰 설명 수위를 조정한 기록. 동료 B와 담당 분배(Human Input API 연동), 고객사(공공기관·공기업·제조사) 요건이 제품 방향에 반영되는 과정 경험.

## 11. 한계 — 먼저 말할 것

1. **데모/PoC 단계**다. 실사용 지표(사용자 수·만족도·처리량)가 없다.
2. **정량 수치가 없다.** 3~4월 데일리 전수 확인 결과 응답시간·정확도·성공률 측정치 0건. 수치가 필요하면 [[포트폴리오/01 SPX-Agent 데이터마트 — 4대 역량 정리.md]]를 쓸 것.
3. **모델 비교 테스트는 설계만 하고 실행하지 않았다.** A/B 테스트를 돌려본 경험이 아니다.
4. 토큰 ~70% 절감은 **설계상 추정**이다.
5. 코드 생성은 AI(Claude Code·Codex)가 했다. 내 몫은 원인 규명·구조 판단·평가 설계다.
