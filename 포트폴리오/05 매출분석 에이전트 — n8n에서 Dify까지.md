## 2. 장면 ① — 만든 게 아니라 "왜 깨지는지"를 찾았다

📎 [[4. 지식노트/Dify Agent - gpt-oss vLLM Function Calling 트러블슈팅.md]]

### 증상
20b+Ollama에서 잘 되던 function calling이, 120b+vLLM으로 올리자 무너졌다.
- 존재하지 않는 테이블명(`sales`, `salesorderheader`)을 만들어냄 → 빈 결과 → 원인 모름 → 무한 루프
- **1라운드에서만 도구 12회 이상 호출**, 유의미한 결과 0

### 좁히기 — 조합 매트릭스
| 조합 | 결과 |
|---|---|
| 20b + Ollama + SQL Executor | 정상 |
| 120b + vLLM + PostgresqlTool | 병렬호출 + 환각 + 루프 |
| 20b + vLLM + PostgresqlTool | 내부 추론이 텍스트로 새어나옴 |
| 20b + Ollama + PostgresqlTool | `PluginInvokeError: KeyError` |

→ **"multi-action 도구로 바꾸면 어떤 조합이든 깨진다"**는 패턴 발견

### 근본 원인 3개
1. **chat_template 미적용** — gpt-oss는 `tokenizer_config.json`에 `chat_template` 필드가 없고 별도 jinja 파일로만 존재. vLLM이 fallback 템플릿을 써서 tool call 특수 토큰을 전혀 처리하지 못함
2. **포맷 불일치** — gpt-oss의 `<|call|>`·채널 시스템(analysis/commentary/final)이 `--tool-call-parser openai`가 기대하는 표준 JSON과 완전히 다름
3. **multi-action 도구의 취약성** — `table_name`이 자유 텍스트라 모델이 아무 값이나 넣고, 빈 결과만 돌아와 원인 파악 불가

### 결정적 발견
chat_template.jinja 원문의 주석:
```
{#- We assume max 1 tool call per message #}
```
→ **템플릿이 제대로 적용되면 병렬 호출 문제까지 같은 뿌리에서 해결된다**는 걸 확인.

> 💬 면접용: "플랫폼 문서에 답이 없어서 모델의 jinja 템플릿 원문을 읽었습니다. 거기 주석 한 줄이 세 가지 증상을 하나로 묶어줬습니다."

## 3. 장면 ② — 제품 동작의 원인이 프레임워크 구현에 있었다

📎 [[4. 지식노트/Dify vs n8n - Agent 메모리 구조 비교.md]]

### 증상
"차트로 그려줘" 같은 **후속 요청에서 SQL을 다시 실행**한다. instruction에 "재호출 금지"를 박아도 소용없음.

### 규명 — 양 플랫폼 소스를 직접 비교
| 항목 | Dify (`token_buffer_memory.py`) | n8n (`memoryManagement.ts`) |
|---|---|---|
| 저장 단위 | user 텍스트 + assistant 텍스트 | Human + AI(tool_calls) + **ToolMessage** + AI |
| tool_result 포함 | **No** | **Yes** |
| 후속 턴에서 원본 데이터 | 마크다운 텍스트만 | 원본 JSON 참조 가능 |

**프롬프트 문제가 아니라 플랫폼이 tool_result를 애초에 저장하지 않는 구조였다.** 지시를 아무리 해도 참조할 데이터가 컨텍스트에 없었던 것.

### 대응
1. instruction을 신규 차트 / 후속 차트로 분기
2. chart workflow가 JSON 배열뿐 아니라 마크다운 표도 입력으로 받게 유연화

> 💬 면접용: "'모델이 말을 안 듣는다'로 끝날 문제를 양쪽 프레임워크 소스까지 내려가서 확인했더니, 지시의 문제가 아니라 컨텍스트에 데이터가 없는 문제였습니다."

## 4. 장면 ③ — 무엇을 LLM에 맡기고 무엇을 코드에 맡길까

📎 [[3. 프로젝트/Sales Analysis 에이전트 구조 설계.md]] · [[3. 프로젝트/Dify 차트 시각화 설계.md]]

### 문제
에이전트 하나에 SQL 생성·실행·분석 서술·차트 데이터 구성·이메일·JSON 조립이 전부 몰려 있었다. 프롬프트는 무거워지고, 후속 요청에도 불필요한 로직이 섞였다.

### 재설계
```
Sales Analysis Agent (의도 분류 · 메모리 · 호출 순서 판단 · 최종 응답)
├── NL2SQL Tool   (Workflow) — 질문 → 데이터, stateless
├── Chart Tool    (Workflow) — 데이터 → 이미지
└── Email Tool    (Workflow) — 내용 → 발송
```

### 이 프로젝트의 핵심 판단 — 경계 설정
| 판단 | 근거 |
|---|---|
| 차트 생성은 도구가 아니라 **코드 노드** | "차트 생성은 기계적 변환이지 LLM 판단이 아니므로" |
| `raw_data`는 LLM이 만들지 않고 **코드가 파싱** | "NL2SQL Agent는 SQL 생성/실행만 담당, 결과 데이터는 코드가 책임" |
| Chatflow vs Workflow **기준 명문화** | 대화 메모리·사용자 대면 필요 여부 |
| 차트 첨부 메일 **미지원 결정** | Dify 메일 노드가 첨부 미지원 → JSON에서 email 플래그 자체를 제거 |

> 💬 면접용: "AI 제품에서 제일 중요한 설계 결정은 모델을 고르는 게 아니라 **어디까지를 모델에 맡길지 선을 긋는 것**이라고 생각합니다."

- [[4. 지식노트/Dify - 멀티턴 Agent 출력 wrapper 선택 전략.md]] — `max(row_count)` 휴리스틱이 단일턴→멀티턴 전환 순간 깨진 이유를 설명하고 `last valid`로 교체

## 5. 장면 ④ — 평가 체계를 설계했다

📎 [[3. 프로젝트/목적별 모델 비교 테스트 설계.md]]

### 문제 재정의
"어떤 모델이 제일 좋냐" → **"의도분류 · 도구호출 · 쿼리작성 3능력을 각각 독립 측정"**

기존 매출분석 워크플로우에서는 능력이 섞여 있었다. NL2SQL 에이전트는 도구 호출과 쿼리 작성을 동시에, 마스터는 의도 분류와 도구 호출을 동시에 한다.

### 변수 통제
> "연결해서 하나로 만들면 앞 단계 실패가 뒤 단계를 오염시킨다. 의도 분류를 틀리면 도구 호출도 당연히 틀리고 SQL도 엉뚱하게 나오는데, 이러면 실제로는 분류만 못하는 모델을 '전부 못한다'고 잘못 평가하게 된다."

→ 워크플로우 3개 분리, 시나리오는 통일

### 실험 조건
- temperature 고정 (분류/도구호출 0.1, SQL 0)
- **반복 3~5회 일관성** — "한 번 맞추는 것보다 매번 안정적으로 맞추는 게 프로덕션에서는 더 중요하다"
- 동일 GPU · 동일 추론엔진(vLLM)
- 프롬프트 통일 vs 모델별 최적화 — **트레이드오프를 미결 쟁점으로 명시**

### 능력별 평가 기준
| 능력 | 지표 |
|---|---|
| 의도 분류 | 분류 정확도, 애매한 입력 시 되묻는지 |
| 도구 호출 | 성공률, hallucination, 파라미터 정확성, 병렬 호출 안정성 |
| 쿼리 작성 | 실행 정확도, 문법 유효성, JOIN 정확성 |

+ 실패 원인 분류 체계 (문법인지 결과인지 / 안 부른 건지 파라미터가 틀린 건지)

> ⚠️ **현재 상태: 설계까지.** DSL 3개는 프롬프트·도구가 비어 있음. → [[#다음 단계]]

## 8. 한계 — 먼저 말할 것

1. **데모/PoC 단계**다. 실사용 지표(사용자 수·만족도·처리량)가 없다.
2. **정량 수치가 없다.** 3~4월 데일리 전수 확인 결과 응답시간·정확도·성공률 측정치 0건. 수치가 필요하면 데이터마트 프로젝트를 쓸 것.
3. **모델 비교 테스트는 설계까지**다. A/B 테스트를 실행한 경험이 아니다.
4. 토큰 ~70% 절감은 **설계상 추정**이다.
5. 코드 생성은 AI(Claude Code·Codex)가 했다. 내 몫은 원인 규명·구조 판단·평가 설계다.
