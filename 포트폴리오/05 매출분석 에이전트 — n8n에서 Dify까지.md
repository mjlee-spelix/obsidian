## 한 줄 요약 (서류용)

> 사내 AI 플랫폼의 매출 분석 에이전트를 n8n 프로토타입에서 Dify로 이관하며 개선 사이클을 리딩. 자연어 → SQL → 시각화 → 메일 흐름에서 발생한 **도구 호출 실패·값 환각·출력 파싱 오류**의 원인을 모델 chat_template과 프레임워크 메모리 구현까지 파고들어 규명했고, 과중한 단일 에이전트를 **3개 서브도구로 분해**했다. 동시에 데모 일정에 맞춰 기능을 잘라내고, 응답 정책을 수치 규칙으로 정의하고, 구현 불가능한 요구를 스펙에서 제거하는 **제품 판단**을 함께 수행.

## 2. 전환 — 라이선스가 플랫폼을 바꿨다

### n8n 시기에 이미 제품은 돌고 있었다
3월 내내 n8n으로 AdventureWorks 매출분석을 만들었고, 기능적으로 동작했다. 이때의 디버깅 기록:

- `create_chart`에 `query_result` 대신 `input`이 넘어가 **모델이 임의로 차트를 생성** → 도구 description에 `Input: {{$json.query_result}}` 명시로 해결
- **`execute_sql` 없이 `create_chart`를 먼저 호출**하는 순서 위반 → 프롬프트에 명시해도 안 고쳐짐
- `query_result`가 길면 파싱 에러 → 차트 워크플로우에 `execute_sql`을 넣었더니 *"이러면 그래프를 너무 이상하게 만드네"*
- **quickchart 노드 한계**: binary 반환, **단일 시리즈만 지원**

### 그런데 제품화하려는 순간 다른 제약이 걸렸다
**n8n은 소스를 수정할 수 없다.** 오픈소스처럼 보이지만 라이선스상 소스 수정·재배포에 제한이 있어, **회사 자체 솔루션에 넣고 커스터마이즈하려면** 별도 에디션/라이선스가 필요했다.
`[NEEDS CLARIFICATION: 정확한 라이선스 명칭과 조항 미확인 — n8n은 OSI 오픈소스가 아닌 fair-code 계열로 알려져 있으나, 당시 검토한 조항 원문을 확인해 채울 것]`

→ **Dify로 이관.** 소스 수정이 가능해 자체 솔루션에 통합할 수 있었다.

### 왜 이게 중요한가
기능 비교로 고른 게 아니라 **제품화 가능성(라이선스)이라는 비기능 요건이 기술 선택을 뒤집은 사례**다. 이 팀에서 라이선스 검토는 일회성이 아니었다 — 차트도 *"QuickChart 같은 외부 API 대신 내부 처리, 플러그인 라이선스 확인 필요"*로 같은 축에서 결정됐다(온프레미스 고객 환경 제약).

> ⚠️ **면접에서 "플랫폼 바꿔서 해결됐다"로 말하지 말 것.** 전환 후에도 같은 문제 3종(도구 호출 순서 / 파라미터 환각 / 출력 파싱)이 그대로 재현됐다. 그건 3·4장에서 따로 풀었고, 오히려 **"LLM 에이전트의 구조적 문제"**라는 주장의 근거가 된다.

> 💬 "기능은 n8n으로 이미 돌고 있었습니다. 그런데 자체 솔루션에 넣으려면 소스를 고쳐야 했고, 라이선스가 그걸 막았습니다. 동작하는 프로토타입을 버리는 결정이었습니다."

## 3. 구조 — 무엇을 LLM에, 무엇을 코드에

### 문제 — 기능이 늘어난 게 아니라, 처음부터 만능이었다
n8n 시절부터 한 에이전트가 `execute_sql` + `create_chart` + `create_sheet` + 메일을 전부 들고 있었고, Dify 이관 후에도 **SQL 생성·실행·분석 서술·차트 데이터 구성·이메일 판단·JSON 조립**이 그대로 몰려 있었다. 프롬프트는 무거워지고, 후속 요청("차트로 그려줘")에도 불필요한 로직이 섞였다.

**게다가 에이전트는 판단자도 아니었다.** 재설계 전 구조는 이랬다:
```
[시작] → [에이전트] → [코드: JSON 파싱] → [IF/ELSE] ─TRUE→ [이메일 발송 도구] → [답변2]
                                              └────────FALSE→ [답변]
```
에이전트는 `chart` / `email` / `email_to` 같은 **플래그를 뱉기만** 하고, "메일을 보낼까"는 IF/ELSE 조건(`chart != true AND email == true`)이 결정했다. 즉 **판단 로직이 그래프에 흩어져 있었다.**

### 전조 — 2주 앞선 처방 (3/25)
> "DB 조회 후 **LLM이 SQL 생성/실행만 하도록 역할 분리**. 스키마/테이블/컬럼 조회 쿼리를 **n8n에서 쓰던 걸 가져와** 순서대로 실행하게 하니 **에이전트 하나만으로 잘 동작**했음"

버린 플랫폼의 자산을 재활용해 역할을 좁혔더니 풀렸다. 4/6 재설계는 여기서 이어진다.

### 재설계 (4/6) — 실행자에서 오케스트레이터로
출발점: *"에이전트 하나에 **SQL 생성·실행·분석 서술·차트 데이터 구성·이메일·JSON 조립까지 모든 역할이 몰려** 있다"*

```
Sales Analysis Agent  ← 남긴 것은 "판단"뿐
├── 사용자 의도 분류 (신규 분석 / 차트 / 메일 / 복합)
├── 메모리 관리 (이전 분석 결과 저장·조회 → 후속 요청 처리)
├── 서브 도구 호출 순서 판단
└── 최종 응답 작성 (JSON 또는 MD)
    │
    ├── NL2SQL Tool  (Workflow) — 질문 → {sql, columns, raw_data, row_count}
    ├── Chart Tool   (Workflow) — raw_data → matplotlib → base64 PNG
    └── Email Tool   (Workflow) — {to, subject, body} → 발송
```
> 원칙 한 줄: **"서브 워크플로우(도구)로 분리하되, 호출 판단은 Sales Agent가 수행"** — 판단은 에이전트, 실행은 도구.

**두 방향이 동시에 일어났다.**
| | 재설계 전 | 재설계 후 |
|---|---|---|
| 실행(SQL·차트·메일) | 에이전트가 직접 | **→ 밖으로** 서브도구 3종 |
| 분기 판단(메일 보낼까) | IF/ELSE 그래프가 | **→ 안으로** 에이전트가 도구 직접 호출 |

JSON 응답에서 `email` / `email_to` / `email_subject` 필드를 **삭제**하고 *"모든 메일은 Sales Agent가 Email Tool을 직접 호출하여 처리"*로 바꾼 게 이 회수의 실체다.

> 💬 "기능이 늘어서 구조가 커진 게 아닙니다. **처음부터 다 하던 에이전트에서 실행을 덜어내고, 대신 그래프에 흩어진 판단을 에이전트로 모았습니다.**"

출력은 **JSON 모드**(Next.js UI가 렌더링) / **MD 모드**(Dify 웹앱용 마크다운+이미지).

### 역할 재정의를 강제한 장치 — 프롬프트 재배치
역할을 나눈 뒤 프롬프트를 따라 옮겼다. 이게 분리를 말이 아니라 구조로 만든 부분이다.

| 항목 | 기존 | 변경 후 |
|---|---|---|
| DB 스키마 · SQL 규칙 · 테이블 선택 가이드 | 메인 프롬프트 | **NL2SQL Tool** |
| 출력 포맷 규칙 · 인사이트/분석 규칙 | 메인 프롬프트 | **Sales Agent** |
| 차트 규칙 (JSON) | 메인 프롬프트 | Sales Agent (chartData 구성) |
| 차트 규칙 (MD) | 메인 프롬프트 | **Chart Tool** (matplotlib) |
| 이메일 규칙 | 메인 프롬프트 | Sales Agent(주소 추출·판단) + **Email Tool**(발송) |

### 핵심은 경계 설정이다
| 판단 | 근거 (원문) |
|---|---|
| 차트 생성은 도구가 아니라 **코드 노드** | "차트 생성은 기계적 변환이지 LLM 판단이 아니므로" |
| `raw_data`는 LLM이 만들지 않고 **코드가 파싱** | "NL2SQL Agent는 SQL 생성/실행만 담당, 결과 데이터는 코드가 책임" |
| **Chatflow vs Workflow 기준 명문화** | Chatflow = 대화 메모리·멀티턴·사용자 대면 / Workflow = stateless 단일 입출력 |
| 마스터에 **모든 도구 설명을 넣지 않음** | 설명이 길어져 성능 저하. 공통 유틸(메일)은 util agent로 분리 |
| 메모리로 SQL 재실행 방지 | 후속 요청 시 raw_data 로드만 — 토큰 ~70% 절감 **(설계상 추정)** |

> 💬 "AI 제품에서 제일 중요한 설계 결정은 모델을 고르는 게 아니라 **어디까지를 모델에 맡길지 선을 긋는 것**이라고 생각합니다."

## 4. 규명 — 왜 깨지는지 찾은 5건

### ① gpt-oss vLLM Function Calling ★ 대표 사례

**증상** — 20b+Ollama에서 잘 되던 function calling이 120b+vLLM으로 올리자 무너졌다. 존재하지 않는 테이블명(`sales`, `salesorderheader`)을 만들어내고 → 빈 결과 → 원인 모름 → 무한 루프. **1라운드에서만 도구 12회 이상 호출**, 유의미한 결과 0.

**좁히기** — 모델 × 추론엔진 × 도구설계 조합 매트릭스

| 조합 | 결과 |
|---|---|
| 20b + Ollama + SQL Executor | 정상 (round당 1회 순차) |
| 120b + vLLM + PostgresqlTool | 병렬호출 + 환각 + 루프 |
| 20b + vLLM + PostgresqlTool | 내부 추론이 텍스트로 새어나옴 |
| 20b + Ollama + PostgresqlTool | `PluginInvokeError: KeyError` |

→ **"multi-action 도구로 바꾸면 어떤 조합이든 깨진다"**

**근본 원인 3개**
1. **chat_template 미적용** — gpt-oss는 `tokenizer_config.json`에 `chat_template` 필드가 없고 별도 jinja 파일로만 존재. vLLM이 못 읽으면 fallback 템플릿이 적용되어 tool call 특수 토큰(`<|call|>`, `<|channel|>`)을 전혀 처리 못 함
2. **포맷 불일치** — gpt-oss는 채널 시스템(`analysis` 내부추론 / `commentary` 도구호출 / `final` 최종응답)을 쓰는데 `--tool-call-parser openai`가 기대하는 표준 JSON과 다름. "내부 추론이 텍스트로 출력된" 증상의 원인
3. **multi-action 도구의 취약성** — `table_name`이 자유 텍스트라 아무 값이나 들어가고, 에러 없이 빈 결과만 돌아와 원인 파악 불가

**결정적 발견** — chat_template.jinja 원문의 주석
```
{#- We assume max 1 tool call per message #}
```
템플릿이 제대로 적용되면 **병렬 호출 문제까지 같은 뿌리에서 해결**된다는 걸 확인. (vLLM에 `--max-tool-calls-per-turn` 같은 옵션이 없어 다른 경로가 없었다.)
→ 조치: `--chat-template`로 jinja 파일 명시 + 도구를 단순 파라미터로 회귀.

> 💬 "플랫폼 문서에 답이 없어서 모델의 jinja 템플릿 원문을 읽었습니다. 거기 주석 한 줄이 세 가지 증상을 하나로 묶어줬습니다."

### ② 후속 요청에서 SQL을 재실행하는 이유 ★

"차트로 그려줘" 같은 후속 요청에서 SQL을 다시 실행했다. instruction에 "재호출 금지"를 박아도 소용없었다. **양 플랫폼 소스를 직접 비교**:

| 항목 | Dify (`token_buffer_memory.py`) | n8n (`memoryManagement.ts`) |
|---|---|---|
| 저장 단위 | `message.query` + `message.answer` 두 필드만 | Human + AI(tool_calls) + **ToolMessage** + AI |
| tool_result 포함 | **No** | **Yes** |
| window 제어 | 메시지 개수 | 토큰 수 |

**프롬프트 문제가 아니라 Dify가 tool_result를 애초에 저장하지 않는 구조였다.** 참조할 `raw_data`가 컨텍스트에 없었던 것 — n8n에는 없던, 이관으로 새로 생긴 제약.
→ 대응: instruction을 신규/후속 차트로 분기 + chart workflow가 마크다운 표도 입력으로 받게 유연화.

> 💬 "'모델이 말을 안 듣는다'로 끝날 문제를 양쪽 프레임워크 소스까지 내려가 확인했더니, 지시의 문제가 아니라 컨텍스트에 데이터가 없는 문제였습니다."

### ③ 카테고리명 환각
"자전거"를 치면 LLM이 DB 실제값 `Bikes` 대신 `Bicycle`을 만들어 결과 0건. 대안 3개를 **각각의 비용과 함께** 비교 — DISTINCT 사전조회(토큰·쿼리 증가) / 용어사전 삽입(값이 고정적일 때) / ILIKE 부분일치(노이즈 포함). → **셋을 조합**해 적용.

### ④ 멀티턴 출력 파싱
에이전트가 도구를 여러 번 부르면 출력에 JSON wrapper가 여러 개 섞인다(탐색 결과 + 환각 preview + 진짜 답). 초기 코드는 `max(row_count)`로 골랐는데 **단일턴에서 우연히 맞았고 멀티턴에서 깨졌다** — 탐색 쿼리(DISTINCT)는 row가 많고 진짜 답은 집계라 1 row라서. → **`last valid`**(뒤에서부터 첫 유효 wrapper)로 교체.

### ⑤ UNION 쿼리 플러그인 에러
LLM이 만든 `UNION` 쿼리가 루트가 `Select`가 아니라 `Invalid operation type` 에러. → 집합 연산을 **서브쿼리로 감싸도록** instruction에 룰로 강제.
교훈: *"LLM이 생성할 수 있는 SQL 패턴을 사전 제약으로 좁히는 게 fallback 처리보다 안정적."*

> ③④⑤를 묶으면 **"LLM 출력을 신뢰하지 않고 제약을 거는"** 일관된 태도가 된다.

## 5. 제품 판단 — 만들 것과 안 만들 것

> 4장이 "왜 깨지는지 찾은" 기록이라면, 이건 **무엇을 만들고 무엇을 안 만들지 정한** 기록이다.

### ① 기능을 잘라 데모 일정을 지켰다 (3/11~3/12)
3/17 데모를 앞두고 HITL을 n8n Human Review 노드로 구현하려 했으나 **embedded 모드에서 워크플로우가 아예 안 돌았고, host 모드에서도 2분 넘게 넘어가지 않았다.**
→ 다음 날 원래 설계를 접고 **"워크플로우 한 턴 돌려서 물어보는 방식"으로 대체.** 기능의 겉모습(사람이 개입한다)은 지키고 구현 방식을 바꿔 일정을 맞췄다.
> 부수 발견: 승인 버튼을 눌러도 터널링 문제로 n8n은 계속 실행 중 → **실패 상태가 사용자에게 전달되지 않는 문제**까지 확인.

### ② 응답 정책을 숫자로 못박았다 (3/12)
- 결과 **20건 이상** → 시트 생성 도구 호출 (**사용자 승인 필요**)
- **20건 초과** → "데이터가 많아 요약하여 보여드립니다" + **상위 5건만**
- **20건 이상 / 2개 이상 그룹** → 채팅에 쏟지 않고 **시트 링크로 분기**

"적당히 요약해줘"가 아니라 판정 가능한 규칙. **어느 시점부터 사람 승인을 받을지를 데이터 양으로 정의**했고 출력 채널을 분기시켰다.

### ③ 차트 렌더링 책임을 어느 레이어에 둘지 (3/25~3/27)
| 시점 | 판단 |
|---|---|
| 3/25 | base64 이미지가 **context를 잡아먹는 비용** 확인 |
| 3/26 | Dify 코드 노드로 직접 렌더링 불가 확인 |
| 3/27 | **"Dify에서는 차트 빼고, 차트는 프론트 UI에서"** — 프론트로 이관 |
| 이후 | 샌드박스에 matplotlib 투입 가능해지자 **서버 렌더링 재도입** |

결정이 한 번 뒤집혔지만 최종적으로 **JSON 모드(프론트) / MD 모드(서버)로 채널별 분리**에 수렴. 번복이 아니라 "채널마다 답이 다르다"로 정리된 사례.

### ④ 제약 발견 → 우회 → 스펙 삭제 (3/25 → 4/6)
1. **발견**(3/25) 메일 워크플로우에 **파일 첨부 불가** (base64 → file 변환 없음)
2. **우회**(3/26) base64→이미지 플러그인 투입, `FILES_URL` 환경변수로 부분 해결
3. **삭제**(4/06) "차트 첨부 메일은 애초에 지원 대상이 아님" → **JSON 응답에서 email 플래그 자체를 제거**

"안 되니까 포기"가 아니라 **고쳐보고, 비용을 보고, 요구 자체를 걷어낸** 3단계.

### ⑤ 이슈를 해결/미해결로 분류해 추적 (3/26)
하루 작업 이슈를 **(해결) 2건 / (미해결) 4건**으로 분류하고 각각 지식노트로 링크. "막히면 리스트만 쌓고 진행한다"는 태도의 근거.

### ⑥ 채팅 입력을 어디까지 자유롭게 둘 것인가 (3/25 스크럼)
`[NEEDS CLARIFICATION: 내가 꺼낸 제안인지, 스크럼에서 나온 걸 기록했는지 미확인. 내가 꺼낸 것이면 위 5건보다 강한 카드이므로 반드시 확인할 것]`
- "채팅으로 입력받으면 **가능한 덜 받고 정확하게** 받아야 하는데, 전부 텍스트인지 **입력폼을 줄지**"
- "리스트는 **몇 개까지, 어떤 걸 미리보기로** 보여줄지"
- → "**선택지 JSON을 따로 만들어 output으로 내는 방식**(후보 버튼)은 어떤지"
- → "**기존 채팅형 AI의 UI를 벤치마킹**하자, 그들도 같은 고민을 한 거니까"

## 6. 평가 — 체계를 설계했다 (실행하지 않음)

> ⛔ **DSL 3개를 만들어 뒀지만 프롬프트·도구가 빈 상태로 중단됐다.**
> **"실험을 설계했다"로만 말할 것.** "테스트했다/비교했다"는 거짓이 된다.

**문제 재정의** — "어떤 모델이 제일 좋냐" → **"의도분류·도구호출·쿼리작성 3능력을 각각 독립 측정"**
기존 워크플로우에서는 능력이 섞여 있었다. NL2SQL은 도구 호출과 쿼리 작성을 동시에, 마스터는 의도 분류와 도구 호출을 동시에 한다.

**변수 통제**
> "연결해서 하나로 만들면 앞 단계 실패가 뒤 단계를 오염시킨다. 의도 분류를 틀리면 도구 호출도 당연히 틀리고 SQL도 엉뚱하게 나오는데, 이러면 **실제로는 분류만 못하는 모델을 '전부 못한다'고 잘못 평가**하게 된다."

→ 워크플로우 3개 분리(의도분류: LLM 노드만 / 도구호출: 에이전트+더미도구 / SQL: LLM 노드만), 시나리오는 통일.

**실험 조건** — temperature 고정(분류·도구호출 0.1, SQL 0) ｜ **반복 3~5회 일관성**(*"한 번 맞추는 것보다 매번 안정적으로 맞추는 게 프로덕션에서는 더 중요하다"*) ｜ 동일 GPU·vLLM ｜ 프롬프트 통일 vs 모델별 최적화를 **미결 쟁점으로 명시**

**능력별 지표**
| 능력 | 지표 |
|---|---|
| 의도 분류 | 분류 정확도, 애매한 입력 시 되묻는지 vs 임의 판단하는지 |
| 도구 호출 | 성공률, hallucination, 파라미터 정확성, 병렬 호출 안정성 |
| 쿼리 작성 | 실행 정확도, 문법 유효성, JOIN 정확성 |

+ 실패 원인 분류 체계(문법인지 결과인지 / 안 부른 건지 파라미터가 틀린 건지)

> 💬 "기술 선택을 '안 했다'가 아니라 '이런 조건에서는 안 하는 게 맞고, 조건이 바뀌면 이렇게 전환한다'까지 문서로 답했습니다."
