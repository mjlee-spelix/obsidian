# 성능 검증 스토리 — EXPLAIN ANALYZE에서 검증 체계까지

> [!info] 이 노트의 목적
> [[포트폴리오/01 SPX-Agent 데이터마트 — 4대 역량 정리.md]] § 2가 **결과 수치**(830배, 87%↓)만 보여준다면,
> 이 노트는 **어떻게 측정했고 왜 3번이나 진단이 바뀌었는지**, 그리고 **그 경험이 이후 검증 방식을 어떻게 바꿨는지**를 담는다.
>
> 핵심 메시지: **"빨라졌다"보다 "무엇이 느린지 어떻게 알아냈나"가 실력이다.**

**기간**: 2026-05-19 ~ 2026-06-10 · **측정 도구 3종** · **진단 3회 수정**

## Act 1 — 약식 측정: EXPLAIN ANALYZE 매트릭스 (5/19)

### 측정 설계 — 4단계로 나눴다

바로 쿼리를 돌리지 않고 순서를 잡았다. 이게 나중에 판단의 근거가 됐다.

| 단계 | 내용 | 결과 |
|---|---|---|
| **A.1 사전 조사** | 마트·RBAC 인덱스 **전수 조사** | `spx_*` 인덱스 **47건** 확인. `spx_mv_audit_enriched`는 **`id` UNIQUE 하나뿐** ← 이게 범인의 단서 |
| **A.3 정합 확인** | 시드 카디널리티 실측 vs 기대값 | 핵심 마트 3종 **정합 통과** (450,156 / 6,522 / 155) |
| **C 측정** | endpoint **15종 전수** EXPLAIN ANALYZE | plan + actual time + buffers 매트릭스 |
| **D·E 분석** | Seq Scan 매트릭스 + 인덱스 권장 | trade-off까지 명시 |

> **먼저 인덱스를 전수 조사한 게 핵심이었다.** "450K행 MView에 `id` 인덱스만 있다"를 먼저 알고 들어가니
> Seq Scan이 나왔을 때 원인 추정이 바로 됐다. 측정 결과부터 봤으면 한참 헤맸을 것.

### 결과 — Seq Scan이 한 곳에 집중됐다

**Layer 2 기반 (6,522행) — 전부 Index Hit ✅**

| 쿼리 패턴 | Plan | Actual |
|---|---|---|
| SUM(calls) WHERE tenant+day | Bitmap Index Scan | **0.57ms** |
| COUNT(DISTINCT target_app_id) | Index Only Scan | **1.89ms** |
| ROW_NUMBER() 윈도우 | Bitmap Index Scan | **1.84ms** |

**Layer 1 기반 (450,156행) — 전부 Seq Scan 🔴**

| Endpoint | Plan | Actual |
|---|---|---|
| model-call-share | Parallel Seq Scan | 1,480ms |
| model-users | Parallel Seq Scan | 2,275ms |
| dept-user-activity DAU | Parallel Seq Scan | 1,121ms |
| error-table cause | Parallel Seq Scan | 1,362ms |
| dept-user-activity **NEW** | **Seq Scan ×2** (NOT IN) | **3,333ms** 🔥 |
| dept-user-activity **CHURNED** | **Seq Scan ×2** (NOT IN) | **3,274ms** 🔥 |

**응답 시간 분포**

| 구간 | 개수 |
|---|---|
| < 2ms | **12개** |
| 1~2.3s | 4개 |
| **> 3s** 🔥 | **2개** |

> **판정: p95 ~3,333ms — 3초 임계 초과.** (회의에서 나온 "3초 이내" 요구 미달)
> **원인: 모든 Seq Scan이 `spx_mv_audit_enriched` 단일 객체에 집중. `(tenant_id, occurred_at)` 복합 인덱스 부재.**

### 권장안에 trade-off를 같이 적었다

| 우선순위 | 인덱스 | 예상 효과 | **trade-off** |
|---|---|---|---|
| 🔥 높음 | `(tenant_id, occurred_at)` | 7개 endpoint, **60~100배** | REFRESH CONCURRENTLY 시 인덱스 재구축 **450K행 기준 1~2초 추가** |
| 중 | `INCLUDE (actor_dept_id, model_id)` 확장 | Index Only Scan | 인덱스 크기 **~2배**, REFRESH 부담 증가 |
| 낮음 | Layer 2는 추가 없음 | — | 현재로 충분 |

→ "빨라진다"만 쓰지 않고 **비용도 같이 적은 게** 나중에 중 우선순위를 기각할 때 근거가 됐다.

### 부수 발견 — 측정하러 갔다가 장애를 찾았다

chain refresh가 **실패 중**이었다.
```
relation "public.spx_v_audit_enriched" does not exist
```
- 5/19 마이그레이션이 `_v_` → `_mv_`로 rename했는데, **실행 중인 dify-audit 컨테이너가 구 빌드**라 옛 이름을 참조
- 영향: **마트 데이터가 갱신 안 되고 있었음** (autovacuum 시점에 동결)
- 위임 범위 밖이라 보고만 하고 진행 금지 항목으로 분리

> 측정 작업이 **모니터링 역할까지 한** 사례. 이후 "마트 신선도"를 정식 모니터링 메트릭 6개 중 하나로 넣었다.

## Act 2 — 인덱스 적용, 그리고 도구를 바꿨다 (5/20)

### 인덱스 효과 — 예상대로

| 지표 | Before | After |
|---|---|---|
| p95 | 3,333ms | **420ms** (87%↓) |
| Seq Scan | 7건 | **0건** |

여기서 끝냈으면 "인덱스 추가로 87% 개선"이라는 깔끔한 결론이었다. **그런데 사용자 체감이 안 바뀌었다.**

### 그래서 k6로 정식 부하 테스트를 했다

약식 측정(EXPLAIN)은 **DB 단독 · 부하 0** 조건이다. 실제 운영은 다르다.

| 조건 | 내용 |
|---|---|
| 도구 | k6 v0.56.0 |
| 인증 | Keycloak password grant → access_token + csrf 쿠키 |
| API | Gunicorn gevent worker **1개** (`SERVER_WORKER_AMOUNT=1`) |
| DB pool | `POOL_SIZE=30`, `MAX_OVERFLOW=10` |
| 시드 | `spx_mv_audit_enriched` **450,224행** |

**S1 baseline (10 RPS, 3분)**

| Endpoint | p50 | p95 |
|---|---|---|
| model-call-share | 1.45s | 3.11s |
| model-users | 2.83s | 4.39s |
| dept-user-activity DAU | 5.80s | **7.65s** |
| dept-user-activity NEW | 5.80s | **8.09s** |

- 유효 처리량 **682/1,800 (38%) = ~3.7 RPS**
- **에러율 0%** — 전부 200 OK
- **dropped iterations 1,119 (62%)**

**S2 stress (50 RPS, 5분)**

- p95가 **16~21초**로 악화
- 유효 처리량 **1,129/15,000 (7.5%) = ~3.5 RPS**
- **에러율 여전히 0%**, dropped **92%**

**S3 breakpoint는 생략했다** — S1과 S2가 똑같이 ~3.5 RPS 천장을 보였으니 RPS를 더 올려봐야 의미가 없었다.

### ⚡ 여기서 가장 중요한 해석

> **에러율 0%인데 92%가 드롭됐다.**

이게 신호였다. 실패가 아니라 **큐잉**이라는 뜻이다. 요청이 죽는 게 아니라 **순서를 기다리다 타임아웃 전에 밀려난** 것.
→ "에러가 없으니 괜찮다"로 읽으면 완전히 틀린 결론이 나온다.

### 진단 ③ — DB가 아니라 Gunicorn

| 레이어 | 측정 |
|---|---|
| DB (EXPLAIN ANALYZE) | **0.76ms ~ 420ms** |
| HTTP (k6 단일 호출) | **1.45s ~ 5.8s** |
| HTTP (k6 10 RPS) | 3.11s ~ 8.09s |

→ **DB 대비 10~100배 느림.** 원인 3가지를 특정했다:
1. **Gunicorn 워커 1개** — gevent 기반이지만 SQLAlchemy의 psycopg2가 blocking I/O라 greenlet이 DB 대기 중 다른 요청을 못 받음
2. **dept-user-activity가 1 요청에 7회 DB 왕복** — 개별 쿼리가 빨라도 누적되면 수초
3. **POOL_SIZE=30인데 워커 1개라 동시 활용 불가** — 단일 greenlet만 실제 실행, 나머지는 큐 대기

### 그 결과 두 가지 권고를 낮췄다

| 후속 제안 | 판정 | 사유 |
|---|---|---|
| INCLUDE 확장 인덱스 | **보류** | "현재 병목이 DB가 아닌 Gunicorn 레이어이므로 **DB 인덱스 추가 효과 미미**" |
| NOT IN → LEFT JOIN 리팩토링 | **우선순위 낮춤** | "7회 왕복 구조 자체가 더 큰 문제. 개별 쿼리 최적화일 뿐" |
| Gunicorn 워커 증설 | 🔥 **1순위** | "처리량 3~4배 즉시 개선. 가장 쉬운 조치" |

> 측정이 없었으면 "인덱스 더 넣자"로 갔을 것이다. **좋아 보이는 최적화를 실측으로 기각한 지점.**

## Act 3 — 진단 ②가 틀렸다는 걸 스스로 확인 (5/20)

5/19에 "dept-user-activity 5.8초 = N+1 7쿼리"로 진단했었다. CTE로 통합해봤다.

| 측정 방식 | Before | After |
|---|---|---|
| 순차 단독 | 5.8s | **7ms** (**830배**) |
| 동시 3개 병렬 | — | **1.85s** |

→ **단독은 830배 빨라졌는데 동시 3개는 여전히 1.85초.**
→ 즉 **N+1은 0.1초 영향뿐**이었고, 동시 요청 지연은 `SERVER_WORKER_AMOUNT=1` 때문이었다.

**판정을 이렇게 나눴다**:
> V.3 판정: **코드 수준 PASS** (단독 7ms < 1s 목표 달성). 동시 요청 지연은 인프라 이슈로 분리.

> 이게 중요하다. **"내 코드는 통과 / 인프라는 별건"**으로 책임을 분리해서 보고했다.
> 안 그러면 "고쳤는데 왜 아직 느리냐"에서 논의가 멈춘다.

### 그리고 세 번째 원인이 나왔다 — work_mem

CTE 통합 후에도 5.9초가 남아서 더 팠더니:
```
Sort Method: external merge  Disk: 4496kB
temp read/written 1,600+
```
- `work_mem 4MB`(Dify 기본값) 한도를 초과해 **정렬이 디스크로 넘어감**
- 16MB로 올리니 **1,480ms → 484ms (3배)**

하지만 여기서 멈추지 않았다. **"work_mem을 올리는 게 답인가?"**를 다시 물었다.

## Act 4 — 측정 환경 자체를 고쳤다 (5/20)

> 진짜 해결책 = **시드 분포 정상화** (정렬 대상 행 수 자체를 줄이기).
> 운영 환경에서는 자연 분포라 4MB로도 충분할 가능성이 큼.

5/19 시드는 **인위적**이었다. 그래서 전면 재구성했다.

| 축 | Before (5/19) | After (5/20) |
|---|---|---|
| 카디널리티 | 30부서 / 300계정 / 150앱 / 450K events | **10 / 150 / 100 + KB 30 + Tool 40 / 180K** |
| 시간 분포 | 30일 편중 | **90일 균등** (일평균 2,000, 주말 30% 감소) |
| 모델 | 5종 | **12종** (gpt-4o 25% ~ 임베딩 0.3%) |
| 이벤트 타입 | 2종 | **7종** |
| 분포 패턴 | 균등 | **power-law** (상위 10앱 40%, 다음 20앱 30%, 나머지 70앱 30%) |
| 필터 검증 패턴 | 없음 | **debug 10% / 에러 5% / 미배정 3%** |

**결과**

| 검증 | 값 |
|---|---|
| V.1 카디널리티 | 10/150/150/100/170/180K 정확 |
| V.5 마트 필터링 | error **3,948** / debug **7,304** / 미배정 **9,314** |
| V.6 EXPLAIN | quicksort **776kB, 57ms** — **work_mem 4MB로 안전** |

→ **1,480ms → 57ms (26배)**. work_mem을 안 올리고 해결했다.

> **배운 것**: 측정 환경이 운영을 닮지 않으면 측정값은 거짓말이다.
> **카디널리티 · 시간 분포 · 분포 패턴** 셋이 값을 통째로 좌우한다.
> 그리고 시드에 **debug/에러/미배정 비율을 의도적으로 심어서** 마트 필터가 실제로 동작하는지까지 검증했다.

## Act 5 — 서버 DB 재측정, 그리고 옵티마이저를 이해함 (5/21)

로컬이 아닌 실제 서버 DB에서 다시 쟀다.

| 윈도우 | Plan | Actual | 매칭 행 |
|---|---|---|---|
| 7일 | **Bitmap Index Scan** | **12.1ms** | 9,124행 |
| 90일 | **Parallel Seq Scan** | **40.8ms** | 전체 130K |

→ 5/19 5,800ms → 5/21 12ms = **480배**

**여기서 옵티마이저 동작을 이해했다**:
> 옵티마이저가 **필터 selectivity**로 자동 분기한다. 90일은 거의 다 매칭되니 필터 효과가 없어서 **풀스캔 + 병렬화가 더 빠르다**.
> → **인덱스는 selective 쿼리에서만 의미가 있다.**
> → **광범위 집계는 Layer 2 daily mview로 사전 집계해야 운영급** — 이게 `spx_mv_kpi_calls_daily`의 존재 이유다.

> 즉 측정이 **설계를 사후 정당화**해줬다. 2계층 구조를 만든 이유가 숫자로 증명된 순간.

## Act 6 — 이후 검증은 이렇게 바뀌었다 (5/21 ~ 6/10)

세 번의 오진을 겪고 나서, 검증 방식 자체가 달라졌다.

### 6-1. 측정 도구를 3종으로 분리했다

| 도구 | 보는 것 | 못 보는 것 |
|---|---|---|
| **EXPLAIN ANALYZE** | DB 단독 성능, plan 선택 | 동시성, 애플리케이션 레이어 |
| **k6** | 전 스택 + 동시성, 처리량 천장 | 쿼리가 왜 느린지 |
| **화면 검증(브라우저)** | 사용자 체감, UX 결함 | 수치 |

> "약식 측정 = DB 단독 = 운영 환경 일부만 / 정식 측정 = 전 스택 + 동시성 = 진짜 운영 환경.
> **둘 사이의 격차가 진짜 진단의 시작점.**"

### 6-2. 규약 준수는 사람이 아니라 grep이 검사한다

문서에 "raw 테이블 직접 조회 금지"라고 써두는 것만으론 안 지켜졌다. **PR 조건으로 grep 게이트**를 걸었다.

| 게이트 | 기대 | 실제 |
|---|---|---|
| `VAuditEnriched\|enriched` in drill_calls_service | 0 | **0 hit** ✅ |
| `FROM (messages\|workflow_runs\|workflow_node_executions)` in services/admin/ | 0 | **0 hit** ✅ |
| `process_data` in workflow-nodes.ts | 있어야 함 | **7 hit** ✅ |
| `"미배정"` in services/admin/ | 0 | **0건** ✅ |

→ **"있으면 안 되는 것"과 "있어야 하는 것"을 둘 다 검사**하는 게 포인트. 후자가 없으면 "지우기만 하고 안 넣은" 상태를 못 잡는다.

### 6-3. 합 보존 검증 — 수치가 맞는지를 등식으로

집계 로직을 바꿀 때마다 **총합이 보존되는지**를 확인했다.

| 검증 | 결과 |
|---|---|
| Layer 1 = Layer 2 정합 | **292 = 292** 완전 일치 |
| 챗플로우 토큰 (B안) | `node_tokens(24,000) == msg_tokens(24,000)`, **미분류 0건** |
| 중첩(iteration/loop) 노드 | 롤업 1회만 부모에 누적 → **모델 노드 각 1회** → 합 보존 성립 확인 |

> 특히 B안은 **이중집계 위험**이 핵심이었다(챗플로우 message + 노드 양쪽 집계). 등식으로 증명하지 않으면 "대충 맞는 것 같다"로 끝났을 것.

### 6-4. idempotency 검증 — 두 번 돌려본다

| 검증 | 결과 |
|---|---|
| 시드 2회 실행 | `177,638 → 180,000` **자동 정합** (DELETE+INSERT replace 패턴) |
| audit_mock.sql 2회 실행 | wn_ 260 / ms_ 30 / ae_ 180K **동일, 중복 0** |

→ 마이그레이션·시드는 **"한 번 돌아간다"가 아니라 "여러 번 돌려도 같다"**가 통과 기준이 됐다.
→ 이건 5/18 Shadow DB 부채를 겪고 나서 `delegation-standard.md` § 3에 정식 가드로 박았다.

### 6-5. 환경 변경은 원복까지가 검증이다

194 DB가 다운됐을 때 로컬로 전환해서 E2E 검증을 했는데, 절차를 7단계로 나눴다.

```
LV-1  현재 환경 기록 (DB_HOST / DB_PORT 원본 저장)
LV-2  로컬 전환 + api recreate
LV-3  로컬에 마트·RBAC mock 존재 확인
LV-4  서비스 검증 (flask app_context 직접 실행)
LV-5  프론트 구조 검증 (코드 리뷰)
LV-6  DB 호스트 194 원복 + api recreate
LV-7  .env diff 0 확인 ← 원복 흔적 없음 증명
```

> **LV-7이 핵심.** 검증하려고 바꾼 설정이 남아 있으면 다음 사람이 그걸 진짜 설정으로 안다.
> 실측 스크립트도 마찬가지로 **"일회성 probe는 실행 후 삭제"**(자격증명 하드코딩 회피)를 규칙으로 했다.

### 6-6. 못 한 검증은 "대기"로 명시한다

194 DB가 스토리지 손상으로 다운됐을 때, 실데이터 검증이 필요한 항목을 **추측으로 메우지 않고** 남겼다.

> **194 대기 항목**: task 27(provider 포맷 spot-check), task 28(중첩 노드 이중집계) — **194 복구 후 실데이터로 검증.**

→ task 문서 전체에 `[194 대기]` 마커를 달았다.
→ 같은 원칙으로 조사 문서엔 **"mart의 `model_provider` 형식은 플러그인 경로일 가능성 높으나, 미확인"**처럼 **확인과 추정을 분리 표기**했다.

### 6-7. 테스트로 회귀를 고정한다

검증 중 발견한 버그는 **고치고 끝내지 않고 테스트로 박았다.**

| 발견 | 조치 |
|---|---|
| `MvModelTokensDaily.tenant_id`가 StringUUID → `::UUID` 캐스트 오류 | `sa.Text`로 수정 + **6단계 테스트로 회귀 방지** |
| `tokens`가 BigInteger인데 실제는 numeric | `sa.Numeric`으로 수정 |
| 로컬 provider 라벨 | `test_local_provider_label` 신설 — ollama → `"llama3 (로컬)"` |
| B안 워크플로 모델 등장 | `test_workflow_models_included` 신설 |

→ 최종 **pytest 15 passed / 0 failed**, grep 게이트 **3/3**.

### 6-8. 단, 테스트 통과가 운영 정상을 보장하지 않는다는 것도 배웠다

같은 6/10에 이런 걸 발견했다:
> 운영 provider는 `langgenius/ollama/ollama` 같은 **namespaced** 형식인데 `LOCAL_PROVIDERS`는 bare 매칭(`{"ollama",...}`).
> **시드·테스트가 bare라 green이지만 운영에선 라벨 0건** — ollama조차 안 잡힘.

→ **"시드가 운영을 닮지 않으면 테스트는 통과하면서 버그를 숨긴다."** Act 4의 교훈이 다른 형태로 반복됐다.
→ 그래서 운영 DB(읽기전용)에서 **provider 실제 분포를 직접 SELECT**해서 확인하는 단계를 추가했다.

## 면접용 3분 버전

> 대시보드가 느리다는 보고를 받고 EXPLAIN ANALYZE로 엔드포인트 15종을 전수 측정했습니다. 먼저 인덱스를 전수 조사했더니 45만 행짜리 MView에 `id` 인덱스 하나뿐이었고, 실제로 Seq Scan 7건이 거기 집중돼 있었습니다. 복합 인덱스를 추가해서 **p95를 3,333ms에서 420ms로** 줄였습니다.
>
> 그런데 **사용자 체감이 안 바뀌었습니다.** EXPLAIN은 DB 단독에 부하 0 조건이라서요. k6로 정식 부하 테스트를 했더니 이상한 게 나왔습니다 — **에러율은 0%인데 요청의 92%가 드롭**되고 있었어요. 실패가 아니라 큐잉이라는 뜻이었죠. DB는 0.76~420ms인데 HTTP는 1.45~5.8초, **10~100배 차이**였습니다. 진짜 병목은 Gunicorn 단일 워커였습니다.
>
> 이 과정에서 제 초기 진단 두 개가 틀렸습니다. "N+1 7쿼리가 원인"이라고 봤는데, CTE로 통합했더니 **단독 실행은 830배 빨라졌지만 동시 3개는 여전히 1.85초**였어요. N+1은 0.1초 영향뿐이었습니다. 그래서 "코드는 통과, 나머지는 인프라 이슈"로 책임을 분리해서 보고했습니다.
>
> 그리고 세 번째로 배운 게, **측정 환경 자체가 틀렸다**는 거였습니다. 시드가 30일 편중에 균등 분포라 인위적이었어요. 90일 균등 + power-law로 재구성했더니 같은 쿼리가 **1,480ms에서 57ms**가 됐습니다. work_mem을 올리지 않고 해결한 거죠.
>
> 이 경험 이후로 검증 방식을 바꿨습니다. 측정 도구를 DB 단독·전 스택·화면 검증 3종으로 나누고, 규약 준수는 grep 게이트로 기계가 검사하게 하고, 집계를 바꿀 땐 합 보존 등식으로 증명하고, 환경을 바꿨으면 원복 diff가 0인지까지 확인합니다. 그리고 **못 한 검증은 추측으로 메우지 않고 "대기"로 표시**합니다.
