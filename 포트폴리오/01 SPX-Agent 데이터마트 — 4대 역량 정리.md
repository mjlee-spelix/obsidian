# SPX-Agent 데이터마트 — 4대 역량 정리

> [!info] 위치
> [[포트폴리오/00 성과 뱅크.md]] § "1. 데이터마트 아키텍처"의 **상세 근거 노트**.
> 성과 뱅크는 3~5줄 요약, 이 노트는 면접·서류에서 꺼낼 수치와 서사를 담는다.

> [!warning] 정직 기준 (성과 뱅크 원칙 준수)
> 코드 생성은 Claude Code가 했다. 이 노트에 적는 건 **내가 판단·검증·표준화한 부분**이다.
> - ✅ **내 것으로 말해도 되는 것**: 설계 대안 비교와 채택 근거, SQL 실측·검증, 스코프 판단(무엇을 없앨지), 표준 정의
> - ⚠️ **"AI로 구현"이라 말해야 하는 것**: DDL·서비스 코드·프론트 컴포넌트의 타이핑 자체
> - 판별 기준: **왜 이렇게 설계했는지 내 언어로 설명 가능한가** → 아래 4개 항목은 전부 가능

**기간**: 2026-05-04 ~ 2026-06-15 (데일리 노트 24건 · 마이그레이션 13개 · 회의 결정 3회)

## 한 줄 요약 (서류용)

> Dify 셀프호스트 운영 대시보드의 데이터 마트를 설계·표준화. 설계안을 3차례 전면 재검토한 끝에 **신규 테이블 없이 2계층 4객체 구조**로 확정했고, EXPLAIN ANALYZE 실측으로 병목을 3단계 좁혀 **p95 3,333ms → 420ms(최대 830배)** 개선. 위젯 후보 10개·데이터소스 12종·차트 드로어 4종을 근거를 대고 잘라내 범위를 확정.

## 0. 임팩트 맥락 — 이 수치가 왜 중요한가

> 수치만 있으면 "그래서?"가 붙는다. 이 화면이 **누가 · 언제 · 몇 번** 보는 화면인지가 크기 감각을 만든다.

### 이 대시보드는 로그인하면 **무조건 처음 보이는 화면**이다

| 조건 | 내용 |
|---|---|
| 로그인 후 기본 경로 | **`/dashboard`** — 기존 `/apps` 디폴트 완전 폐기(5/13). `DEFAULT_POST_LOGIN_PATH` 상수 도입, 하드코딩 7곳 일괄 교체 |
| 헤더 진입점 | 톱 네비 **첫 번째 메뉴** (`DashboardNav`) |
| 사용자 범위 | **로그인 사용자 전체** — "관리자 전용" 폐기(5/13, 이사님 "데이터 노출 OK") |
| 대상 규모 | Keycloak 등록 사용자 **150명** / 부서 **10개** (목업 기준) |
| 첫 화면 동시 호출 | **4개 엔드포인트 동시** + KPI 카드 클릭 시 **3개 추가** |

→ **"관리자 몇 명이 가끔 보는 리포트"가 아니라, 전 사용자가 매 로그인마다 마주치는 첫 화면.**
→ 그래서 **p95가 곧 체감 품질**이고, 느린 엔드포인트 1개가 페이지 전체 인상을 지배한다.

### 개선 전에 실제로 어땠나

| 시점 | 체감 | 내역 |
|---|---|---|
| 초기 | **화면 wall clock 약 10초** | 백엔드 2.7s + 프론트 + **토스트 retry 누적** — 로그인 직후 첫 화면이 10초간 비어 있고 에러 토스트가 쌓임 |
| 데이터 증가 후 | **최악 3,333ms (단건)** | 450K행 마트에서 drill 2종이 Seq Scan ×2 |
| 개선 후 | **420ms** | 인덱스 추가로 Seq Scan 7 → 0 |

### "3초"는 내가 정한 숫자가 아니다

`2. 회의록/0507 AAI 주간 보고.md` 원문:
> - 우선 **배치**로 갱신 (실시간 X)
> - **3초 이내로 응답 뽑아오는 게 목표**
> - ETL 배치 vs 실시간 — 우선 배치

→ **5/7 주간보고에서 나온 요구사항**이 그대로 5/19 EXPLAIN 매트릭스의 판정 임계치가 됐다.
→ 측정 결과 "15종 중 2종이 3초 초과 = **요구 미달**"로 판정 → 인덱스 작업 착수 → 충족.
→ 즉 이 수치는 **내가 세운 목표가 아니라 합의된 SLA를 통과시킨 기록**이다.

### 비용 측면 임팩트

- 모델별 토큰 차트가 **유료 외부 API 사용을 가시화** — 운영 DB 실측에서 `gemini-embedding-001`(유료)이 1개 데이터셋에 붙어 있고 인덱싱 토큰 **44.5만** 실재
- 차트 개선 전에는 챗플로우·워크플로우 토큰이 **'미분류'로 뭉뚱그려지거나 아예 누락** → 어떤 모델이 비용을 쓰는지 알 수 없는 상태였음
- B안 UNION 재작성 후 **미분류 0건**, 모델 13종 정상 집계

## 1. 마트 구조 설계·표준화

### 설계안 3차 전환 — 최종적으로 신규 테이블 0개

| 시점 | 안 | 결과 |
|---|---|---|
| 5/8 | 4-fact (신규 테이블 4개 + 별도 ETL) | 폐기 |
| 5/11 | OLTP 3-fact | 폐기 |
| 5/12 | **audit 단일 SoT + RBAC JOIN** | ✅ 확정 — **신규 테이블 0개** |

```
[원본]    public.spx_audit_events   (Generated Column 8개 보강)
           + RBAC 5종 (spx_departments / spx_department_members / spx_resource_ownership …)
              │
[Layer 1]  spx_mv_audit_enriched             MView · 18컬럼 · 이벤트 1건 = 1행
           spx_v_resource_ownership_enriched View  ·  7컬럼 · state 스냅샷
              │
[Layer 2]  spx_mv_kpi_calls_daily            MView · 11컬럼 (차원 6 + 측정 5)
           spx_mv_model_tokens_daily         MView ·  6컬럼 (차원 4 + 측정 2)
```

**MView / View 선택 기준을 규모로 명시** — enriched는 900만 행 + 5분 stale 허용 + 5개 컴포넌트 공용 → MView. ownership은 수천 행 + 부서명 즉시 반영 필요 → View.

### 정량

| 항목 | 수치 |
|---|---|
| 마트 객체 | **4종 / 2계층** |
| Generated Column | **8개** (`_d` 접미사 7 + `target_app_id` 예외 1) |
| 인덱스 | 원본 **13개**(기존 8 + 마트 가속 5) + Layer 1·2 **5개** |
| Prisma 마이그레이션 | **13개** 중 마트 전용 **11개** |
| 모니터링 메트릭 | **6개** (collector lag / mart lag / REFRESH 소요 / 행수 차이 / dept NULL / actor NULL 5%) |
| 백엔드 전환 | 신규 `api/models/mart.py` **152줄**, 수정 **10파일**, `query_helpers.py` 헬퍼 **7개 전부 제거** |
| 쿼리 단순화 | 소스 테이블 **8종 + 최대 9-CTE** → 마트 **4객체 SELECT** |
| SLA | 마트 신선도 **< 7분** · collector lag **< 10분** · 첫 페인트 **< 3초** |

### 내가 정의한 표준

- **네이밍** — `audit`/`mart` 별도 스키마 폐기 → `public` 단일 + **`spx_` 접두사**. MView는 `spx_mv_`, View는 `spx_v_`. 잘못 붙은 `spx_v_audit_enriched` → `spx_mv_`로 바꾸는 **전용 마이그레이션까지 작성**
- **공통 컬럼** — details JSON 추출 컬럼 전부 `_d` 접미사. 출처 자체기록 + 미래 top-level 컬럼과 충돌 방지
- **날짜** — `date_trunc('day', occurred_at AT TIME ZONE 'Asia/Seoul')` 단일 경계 → 모든 기간 비교가 `SUM` 한 번
- **부서 차원** — 옵션 A~D 비교 후 **B(ID만 사전 JOIN, 부서명 query-time)** 채택 → 부서명 변경 즉시 반영. `actor_dept_id`(채택 폭) / `app_owner_dept_id`(호출량) **둘 다 GROUP BY 보존**
- **sentinel UUID 2종** — `…000000000000`=미배정 / `…ffffffffffff`=외부.
  근거가 기술적으로 명확: PostgreSQL은 표현식 인덱스에 `REFRESH CONCURRENTLY` 불가 → SELECT 단계에서 NULL을 치환해 인덱스를 단순 컬럼으로 유지
- **타입 가드 (H-MART-01)** — `actor_type IN ('account','end_user')`일 때만 `::uuid` 캐스트.
  mock에 account만 있어 테스트는 통과하지만 운영의 `'system'` / `'chatbot-public-001'`에서 터질 결함을 **운영 진입 전 차단**
- **비즈니스 규칙을 마트가 흡수** — "컴포넌트는 SELECT만 한다"가 황금 규칙. `is_debug`(H-DASH-03) · `is_canonical_call`(H-DASH-01)을 플래그 컬럼으로 박음

### 규약을 코드로 강제한 부분 (면접 포인트)

`architecture.md`에 **마트 인터페이스 의무화(5/18)** 명문화 — raw 테이블 직접 SELECT ❌ / `details->>` raw 추출 ❌ / `_d` 컬럼 직접 참조 ❌.
→ **grep 게이트 4종**을 PR 조건으로 걸어 위반 3종 **0 hit**, 정상 참조 **22 hits** 통과.
→ "미배정" 하드코딩도 SQL 5곳 + Python 2곳 → 중앙 상수로 통합해 **grep 0건**.

## 2. SQL로 데이터 직접 탐색·검증

### 성능 — EXPLAIN ANALYZE 기반, 최대 830배

엔드포인트 **15종 전수 EXPLAIN ANALYZE 매트릭스**를 만들어 병목을 특정.

| 개선 | Before | After | 배수 |
|---|---|---|---|
| p95 응답 (인덱스 추가) | 3,333ms | **420ms** | 87%↓, Seq Scan **7 → 0** |
| model-call-share (시드 재구성) | 1,480ms | **57ms** | **26배** |
| dept-user-activity (CTE 통합) | 5,800ms | **7ms** | **830배** |
| 서버 DB 재측정 (7일 윈도우) | 5,800ms | **12.1ms** | **480배** |

**진단이 다층적이었던 게 핵심** — 이 서사가 면접에서 제일 잘 먹힘:
1. 5/19 약식 측정 → "N+1 7쿼리가 원인"
2. 5/20 단일 CTE 통합 후에도 **5.9초** → N+1은 0.1초 영향뿐
3. 진짜 원인 = base CTE **437K행 정렬 시 work_mem 4MB 초과 → `external merge Disk: 4496kB`**
4. 더 나아가 DB 0.76~420ms vs HTTP 1.45~5.8s(**10~100배 차이**) 대조 → **"DB가 아니라 Gunicorn 단일 워커가 병목"** 결론
5. → 추가 인덱스(INCLUDE) 제안을 **오히려 기각**

### SQL이 아니었으면 못 잡았을 것들

| 발견 | 내용 |
|---|---|
| RBAC 테이블 존재 오인 | "타 담당자 ETA 대기"로 이틀 낭비 → `\dt \| grep department`로 이미 DB에 5종 잔존 발견. 이후 **H-DASH-17(관찰 부족 함정)** 정식 등록 + "운영 인프라 검증" 절차 신설 |
| 테이블 접두사 2회 정정 | `sp_`(가정) → 무접두(가정) → **`spx_`(확정)**. 라이브 DB `\dt` 직접 대조로 종결 |
| '미분류' 토큰의 정체 | 워크플로우가 아니라 **챗플로우(advanced-chat)** — message의 모델 컬럼이 NULL로 생성됨. 순수 워크플로우는 아예 누락 |
| `LOCAL_PROVIDERS` 운영 라벨 0건 | 운영은 `langgenius/ollama/ollama` 형식인데 코드는 bare 매칭 → **시드·테스트가 bare라 green이지만 운영에선 라벨 0건** |
| vLLM 전제 오류 | 전제("openai_api_compatible로 등록")와 달리 독립 플러그인. `provider_type`도 `custom`/`system`(자격증명 범위)이라 **로컬 판별 신호로 사용 불가** |
| 디버깅 대상 DB 오인 | api 컨테이너는 원격 DB에 연결. 로컬 DB를 보며 헤맴 → `docker exec … env \| grep DB_` 필수 절차화 |
| ORM ↔ 실제 타입 불일치 2건 | `tenant_id` StringUUID→Text, `tokens` BigInteger→Numeric |

### 정합성 검증 수치

- **계층 합 대조**: Layer 1 **292** = Layer 2 calls 합 **292** 완전 일치 / Layer 1 316건 **100% 매칭**
- **시드 카디널리티**: 450,156 / 6,522 / 155 — 핵심 마트 3종 정합 통과
- **idempotency**: 시드 2회 실행 → `177,638 → 180,000` 자동 정합, **중복 0**
- **실측으로 컬럼 선택**: `created_by` 매핑률 **29%** vs `owner_account_id` **94.7%(18/19)** → top-owners를 후자 기준으로 확정
- **운영 모델 타입 분포**: `text-generation 9` / `embeddings 4`, rerank·STT·TTS·moderation **등록 0건**
- **게이트**: collector 6케이스 전수 + **pytest 15 passed / 0 failed** + **grep 3/3**

## 3. 원천 ~ 마트 전체 흐름 설명

### 8단계 파이프라인

```
[1] 원천   Dify OLTP (messages / workflow_runs / workflow_node_executions / apps / conversations …)
           RBAC 5종 · Keycloak 4테이블 (user_entity / groups / user_group_membership / credential)
              │  수집 경로 14종 = DB폴링 collector 13 + nginx log-watcher + pg_trigger 5종 + self-audit
[2] 적재   public.spx_audit_events        (source 5종으로 수집 경로 구분)
[3] 보강   Generated Column 8개 + 마트 가속 인덱스 5개
[4] L1     spx_mv_audit_enriched          ← ownership INNER JOIN + members LEFT JOIN
[5] L2     spx_mv_kpi_calls_daily / spx_mv_model_tokens_daily
[6] 백엔드 api/models/mart.py → services/admin/dashboard_*_service.py (9파일 1,897줄)
[7] API    GET /console/api/dashboard/{kpi, dept-objects, model-tokens, dept-activity, drill/{metric}/{chart}}
[8] 프론트 use-admin-dashboard.ts / use-admin-drill.ts (TanStack, staleTime 5분)
           → /dashboard/page.tsx → KPI 4 + 차트 2 + 표 1 + drill 차트 8 + drill 표 4 (ECharts)
```

| 구간 | 수치 |
|---|---|
| 수집 경로 | **14종** (collector 소스 16개 중 유틸 2 제외) |
| DB 폴링 collector | **13종**, 5분 주기, 상태는 `spx_collector_state` 기록 |
| pg_trigger | **5종** (documents / datasets / apps / api_tokens / tenant_account_joins) |
| 원천 테이블 | Dify OLTP **5** + RBAC **5** + Keycloak **4** |
| API 라우트 | **17개** (KPI 4 + drill 12 + drawer 1) |
| 프론트 | KPI 4 + 메인 차트 2 + 표 1 + **drill 차트 8 + drill 표 4** |

### 동기화 — 구간별 지연을 수치로 관리

| 구간 | 방식 | 주기 |
|---|---|---|
| Dify OLTP → audit | collector 폴링 | 5분 |
| Dify DELETE/UPDATE → audit | `spx_log_dify_change()` pg_trigger | 실시간 |
| nginx access.log → audit | log-watcher (offset 추적) | 실시간 |
| audit → 마트 | `refreshMartChain()` CONCURRENTLY ×3 순차 | 5분 (collector 사이클 끝) |
| 마트 → 프론트 | TanStack staleTime | 5분 |

**pg_cron을 안 쓴 이유를 흐름으로 설명할 수 있음** — mat별 분리 cron이면 collector 5 + enriched 5 + mat 5 = **최악 15분**. collector 사이클 끝에 chain을 붙이면 **mat 단계 추가 지연 0분 → 최악 10분**. 그리고 "전체 lag = MAX(병목 단계)이고 진짜 병목은 collector 5분 폴링이라 마트만 실시간으로 만들어도 체감 0"까지 문서화. 구현 **+16줄**, try/catch 격리로 마트 실패가 collector 다음 회차를 막지 않게 처리.

**도구·권한 분리도 흐름의 일부** — DDL은 Prisma migration 소유(Alembic 아님), `mart.py`는 `info: {'is_view': True}` 마커로 Alembic autogen 제외. `audit_writer`는 ALTER 권한이 없어 superuser DDL + `prisma migrate resolve --applied` 패턴.

**흐름 재설계까지 수행 (B안, 6/10)** — 워크플로/챗플로 모델이 차트에 안 잡히는 문제를 `spx_mv_audit_enriched` 의존 → **`spx_audit_events` 직접 조회 + UNION ALL 2갈래**로 재작성. 모델 차트는 부서 차원이 없어 RBAC JOIN이 불필요하다는 판단으로 refresh chain에서 독립. 챗플로우 이중집계는 (1)에서 제외하고 (2) 노드에서만 집계 → 검증 `node_tokens(24,000) == msg_tokens(24,000)`, 미분류 **0건**.

## 5. 장애물 — 실제로 막혔던 지점

> 성과표만 보면 순탄해 보이지만, 실제로는 **되돌린 작업과 헛수고가 꽤 있었다.** 그 기록이 오히려 판단력의 근거다.

### 5-1. 가장 크게 막힌 것 — 외부 의존 명세를 추정으로 박음 (H-DASH-17)

5/4 spec 작성 때 RBAC 영역을 `sp_*` 접두사로 **가정**하고 써버렸다. 그래서 5/6 오후까지 "RBAC 테이블은 타 담당자 ETA 대기 중"이라고 잘못 인식했다. 실제로는 **우리 docker DB에 이미 5종이 다른 이름으로 영속 잔존**하고 있었다.

발견 흐름이 3단계였는데, 세 번째가 결정적이었다:
1. "RBAC 테이블이 rbac 브랜치에 있지 않을까?" → `git show origin/feat/rbac:api/models/sp_*` 비어있음
2. "docker DB에 있지 않을까?" → `\dt | grep sp_` 비어있음
3. **"근데 이름이 다를 수도?"** → `\dt | grep department` ✨ 발견

- **비용**: 이틀치 인식 오류 + 이후 **spec 24파일 정정 위임**
- **접두사는 결국 2회 정정**: `sp_`(가정) → 무접두(가정) → **`spx_`(확정)**
- **남긴 것**: H-DASH-17 정식 등록 + "운영 인프라 검증"(`\dt` / `\d` / `SELECT count(*)`) 절차 신설

### 5-2. 자가 검증이 거짓이었던 사고 — 같은 패턴 2회 재발

AI 에이전트가 audit 스키마 rename 작업 후 **"사전 조건 3건 OK"로 자가 검증을 박아** 세션 기록에 그대로 남았다. 직접 검증해보니:
- audit 스키마 폐기 안 됨
- trigger 함수 미교체 → 옛 함수가 살아 있고 trigger 5개가 그걸 가리킴
- **17건이 옛 테이블로 INSERT 진행 중**

5/18에 같은 패턴이 또 났다(마이그레이션 파일을 안 만들고 SQL만 DB에 적용해놓고 "완료" 보고).
→ **`delegation-standard.md` § 2 "자가 검증 거짓 가능성" 가드 신설.** 위임 완료 보고 후 본인 검증 단계를 빼지 않는 걸 규칙으로 굳혔다.

### 5-3. 고친 게 부팅할 때마다 되돌아간 사고 — self-heal cycle

5/19 마이그레이션은 `_v_` DROP + `_mv_` 생성 + Layer 2 재바인딩까지 **의도는 완벽**했다. 그런데 `entrypoint.sh`의 self-heal 블록이 마트 객체 누락을 감지하면 **매 부팅마다 옛 마이그레이션 4개를 재실행**했다. 결과:
- `_v_`가 부활 → Layer 2가 도로 `_v_`에 묶임
- 백엔드 ORM과 refresh 워커는 `_mv_`를 참조 → **stale 데이터 위험 + 디스크 2배 + refresh 비용 2배**
- DB에 `_v_`와 `_mv_`가 **동시에 존재하는 좀비 상태**

→ 교훈: **rename 마이그레이션 + 인프라(entrypoint) 동기 갱신 필수.** 한쪽만 박으면 자동 복구 메커니즘이 **의도와 반대로 작동**한다. 정리 전용 마이그레이션(`20260521000000_finalize_audit_enriched_rename`)을 따로 만들어 해소.

### 5-4. 성능 진단이 두 번 틀렸다

## 6. 판단의 배경 — 무엇을 우려했나

> 의사결정 표는 "무엇을 골랐나"만 보여준다. 여기엔 **탈락한 안이 왜 별로였는지, 고를 때 무엇이 걱정이었는지**를 적는다.

### 6-1. RBAC JOIN 옵션 B — A도 C도 각자 다른 방식으로 나빴다

| 안 | 왜 별로였나 |
|---|---|
| A. 부서명까지 마트에 박음 | 부서명이 바뀌면 **최대 5분간 옛 이름이 화면에 남음**. 조직개편이 잦은 회사에서 "이름 바뀌었는데 대시보드는 옛날 이름"은 신뢰도를 직접 깎음 |
| C. 완전 분리 (JOIN 안 함) | 부서 dimension이 작은데도 **매 쿼리마다 hash build를 반복**. 비싼 결합을 사용자 요청 시점에 떠넘기는 구조 |
| **B. ID만 사전 JOIN** ✅ | 비싼 결합(audit × dept_members 만 단위)은 **refresh 1회로 흡수**, 작은 dimension(부서명 백 단위)은 query-time → **즉시 반영** |

**우려했던 것**: B는 "절반만 미리 계산"이라 어중간해 보일 수 있다. 하지만 비용이 큰 쪽과 변경이 잦은 쪽이 정확히 반대여서, 이 경계가 자연스러운 절단면이라고 판단했다.

### 6-2. View가 아니라 MView로 시작한 이유 — "전체 공개" 결정이 앞에 있었다

5/13에 **사용자 범위가 "관리자 전용" → "로그인 사용자 전체"로 바뀐 게 결정적**이었다.
- View로 시작하면 **동시 쿼리 부하가 사용자 수에 비례**해서 붙는다
- 전체 공개로 바뀐 이상 "일단 View로 시작하고 느려지면 MView로" 전략은 위험
- `REFRESH CONCURRENTLY`(UNIQUE INDEX 전제)로 **다운타임 0 새로고침**이 가능하니 초기 비용을 감수

→ **기술 선택이 아니라 사용자 범위 결정이 선행 변수였다.**

### 6-3. pg_cron을 안 쓴 진짜 이유 — "빠르게 만들어도 체감이 안 바뀐다"

표면 이유는 "`postgres:15-alpine`에 pg_cron 미포함 → 이미지 교체나 Dockerfile 빌드 필요, 반면 collector chain은 코드 5줄"이다. 하지만 더 중요한 판단은 이거였다:

> **전체 lag = MAX(병목 단계)**. 진짜 병목은 collector 5분 폴링이므로, **마트만 실시간으로 만들어도 사용자 체감은 0**이다.

또 mat별로 cron을 분리하면 collector 5 + enriched 5 + mat 5 = **최악 15분**이 되는데, collector 사이클 끝에 chain을 붙이면 **mat 단계 추가 지연이 0분** → 최악 10분.
**우려**: 마트 refresh 실패가 collector 다음 회차를 막는 것. → try/catch로 격리해 해소.

### 6-4. 측정이 "마트 무용"이라고 나왔는데도 마트를 만든 이유

5/11 측정 결과는 냉정했다 — **"8/15 엔드포인트 단축 → 0% 단축"**. DB는 9-CTE 최복잡 쿼리도 1.5ms였고, 백엔드 non-DB가 99.9%였다. 즉 **지금 데이터 양에서 마트는 효과가 없다**.

그런데도 만들었다. 근거:
> **운영 데이터 양 증가는 기정 사실** (mockup 375건 → 운영 100만+)

→ **"지금 안 아프다"와 "나중에 안 아프다"는 다르다**는 판단. 실제로 5/19에 450K행을 넣자마자 Seq Scan 7건 / 3.3초가 튀어나왔고, Layer 2 기반 엔드포인트는 그때도 **0.5~2ms**를 유지했다. 마트가 없었으면 그 시점에 전면 재작업이었을 것.

### 6-5. Generated Column을 STORED로, 그것도 DB에 위임한 이유

**우려했던 것**: collector가 14종인데 각자 details 구조가 다르다. 모든 collector에 "이 컬럼도 INSERT해"를 강제하면 **스키마와 collector가 강결합**된다. collector 하나 추가할 때마다 마트가 깨질 수 있다.

→ DB 측 `GENERATED ALWAYS AS (details->>'X') STORED`로 추출을 위임. collector는 자유롭게 details만 박고, 컬럼화는 DB가 한다.
→ `STORED`인 이유는 단순하다: **`VIRTUAL`은 매 쿼리 계산이라 인덱스를 못 건다.**
→ expression index 대안 대비 핵심 이점: `spx_audit_events` 자체가 **마트 + 보안 + 운영의 공용 인터페이스**가 된다.

### 6-6. sentinel UUID — 우아하지 않은 걸 알면서 선택했다

매직 UUID(`…000000000000`)를 박는 건 보기에 안 예쁘다. 그런데 PostgreSQL 제약이 명확했다:
> 표현식 인덱스(`COALESCE(...)` in INDEX)가 걸리면 **`REFRESH MATERIALIZED VIEW CONCURRENTLY`를 못 쓴다.**

CONCURRENTLY를 포기하면 refresh 때마다 다운타임이 생긴다 — **로그인 첫 화면인 페이지에서** 그건 받아들일 수 없었다.
→ SELECT 단계에서 NULL을 sentinel로 치환하고 인덱스는 단순 컬럼으로 유지.
→ 나중에 "미배정"과 "외부"를 구분해야 해지면서 sentinel을 2종으로 분리했는데, 이때도 **매핑은 백엔드 응답 직전에만** 하도록 못박았다(프론트 매핑 금지).

### 6-7. 인덱스를 더 넣자는 제안을 기각한 이유

`INCLUDE (actor_id, actor_dept_id, model_id)`로 Index Only Scan을 만들자는 후속 제안이 있었다. 기각했다:
- 그 시점 병목은 **DB가 아니라 Gunicorn 레이어**로 이미 판명 (DB 0.76~420ms vs HTTP 1.45~5.8s)
- `REFRESH CONCURRENTLY` 시 **인덱스 재구축 비용이 450K행 기준 1~2초 추가**
- 즉 **체감 개선은 미미한데 refresh 비용은 확실히 오른다**

→ "좋아 보이는 최적화"를 실측 근거로 거절한 사례.

### 6-8. 삭제 대신 비활성을 고른 판단들 — 회복 비용 비대칭

| 대상 | 선택 | 우려 |
|---|---|---|
| 외부 연결 제거 | 직접 삭제(24파일 2,000줄) ❌ → **피처플래그(20줄)** | 원본 무수정 원칙 위반 + **비가역** + upstream 머지 충돌 |
| `ja/`·`zh/` 문서 | 삭제 ❌ → **nav 비활성** | 삭제하면 orphan이라 **git 히스토리로도 복원 불가** |
| `context-bar` | 코드 삭제 ❌ → **렌더링만 비활성** | 재도입 결정이 나면 다시 짜야 함 |
| fallback 테스트 3건 | 삭제했다가 **복원** | "서비스에 try-except가 없어서 지운 것"이 아니라 **방어를 잃은 걸 테스트만 지워 덮은 것**으로 재판단 |

→ 공통 원칙: **제거는 비가역이므로, 되돌릴 비용이 비대칭이면 가역적인 쪽을 고른다.**

### 6-9. 차트 드로어를 없앨 때의 망설임

이사님 의문이 출발점이었다: *"사용자가 정말 그 깊이를 원하나? 관리자만 필요한 거 아닌가?"*
- 4종 설계를 다 해놓고 버리는 게 아까웠지만, **판정 기준을 먼저 세운 게 도움이 됐다** — "4개 다 의미 있어야 살아남는다, 하나라도 아니면 전체 제거"
- 검증해보니 KPI 4번 드로어 지표가 **하단 표 컬럼과 100% 일치**
- spec 본문은 보존해서 **재검토 시 base로 쓸 수 있게** 남김 → 아까움을 "폐기"가 아니라 "보류"로 처리

## 7. 배운 점 — 이 경험으로 뭐가 바뀌었나

> 전부 데일리 노트 "배운 것" 섹션에 당시에 적어둔 것. 사후 미화가 아니다.

### 7-1. 추정으로 명세를 쓰지 않게 됐다

가장 비싸게 배웠다. 외부 팀 소유 영역을 "아마 이럴 것"으로 spec에 박으면, 그게 **사실처럼 굳어서 며칠간 판단을 오염시킨다.**
→ 이제 외부 의존이 걸리면 **코드 grep + DB `\dt` + 담당자 확인**을 먼저 한다. 5분이면 끝나는 확인이 이틀을 아낀다.
→ 부수 학습: **git author ≠ 실제 작업자.** git 메타데이터는 commit 책임자만 알려준다. 분담은 사람한테 물어봐야 정확하다.

### 7-2. AI 위임 결과를 그대로 믿지 않게 됐다

이 프로젝트의 코드는 대부분 AI가 짰다. 그래서 **자가 검증 보고가 거짓일 수 있다**는 게 치명적 리스크였고, 실제로 2회 터졌다.
→ 위임 완료 보고 뒤에 **반드시 내 검증 단계를 끼워넣는다.**
→ "VSCode 자가 검증 결과"와 "내 검증 결과"를 기록에서 **분리 표기**한다.
→ 이걸 `delegation-standard.md` 5개 가드로 문서화해서 다음 위임부터 자동 적용되게 했다.

### 7-3. 진단은 한 층에서 끝나지 않는다

표면 에러와 실제 원인 사이에 **4계층**이 있던 사례를 겪었다(컨테이너 안 동작 → DB 상태 → 호스트 파일 형태 → git 메타).
성능도 똑같았다(N+1 → work_mem → Gunicorn).
→ 첫 가설이 "말이 되는지"가 아니라 **"고쳤더니 실제로 숫자가 움직였는지"**로 판정한다.
→ 가설이 여럿이면 한 번에 다 고치지 않고 **변수 하나씩 분리해서** 검증한다. 안 그러면 진짜 원인이 묻힌다.

### 7-4. 측정 환경이 운영을 닮지 않으면 측정값은 거짓말이다

5/19 시드는 30일 편중 + 균등 분포였다. 5/20에 90일 균등 + power-law로 바꾸자 같은 쿼리가 **1,480ms → 57ms**로 변했다.
→ **카디널리티 · 시간 분포 · 분포 패턴**이 측정값을 통째로 좌우한다.
→ 같은 맥락에서, `LOCAL_PROVIDERS` 버그는 **시드가 bare 이름이라 테스트는 green인데 운영에선 라벨 0건**이었다. **"테스트 통과"가 "운영 정상"을 보장하지 않는다.**

### 7-5. 검증 도구는 결함 유형마다 다르다

PostgreSQL 트랜잭션 abort(`InFailedSqlTransaction`)는 **단위 테스트 mock 환경에서 원리적으로 재현이 안 된다** — 통합 테스트로만 잡힌다.
빌드 결함은 grep으로 안 잡히고 `docker compose build`가 진짜 게이트다.
"기능이 없다"는 걸 증명할 땐 화면 클릭보다 **코드 grep이 더 단정적**이다.
→ "테스트 다 통과했으니 안전"이라고 말하지 않게 됐다. **무엇을 못 잡는 테스트인지**를 먼저 본다.

### 7-6. 문서에 적는 것만으로는 규칙이 안 지켜진다

"raw 테이블 직접 조회 금지"를 문서에 써두는 것만으론 부족했다. **grep 게이트를 PR 조건으로 걸고 나서야** 0 hit가 유지됐다.
"미배정" 하드코딩도 마찬가지 — 중앙 상수를 만들고 **`grep "미배정" → 0건**을 확인하는 절차까지 만들어야 끝났다.
→ 규칙은 **기계가 검사할 수 있는 형태**로 바꿔야 산다.

### 7-7. spec과 코드는 같은 PR에서 정합해야 한다

5/14에 spec만 갱신하고 코드를 안 고친 트랙이 **6일 누적**됐고, 부하 테스트에서 옛 명세의 `NOT IN` 쿼리가 진짜 병목으로 터졌다.
반대 방향도 겪었다 — 화면 검증이 끝난 코드가 정답이라 **spec을 코드 쪽으로 정합**시킨 예외 케이스(평소 원칙을 한 번 뒤집음).
→ 어느 쪽이 정답이든 **한쪽만 박으면 잠재 부채**라는 게 결론.

### 7-8. 자기 검토에는 구조적 한계가 있다

내가 쓴 spec을 내가 검토하면 **같은 추상 수준에 갇혀서** 어긋남이 안 보인다(H-DASH-16). 차트 4개를 다 만들고 나서야 "표였어야 했는데"를 알았다.
→ 대응 3종을 게이트로 박았다: **외부 산출물 직접 대조 / AI에 검토 위임 / 시간차 검토** 중 최소 하나.

### 7-9. 제약을 받아들이면 모델이 단순해진다

ESC 키를 가로챌 수 없는 모달 환경 제약을 인정하자 "재클릭 토글"이라는 더 단순한 해제 경로가 나왔다.
CONCURRENTLY 제약을 인정하자 sentinel이라는 단순한 답이 나왔다.
→ 제약을 우회하려 들기 전에, **제약을 전제로 다시 설계하면 더 나은 답이 나오는 경우**가 있다.

### 7-10. 재발은 가장 강한 검증 신호다

가설 단계의 결함을 카탈로그에 박으면 신호 대 잡음비가 흐려진다. 그런데 **같은 게 두 번 나면 그건 현장 검증을 통과한 것**이다.
→ "1차 발생은 후보(CAND), 재발하면 정식 등록"이라는 승격 규칙을 만들었고, 이 프로젝트에서 **결함 카탈로그 15패턴**이 그렇게 쌓였다.
