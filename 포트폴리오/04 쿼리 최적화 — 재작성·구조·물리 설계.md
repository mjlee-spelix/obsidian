# 쿼리 최적화 — 재작성·구조·물리 설계

> [!info] 이 노트의 목적
> [[포트폴리오/03 성능 검증 스토리 — EXPLAIN ANALYZE에서 검증 체계까지.md]]가 **어떻게 측정했나**라면,
> 이 노트는 **측정 결과로 쿼리를 어떻게 고쳤나**를 담는다.
>
> "830배 개선"이라는 숫자 뒤에 실제로 쓴 SQL 기법이 무엇인지. 면접에서 **"쿼리 최적화 해봤나요"**에 바로 걸리는 노트.

**핵심**: 최적화를 **4개 층위**로 했다 — 쿼리 재작성 / 구조로 쿼리 제거 / 물리 설계 / **기각 판단**

---

## 0. 한눈에 — 4개 층위

| 층위 | 한 일 | 대표 성과 |
|---|---|---|
| **1. 쿼리 재작성** | 7쿼리 N+1 → 4-CTE 단일 쿼리 | **5,800ms → 7ms (830배)**, `NOT IN` 2건 제거 |
| **2. 구조로 제거** | 9-CTE·7-CTE를 마트가 흡수 | 현재 코드에 `NOT IN` 0 / `ROW_NUMBER` 0 / `WITH` 1건 |
| **3. 물리 설계** | 인덱스가 걸리게 만드는 작업 | Generated Column STORED · partial index · sentinel UUID |
| **4. 기각 판단** | 실측 근거로 최적화를 거절 | INCLUDE 인덱스 보류 / work_mem 증설 미채택 |

> 4번이 있는 게 핵심이다. **최적화를 많이 한 것보다, 안 해도 되는 걸 판별한 게 더 어렵다.**

## 1. 쿼리 재작성 — 7쿼리 N+1 → 단일 CTE

### 문제

5/19 EXPLAIN ANALYZE에서 `dept-user-activity`가 p95 **3,333ms**(NEW) / **3,274ms**(CHURNED)로 3초 임계를 넘었다.
plan을 보니 `Seq Scan × 2` — **`NOT IN` 서브쿼리가 450K행을 두 번 풀스캔**하고 있었다.

그리고 구조 자체가 나빴다. 1 엔드포인트가 **DB를 7번 왕복**했다:

```
dau_rows / wau_rows / curr_users_rows / prev_actors_q / new_rows / curr_actors_q / churned_rows
```

### 재작성한 쿼리

```sql
WITH base AS (                      -- ① 450K행을 한 번만 스캔, 아래서 재사용
  SELECT actor_dept_id, actor_id, target_app_id
  FROM spx_mv_audit_enriched
  WHERE tenant_id = :tenant
    AND occurred_at BETWEEN :start AND :end
),
agg AS (
  SELECT
    actor_dept_id,
    COUNT(DISTINCT actor_id)      AS user_count,
    COUNT(DISTINCT target_app_id) AS adopted_apps
  FROM base
  GROUP BY actor_dept_id
),
top_app AS (                        -- ② 그룹별 Top-1을 서브쿼리 없이
  SELECT DISTINCT ON (actor_dept_id)
    actor_dept_id, target_app_id
  FROM base
  GROUP BY actor_dept_id, target_app_id
  ORDER BY actor_dept_id, COUNT(*) DESC
),
prev_agg AS (                       -- ③ 이전 기간 비교를 NOT IN 대신 사전 집계
  SELECT actor_dept_id, COUNT(DISTINCT target_app_id) AS prev_adopted
  FROM spx_mv_audit_enriched
  WHERE tenant_id = :tenant
    AND occurred_at BETWEEN :prev_start AND :prev_end
  GROUP BY actor_dept_id
)
SELECT
  COALESCE(a.actor_dept_id::text, :unassigned_id)               AS department_id,
  COALESCE(d.name, :unassigned_name)                            AS dept_name,
  a.user_count,
  ROUND(a.adopted_apps::numeric / NULLIF(a.user_count, 0), 1)   AS apps_per_user,   -- ④
  app.name                                                      AS top_app_name,
  (a.adopted_apps - COALESCE(pa.prev_adopted, 0))::float
    / NULLIF(pa.prev_adopted, 0) * 100                          AS trend_pct,       -- ④
  CASE
    WHEN COALESCE(pa.prev_adopted, 0) = 0 AND a.adopted_apps > 0 THEN '+신규'
    WHEN COALESCE(pa.prev_adopted, 0) = 0 AND a.adopted_apps = 0 THEN '-'
    ELSE NULL
  END                                                           AS trend_label
FROM agg a
LEFT JOIN spx_departments d  ON d.id = a.actor_dept_id
LEFT JOIN top_app ta         ON ta.actor_dept_id = a.actor_dept_id
LEFT JOIN apps app           ON app.id = ta.target_app_id
LEFT JOIN prev_agg pa        ON pa.actor_dept_id = a.actor_dept_id
ORDER BY a.user_count DESC
```

### 적용한 기법 4가지

| # | 기법 | 해결한 것 |
|---|---|---|
| ① | **CTE 1회 스캔 후 재사용** — `base`를 `agg`·`top_app` 두 곳에서 참조 | 같은 450K행을 반복 스캔하던 구조 제거 |
| ② | **`DISTINCT ON` + `ORDER BY COUNT(*) DESC`** | 그룹별 Top-1(PostgreSQL 관용구). 상관 서브쿼리나 윈도우 함수 없이 해결 |
| ③ | **`NOT IN` → 사전 집계 + `LEFT JOIN`** | `Seq Scan × 2`의 직접 원인 제거. "신규/이탈"을 집합 차집합이 아니라 **기간 대비 증감**으로 재정의 |
| ④ | **`NULLIF`로 0분모 차단** | 분모 0 → NaN/Infinity 결함(H-DASH-07) 방어를 SQL에서 |

> ③이 특히 의미 있다. 쿼리만 바꾼 게 아니라 **지표 정의 자체를 바꿔서** 비싼 연산을 없앴다.
> `NOT IN`으로 "지난 기간엔 없고 이번 기간엔 있는 사용자"를 구하던 걸, `prev_agg`와의 **LEFT JOIN 증감 비교**로 대체.
> 마침 UI 개편으로 "신규/이탈" 컬럼이 삭제되면서 정의를 바꿀 수 있는 창이 열렸다.

### 결과

| 측정 | Before | After |
|---|---|---|
| 순차 단독 | **5,800ms** | **7ms** (**830배**) |
| 동시 3개 병렬 | — | 1.85s (Gunicorn 단일 워커 직렬화 — 인프라 이슈로 분리 판정) |

### 검증도 쿼리 레벨로 했다

> **V.2 판정 PASS**: `db.session.execute` **메서드당 1회**, `NOT IN` **0건**, `WITH base ... SELECT` CTE 확인

단위 테스트에도 **"단일 CTE 실행 횟수 검증"** 케이스를 넣어서, 나중에 누군가 쿼리를 쪼개면 테스트가 깨지게 했다.

## 2. 구조 최적화 — 마트가 쿼리를 흡수했다

가장 큰 최적화는 **쿼리를 빠르게 만든 게 아니라 없앤 것**이다.

| 쿼리 | Before | After |
|---|---|---|
| `get_dept_error_table` | **9-CTE** (프로젝트 최고 복잡도) | 제거 — 앱 전용 엔드포인트로 대체 |
| `get_dept_call_rps_table` | **7-CTE + UNION ALL + ROW_NUMBER** | Layer 2에 `SUM(calls) GROUP BY` **2회** |
| `get_model_call_share` | `spx_mv_audit_enriched` 직조회 `COUNT` (450K행) | `MvModelTokensDaily` `SUM(calls)` (155행) |
| Phase 1 KPI 4종 | 원천 테이블 8종 JOIN | 마트 4객체 SELECT |

### 현재 코드 실측 (`api/services/admin/dashboard_*.py` 9파일)

```
NOT IN         0건   ← 전멸
ROW_NUMBER     0건   ← 전멸
LATERAL        0건
WITH           1건   ← §1의 CTE 하나만 남음
FILTER (WHERE) 3건   ← 조건부 집계
NULLIF         3건   ← 0분모 방어
COALESCE      10건
LEFT JOIN      9건
GROUP BY      12건
```

> **CTE가 1건뿐인 게 "최적화를 안 했다"가 아니라 "마트가 흡수했다"는 뜻이다.**
> 비즈니스 규칙과 집계를 마트 DDL로 내리면서 애플리케이션 쿼리가 단순해졌다 — 이게 설계 의도였다.
> ([[포트폴리오/02 마트 설계 진화 — 4-fact에서 2계층까지.md]] § "플래그 컬럼화" 참조)

### 이게 왜 더 나은 최적화인가

| 관점 | 쿼리를 튜닝 | 마트로 흡수 |
|---|---|---|
| 효과 범위 | 그 쿼리 하나 | **같은 마트를 쓰는 전 컴포넌트** |
| 신규 컴포넌트 | 또 튜닝해야 함 | 자동으로 빠름 |
| 규칙 누락 | 매번 복사 → 언젠가 빠짐 | 마트가 강제 |
| 재계산 시점 | 매 요청 | **5분에 1회 refresh** |

## 3. 물리 설계 — 인덱스가 걸리게 만들기

쿼리 문법을 안 바꾸고 **plan을 바꾼** 작업들.

### 3-1. Generated Column `STORED` — jsonb를 인덱싱 가능하게

```sql
ALTER TABLE public.spx_audit_events ADD COLUMN
  model_id_d TEXT GENERATED ALWAYS AS (details->>'modelId') STORED;
```

- `details->>'modelId'`를 매 쿼리에서 추출하면 **인덱스를 못 탄다**
- `VIRTUAL`은 매 쿼리 계산이라 역시 인덱스 불가 → **`STORED` 선택**
- 덤으로 collector 14종과 스키마가 **강결합되지 않는다** (collector는 details만 박고 컬럼화는 DB가)

### 3-2. Partial index — 마트가 보는 행만

```sql
CREATE INDEX spx_audit_events_action_mart_idx
  ON public.spx_audit_events (action)
  WHERE action IN ('message_send','workflow_execute');
```

전체 이벤트 중 마트 ETL이 쓰는 2종만 인덱싱 → 인덱스 크기·유지비 축소.

### 3-3. Sentinel UUID — 표현식 인덱스를 피해 `CONCURRENTLY` 유지

```sql
-- ❌ 이렇게 하면 표현식 인덱스가 필요 → REFRESH CONCURRENTLY 불가
--    COALESCE(app_owner_dept_id, '000…') 를 인덱스에 넣어야 함
-- ✅ SELECT 단계에서 치환 → 인덱스는 단순 컬럼
COALESCE(app_owner_dept_id, '00000000-0000-0000-0000-000000000000'::uuid) AS app_owner_dept_id
...
CREATE UNIQUE INDEX spx_mv_kpi_calls_daily_unique_idx
  ON public.spx_mv_kpi_calls_daily (tenant_id, day, app_owner_dept_id, actor_dept_id, target_app_id, app_mode);
```

> **제약을 우회하지 않고 전제로 받아들여 단순해진 사례.**
> CONCURRENTLY를 포기하면 refresh마다 다운타임 — 로그인 첫 화면인 페이지에선 불가.

### 3-4. 조건부 집계 — `FILTER (WHERE ...)`

```sql
COUNT(*)                                        AS calls,
COUNT(DISTINCT actor_id)                        AS users,
COUNT(*) FILTER (WHERE error_text IS NOT NULL)  AS errors,   -- 별도 쿼리 없이
SUM(total_tokens)                               AS tokens,
MAX(occurred_at)                                AS last_seen
```

에러 건수를 위해 쿼리를 하나 더 돌리는 대신 **같은 스캔에서** 뽑는다.

### 3-5. 복합 인덱스 — Seq Scan 7건을 한 번에

```sql
CREATE INDEX spx_mv_audit_enriched_tenant_occurred_idx
  ON public.spx_mv_audit_enriched (tenant_id, occurred_at);
```

**7개 endpoint 동시 해소**, p95 **3,333ms → 420ms**, Seq Scan **7 → 0**.

### 3-6. Layer 2 사전 집계 — 광범위 조회를 구조로 회피

5/21 서버 재측정에서 옵티마이저 동작을 확인했다:

| 윈도우 | Plan | Actual |
|---|---|---|
| 7일 (9,124행 매칭) | **Bitmap Index Scan** | 12.1ms |
| 90일 (130K 전체 매칭) | **Parallel Seq Scan** | 40.8ms |

> **인덱스는 selective 쿼리에서만 의미가 있다.** 90일은 필터 효과가 없어 옵티마이저가 풀스캔+병렬화를 고른다.
> → 광범위 집계는 인덱스로 못 푼다. **Layer 2 daily mview 사전 집계가 답.**
> → 측정이 2계층 설계를 사후 정당화한 지점.

## 4. 기각한 최적화 — 이게 더 어렵다

| 제안 | 판정 | 근거 |
|---|---|---|
| `INCLUDE (actor_dept_id, model_id)` 확장 인덱스 | **보류** | 병목이 DB가 아니라 Gunicorn 레이어(DB 0.76~420ms vs HTTP 1.45~5.8s = **10~100배**). 인덱스 크기 **2배** + `REFRESH CONCURRENTLY` 시 450K행 기준 **1~2초 추가** |
| `NOT IN` → `LEFT JOIN` 별도 PR | **불필요 판정** | CTE 통합으로 **`NOT IN` 쿼리 자체가 소멸** → 자동 해소. 별도 작업 낭비 |
| `work_mem` 4MB → 16MB | **미채택** | 3배 빨라지지만(1,480→484ms) 근본 원인은 시드 분포. 재구성으로 **1,480→57ms** 달성, work_mem은 **4MB 유지** |
| `dept-user-activity` 7쿼리 유지 + 개별 튜닝 | **폐기** | 개별 쿼리가 빨라도 **7회 왕복 누적**이 본질 |

> 공통점: **측정 없이 "좋아 보여서" 하는 최적화를 전부 거절했다.**
> 특히 work_mem은 "설정만 바꾸면 3배"라 유혹이 컸는데, **측정 환경이 잘못됐다는 걸 먼저 인정**하고 시드를 고쳤다.

## 5. 최적화 판단 원칙 (이 경험에서 나온 것)

| # | 원칙 | 근거가 된 사건 |
|---|---|---|
| 1 | **plan을 먼저 보고 쿼리를 고친다** | `Seq Scan × 2` → `NOT IN`이 범인이라고 특정 |
| 2 | **개별 쿼리보다 왕복 횟수를 먼저 본다** | 7회 왕복이 본질, 개별 튜닝은 부차 |
| 3 | **지표 정의를 바꿔서 연산을 없앨 수 있는지 본다** | NOT IN 차집합 → 기간 증감 비교 |
| 4 | **한 곳을 고쳐 여러 곳이 빨라지는 길을 고른다** | 마트 흡수 > 쿼리 개별 튜닝 |
| 5 | **문법을 못 바꾸면 plan을 바꾼다** | Generated Column STORED, partial index |
| 6 | **제약은 우회하지 말고 전제로 받는다** | sentinel UUID로 CONCURRENTLY 유지 |
| 7 | **개선 권고엔 비용을 같이 적는다** | INCLUDE 인덱스 REFRESH +1~2초 |
| 8 | **병목이 아닌 층을 최적화하지 않는다** | DB가 아니라 Gunicorn |
| 9 | **고쳤으면 숫자가 실제로 움직였는지로 판정한다** | CTE 통합 후에도 5.9초 → 진단 폐기 |
| 10 | **최적화를 테스트로 고정한다** | "단일 CTE 실행 횟수 검증" 케이스 |

## 면접 Q&A

| 질문 | 답변 축 |
|---|---|
| **쿼리 최적화 경험 있나** | 4개 층위로 했다 — ①7쿼리 N+1을 4-CTE 단일 쿼리로 재작성(830배) ②9-CTE·7-CTE를 마트가 흡수하게 해 쿼리 자체를 제거 ③Generated Column·partial index·sentinel로 인덱스가 걸리게 ④실측 근거로 최적화 3건을 기각 |
| **구체적으로 어떤 기법을 썼나** | CTE 1회 스캔 재사용, `DISTINCT ON`으로 그룹별 Top-1, `NOT IN` → 사전 집계 + LEFT JOIN, `NULLIF` 0분모 방어, `FILTER (WHERE)` 조건부 집계, partial index, Generated Column STORED |
| **`NOT IN`을 왜 없앴나** | EXPLAIN에서 `Seq Scan × 2`로 450K행을 두 번 풀스캔하고 있었다. 단순 치환이 아니라 **지표 정의를 집합 차집합에서 기간 증감 비교로 바꿔서** 연산 자체를 없앴다 |
| **가장 효과가 컸던 건** | 개별 쿼리 튜닝이 아니라 **마트로 흡수한 것**. 한 쿼리만 빨라지는 게 아니라 같은 마트를 쓰는 전 컴포넌트가 빨라지고, 신규 컴포넌트도 자동으로 빠르다 |
| **안 한 최적화는** | INCLUDE 인덱스(병목이 DB가 아님 + REFRESH 1~2초 추가), work_mem 증설(근본은 시드 분포), NOT IN 리팩터 별도 PR(CTE 통합으로 자동 해소). **측정 없이 좋아 보여서 하는 최적화는 거절했다** |
| **어떻게 검증했나** | EXPLAIN plan 대조 + `db.session.execute` 호출 횟수 + `NOT IN` grep 0건 + 단위 테스트에 CTE 실행 횟수 케이스 고정 |
