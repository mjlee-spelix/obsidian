# 목적별 모델 비교 테스트 설계

## 개요

목적: 의도 분류 / 도구 호출 / 코드(쿼리) 작성
모델: gpt-oss-120b, Qwen3.5-27b, gemma-4-25b, Qwen3-coder-30b

[SPX Agent 데모 가이드라인.pdf](file:///C:%5CUsers%5CAdministrator%5CDownloads%5CSPX%20Agent%20데모%20가이드라인.pdf)

## 설계 원칙

기존 매출 분석 워크플로우(MasterChatbot, SubWorkflow_NL2SQL, SubWorkflow_메일)는 그대로 두고, 목적별로 능력을 하나씩만 측정하기 위한 테스트 워크플로우를 따로 만든다.

기존 워크플로우에서는 능력이 섞여 있다. NL2SQL 에이전트는 도구 호출과 쿼리 작성을 동시에 하고, 마스터 에이전트는 의도 분류와 도구 호출을 동시에 한다. 한 능력만 정확히 비교하려면 변수를 통제해야 하므로 분리가 필요하다.

워크플로우는 3개 따로 만들되, 시나리오 내용은 통일한다. 연결해서 하나로 만들면 앞 단계 실패가 뒤 단계를 오염시킨다. 예를 들어 의도 분류를 틀리면 도구 호출도 당연히 틀리고 SQL도 엉뚱하게 나오는데, 이러면 실제로는 분류만 못하는 모델을 "전부 못한다"고 잘못 평가하게 된다. 각각 독립 실행해야 "분류는 약한데 SQL은 잘 쓴다" 같은 정확한 인사이트를 얻을 수 있다.

## 테스트 워크플로우

**1) 의도 분류** — LLM 노드만 사용 (에이전트 X, 도구 X)
시작(question) → LLM → 출력(category)
마스터 에이전트의 분류 프롬프트를 가져와서 LLM 노드에 넣는다. 도구 호출 없이 순수하게 분류만 시키고, 모델을 바꿔가며 분류 정확도를 비교한다.

**2) 도구 호출** — 에이전트 노드 + 더미 도구 2~3개
시작(question) → 에이전트 → 출력(호출된 도구명, 파라미터)
간단한 더미 도구를 등록해서(SQL 조회, 차트 생성, 메일 전송 등) 올바른 도구를 올바른 파라미터로 호출하는지만 본다. SQL 품질은 여기서 안 봄. hallucination, 병렬 호출 여부 등만 체크한다.

**3) 코드(쿼리) 작성** — LLM 노드만 사용 (도구 호출 X)
시작(question) → LLM → 출력(generated_sql)
NL2SQL 에이전트의 프롬프트를 그대로 가져오되 SQL Executor Tool 없이 SQL 텍스트만 생성하게 한다. 생성된 SQL은 직접 DB에 돌려보면서 정확성을 확인한다.

## Dify DSL 현황

`~/Projects/dify-llm-test/`에 DSL 3개를 생성해두었다. 현재 3개 모두 `agent-chat` 모드, `gpt-oss-120b`, vLLM provider로 동일하게 설정되어 있고, 프롬프트/도구/파라미터는 아직 비어있다.

| DSL 파일 | 현재 모드 | 변경할 모드 | 채워야 할 것 |
|----------|----------|-----------|-------------|
| Agent-모델비교-의도분류.yml | agent-chat | chat | 마스터 에이전트 분류 프롬프트 |
| Agent-모델비교-도구호출.yml | agent-chat | agent-chat (유지) | 더미 도구 등록, agent_mode 활성화, 도구 호출 프롬프트 |
| Agent-모델비교-SQL.yml | agent-chat | chat | NL2SQL 프롬프트 |

공통으로 설정할 것:
- `completion_params`에 temperature 지정 (의도분류/도구호출: 0.1, SQL: 0)
- 모델 교체 시 `model.name`만 변경 (gpt-oss-120b → Qwen3.5-27b 등)

## 테스트 시나리오 세트

아래 시나리오를 3개 워크플로우에 동일하게 사용한다.

- "제품 카테고리별 매출을 분석해서 marketing@company.com으로 보내줘" — 복합 의도(분석+메일), NL2SQL+메일 도구 순차 호출, GROUP BY 쿼리
- "지난 분기 국가별 매출 추이를 차트로 그려줘" — 복합 의도(분석+차트), NL2SQL+차트 도구 순차 호출, 분기 필터+국가 GROUP BY+시계열 정렬
- "올해 실적 좀 봐봐" — 애매한 의도, 도구를 바로 부르는지 vs 되묻는지, "올해"/"실적" 해석
- "2024년 총매출은?" — 단일 의도(분석), 단일 도구 호출, 단순 SUM 쿼리
- "안녕하세요" — 비업무 질문, 도구 호출하면 안 됨, 쿼리 생성 불필요

## 평가 기준

**의도 분류**
- 분류 정확도: 기대 카테고리와 일치하는지
- 애매한 입력 처리: 되묻는지 vs 임의 판단하는지

**도구 호출**
- 성공률: 올바른 도구를 올바른 파라미터로 호출했는지
- Hallucination 여부: 불필요한 상황에서 도구를 억지로 호출하지 않는지
- 파라미터 정확성: 필수 인자 누락, 타입 오류 등
- 병렬 호출 안정성: 동시에 여러 도구를 호출할 때 파라미터 섞임이나 중복 호출 없는지

**코드(쿼리) 작성**
- 실행 정확도: DB에서 실행 가능하고 결과가 맞는지
- SQL 문법 유효성: 문법 오류 없이 깨끗한 쿼리인지
- JOIN 정확성: 복수 테이블 연결 시 조건이 맞는지

## 테스트 조건

**프롬프트 통일 여부**
현재 프롬프트가 claude-sonnet에 맞춰 작성되어 있다. 이걸 그대로 다른 모델에 넣으면 그 모델에 불리할 수 있다. 프롬프트를 통일해서 공정 비교할지, 모델별로 최적화해서 최선의 성능을 비교할지 먼저 정해야 한다.

**반복 횟수**
같은 질문을 3~5회 반복해서 일관된 결과가 나오는지 확인한다. 한 번 맞추는 것보다 매번 안정적으로 맞추는 게 프로덕션에서는 더 중요하다.

**Temperature 고정**
모델 간 공정한 비교를 위해 동일한 temperature를 사용한다. 의도 분류/도구 호출은 0~0.1, 코드 생성은 0으로 설정.

**인프라 조건 통일**
같은 GPU, 같은 추론 엔진(vLLM)에서 돌려야 속도 비교가 의미 있다.

**실패 분석**
틀린 경우 원인을 기록한다. 문법 자체가 틀린 건지/결과가 틀린 건지, 도구를 안 부른 건지/파라미터가 틀린 건지, 의도를 완전히 다르게 분류한 건지/애매한 걸 다르게 해석한 건지 등. 이게 쌓여야 "이 모델은 이런 상황에 약하다"는 인사이트가 나온다.
