# 대책서 작성 — 비즈니스 로직 정리

> [!summary] 한 줄 요약
> **현상 → 원인 → 대책**을 단계적으로 작성하는 도우미. 각 추천은 **내부(사내 유사사례 RAG, 현재 더미) + 외부(LLM)** 를 섞어 만들고(기본 5/5, 합 최대 10), 항목마다 **유사도/관련도 점수(0~100)** 를 매겨 점수순으로 보여준다. 원인은 **여러 개 선택** 가능하고, 대책은 **선택된 원인마다 따로** 생성한다.

분석 소스: `com.measure` (Spring Boot). 핵심 파일 — `DocumentService`, `OpenAiClient`, `InternalKnowledgeService`, `ScoredItem`, `Suggestion`, `Dtos`.

---

## 1. 전체 흐름

```
[현상 입력] create()
   ↓
[원인 추천]  내부(더미 N) + 외부(LLM N)  → 점수순 표시, 내부/외부 구분
   ↓  (여러 사이클: "나머지 계속 찾기" → exclude 누적 후 재호출)
[원인 선택]  여러 개 선택 가능 (setCause)
   ↓
[대책 추천]  선택된 "원인마다" 따로  내부(더미 N) + 외부(LLM N)
   ↓  (원인별 "대책 더 찾기" = causeId 지정)
[대책 선택]  원인별로 선택 + 비고 (setCountermeasure)
   ↓
[작성완료]   complete() → 세션 종료(COMPLETED)
```

**현상 1 : 원인 N : 대책 N** 구조. 대책은 원인에 `parentCauseId`로 귀속된다.

## 2. 추천 1회 = 내부 + 외부 혼합

`DocumentService.suggestCauses / suggestCountermeasures` 공통 패턴:

1. **개수 보정** `resolveCounts(internalCount, externalCount)`
   - 기본 `internal=5, external=5` (`DEFAULT_INTERNAL/EXTERNAL=5`)
   - 음수 → 0, **둘 다 0이면 에러**
   - `internal>10` → 10, **`internal+external>10`이면 외부부터 축소** (`MAX_TOTAL=10`)
2. **내부(더미 RAG) 먼저** — `InternalKnowledgeService` → `source=INTERNAL`, 점수·RAG근거 채움 → 뽑은 문구를 exclude에 추가(외부가 중복 안 하도록)
3. **외부 LLM** — `OpenAiClient.suggest(..., externalN)` → `source=EXTERNAL`, 점수 채움, RAG근거 null
   - LLM이 지시 어기고 중복 줄 수 있어 **저장 단계에서도 exclude 재확인**
4. 저장 후 **점수 내림차순(동점이면 생성순)** 으로 화면 표시 (`byScoreDescThenCreated`)

`SuggestionSource` = `INTERNAL | EXTERNAL | MANUAL`(직접 입력)

## 3. 내부 지식(더미 RAG) — `InternalKnowledgeService`

> [!warning] 현재 사내 데이터 시스템 호출 불가 → **더미데이터로 동작**. 실제 연동 시 이 서비스 내부만 사내 검색/유사도 엔진으로 교체.

- **풀**: `CAUSE_POOL`(원인 20개), `COUNTERMEASURE_POOL`(대책 20개) — 유사도 높은 순으로 미리 나열
- **선택 로직** `pick()`: 풀에서 exclude에 없는 항목을 **앞에서부터 count개**
- **점수**: 풀 순서가 곧 유사도 → `score = max(40, round((96 - i*2.5)*10)/10)` (첫 항목 96, 한 칸당 2.5 감소, 하한 40)
- **RAG 근거** `buildRag()`: 출처/문서명(`SAMPLE_DOCS` 8개 중)/유사도/검색질의/원문발췌 — **전부 더미 샘플**
- API: `causes(현상, exclude, count)`, `countermeasures(현상, 원인, exclude, count)`

## 4. 외부 LLM — `OpenAiClient`

OpenAI **Responses API** (`/responses`), `store:true`, `previous_response_id`로 문서별 세션 맥락 유지.

### instructions (system) — 개수·점수 반영
**원인**
```
당신은 제조/품질 현장의 원인 분석 전문가입니다.
주어진 '현상'에 대해 서로 다른 관점의 구체적인 '원인' 후보를 정확히 N개 제시하세요.
각 항목은 한 문장으로 간결하게 작성하고, 현상과의 관련도를 0~100 점수(score)로 매기세요.
반드시 지정된 JSON 형식(items 배열, 각 원소는 text 와 score)으로만 응답하세요.
이전에 제시한 항목과 중복되지 않게 하세요.
```
**대책**: 위와 동일 패턴, "개선 대책 전문가", "'현상'과 '원인'에 대해", "원인과의 관련도를 0~100 점수".

### input (user)
- 원인: `현상: {현상}\n이 현상에 대한 원인 후보를 추천하세요.\n` (+ 제외 블록)
- 대책: `현상: {현상}\n원인: {원인}\n이 원인을 해결하기 위한 대책 후보를 추천하세요.\n` (+ 제외 블록)
- 제외 블록(재호출 시): `다음 항목은 이미 제시했으니 제외하고, 새로운 (관점의 원인 | 대책)을 제시하세요:\n- 항목...`
- ※ **개수(N)는 input이 아니라 instructions로 이동**

### 출력 스키마 (strict json_schema) — ⭐ 변경점
```json
{
  "items": [
    { "text": "문구", "score": 0~100 }
  ]
}
```
- 각 원소 = `{text:string, score:number}`, `required:[text,score]`, `additionalProperties:false`
- `minItems = maxItems = count`(요청 개수)
- 파싱: `{text,score}` 우선, 실패 시 줄 단위 fallback(점수 null), 점수는 0~100 clamp

## 5. 다중 원인 / 원인별 대책

- **원인 선택** `setCause(id, List<String> values)`: 여러 개 선택 → `1. ...\n2. ...` 번호 목록으로 원인 칸 구성, 선택 항목 `selected=true`
- **대책 추천** `suggestCountermeasures(..., causeId)`:
  - **선택된 원인들을 루프** 돌며 **원인마다 LLM 1회 호출** → 대책에 `parentCauseId` 부여
  - `causeId` 지정 시 그 원인 1개만 ("원인별 대책 더 찾기")
  - **원인별 제외 목록**(`excludeByCause`)으로 원인마다 독립 누적
- **대책 선택** `setCountermeasure(id, causeId, selectedIds, manualValues, notes)`:
  - 해당 원인 범위만 선택/비고 갱신 (다른 원인 대책 안 건드림)
  - 직접입력 → `MANUAL`로 저장
  - `buildCountermeasureText`: `[원인] … / 1. 대책 … (비고: …)` 원인별 묶음

## 6. 모델 — 최저가 기본값

- `OpenAiProperties.cheapestModel(candidates)`: 후보 중 **(입력+출력 1M 단가) 최저** 모델
- `OpenAiClient.defaultModel()`이 이를 사용 → 외부 LLM 기본값 = 최저가
- 허용 목록 `gpt-5-nano / gpt-5.5 / gpt-5.5-pro` 중 **gpt-5-nano**(0.20/출력1.25)가 최저 → 기본값
- 요청 모델이 허용목록 밖이면 기본값으로 대체(`resolveModel`)

## 7. 도메인 / DTO

**`Suggestion`**: `type`(CAUSE/COUNTERMEASURE), `source`(INTERNAL/EXTERNAL/MANUAL), `content`, `score`, `round`, `responseId`, `parentCauseId`, `ragSource`, `selected`, `note`

**주요 DTO**
- `SuggestRequest(regenerate, model, internalCount, externalCount, causeId, …)`
- `SelectRequest(List<String> values)` — 원인 확정(다중)
- `CountermeasureSelectRequest(causeId, ids, manual, notes)` — 대책 확정(원인 범위)
- `SuggestionView(id, content, source, score, round, selected, parentCauseId, note, ragSource)`
- `SuggestResponse(round, items[], internalAdded, externalAdded, model, callTokens, callCost, totalTokens, totalCost)`

**엔드포인트(논리)**
| Method | URL | 용도 |
|---|---|---|
| POST | `/api/documents` | 현상 입력(문서 생성) |
| POST | `/api/documents/{id}/cause-suggestions` | 원인 추천(내부+외부) |
| POST | `/api/documents/{id}/cause` | 원인 확정(다중) |
| POST | `/api/documents/{id}/countermeasure-suggestions` | 대책 추천(원인별) |
| POST | `/api/documents/{id}/countermeasure` | 대책 확정(원인 범위) |
| POST | `/api/documents/{id}/complete` | 작성완료(세션 종료) |
| GET | `/api/models` | 모델 목록 + 기본값(최저가) |

## 9. 확인 필요 / 한계

- ⚠️ **웹 컨트롤러 불일치**: `DocumentController`가 옛 시그니처(`suggestCauses(id, regenerate, model)` 3-arg, 옛 `SelectRequest`로 `setCountermeasure`)를 호출 → 새 서비스(5~6-arg)·새 DTO와 안 맞음. **현재 그대로면 빌드 실패 가능** → 웹 계층 마저 반영 필요.
- **내부 RAG는 더미**: 실제 사내 검색 엔진 연동 시 `InternalKnowledgeService` 내부만 교체.
- **점수**: 내부=풀 순서 기반 의사 점수, 외부=LLM 자기 평가 점수 → 둘의 척도가 완전히 동일하진 않음(혼합 정렬 시 유의).

## 10. Dify 이전 시사점

현재 Dify 워크플로우([[3. 프로젝트/서연이화/과제5/대책서 작성 도우미.yml]])는 **외부 LLM·단일 문자열·점수없음·단일 대책**이라 아래가 추가로 필요:

1. **LLM 구조화 출력 스키마**: `items:[{text,score}]`, 개수=externalCount(가변)
2. **payload 확장**: `internalCount/externalCount`, (대책) `causeId`/선택 원인 목록
3. **내부 더미 소스 노드**: 풀에서 exclude 제외 top-N + 점수 부여(코드 노드)
4. **병합·정렬 노드**: 내부+외부 합쳐 점수순 + source 태그
5. **원인별 대책 = Iteration 노드**: 선택 원인마다 LLM 호출(구조 대공사)
6. **모델 기본값 = 최저가**(nano 계열)

> 단계적 반영 권장: (가) 스키마+개수+병합정렬 → (나) 내부 더미 → (다) 원인별 대책 Iteration
