# S-CLM '대책서 생성' 탭 — 기능/프롬프트 정리

> 기준: `develop` 브랜치 (2026-07-10, `6b630cc`) · 배포본 measure.wayt.ai 와 동일
> 소스: `src/main/resources/static/index.html` (모든 행번호는 이 파일 기준)
> 백엔드: `src/main/java/com/measure/web/ReportController.java` (`/api/report/ai`)

## 1. 전체 구조 — 3단계 위저드

```
① 현상/원인 입력  →  ② 대책 검토 및 선택  →  ③ 대책서 생성
   (보완 질의 + 원인 자동 보완)   (추천 TOP10 / 상세 / 연계 대책)   (문서 조립·인쇄·다운로드, LLM 미사용)
```

상단 공통 컨트롤:
- **AI 모델 선택**: `gpt-5.5` / `claude-opus-4-8` / `claude-sonnet-5` (`CM_AI_MODEL`, 7344행)
- **상세 조회 방식**(`CM_DETAIL_MODE`, 7413행): `batch`(한꺼번에) / `rec`(대책 선택 시) / `action`(액션 선택 시)
- **누적 비용 표시**: 1단계 등록 시 `cmResetCost()` 후 응답마다 합산
- 파일저장 / 불러오기 / 임시저장

## 2. 공통 AI 인프라

- 프록시 엔드포인트: `/api/report/ai` (`CM_AI_PROXY_URL`, 7343행). 요청 바디 `{prompt, provider, model, sessionId, reset}` (`cmReqBody`, 7453행)
- **세션 묶음**: 1단계 "등록" 시 `cmNewSession()`(7446행)으로 sessionId 생성, 첫 요청에 `reset=true`.
  백엔드는 OpenAI=`previous_response_id`, Claude=messages 히스토리로 같은 대화 문맥 유지.
  → measure 원칙(문서 1건 = 세션 1개) 계승. 이후 2단계의 모든 호출이 같은 세션에서 문맥을 이어받음.
- **호출 직렬화**(`_cmAiQueue`, 7462행): 지연 모드에서 상세/가이드 동시 조회 시 대화 체인 꼬임 방지
- 타임아웃 120초. JSON 파싱은 코드펜스 제거 후 첫 `{` ~ 마지막 `}` 추출(`cmParseJson`)

## 3. 1단계 — 현상/원인 입력

입력 필드: **현상(필수)** / **직접원인(필수)** / **간접원인(선택, AI 자동 보완)** — 각 500자.

### 3-1. 보완 질문 생성 — `c3BuildQuestionsPrompt` (5783행)

"등록" 클릭(`c3RegisterInputAI`, 5792행) → 비용 리셋 + 새 세션 → LLM 1회 호출.

```
당신은 자동차 부품 품질엔지니어입니다. 아래 현상/직접원인을 바탕으로 원인을 구체화하기 위한 보완 질문 4개를 만들어 주세요.
각 질문을 직접원인(direct) 또는 간접원인(indirect) 으로 분류하고, 예시 답변(sample)과 그 답변으로 보완될 원인 문구(add)를 함께 제시하세요.

[현상]
{현상}

[직접원인]
{직접원인}

[출력 형식] 아래 JSON만 출력. 마크다운/설명 금지.
{"questions":[{"q":"질문(번호 포함)","hint":"(예시 힌트)","type":"direct 또는 indirect","sample":"예시 답변","add":"보완 원인 문구"}]}
- 4개, 앞 2개 direct, 뒤 2개 indirect 권장.
```

- 질문 카드마다 "직접원인으로 분류 / 간접원인으로 분류" 태그 + 답변 입력란 렌더(`c3RenderQ`)
- **미입력 답변은 `sample`(예시 답변)로 자동 대체**(`c3AnswerQ`)
- `add` 필드는 생성되지만 현재는 미사용(아래 3-2의 2차 호출로 대체된 예비 필드)

### 3-2. 직접/간접 원인 정리 — `c3BuildCauseItemsPrompt` (6375행)

"응답 등록"(`c3AnswerAll`, 6395행) → 질문+답변 전체를 모아 LLM 2차 호출.

```
당신은 자동차 부품(인테리어/플라스틱) 품질엔지니어입니다.
아래 [현상]과 각 보완 질문/답변을 바탕으로, 질문 "건별로" 원인 문구를 1개씩 작성하세요.
- 각 항목은 그 질문의 답변 의미를 반영한 간결한 한 문장(원인 진술).
- type 은 입력 분류(direct=직접원인 / indirect=간접원인)를 그대로 유지.
- 답변에 근거 없는 내용을 지어내지 말 것. 기존 원인과 중복 표현은 피하되 항목은 질문 수만큼 유지.
- items 의 순서·개수는 입력 질문과 동일하게(질문 N개 → items N개).

[현상]
{현상}

[기존 직접원인(참고)]
{직접원인}

[기존 간접원인(참고)]
{간접원인}

[보완 질문/답변]
1. [direct] 질문: ...
   답변: ... (무응답 시 "(무응답)")

[출력 형식] 아래 JSON만 출력. 마크다운/설명 금지.
{"items":[{"type":"direct 또는 indirect","text":"원인 한 문장"}]}
```

- 반환 items를 유형별로 **직접/간접원인 텍스트영역에 `•` 불릿으로 append**(기존 내용 보존, 플래시 하이라이트)
- 이력: 처음엔 원인 전체 재작성 방식(`cccb15b`, "옵션 A") → 당일 **건별 append 방식**(`cd02c4f`)으로 변경
- 미응답 상태로 "다음 단계" 시 확인 모달(`c3NextFromS2`) 경유

## 4. 2단계 — 대책 검토 및 선택

진입 시 **자동 생성**(`c3AutoGenDone` 플래그) · 모델 변경 후 재진입하면 재생성(`c3GenModel` 비교).
컨텍스트(`c3CtxBlock`, 5846행): 제품 기준정보(품번/품명/END·SUB PART/생산처/소재업체/GRADE/금형/사양) + 현상 + 직접원인 + 간접원인.

### 4-1. 추천 대책 TOP10 — 배치 모드 `c3BuildRecPrompt` (5853행)

목록 + 모든 상세 + 가이드를 **단일 호출**로 생성:

```
당신은 자동차 부품(인테리어/플라스틱) 품질엔지니어입니다.
아래 [제품 기준정보] [현상] [직접원인] [간접원인] 을 종합하여 개선 대책을 정확도(관련도 0~100) 내림차순으로 정확히 10개 제안하세요.

{컨텍스트 블록}

[출력 형식] 아래 JSON만 출력. 마크다운/주석/설명 텍스트 절대 금지.
{"measures":[{"tag":"llm 또는 rag","acc":96,"link":"짧은 대책 라벨(20자 이내)","title":"대책 내용 한 문장",
  "doList":["실행 내용"],"effect":["예상 효과"],
  "plan":{"s1":["1단계 임시조치 항목"],"s2":["2단계 개선대책 항목"],"s3":["3단계 유효성 항목"]},
  "guide":{"purpose":"목적 1~2문장","steps":["실행 절차(따라하기)"],"checks":["점검 포인트"],"cautions":["주의 사항"]}}]}
- measures 는 반드시 10개(정확도 0~100 내림차순). doList 2~4개, effect 1~2개, plan 각 단계 2~3개, steps 3~5개, checks 2~4개, cautions 2~3개.
- s1=당일~1주(즉시 차단/안정화), s2=1주~1개월(원인 개선), s3=1~3개월(재발방지/표준화). 구체적·실행 가능하게.
```

### 4-2. 지연 모드 (rec / action) — 3개 프롬프트로 분해

같은 세션이므로 이전 문맥(현상/원인/이전 응답)을 이어받는다.

| 시점 | 함수 (행) | 내용 |
|---|---|---|
| 진입 시 | `c3BuildRecListPrompt` (5866) | 목록만 — tag/acc/link/title 정확히 10개, acc 내림차순 |
| 대책 선택 시 | `c3BuildMeasureDetailPrompt` (5876) | 선택 1건의 doList/effect/plan (+ rec 모드면 guide 포함) |
| 액션 항목 클릭 시 (action 모드) | `c3BuildActionGuidePrompt` (5890) | 해당 단계 항목 1건의 guide(purpose/steps/checks/cautions)만 |

모드 전환 시(`cmSetDetailMode`, 7414행): batch로 바꾸면 전체 재생성, 지연으로 바꾸면 로드된 상세를 비워 "선택 시 조회"가 실동작.

### 4-3. 3열 화면 구성

1. **추천 대책 TOP10** — 체크 선택. `tag`는 llm/rag 구분 배지(현재 전부 llm — **rag는 추후 RAG 도입용 예약**)
2. **선택 대책 상세** — 실행 내용(doList) / 예상 효과(effect) / 단계별 계획(plan)
3. **연계 대책** — **별도 LLM 호출 없음.** 선택한 대책들의 `plan`(s1 임시조치 / s2 개선대책 / s3 유효성)을
   단계별 아코디언으로 자동 구성. 항목별 라디오(선택/효과없음/미선택), 결과 등록 완료 시 체크 표시,
   상단 요약 "임시조치 N건 · 개선대책 N건 · 유효성 N건"(`c3LinkSummary`)
- 결과 등록 드로어(`c3OpenResult`): 결과 입력 + '이력' 테이블(기존 더미 유지, `7dce9ad`)

## 5. 3단계 — 대책서 생성

**LLM 호출 없음.** 1·2단계 상태로 A4 가로 문서 HTML 조립(`c3BuildDocPages` → `c3RenderDoc`, 6291행).
- 인쇄: 팝업 + `window.print()` (`c3PrintDoc`)
- 다운로드: 완결형 HTML Blob (`c3DownloadDoc`)

## 6. 요구기능 1~3 대응표

| 요구 기능 | 상태 | 구현 |
|---|---|---|
| 1) 현상/직접원인 → AI 보완 질의 생성 | ✅ 배포됨 | `c3BuildQuestionsPrompt` — 4문항, direct/indirect 분류 + 예시답변 |
| 2) 답변 → 직접/간접 원인 정리 | ✅ 배포됨 | `c3BuildCauseItemsPrompt` — 질문 건별 원인 1문장, 유형 유지, 불릿 append |
| 3) TOP10 + 상세 + 연계 한 번에 | ✅ 배포됨 (batch) | `c3BuildRecPrompt` 단일 호출. 연계 대책은 plan에서 파생(비-LLM). RAG는 `tag:"rag"` 예약 |

## 7. Agent Designer(LangGraph) 이식 시 매핑 메모

현재 로직은 브라우저 JS + `/api/report/ai` 프록시 구현. 플로우로 옮길 때:

- 프롬프트 5종을 `ai.llm_prompt_normalizer`/`llm.chat` 노드 파라미터로 이전 (문구 그대로 사용 가능)
- 세션(sessionId + reset) → LangGraph **thread(checkpoint)** 로 대체
- 보완 질의 → 답변 대기 → 원인 정리 구간은 `human.input`(HITL interrupt/resume)으로 자연 표현 가능
- batch/지연 모드 → `router.branch` 분기 또는 별도 플로우 2종
- `tag:"rag"` 확장 → `retrieval.search`(과거 대책서 인덱스) 노드 삽입 + 컨텍스트 주입 ("5-1 과거 대책서 수집·저장" 템플릿이 색인 파이프라인)

## 8. Agent Designer 노드 구성 설계

> 근거 스펙(agent-designer main 브랜치 `flow_compiler/nodes.py`):
> `llm.chat`은 `systemPrompt`/`responseFormat:"json_object"` 지원, **state.messages 가 노드 간 누적**(대화 히스토리).
> `human.input`은 `interrupt()`로 중단 → `awaiting_input` 이벤트 → resume 값이 HumanMessage로 히스토리에 추가.
> → 웹의 sessionId 세션을 "플로우 1회 실행 = 세션 1개"로 재현 가능.

### Flow A — 현상/원인 보완 (기능 1+2 통합, HITL) ★권장

```
core.start
  → data.input          (runInput: {phenomenon, directCause, indirectCause?})
  → ai.llm_prompt_normalizer   [c3BuildQuestionsPrompt 본문, outputFormat: questions 스키마]
  → llm.chat ①          (질문 4개 생성 — responseFormat json_object, temperature 0.4)
  → human.input          (답변 입력 — {"answers":[{"no":1,"answer":"..."}]}, 미입력=sample 적용은 클라이언트가 resume 전에 채움)
  → ai.prompt_builder    [c3BuildCauseItemsPrompt 규칙부만 — 현상/질문/답변은 메시지 히스토리로 전달됨]
  → llm.chat ②          (건별 원인 문구 — items 스키마)
  → core.end             (outputs: causeItems)
```

분리형 대안(measure UI가 답변 UI 소유 시): A1(질문 생성)/A2(원인 정리) 두 플로우.
플로우 실행 간 메모리가 없으므로 A2는 runInput으로 `{phenomenon, directCause, indirectCause, qaPairs[]}` 전부 수령
→ normalizer가 웹의 `c3BuildCauseItemsPrompt` 원형(컨텍스트 블록 포함)을 그대로 구성.

### Flow B — 추천 대책 TOP10 batch (기능 3)

```
core.start
  → data.input     (runInput: {prodInfo, phenomenon, directCause, indirectCause})
  → ai.llm_prompt_normalizer   [c3BuildRecPrompt — 정확히 10개, measures 스키마]
  → llm.chat       (json_object — TOP10+doList+effect+plan+guide 단일 호출)
  → code.sandboxed [연계 대책 파생 — plan.s1/s2/s3 → 단계별 항목 + 임시조치/개선대책/유효성 카운트. 비LLM(웹과 동일)]
  → core.end       (outputs: measures, linkSummary)
```

지연 모드(rec/action)는 소형 플로우 3개로 분리: 목록만(`c3BuildRecListPrompt`) / 상세 1건(`c3BuildMeasureDetailPrompt`, runInput에 선택 대책 {link,title} 추가) / 가이드 1건(`c3BuildActionGuidePrompt`).

### Flow B′ — RAG 도입 시 확장형 (프롬프트 스키마 변경 없음)

```
data.input ─┬→ retrieval.search(indexName:"clm_countermeasures", topK:8)
            │     → normalizer[내부: RAG 근거, tag:"rag", ragSource] → llm.chat(INTERNAL)
            └→ normalizer[외부: 순수 LLM, tag:"llm"]                → llm.chat(EXTERNAL)
  → ai.suggestion_merge_rank(candidatePaths:[내부,외부], dedupe:true, topK:10)   ← TOP10 확정
  → llm.chat(확정 10건 상세 채우기) → code.sandboxed(연계 파생) → core.end
```

기존 "5-2 최적 대책서 추천" 템플릿(agent-designer templates.ts 847행~)이 동일 이원화 패턴 — 복사·개조.
인덱스는 "5-1 과거 대책서 수집·저장" 템플릿이 생성. `tag:"llm|rag"` 필드가 그대로 살아 UI 무변경.

### 실무 체크포인트

1. **모델/키**: `gpt-5.5`/`claude-opus-4-8`/`claude-sonnet-5`를 llm.chat `model`에 지정, API 키는 designer secrets(AES-GCM)로 이전. 모델 선택은 runInput 바인딩 또는 모델별 published version으로.
2. **JSON 안정성**: 웹의 코드펜스 제거+`{…}` 추출 방어 대신 `responseFormat:"json_object"`로 원천 보장.
3. **호출 전환**: measure UI의 `/api/report/ai` → designer-api run 시작 + SSE 스트림. HITL은 `awaiting_input` 이벤트 수신 → 답변 폼 → resume.
4. **등록**: 캔버스 직접 조립 또는 templates.ts에 템플릿 추가 → publish(버전 고정·감사 가능) 후 measure가 호출.
