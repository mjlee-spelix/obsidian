# 과제5(구 과제6) 표준품명 — 비즈니스 로직 정리

> [!important] 한 줄 요약
> 노트 [[3. 프로젝트/서연이화/과제5/무제.md]]의 7단계는 **자동차 도어트림(DR TRIM) 부품의 "표준 대표품명"을 규칙기반으로 만들고, 엑셀 원본 분류가 맞는지 검증하는** 기능이다.
> **OpenAI/LLM을 전혀 쓰지 않는다 (100% 규칙기반).** → Dify에서도 LLM 없이 **코드 노드 + 사전 데이터**로 그대로 재현 가능하다.

분석 대상 사이트: `http://measure.wayt.ai` (로그인: `/api/login`, 비번 `spelix1@`)
GNB가 두 개로 나뉜다 — 이 과제는 **표준품명 관리(`/standard.html`)** 쪽이다.

| 메뉴 | URL | 성격 |
|------|-----|------|
| 대책서 작성 | `/` | OpenAI(ChatGPT) 기반 — **이 과제 아님** |
| 표준품명 관리 | `/standard.html` | **규칙기반 — 이 과제 (7단계)** |

## 1. "엑셀"이 뭔가?

서연이화가 준 **DR TRIM 부품 마스터 시트**다. 구조가 핵심:

- **엑셀 행 1개 = 품목 그룹 1개** (예: "트림패널" 한 줄)
- 그 행의 한 셀 안에 **세미콜론으로 묶인 여러 "변형 표기(variant)"** 가 들어있음
  - 예) 트림패널 행 안에 `PNL ASSY-FR DR TRIM UPR,L/RH` / `PNL-FR DR MAIN TRIM,LH/RH` … 등 여러 실제 표기
- 전체 규모: **품목 그룹 약 80여 개, 변형 표기 총 580개**

### 엑셀(=품목 그룹) 컬럼 의미

| 컬럼(필드) | 의미 | 예시 |
|---|---|---|
| excelRow | 엑셀 행 번호 | 2, 6, 59 |
| itemKo | 대분류(한글) | 트림패널, 기타 |
| itemEnHead | 대분류 영문(head) | PNL |
| itemEnMid | 중분류 영문(mid) | TRIM |
| sideCode | 면 | FR / RR |
| positionCode | 세부위치 | UPR / CTR / MAIN / LWR (없을 수 있음) |
| handleCode | 기타구분 | LH_RH → LH/RH |
| proposedName | 엑셀의 기존 "대표품명(제안)" | (없으면 미인식) |
| standardName | **새 시스템이 생성한 표준명** | PNL-FR DR TRIM UPR, LH/RH |
| variantCount / reclassifiedCount / unknownCount | 변형 수 / 재분류 수 / 미인식 수 | — |

### 변형(variant) 컬럼

| 컬럼 | 의미 | 예시 |
|---|---|---|
| rawName | 엑셀 원본 변형 표기 | `PNL ASSY-FR DR TRIM UPR,L/RH` |
| projectCodes | 적용 차종 | DL3a, MX5a PE |
| contentItemKo | **내용으로 다시 판정한 대분류** | 무드/조명, 베젤 … |
| standardName | 그 변형의 내용기반 표준명 | LAMP-FR DR MOOD, LH/RH |
| status | 정상 / 재분류 / 미인식 | — |

## 2. 핵심 로직 3가지

### (A) 표준명 생성 규칙 — "세그먼트 조합"

정해진 **형식(순서)** 대로 영문 구성요소를 이어 붙인다. 기본 순서:

```
대분류(head) → -면 → 부위(DR) → 중분류(mid) → 세부위치 → , 기타구분
PNL        + -FR + " DR"   + " TRIM"     + " UPR"   + ", LH/RH"
= PNL-FR DR TRIM UPR, LH/RH
```

규칙:
- 각 세그먼트는 `구분자(prefix) / 접미사(suffix) / 사용여부(enabled)` 를 가짐
- **prefix는 앞 세그먼트와 이을 때만 붙음** (첫 세그먼트는 무시)
- **값이 빈 세그먼트는 자동 생략** (예: 중분류 없는 암레스트 → `ARMREST-FR DR LWR, LH/RH`)
- 영문 변환값은 전부 **표준어 사전**에서 가져옴

### (B) 변형분석 상태 판정 — 정상 / 재분류 / 미인식

엑셀이 묶어둔 분류가 맞는지 **내용 기반 판정과 비교**해서 결정:

| 상태 | 판정 기준 | 예시 |
|---|---|---|
| **정상** | 엑셀 행 대분류 == 내용 판정 대분류 | 트림패널 셀의 PNL 표기 → 내용도 트림패널 |
| **재분류** | 엑셀 행 대분류 ≠ 내용 판정 대분류 | "트림패널" 셀에 섞인 `LAMP ASSY...` → 실제론 램프, `PULL HDL...` → 핸들 |
| **미인식** | 엑셀이 "기타"이고 내용으로도 대분류 못 잡음(proposedName 없음) | `PCB HOUSING-FR DR`, `SHRINKABLE TUBE` |

> 노트 5단계 "어떤 로직이 잘못됐는지 판단" = **엑셀이 한 행에 잘못 묶어둔 변형(재분류)이나 분류 불가(미인식)를 가려내는 작업.** 비교 포인트는 `rawName`(엑셀 원본) + `proposedName`(엑셀 기존) vs `standardName`(새 표준명) + `status`.

집계: 전체 580개 중 **정상 470 / 재분류 99 / 미인식 11 / 제안없음 40**

### (C) 표준화 매칭 3단계 (노트 6~7단계, "표준화 테스트")

비표준 부품명 1건을 넣으면 아래 순서로 매칭:

1. **EXACT** (정확 일치)
2. **NORMALIZED** (정규화 후 일치)
3. **CONTENT/INFERRED** (내용 기반 추론) ← 실제 대부분 여기로 떨어짐
4. 실패 시 **NONE**

CONTENT 추론 동작:
1. 입력의 약어/별칭으로 대분류 인식 (사전 `aliases` 매칭)
2. 면(FR/RR)·세부위치·기타구분 토큰 추출
3. 형식 순서대로 사전값으로 치환·결합
4. 표준명 출력 + `explanation[]`(로직 분석 단계 설명)

- 입력 끝 `[BC3 5DR]` 같은 대괄호는 **프로젝트명으로 분리**되어 표준명에서 제외
- **대분류·면을 못 잡으면 실패(NONE)** — 예: `CURTAIN`(면 없음), `ZZZZ UNKNOWN`(대분류 없음)

## 3. 표준어 사전 (규칙의 핵심 데이터)

| 사전 타입 | 역할 | 핵심 필드 |
|---|---|---|
| ITEM (대분류, 24개) | 대분류 인식 + head 영문 | nameKo, nameEn(head), nameEnSub(mid 기본), aliases, matchPriority |
| SUBCAT (중분류) | mid 결정 | itemCode별 nameEn(mid), aliases, matchPriority |
| SIDE | 면 | FR / RR |
| POSITION | 세부위치 | UPR / CTR / MAIN / LWR |
| HANDLE | 기타구분 | LH_RH→LH/RH 등 |
| AREA | 부위 | DR (도어) |

- **aliases(별칭)** 에 오타 변형까지 등록됨 (예: PW스위치 별칭에 `POWER WIDOW`, `P/W S/W` 등)
- 한 표기에 여러 대분류가 걸리면 **matchPriority 높은 쪽** 채택
- 사전은 **입력 인식(별칭)** + **출력 영문 치환** 양쪽에 쓰임

---

## 4. "OpenAI로 뭘 해야 하나?" → 이 과제는 **불필요**

- 표준품명 관리 기능(7단계)은 코드에 `openai/gpt/llm` 문자열이 **0건**, 전부 규칙기반 API.
- OpenAI를 쓰는 건 **별도 페이지 "대책서 작성(`/`)"** 이다 (현상→원인→대책 추천, gpt-5-nano 등). 그건 이 과제가 아님.
- 따라서 **Dify에서도 LLM 노드 없이 코드 노드로 충분**하다.
  - (선택) 향후 신규 raw 표기를 별칭 사전에 자동 등록하는 보조 용도로만 LLM 검토 가치 있음.

## 5. Dify 구현 설계

**런타임 입력**: 비표준 부품명 raw 문자열 1건 (예: `PNL-FR DR UPR,LH/RH [BC3 5DR]`)

**규칙 데이터(사전 — 아래 GET API로 export해서 Dify에 적재)**

| 데이터 | 가져오는 API |
|---|---|
| ITEM 사전 | GET `/api/dictionary?type=ITEM` |
| 중분류 | GET `/api/subcategories?itemCode=*` |
| SIDE/POSITION/HANDLE/AREA | GET `/api/dictionary?type=SIDE` 등 |
| 형식(세그먼트 순서) | GET `/api/format` |
| 전체 변형 검증셋(580) | GET `/api/standardize/analyze` |

**변환 파이프라인(코드 노드)**
1. 입력에서 `[...]` 프로젝트명 분리
2. 대분류 인식: ITEM.aliases 부분일치, 충돌 시 matchPriority
3. 면/세부위치/기타구분 토큰 추출
4. 대분류·면 미인식 → 실패(NONE) 반환
5. 중분류 = 해당 대분류 SUBCAT 별칭 매칭 or 우선순위 첫 값(없으면 ITEM.nameEnSub)
6. 형식 순서대로 영문 치환 + prefix 결합, 빈 세그먼트 생략

**출력**: `{ matched, method, standardName, itemKo, sideCode, positionCode, handleCode, projectName, explanation[] }`

**이관 검증 기준**: 580개 변형 전체에 규칙 적용 → 엑셀 행 대분류 vs 내용 판정 대분류 비교 → **정상 470 / 재분류 99 / 미인식 11 / 제안없음 40** 을 재현하면 성공.
