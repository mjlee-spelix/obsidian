## 1. 🔴 설계 차단 모호점 (사용자가 든 예시 포함)

### Q1. 외부(LLM) 점수는 어떤 식으로 계산? ⭐사용자 예시
- **설계서 근거**: 슬라이드5/6 A5 "외부 LLM 답변과 내부 RAG 결과를 **점수순**으로 통합·정렬". → 외부에도 점수가 있다는 전제인데, **그 점수의 출처를 정의 안 함**.
- **현 구현(measure)**: LLM 자기평가 0~100 (`{text, score}` 스키마, LLM이 스스로 매김).
- **기존 결정**: B1에서 **내부 = 검색 유사도×100(grounded)** 으로 고정, 외부는 "LLM 자기평가 폐기 검토" 상태 → **외부 점수 출처 미정**.
- **풀어야 할 것**: 외부 점수를 (a) LLM 자기평가 유지 (b) 폐기하고 null (c) Rerank 모델로 재점수 중 택1. → Dify에서 **LLM 출력 스키마(score 포함 여부)** 와 **Rerank 노드 유무**가 여기서 갈림.

### Q2. 내부/외부 점수 통합 정렬은 어떤 기준? ⭐사용자 예시
- **설계서 근거**: 동일 A5 "점수순 통합·정렬". **두 척도(내부 cosine 기반 vs 외부 LLM 자기평가)를 어떻게 한 줄로 섞는지** 미정의.
- **기존 결정**: B1 "두 척도 통일 미정" — 외부 독식 경향(외부 임의 90 > 내부 진짜 60) 우려 명시.
- **풀어야 할 것**: 통일 방식 — (가) 외부 null + 내부만 정렬, (나) min-max 정규화, (다) Rerank 단일 척도. → **병합·정렬 코드 노드의 로직**이 통째로 여기 종속. **Q1과 한 세트로 결정해야 함.**

### Q3. 모델은 사용자가 선택한 모델이어야 하나? ⭐사용자 예시 — ⚠️설계서 vs Dify 충돌
- **설계서 근거**: 슬라이드5 입력 예시 "**모델 : gpt-5-nano·5.5·5.5-pro 선택**", R1 "모델 선택 가능". → **사용자 런타임 모델 선택을 명시적으로 그림**.
- **충돌**: Dify 표준 LLM 노드는 **모델이 design-time(노드 설정) 고정** → `payload.model` 런타임 주입 **불가**(기존 A6 정정). 과제정의서 02 협의사항엔 모델 선택 항목 자체가 **없음**(설계서에만 등장).
- **풀어야 할 것**:
  - (1) 사용자 모델 선택이 **진짜 요구**인가, 아니면 슬라이드 작성 시 measure 화면을 그대로 옮긴 것인가? → 서연이화/지산 확인.
  - (2) 요구라면 Dify 구현은 (a) 멀티 LLM 노드 + IF/ELSE 라우팅 (b) HTTP Request 노드로 OpenAI 직접 호출(measure 방식, model을 payload 주입) 중 택1 → **노드 구조가 근본적으로 달라짐**.

### Q4. ChatGPT 세션 관리를 Dify에서 해야 하나? ⭐사용자 예시 — ⚠️A1 충돌 소지
- **설계서 근거**: 슬라이드5 A4/A6 "Responses API·**문서별 세션 컨텍스트(prev_response_id→response_id) 유지·중계**", "세션 체이닝 1~3회 반복", R3 "작성완료 시 ChatGPT **세션 종료**".
- **충돌**: 기존 A1 = **Dify는 stateless workflow, 상태는 백엔드 DB**. 그런데 `prev_response_id`는 **호출 간 보존이 필요한 상태** → 누가 들고 있나?
- **풀어야 할 것**: `previous_response_id` 보관·전달 주체 = (a) 백엔드가 DB에 저장하고 매 호출 payload로 주입(A1 일관) (b) Dify가 대화 세션(chatflow) 모드로 직접 관리(A1 뒤집힘). → **워크플로우 vs 챗플로우 모드 선택**, **payload에 responseId 필드 추가 여부**가 갈림. **A1을 깨지 않으려면 (a)** 가 맞는데, 설계서 문구가 "AI 플랫폼이 유지·중계"로 읽혀 확인 필요.

### Q5. 내부 RAG 결합 자체가 확정 요구인가? — ⚠️협의11 미확정
- **설계서 근거**: 슬라이드1·2·5 전부 "외부 LLM 생성 + 내부 RAG 검색 **결합**"을 전제. 그러나…
- **협의사항 02-11(서연이화, 확인 필요)**: "외부망 상용 LLM을 활용하는데 **내부 과거 개선 대책서를 활용하는지에 대한 확인 필요**" → **결합 여부가 공식 미확정**.
- **풀어야 할 것**: 내부 RAG가 (a) 필수 결합 (b) 선택(외부만으로도 가능) 인지. → A9(external_count=0 분기)와 반대로 **internal=0 단축** 분기 필요 여부, **지식검색 노드를 메인 경로에 둘지** 결정. 미확정이면 **노드를 옵셔널 분기로** 설계해야 안전.

## 2. 🟡 설계 영향 모호점

### Q6. 협의10 "내부 대책서 검색"(코난)과 5-2 내부 RAG의 관계
- **협의10**: "상용 LLM 원인이나 대책 답변에 **기존 관련 대책서를 검색하여 제시**" — 담당 **코난**.
- **모호**: 이게 5-2 본문의 내부 RAG(유사사례 검색)와 **같은 기능인지, 별도(LLM 답변 사후 근거 첨부)인지** 불명. 같으면 노드 1벌, 별개면 **LLM 후처리 검색 노드**가 추가.

### Q7. 점검항목(점검시트) 생성 방식
- **과제개요/협의6**: 최종 산출 = "현상-원인-대책 초안 **+ 필수 점검항목(점검시트) 가이드**", AI는 방향 제시·사람이 완성(HITL).
- **모호**: 흐름도 슬라이드5/6 어디에도 **점검항목 생성 노드가 없음**(대책 그룹 생성까지만). 점검항목을 (a) 대책 LLM 출력에 포함 (b) 별도 LLM 노드 (c) 양식 템플릿 고정값 인지 미정. → **출력 스키마·노드 1개 추가** 여부.

### Q8. 원인 추천 단계에도 내부+외부·점수가 적용되나
- **모호**: 설계서는 "현상→**원인 추천**→원인별 대책"이라 하지만, 흐름 상세(A3~A5)는 **대책 생성 중심**으로만 서술. measure는 원인도 내부+외부 혼합·점수·exclude 누적 동일 적용.
- **풀어야 할 것**: 원인 추천도 대책과 **동일 파이프라인(내부+외부+점수+재검색)** 인지 → A5(단일 워크플로우 step 분기)에서 cause/countermeasure가 **대칭이라는 전제** 검증 필요.

### Q9. 원인 공란 분기 "유사 현상 기반"의 수단
- **협의7(확정)**: 원인 공란 → "유사 현상 기반 원인+대책 제시" / 기입 → "현상·원인 기반 대책 제시".
- **모호**: 공란일 때 "**유사 현상 기반**"이 (a) 내부 RAG 검색으로 유사 현상 찾기 (b) LLM에 현상만 주고 원인 추론 인지. → 분기 노드 **이후 경로(지식검색 호출 vs LLM only)** 가 갈림.

### Q10. 확정 대책서 증분 색인 트리거·주체
- **설계서 근거**: 슬라이드5/6 A7 "사용자 확정 대책서를 **증분 색인**하여 검색 DB 재활용".
- **모호**: 색인을 (a) Dify 워크플로우가 (b) 백엔드가 (c) 5-1 색인 파이프라인 재사용 인지, 트리거 시점(작성완료 시?)이 불명. → **별도 워크플로우/엔드포인트** 필요 여부.

### Q11. 보고서 양식(현상-원인-대책 템플릿)
- **협의5(서연이화, 확인 필요)**: 대책서 보고서 양식 미확정.
- **영향**: 양식이 정해져야 **출력 포맷팅 노드(`buildCountermeasureText` 상당)** 의 최종 구조 확정. 지금은 measure의 `[원인]…/1. 대책…(비고)` 묶음 가정.

### Q12. 개수 정책(기본 5/5, 합 최대 10)이 공식 요구인가
- **출처 차이**: "합 최대 10"은 슬라이드6 A5에 등장 → 확정. 그러나 **기본 5/5, internalCount/externalCount 가변**은 measure 구현 가정이지 과제정의서에 없음.
- **풀어야 할 것**: 사용자가 내부/외부 개수를 **조절하는 UI가 요구**인지, 아니면 고정 분배인지 → payload(`internalCount/externalCount`) 노출 여부(A2와 연계).

## 3. 🟢 이미 확정 (Dify 설계에 반영만)

- **Q13(부분)**: OCR 추출 항목 = 발생형태·귀책사유·발생장소·중요도·발생년도·대책방안(6항목)으로 **슬라이드에 기술**되나, 데이터구축 03 메모 "품질문제 마스터 DB에서 제공하지 않는 항목인지 확인 필요" + 협의1·2·4 "확인 필요" → **5-1 영역이라 5-2 노드 설계엔 비차단**이나, 검색 DB 메타데이터 키가 여기서 확정돼야 RAG 필터(C1) 설계 가능.
- **Q14**: 첨부 이미지 → **분석에 미사용, 보고서 원인란에만 삽입**(협의8 확정). ⇒ **Dify 입력에 멀티모달 이미지 노드 불필요.**
- **Q15**: 원인 공란/기입 분기 자체는 확정(협의7). ⇒ Dify에 **IF/ELSE 분기 노드 필요**(수단은 Q9).
- 모델 후보 목록 `gpt-5-nano / 5.5 / 5.5-pro`, 세션 체이닝 1~3회, 합 최대 10 → 설계서에 명시.

## 4. 결론 — 노드 설계 착수 전 먼저 확정할 5개

1. **Q3 모델 사용자 선택 여부** → 워크플로우 vs HTTP 직접호출 구조 결정.
2. **Q4 세션(prev_response_id) 보관 주체** → workflow/chatflow 모드 + payload 필드.
3. **Q5 내부 RAG 결합 필수 여부** → 지식검색 노드를 메인 경로 vs 옵셔널 분기.
4. **Q1+Q2 외부 점수 출처 & 통합 정렬** → LLM 스키마(score 유무) + Rerank 노드 + 병합 로직.
5. **Q7 점검항목 생성 노드** → 출력 스키마/노드 추가.

> Q3·Q4·Q5는 **고객(서연이화/지산) 확인**이 필요(요구 정의 충돌). Q1·Q2·Q7은 **개발 내부 결정** 가능하나 점수 정책은 코난 프롬프트와 맞물림.

## 5. 사용자 정리(2026-06-29) 반영 — 조정·신규

> [!info] "설계서 우선" 규칙 적용
> 설계서(PPTX)가 과제정의서보다 최신 → **둘이 다르면 설계서를 따른다.** 이 규칙으로 차단급 모호점 일부가 "요구 확정"으로 정리됨.

### 규칙 적용으로 정리된 것
- **Q3 모델 선택**: 정의서엔 없으나 설계서 슬라이드5가 "모델 선택" 명시 → **사용자 모델 선택은 요구로 확정.** 남는 질문은 "요구냐"가 아니라 **Dify 런타임 구현**(멀티 LLM 노드 + IF/ELSE 라우팅 / HTTP Request 직접호출) 택1.
- **Q5 내부 RAG 결합**: 협의11 "확인 필요"보다 설계서가 최신·결합 전제 → **결합은 요구로 확정.** 남는 건 더미→실제 RAG 구축 타이밍(차단 아님).
- **Q9 원인 공란 액션 (★사용자 2번)**: 전달받은 **HTML(현 동작)=원인 공란이면 대책 추천 불가** ↔ **설계서=공란이어도 "유사 현상 기반 원인+대책 제시"**. 설계서 우선 → **현 HTML 동작을 변경**해 공란일 때도 원인 추천→대책 추천을 진행해야 함. 단 설계서가 "유사 현상 기반"의 **구체 액션(RAG로 유사현상 검색→원인 도출 후 대책 / LLM이 현상만으로 원인+대책 일괄)을 안 적음** → 차단급 모호점으로 승격.

### 신규 (사용자 정리 6·7)

#### Q16. 세션 체이닝 1~3회 제한을 Dify에서 강제하나
- **설계서 근거**: 슬라이드5 A4 "prev_response_id 세션 체이닝으로 **1~3회 반복** 호출".
- **모호**: 이 "1~3회" 반복 제한·종료 조건을 (a) Dify 워크플로우 내부 루프/카운터로 강제 (b) 백엔드가 호출 횟수를 통제하고 Dify는 1회 호출만 담당 인지. → Dify에 **반복(loop) 노드·카운터 상태**가 필요한지가 갈림(Dify stateless 전제 A1과 연계).

#### Q17. 토큰·비용 누적 계산 주체
- **설계서 근거**: 슬라이드5 A5 "원인별 대책 그룹 생성 후 S-CLM 전달(**토큰·비용 집계**)", measure도 `callTokens/callCost/totalTokens/totalCost` 집계.
- **모호**: 누적 집계를 (a) Dify가 봉투(envelope)에 토큰·비용 넣어 반환 (b) Dify는 단발 usage만 넘기고 **백엔드가 누적**(round 누적은 백엔드가 상태 보유) 인지. → A1(상태=백엔드) 일관성상 **(b) 단발 usage만 반환·백엔드 누적**이 자연스러우나, 설계서 문구는 AI 플랫폼이 집계로 읽혀 확인 필요. 봉투에 `callTokens/callCost`(단발)만 둘지 `totalTokens/totalCost`(누적)까지 둘지 결정.

### 미세 조정
- **Q12 개수 정책**: 설계서 "합 최대 10"은 확정. **기본 5/5·가변 UI**는 measure 가정 → 사용자 조절 UI가 요구인지만 확인(영향도 낮음).

## 6. PM/고객 답변 확정 (2026-06-29) — 가장 최신, 위 항목보다 우선

> [!success] 이 절이 최신 확정값. 위 1~5절 분석 중 충돌하는 부분은 여기 기준으로 덮어쓴다.

### 확정 1. 원인 공란 시 동작 (Q9 — 내 이전 결론 ✗정정)
- **PM 답변**: "원인에 대한 대책을 추천받는 거라 **원인이 지정 안 되면 대책을 못 받는 게 맞다**." 샘플 페이지가 기준.
- **확정 해석**: **원인은 대책의 필수 선행 입력.** 원인 공란이면 → 원인 추천(유사 현상 기반) → 사용자가 원인 지정 → 그 원인으로 대책 추천. **공란 상태로 대책 직행 불가.** (measure 흐름과 동일)
- ⚠️ 1~5절의 "설계서 우선이라 현 동작(공란이면 대책X)을 바꿔야 한다"는 **폐기**. 현 HTML/샘플 동작이 맞음.

### 확정 2. 점수 평가기준 (Q1·Q2)
- **PM 답변**: "현재 평가기준은 없다."
- **확정**: 외부 점수 산정·내부/외부 통합 정렬에 **고객이 정한 기준 없음 → 개발이 결정.** (예: 내부=검색유사도×100, 외부=LLM 자기평가, 통일 방식 택1 — B1 참고). 고객 승인 불필요.

### 확정 3. Dify 구현 범위 (Q3·Q4·Q16·Q17)
- **PM 답변**: **전체를 Dify로 구현, 별도 백엔드 없음.** 호출 횟수 제한은 **프론트에서**. 토큰·비용은 확인용이라 **실제 구현에선 미사용(드랍)**.
- **확정 파생**:
  - **Q16 호출 횟수 제한**: Dify workflow는 호출마다 독립(stateless) → **Dify가 누적 카운트 불가, 프론트가 제한.** (chatflow 모드면 가능하나 미채택)
  - **Q17 토큰·비용**: 실제 구현 미사용 → **비용 집계 노드 불필요.**
  - **Q3 모델 선택**: 요구 확정 → 표준 LLM 노드 대신 **HTTP Request 노드**(model을 payload로). 
  - **Q4 세션/멀티턴**: 백엔드가 없으므로 **프론트가 상태(exclude 목록·원인 선택·횟수) 보유**, Dify는 무상태 추천기. 멀티턴은 **exclude 방식 유지**(previous_response_id 미도입 권장). HTTP 노드 교체만으로 현 exclude 멀티턴 그대로 동작.
  - 상태 주인 = **프론트**. (확정 대책서 증분 색인 A7만 Dify 지식베이스 쓰기로 처리 가능 — Q10)

### 확정 4. 내부 RAG = 코난 RAGops 노드 (Q18·Q5·Q6) ⭐신규
- **PM 답변**: "Dify로 한다면 **코난에서 Dify에서 사용 가능한 RAG용 노드를 만들어 줄 것.**"
- **확정**: 내부 RAG는 **Dify 내장 지식검색이 아니라 코난 RAGops 솔루션** 사용. 코난이 **Dify용 커스텀 RAG 노드** 제공.
- **파생 작업**: 현재 더미 지식베이스(bge-m3-ko, parent-child)는 **개발용 임시**. **코난 RAG 노드의 입출력 스키마를 받아야** 병합·정렬·점수 매핑(B2)·`ragSource` 구조 최종 확정 가능 → **코난에 노드 인터페이스 요청** 필요.
