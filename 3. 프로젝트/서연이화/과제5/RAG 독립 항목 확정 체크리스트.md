## A. 상세 (육하원칙)

### A1. 상태 경계
- **무엇/어디서**: Dify workflow가 세션·선택·round 같은 상태를 안 가짐. 상태를 Dify(chatflow)에 둘지 백엔드 DB에 둘지.
- **왜 문제**: 잘못 정하면 트랜잭션·격리·감사 보장이 안 되고, Dify·백엔드가 같은 상태를 **이중 관리**. 나중에 갈아엎기 **가장 비싼 결정**(다른 모든 결정의 전제).
- **누가/언제**: 백엔드 소유 권장. 설계 착수 시점(지금) — 다른 항목보다 먼저.
- **어떻게**: **stateless 확정**, 상태는 백엔드 DB(measure `Suggestion` 상당). 문서에 경계 명문화. (근거: 비교노트 6절 "맥락 기억" 콜아웃)

### A2. 입력 계약(payload)
- **무엇/어디서**: `step / phenomenon / cause / exclude / internalCount / externalCount` 필드·타입·필수여부. 시작·파싱 노드.
- **왜 문제**: 계약이 흔들리면 프론트·백엔드·Dify가 **동시에 깨짐**(통합 지점). 필드 누락·타입 불일치는 런타임에야 발견.
- **누가/언제**: 백엔드와 합의해 지금 고정. 이후 변경은 **옵셔널 추가만**(하위호환).
- **어떻게**: 필드별 필수/옵셔널·타입·기본값 표로 명시. `filter` 확장 여지(C1) 남김.

### A3. 에러·가드 응답 표준화
- **무엇/어디서**: 파싱 노드가 `raise Exception('현상이...')`로 죽음 → 워크플로우 5xx.
- **왜 문제**: 백엔드가 **실패 사유를 못 받아** 사용자 메시지를 못 띄움. "현상 없음" 같은 정상 가드가 **장애처럼** 보임.
- **누가/언제**: 운영에서 가드 위반마다(빈 입력 등 흔함). 지금 표준화.
- **어떻게**: 예외 대신 **정상 출력** `{ ok:false, errorCode, message, items:[] }` 를 200으로 내려 백엔드가 파싱·표시. (A4 봉투와 한 세트)

### A4. 응답 봉투(envelope) 메타데이터
- **무엇/어디서**: 현재 `result = { items }` 만. 끝 노드.
- **왜 문제**: 화면이 **"내부 몇 / 외부 몇"**(요구 ①), round, 사용 모델, 비용을 **표기 못 함**. 운영 디버깅 단서 부족.
- **누가/언제**: 프론트 표기·운영 추적. 지금.
- **어떻게**: `round / internalAdded / externalAdded / model`(+비용) 메타를 봉투에 추가. measure `SuggestResponse` 참고.

### A5. 워크플로우 구성 (A/B/C)
- **무엇/어디서**: 단일 step 분기(A) / 원인·대책 분리(B) / Iteration(C).
- **왜 문제**: 늦게 바꾸면 노드·지식베이스 **재배선**. 코드 중복(내부풀·병합 2벌)도 이 결정에 묶임.
- **누가/언제**: 지금 방향만, 운영 안정화 때 B 재검토.
- **어떻게**: **A로 시작** → RAG·프롬프트 독립 튜닝 필요해지면 B → 지연 문제 시 C. (비교노트 5절)

### A6. 모델 선택 방식 (변수화 ❌ — design-time 고정)
- **무엇/어디서**: LLM 노드 `name: gpt-5-nano` 가 노드 설정에 고정.
- **⚠️ 정정**: Dify **표준 LLM 노드는 모델을 design-time(노드 설정)에서 선택**하는 구조 → `payload.model` 로 **런타임 주입 불가**. (모델은 공급자 인증 + 토글 ON 으로 미리 등록돼 있어야 노드에서 고를 수 있음)
- **왜 (큰) 문제 아님**: 무제.md 요구에 **런타임 모델 선택 없음**(그건 measure `cheapestModel` 기능이지 과제 요구 아님). 설계/PoC 단계라 모델 변경은 드묾.
- **어떻게 (동적 선택이 필요하면)**:
  - **(a) design-time 고정** ← **지금 권장**. 변경 시 워크플로우 편집. Dify LLM 노드 기능(구조화출력·비용추적) 그대로 사용.
  - (b) 멀티 LLM 노드 + IF/ELSE 라우팅 — 노드 증식·모델별 등록 부담.
  - (c) HTTP Request 노드로 OpenAI API 직접 호출 — model을 payload로 주입(measure 방식). 런타임 유연하나 Dify LLM 노드 기능 상실.
- **전제**: 어느 방식이든 Dify에 **모델 등록(공급자 인증 + 사용 모델 토글 ON)** 필요.

### A7. step 확장성
- **무엇/어디서**: IF/ELSE가 `cause / countermeasure` 2값 고정.
- **왜 문제**: 과제정의서 HITL("AI는 점검항목 제시")처럼 **"점검 가이드 생성" 단계 추가** 시 분기 구조를 재설계해야.
- **누가/언제**: 단계 확장 요구 시.
- **어떻게**: step을 라우팅 가능한 값으로 설계(2분기 고정 회피), 분기 추가 여지 확보.

### A8. exclude 정규화 위치 일원화
- **무엇/어디서**: trim/중복제거가 파싱·내부풀·병합 **3군데** 흩어짐.
- **왜 문제**: 정규화 규칙이 어긋나면 **중복 누락 또는 과잉 제거** → 추천 품질 버그, 추적 어려움.
- **누가/언제**: 재추천 누적(요구 ③) 시.
- **어떻게**: 파싱 노드 한 곳에서 정규화하고 이후 단계는 신뢰.

### A9. 외부 LLM 분기 (external_count=0 단축 포함)
- **무엇/어디서**: 내부만 원해도(external=0) 외부 LLM 노드가 실행됨.
- **왜 문제**: **불필요한 비용·지연**. 내부 더미만 쓰는 테스트에서도 LLM 호출.
- **누가/언제**: 내부 전용 모드·비용 민감 시.
- **어떻게**: `external_count==0`이면 LLM 노드 건너뛰는 IF/ELSE 한 단 추가.

### A10. 부분 실패 처리- **무엇/어디서**: 내부(코드)+외부(LLM) 병렬 → 병합 노드가 둘 다 기다림.
- **왜 문제**: 외부 LLM이 **타임아웃·쿼터 초과로 실패하면 워크플로우 전체가 실패** → 멀쩡한 내부 결과까지 손실, 사용자 빈손.
- **누가/언제**: LLM 장애·레이트리밋(운영에서 흔함).
- **어떻게**: 병합 노드가 외부 실패를 **허용**(try/except)하고 **내부만이라도 반환** + 봉투에 `partial:true` 플래그. (A3·A4와 연계)

### A11. 개수 부족 보장- **무엇/어디서**: LLM이 요청 N개보다 **적게** 반환. 병합 slice는 초과만 자르고 부족은 못 채움.
- **왜 문제**: 화면에 **빈자리**(요구 개수 미달). Dify 정적 스키마라 min 강제 불가.
- **누가/언제**: LLM 변덕·짧은 응답 시.
- **어떻게**: 부족 시 정책 택1 — (a) 그대로 노출 + 실제 개수 표기, (b) 1회 재호출, (c) 내부로 보충. **봉투에 실제 생성 개수** 포함(A4).

### A12. exclude 페이로드 비대화 상한- **무엇/어디서**: 라운드를 거듭하면 exclude 리스트가 계속 커짐. payload·LLM 프롬프트에 그대로 주입.
- **왜 문제**: **토큰 비용↑·입력 길이 한계·지연↑**. 사이클 많을수록 악화(요구 ③ 다중 사이클).
- **누가/언제**: 여러 번 "나머지 계속 찾기" 시.
- **어떻게**: 백엔드가 **최근 N개만** exclude로 전달 + 나머지는 RAG 메타 필터/후처리 dedup으로 처리. exclude 상한 정책 명시.

### A13. 입력 검증 / 프롬프트 인젝션 방어- **무엇/어디서**: `phenomenon / cause` 사용자 입력이 LLM 프롬프트에 **직접 삽입**.
- **왜 문제**: "이전 지시 무시…" 같은 **프롬프트 인젝션**·이상 입력이 출력을 오염. 운영 보안 리스크.
- **누가/언제**: 운영 사용자 입력 단계.
- **어떻게**: 백엔드 입력 검증·길이 제한, 프롬프트에 입력 **구분자/방어 문구**, 출력 스키마 강제(이미 있음)로 영향 축소.

### A14. 동점 정렬 안정성(tie-break)- **무엇/어디서**: 병합 노드가 `score desc`만으로 정렬. 동점 tie-break 없음.
- **왜 문제**: 같은 점수 항목 순서가 **호출마다 흔들려** 화면 순서 불안정. measure(점수desc + 생성순)와 불일치. (내부 의사점수는 동률 잦음)
- **누가/언제**: 점수 동률 발생 시.
- **어떻게**: 2차 정렬키(생성순/내부 우선/원문 순서) 추가해 **안정 정렬**.

### A15. 입출력 계약 버저닝- **무엇/어디서**: payload/result에 버전 식별자 없음.
- **왜 문제**: 워크플로우 갱신(v0.0.3 등) 시 백엔드와 스키마 불일치를 **조용히** 일으켜 디버깅 난이도↑.
- **누가/언제**: 워크플로우 버전업 시.
- **어떻게**: payload/result에 `schemaVersion` 필드 또는 워크플로우 URL 버전 고정 + 백엔드가 기대 버전 명시.

## B. 상세 (육하원칙) — 원칙만 지금, 구현은 spike 후

### B1. 점수(score) 정책
- **무엇/어디서**: 내부=벡터 유사도, 외부=LLM 자기평가. 척도가 다름. 병합·정렬 노드.
- **왜 문제**: 다른 척도를 한 줄로 섞어 정렬하면 **왜곡**(외부 임의 90점이 내부 진짜 60점 위로). 점수 신뢰성 훼손.
- **누가/언제**: 혼합 결과 표시할 때마다.
- **어떻게(원칙 지금)**: 외부 score=null(내부만 점수) **또는** Rerank로 통일 — 방향만 결정. **구현은** RAG 점수 척도(0~1? 0~100?) 확인 후.
- **✅ spike 확정 (2026-06-29)**: RAG 검색 score = **cosine 0~1**(`metadata.score`). v0.0.5에서 **내부 score = 검색 유사도×100**으로 고정(LLM 자기평가 폐기 — 내부 점수를 grounded하게). LLM 추출은 score 대신 근거 문서번호(`source_doc`)만 출력.
- **🔶 남은 결정**: 내부(검색, 관련문서 71~76) vs 외부(LLM, 80~95) **두 척도 통일 미정**. 실행 데이터 보고 (가)외부 null (나)min-max 정규화 (다)rerank 중 택1. → 정렬 시 외부 독식 경향 확인 후 결정.

### B2. 출력 계약 item 키
- **무엇/어디서**: item 키(`content/text/source/ragSource/score`). measure API는 `content`·대문자 `INTERNAL/EXTERNAL`.
- **왜 문제**: RAG output 키 모양에 따라 매핑이 달라져, **미리 박으면 두 번 일**.
- **누가/언제**: spike 후.
- **어떻게**: 봉투는 지금 확정, **item 키는 RAG output 캡처 후** measure(`SuggestionView`) 기준 매핑(text→content, source 대문자화 — 비교노트 4.5절).
- **✅ spike 확정 (2026-06-29)** — Dify 지식검색 `result[]` 실제 키:
  - 본문 `content`(전체 문서, parent-child 청킹) · 점수 `metadata.score`(0~1) · 식별 `metadata.document_id`/`document_name`/`segment_id`/`dataset_id` · `title`
  - `source`/`ragSource`는 RAG 미제공 → **정형화 코드 노드가 부여**
  - **산출 item(워크플로우 출력)** = `{text, score(0~100), source('internal'|'external'), ragSource}`
  - **`ragSource`는 객체**(v0.0.6): `{document_id, document_name, dataset_id, segment_id, similarity(0~1), excerpt}` — string 아님(계약 변경, 백엔드 공유 필요). 상위 `source:internal`과 중복되던 `ragSource.source` 상수는 제거
  - 측정 API 매핑(4.5절): 백엔드에서 `text→content`, `source` 대문자화 적용. `INTERNAL` 근거 = ragSource.document_id로 원본 링크.

## C. 상세 — 여지

### C1. 검색 필터(품명·이슈타입) 여지
- **무엇/왜**: 운영 RAG 품질에 품명·이슈타입별 검색(과제 요약 "검색 볼륨 분리")이 필수가 될 가능성 큼 → 나중에 payload 변경을 유발.
- **어떻게**: 지금 구현하지 않되, payload에 `filter` **옵셔널 자리**만 남겨 하위호환 확보.
