### 요약 — 진짜 큰 공사 2개
1. **LLM 노드 → HTTP 노드**(모델 선택). 멀티턴(exclude)·가드·봉투 구조는 살림 → 전면 재설계 아님, 노드 교체+body 이전이 핵심.
2. **Dify 지식검색 → 코난 RAG 노드**. **코난 노드 스키마 수령 후 착수**. 그 전까진 현 v0.0.6(지식검색)로 개발 지속.
- 나머지(가드·횟수·비용·원인별 대책)는 이미 맞거나 변경 거의 없음. 신규 추가는 점검항목·증분색인 2개(요구 미확정).

### ⚠️ 5-1 (수집·저장 에이전트) — 미정, **아마 Dify로 작업 필요**
- 통합 문서 4절(OCR 추출→정규화→검색DB 색인, S1~A7)은 **v0.0.6에 전혀 없음.**
- "전체 Dify"라면 5-1도 **Dify로 별도 워크플로우** 신설 가능성 큼. 단 OCR은 별도 모듈, 색인은 검색엔진/코난 영역이라 **5-1 중 우리 Dify 몫의 경계는 아직 불명** → 스코프 확인 필요.

### HTTP 노드 교체 상세 (외부 LLM 2개만 대상)

> [!note] RAG는 **현 Dify 지식검색 유지**(지금 변경 안 함). 코난 노드 수령 시 노드 교체 + 필드(ragSource/score) 매핑만 수정 예정. 아래는 **외부 LLM 경로**만의 작업.

**대상 노드** (v0.0.6 LLM 4개 중 2개)
- `2003000000006` **LLM · 외부 원인** (gemma-4-26b) → HTTP
- `2003000000010` **LLM · 외부 대책** (gemma-4-26b) → HTTP
- ※ `LLM · 내부 원인/대책 추출(RAG)` 2개는 RAG 경로 → 코난 교체 때 처리(지금 손대지 않음)

**LLM 노드 → HTTP 노드 변환 체크리스트**
| # | 항목 | 내용 |
|---|---|---|
| 1 | Method/URL | `POST https://api.openai.com/v1/chat/completions` |
| 2 | Headers | `Authorization: Bearer {{API_KEY}}`(Dify 시크릿/환경변수), `Content-Type: application/json` |
| 3 | Body.model | `{{#2003000000002.model#}}` — 파싱노드에 model 출력 추가 필요 |
| 4 | Body.messages | 기존 sys/user 프롬프트 이식(phenomenon/external_count/exclude_block 변수 유지) |
| 5 | Body.response_format | `{type:json_schema, json_schema:{strict:true, schema:<기존 items 스키마 재사용>}}` |
| 6 | 응답 언랩 | HTTP `body`(OpenAI 전체응답) → `choices[0].message.content` 추출 **코드노드 신설** → 병합노드 연결 |
| 7 | 에러 전략 | HTTP 노드 "실패 시 계속(기본값)" 설정 → A10(외부 실패해도 내부만+partial) 유지 |

→ 외부 LLM 1개당 **HTTP + 언랩 코드노드** 2개 (원인·대책 총 4개 노드).

**부수 변경**
- **파싱노드 `2003000000002`**: payload `model` 추출 + 화이트리스트 검증(gpt-5-nano/5.5/5.5-pro, 외 값은 기본값), 출력 변수 추가
- **병합·정렬 노드** `2003000000007`(원인)/대책: `external_obj` 입력을 `...006.structured_output` → **언랩 코드노드 출력**으로 변경, `meta.model` 하드코딩(`'gpt-5-nano'`) → **선택 model 변수로 동적화**

**주의**: ① 구조화출력 자동→수동(strict json_schema를 body에 직접), 개수 N은 프롬프트로만 강제 ② HTTP는 Dify 모델 등록 우회(장점) ③ 코난 RAG와 독립이라 지금 착수 가능

### v0.0.7 구현 완료 (2026-06-29) — HTTP 교체

**적용 결과** (5-2 외부 LLM 경로만, RAG는 v0.0.6 유지):
- 외부 LLM 노드 2개(`2003000000006` 원인 / `2003000000010` 대책) → **HTTP Request 노드**(`POST api.openai.com/v1/chat/completions`)
- **요청바디 구성 코드노드 2개 신설**(`2003000000020` 원인 / `2003000000021` 대책): model·프롬프트·json_schema를 `json.dumps`로 안전하게 직렬화 → HTTP body는 `{{#노드.request_body#}}` 단일 변수 (exclude_block 줄바꿈 등 escaping 깨짐 방지)
- **파싱노드**: `model` 추출 + 화이트리스트 검증(gpt-5-nano/5.5/5.5-pro, 외 값→nano)
- **병합노드 2개**: 외부 입력을 HTTP `body`에서 `choices[0].message.content` **언랩** 후 items 파싱, `meta.model` **동적화**
- **API 키**: `OPENAI_API_KEY` 환경변수(secret) 추가, HTTP 헤더 `Authorization:Bearer {{#env.OPENAI_API_KEY#}}`
- 엣지 재배선: 분기→요청바디→HTTP→병합

**검증 통과**(스크립트): YAML 재파싱 / 모든 코드노드 컴파일 / 요청바디=유효 JSON(모델 선택 반영) / 병합 언랩·점수정렬·동적 model / 화이트리스트 fallback / HTTP 노드·엣지 재배선.

**[B] Responses API + previous_response_id 세션 체이닝 전환 (2026-06-29, v0.0.7 내 수정)**
- 결정: 멀티턴을 exclude(A)가 아닌 **OpenAI Responses API 세션 체이닝(B)** 으로. 설계서 원안 충실.
- HTTP URL `/v1/chat/completions` → **`/v1/responses`**, 바디 `messages/response_format` → **`instructions/input/store:true/text.format(json_schema strict)`**
- **payload에 `previous_response_id` 추가** → 파싱노드가 수신 → 요청바디에 주입(첫 호출은 빈값이면 생략, 이어지면 포함)
- 병합노드: 응답 언랩을 Responses 형식(`output[type=message].content[type=output_text].text`)으로, **응답 `id`를 `meta.responseId`로 반환**
- **프론트 계약(중요)**: 프론트가 `result.meta.responseId`를 **문서별로 보관 → 다음 호출 payload.previous_response_id로 재투입**(round-trip). 백엔드 없으므로 프론트가 세션 상태 소유.
- 검증 통과: 첫 호출 prev 생략 / 체이닝 시 prev 포함 / Responses 응답 언랩 + responseId 추출 / 점수정렬 / URL=/v1/responses.
- ※ 지식검색 뒤 내부 추출 LLM(2004…)은 세션·모델선택과 무관 → 그대로 둠(코난 RAG 교체 시 처리).

> [!warning] import 시 확인 필요 (Dify 버전별 차이 가능)
> 1. **HTTP 노드 body 스키마**: `body.type=json, data=[{key:'',type:text,value:'{{#..request_body#}}'}]`로 작성 — Dify 버전에 따라 body.data가 문자열일 수 있음. import 후 HTTP 노드가 깨지면 UI에서 HTTP 노드 1개 만들어 export해 형식 대조.
> 2. **API 키**: import 후 Dify에서 `OPENAI_API_KEY` 환경변수에 실제 키 설정.
> 3. **A10 하드실패**: HTTP가 타임아웃/쿼터로 죽으면 워크플로우 중단 → 진짜 무시하려면 노드 **예외처리(fail-branch/기본값)** UI 설정 필요(병합은 외부 빈값=partial까지만 처리).
> 4. 모델명 `gpt-5.5/5.5-pro`는 설계서 기준 — 실제 사용 가능 여부는 OpenAI 계정/키 측.

## v0.0.3 (2026-06-26)

**변경 동인**: [[3. 프로젝트/서연이화/과제5/RAG 독립 항목 확정 체크리스트.md]] 의 RAG 독립 설계결정 **A1~A10 확정** 반영. (B1·B2는 RAG 적용 후, A11~A15는 다음 차수)

### 반영 (A1~A10)
- **A1 상태 경계**: stateless workflow 유지(상태=백엔드 DB). conversation_variables 미사용.
- **A2 입력계약 고정**: `step/phenomenon/cause/exclude/internalCount/externalCount` (+`model`/`filter` 옵셔널 여지).
- **A3 에러 표준화**: 파싱 노드가 **예외 throw ❌** → `ok/error_code/message/error_result` 반환. **검증 게이트(IF/ELSE)** 추가 → 실패 시 **끝·에러** 노드로 `{ok:false, errorCode, message, items:[]}`.
- **A4 응답 봉투+meta**: 성공 `result={ok:true, items, meta:{internalAdded, externalAdded, requestedInternal, requestedExternal, model, partial}}`. **round 제외**(stateless라 백엔드가 부여).
- **A5 구성**: 옵션 A 단일 워크플로우 유지.
- **A6 모델**: design-time 고정(payload 주입 ❌). LLM 노드에 모델 고정.
- **A7 step 확장성**: step **화이트리스트 검증**(cause/countermeasure, 외 값은 INVALID_STEP).
- **A8 exclude 정규화**: **파싱 노드 1곳**에서 trim+빈값제거+dedup, 이후 단계는 신뢰.
- **A9 외부 분기**: merge가 `external_count` 만큼만 외부 반영(0이면 0개). ⚠️ 완전 노드 skip(비용0)은 후속.
- **A10 부분 실패**: merge가 외부 빈값 허용 → 내부만 반환 + `meta.partial=true`. ⚠️ 노드 자체 실패 무시는 LLM 노드 error 전략(UI) 후속.

### 구조 (v0.0.2 대비 변화)
```
시작 → 코드(파싱/검증) → IF/ELSE(검증 게이트, ok?)
   ├ 거짓 → 끝·에러 (ok:false 봉투)          ← 신규
   └ 참  → IF/ELSE(step==cause?)
        ├ 참  → [내부 원인] + [외부 원인] → 병합·정렬(봉투+meta) → 끝·원인
        └ 거짓 → [내부 대책] + [외부 대책] → 병합·정렬(봉투+meta) → 끝·대책
```
- v0.0.2 대비: **검증 게이트 + 끝·에러 노드 신규**, 파싱/병합 코드 교체, 출력이 `{items}` → `{ok, items, meta}` 봉투.
- 코드 노드는 **literal block scalar(`|`)** 로 작성(임포트 시 이스케이프 안전).

### 후속 / 한계
- **A9 완전 skip**: `external_count==0`일 때 LLM 노드 자체를 건너뛰려면 분기 추가 필요(현재는 호출은 되고 결과만 0개).

- **A11~A15**: 개수 부족 보장·exclude 상한·인젝션 방어·동점 tie-break·계약 버저닝 — 다음 차수.
- **B1/B2**(점수 정책·item 키): RAG output 모양 확인(spike) 후 확정.

## v0.0.1 (2026-06-25)

- 병합: 각 LLM → 자기 End 직접 출력(변수 집계기는 미연결 참고용)

**한계**: 내부(사내) 소스 없음, 점수 없음, 단일 대책(원인별 분리 없음).

## v0.0.2 (2026-06-26)

**변경 동인**: 소스 리팩토링(내부/외부 혼합 + 점수 + 원인별 대책) 반영. 근거 스크린샷 8개 요구사항.

### 추가/변경
- **내부(더미 RAG) + 외부(LLM) 혼합**
  - 코드 노드 `내부 원인(더미)` / `내부 대책(더미)`: 사내 유사사례 풀(더미 20개)에서 제외 제외 top-N, 유사도 점수(96→2.5씩 감소, 하한40), RAG 근거(더미)
  - 외부 LLM과 **병렬 실행** 후 병합
- **항목별 점수** — 출력 스키마 변경: `{"items":[{"text":"...","score":0~100}]}`
  - 외부 LLM instructions에 "정확히 N개 / 관련도 0~100 점수"
  - 개수 N = `external_count`(프롬프트 변수로 주입)
- **병합·정렬 노드(코드)** — 내부+외부 합쳐 중복제거, **점수 내림차순**, `source`(internal/external) 태그. 변수 집계기 대체
- **개수 보정** — `internalCount`/`externalCount`(기본 5/5, 합 최대 10, 외부부터 축소). 둘 다 0이면 에러
- **대책 = 원인 1개(cause)씩 호출** — 원인별 따로(req6,7). 호출자가 원인 수만큼 반복(= 원인별 버튼 각각)
- **모델 기본값 gpt-5-nano**(최저가, req8)

### 입출력 계약
입력 `payload`(object):
```json
{ "step":"cause", "phenomenon":"...", "cause":"", "internalCount":5, "externalCount":5, "exclude":[] }
```
대책: `{ "step":"countermeasure", "phenomenon":"...", "cause":"확정 원인 1개", "internalCount":5, "externalCount":5, "exclude":[] }`

출력 `result`(object):
```json
{ "items": [ { "text":"...", "score":88, "source":"internal", "ragSource":"[출처]..." } ] }
```

### 구조
```
시작 → 코드(파싱) → IF/ELSE(step)
   ├ 참  → [내부 원인(코드)] + [외부 원인(LLM)] → 병합·정렬(코드) → 끝·원인
   └ 거짓 → [내부 대책(코드)] + [외부 대책(LLM)] → 병합·정렬(코드) → 끝·대책
```

### 미구현 / 한계 (다음 버전 후보)
- `external_count=0`(내부만) 단축 분기 없음 — 외부 LLM 노드는 그대로 실행됨
- 출력 개수가 스키마 min/max로 강제되지 않음(Dify 정적 스키마 한계) → 프롬프트 "정확히 N개" + 외부 slice로 보정
- **원인별 대책 Iteration**(한 번 호출로 N개 원인 일괄)은 미구현 → 호출자 루프로 대체
- 내부 RAG는 더미(사내 검색 미연동), 내부·외부 점수 척도 차이
