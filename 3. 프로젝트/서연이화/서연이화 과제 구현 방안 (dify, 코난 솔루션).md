# 목적
서연이화 내 산재된 약 12,000건의 비정형 문서(과거 대책서 7,000여 건, 기술 표준 및 사양서 1,000여 건 등)를 구조화된 데이터(RDB)로 전환하고, 이를 최신 LLM 및 최적화 알고리즘과 연계하여 지능형 업무 자동화를 구현

## 과제 1: 인사 정보 기반 권한 자동 맵핑
#초중급 #룰엔진 #REST-API #배치처리 #JSON파싱 #Dify-Workflow
- **비즈니스 배경**: 서연이화는 수백 명이 근무하는 제조기업입니다. 직원이 부서를 옮기거나 신입이 입사하면, 담당자가 인사발령 내역을 확인하고 업무 시스템(S-PLF)에 접속해 권한을 일일이 손으로 바꿔줘야 합니다. 인사이동이 잦은 조직에서 이 작업이 밀리면 "필요한 메뉴에 접근 못 하는 직원"과 "이미 이동·퇴사했는데 권한이 그대로인 직원"이 동시에 생깁니다. 
- **핵심사항**
	- 그룹웨어의 인사 이동 정보(부서 이동 등)를 일배치로 받아와, 업무 시스템(플랫폼) 내 사용자 권한을 자동으로 변경해주는 규칙 기반(Rule-based) 모델을 구축하는 것입니다.
- **액션 플랜**
	- 고객사가 제공하는 권한 부여 기본 정책 및 예외 케이스를 분석하여 룰베이스 엔진을 개발하고, 에이전트 관리 도구와 연동합니다.
- **dify 구현 방안**
	- **방안 1. Dify Workflow + Code 룰엔진 (dify 중심)**: Start(인사변동 JSON 수신) → HTTP Request(부서·직급별 권한 누적 통계 DB 조회) → Code(정책 1~6 룰 적용·신규/이동/1인부서 분기) → HTTP Request(S-PLF로 변경 권한 전송) → End. S-PLF가 일배치로 Workflow API 호출.
		- 작업량: dify 내 워크플로우 1개 + 룰 Code / dify 외 권한통계 조회 API·S-PLF 배치 연동
		- 복잡도: 중 — 룰은 결정적이나 부서별 권한 집계·예외처리 분기가 많음
	- **방안 2. IF/ELSE 분기 + Template Transform (로우코드)**: Code 최소화, IF/ELSE 노드로 신규·이동·신설·1인부서 분기, Template Transform으로 권한 매핑.
		- 작업량: dify 내 분기 노드 다수 / dify 외 권한통계 DB 조회
		- 복잡도: 중 — 정책 6종+예외로 분기 노드가 비대해져 유지보수 부담
	- **방안 3. 로컬 룰엔진 API + Dify 오케스트레이션**: 권한 룰 전체를 폐쇄망 로컬 API(FastAPI)로 구현, Dify는 수신·HTTP 호출·결과 전송·로깅만 담당.
		- 작업량: dify 내 최소(HTTP 호출) / dify 외 룰 API 개발 대부분
		- 복잡도: 하(dify 기준) — 복잡 룰을 코드로 분리해 테스트·버전관리 용이
	- **코난 솔루션 활용**: 정형 RDB·룰 기반 과제라 코난 검색/LLM 직접 활용도는 낮음. 다만 "권한 설정 추천 근거"(과제정의서 AI/코난 컬럼) 제공이 필요하면 과거 권한설정 사례를 코난 RAG에 색인해 유사 케이스 근거를 함께 제시할 수 있음.
	- **권장 방안**: 방안 1 — "Dify 내 해결 우선" 원칙에 부합하고, DB 조회만 외부로 두어 룰 로직을 Dify에 집중시켜 운영·이력관리가 단순함. (룰이 과도하게 복잡해지면 방안 3으로 분리)
	- **권장 방안 (dify 단독) [보정]**: 방안 1 — 단, "Dify 적용 가치"를 재검토해야 함. 정책 1~6은 LLM이 전혀 개입하지 않는 순수 룰이므로 Dify는 Code 노드+HTTP를 감싸는 오케스트레이터에 그치며, 사실상 외부 Python 스크립트+스케줄러(Cron)/Spring 배치로 구현하는 편이 더 가볍고 효율적임. → **LLM 활용이 없으면 외부 구현이 합리적**이고, ① 타 에이전트와의 통합 운영·관리, ② 향후 '권한 추천 근거' 등 LLM 기능 확장을 염두에 둔다면 그때 Dify Workflow로 통일하는 것이 유리.
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 영향 거의 없음 — 룰은 표준 라이브러리(re·json·산술·dict 조회)만으로 Code 노드 구현 가능하고, DB 조회는 HTTP Request 노드가 담당하므로 서드파티 라이브러리 불필요. 방안 1 그대로 유지.

## 과제 2: 현대차 업무 포털 단가 조회 자동화 (매크로)
#초중급 #RPA #Selenium #Playwright #웹스크래핑 #정규식 #OCR연동
- **비즈니스 배경**: 서연이화는 현대차에 부품을 납품하는 협력사로, 현대차 공급사 포털(VAATZ)에 접속해 아직 가격이 확정되지 않은 '미결 품목'의 단가를 주기적으로 확인해야 합니다. 지금은 담당자가 매일 직접 포털에 로그인해 품목을 조회하고, 단가를 엑셀로 정리한 뒤 사내 시스템(S-CST)에 업로드합니다. 품목 수가 늘어날수록 이 반복 작업에 드는 시간도 함께 늘어납니다.
- **핵심사항**
	- 매일 사람이 현대차 포털에 로그인해 미결 품목을 조회하고 단가를 엑셀로 정리하여 업로드하는 반복 작업을 자동화하는 것입니다.
- **액션 플랜**
	- 크롬 기반의 웹 매크로를 활용해 미결 품목 및 단가를 스크래핑한 뒤, 엑셀 텍스트를 파싱하여 자사 플랫폼으로 일괄 전송하는 프로세스를 개발합니다.
- **dify 구현 방안**
	- **방안 1. 외부 RPA + Dify 후처리 (역할 분담)**: 로그인·미결품목 다운로드·단가 조회·캡처는 외부 RPA(Playwright/Selenium, 폐쇄망)가 수행 → 결과 파일을 Dify Workflow로 전달 → Document Extractor(엑셀 텍스트 추출) → Code(품번/품명/단가 파싱·정규화) → HTTP Request(S-CST 전송·중복검증).
		- 작업량: dify 외 RPA(브라우저 자동화·OTP 로그인) 대부분 / dify 내 파싱·정규화·전송
		- 복잡도: dify 기준 하 / 전체 상 — 브라우저 자동화·로그인이 핵심 난이도이며 Dify 외 영역
	- **방안 2. Dify를 파싱·검증 마이크로서비스로만 사용**: RPA가 OCR·텍스트화까지 끝낸 데이터를 Dify에 전달, Dify는 LLM/Code로 정규화·중복검증·전송만 담당.
		- 작업량: dify 내 매우 적음 / dify 외 RPA+OCR
		- 복잡도: 하 — 단순 파싱·검증만 담당
	- **코난 솔루션 활용**: 본 과제는 RPA 영역이라 직접 연관 낮음. 단가표를 화면캡처→OCR하는 구간은 코난 DocAI/DocuAnalyzer 문서필터로 대체 가능하나, 전처리는 별도 업체 담당이므로 우선순위 낮음.
	- **권장 방안**: 방안 1 — 브라우저 자동화는 Dify가 수행 불가하므로 외부 RPA로 두고, 텍스트 파싱·정규화·전송만 Dify가 맡는 분담이 가장 현실적이고 유지보수에 유리.
	- **권장 방안 (dify 단독)**: 방안 1 — 스크래핑은 코난과 무관하게 외부 RPA가 필수이므로, Dify 범위에서는 Document Extractor+Code로 파싱·정규화·전송을 모두 처리하는 방안 1이 최선(방안 2는 OCR까지 외부 위임해 Dify 활용도가 더 낮음).
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 소폭 변동 — openpyxl 사용 불가하므로 엑셀 파싱을 ① Document Extractor 노드(평문 추출)+정규식(re)으로 처리하거나 ② 외부 RPA가 파싱까지 끝내 정형 JSON으로 전달. RPA가 이미 외부라 영향이 작고, Dify는 텍스트 후처리·전송만 담당.

## 과제 3: 기술 표준 문서 LLM 요약 및 비교
#중급 #LLM #RAG #프롬프트엔지니어링 #청킹 #임베딩 #분할요약 #Map-Reduce
- **비즈니스 배경**: 현대차 같은 완성차 업체는 자신들이 요구하는 부품 사양과 시험 기준을 '기술 표준 문서(PDF·PPT, 문서당 100여 장)'로 서연이화에 전달합니다. 이런 문서가 약 630개가 있고 주기적으로 개정됩니다. 담당자는 두꺼운 문서를 읽고 시험 항목·합격 기준을 뽑아 플랫폼(S-LAB)에 등록해야 하고, 새 버전이 나올 때마다 이전 버전과 무엇이 달라졌는지 직접 비교해야 합니다.
- **핵심사항**
	- 각 100여 장에 달하는 비정형 기술 표준 문서를 LLM을 활용해 중요한 시험 리스트 위주로 요약하고, 과거 버전과 최근 버전 간의 세부적인 기술 표준 차이를 비교 분석하는 기능입니다.
- **액션 플랜**
	- 비정형 문서를 OCR로 구조화한 후(전처리 업체 수행), 추출된 텍스트를 기반으로 핵심 정보를 요약하고 연도별 변경점을 도출하는 LLM 프롬프트를 설계합니다.
- **dify 구현 방안**
	- **방안 1. Dify Workflow 분할요약 + Knowledge (dify 중심)**: Start(문서텍스트/링크) → Document Extractor → Iteration(청크별 LLM 요약) → Variable Aggregator(병합) → LLM(최종 요약) → Knowledge(임베딩 저장)·HTTP(S-LAB 전송). 비교(3-2): Knowledge Retrieval로 2개 문서 청크 검색 → LLM 비교.
		- 작업량: dify 내 요약·비교 워크플로우 / dify 외 OCR(전처리 업체)·S-LAB 연동
		- 복잡도: 중 — 맵리듀스식 분할요약·병합 흐름 설계 필요하나 표준 노드로 구성 가능
	- **방안 2. 코난 RAG 검색 + Dify LLM (권장형)**: 색인·청킹·임베딩·검색은 코난 검색엔진이 담당, Dify는 코난 search API(HTTP Request)로 청크 확보 후 LLM 요약·비교만 수행. 코난을 Dify 외부 지식베이스 API로 연결하면 Knowledge Retrieval 노드로도 사용 가능.
		- 작업량: dify 내 LLM·오케스트레이션 / dify 외 코난 색인·검색
		- 복잡도: 중 — 검색 품질을 코난에 위임해 Dify는 프롬프트 중심으로 단순
	- **방안 3. 배치 대량 요약 분리**: 약 630건 초기 요약은 Dify Workflow API를 외부 스크립트로 반복 호출하거나 KonanLLM Studio 배치(JSONL)로 처리하고, 버전 비교만 실시간 Chatflow로 운영.
		- 작업량: dify 내 요약 워크플로우 / dify 외 배치 러너 또는 코난 배치
		- 복잡도: 중 — 대량 초기적재와 실시간 비교를 분리해 부하 관리
	- **코난 솔루션 활용**: 코난 RAG-X가 색인·청킹(표는 1청크, 소제목 title화)·임베딩(embedding-10)·키워드+벡터 검색을 수행하고 Dify는 /ksm/rag/v5(v6) search로 청크를 받아 요약·비교. 630건 초기 요약은 KonanLLM Studio 배치(JSONL 대량 추론)로 일괄 처리 가능.
	- **권장 방안**: 방안 2 — 폐쇄망에서 색인·검색은 코난이 강점이고 Dify는 요약·비교 프롬프트에 집중해 역할분담이 명확하며 확장성이 높음. 초기 대량 적재는 방안 3(배치)을 병행.
	- **권장 방안 (dify 단독)**: 방안 1 — Dify 자체 Knowledge Base(임베딩·검색)와 Iteration 분할요약으로 색인·요약·비교를 코난 없이 완결. 단, 630건·100여 장 긴 문서에서 검색품질·성능은 코난 RAG 대비 한계가 있어 PoC·초기 구축에 적합.
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 영향 없음 — Document Extractor·Iteration·Knowledge·LLM 모두 Dify 기본 노드라 서드파티 라이브러리가 필요 없음. 방안 1 그대로 유지.

## 과제 6: 과거 대책서 기반 유사 사례 검색 및 대책 생성
#중고급 #RAG #벡터검색 #하이브리드검색 #임베딩 #리랭킹 #LLM생성 #메타데이터설계 #TopK
- **비즈니스 배경**: 공장에서 부품을 찍어내다 보면 불량(예: 도어트림 플라스틱이 깨짐)이 발생합니다. 품질 부서는 이때마다 "왜 불량이 났고, 어떻게 조치했다"라는 '품질 대책서(PPT)'를 작성해 기록으로 남깁니다. 이 기록이 무려 1만 건이 넘습니다.
- **핵심사항**
	- 약 7천~1만 건의 PPT 형태 과거 대책서 데이터를 전처리하여, 사용자가 현재의 '현상'과 '원인'을 입력하면 가장 유사한 과거 사례를 검색(RAG)해 새로운 대책 보고서 텍스트를 구조화하여 생성해 주는 과제입니다.
- **액션 플랜**
	- 전처리 업체(한국딥러닝) 및 고객사와 협의해 과거 대책서의 DB 스키마(현상, 원인, 대책 등)를 명확히 구조화하고, 이슈 타입이나 품명별로 검색 볼륨을 나누어 RAG의 검색 품질과 프롬프트를 고도화합니다.
- **dify 구현 방안**
	- **방안 1. Dify Knowledge RAG Chatflow (dify 중심)**: 6-1은 OCR 텍스트를 Dify Knowledge Base에 메타데이터(형태/연도/사유)와 함께 적재. 6-2는 Chatflow Start(현상·원인) → IF/ELSE(원인 유무 분기) → Knowledge Retrieval(메타 필터) → LLM(보고서 양식 대책 가이드 생성) → Answer.
		- 작업량: dify 내 Chatflow + Knowledge / dify 외 OCR·S-CLM 연동
		- 복잡도: 중 — 표준 RAG 패턴이나 7천건 볼륨·메타 필터·현상/원인 분기 설계 필요
	- **방안 2. 코난 RAG 엔진 + Dify 생성 (권장형)**: 색인·임베딩·검색은 코난(이슈타입·품명별 볼륨 분리, 동의어 사전), Dify는 HTTP Request로 코난 v5/v6 search 호출 → 검색 청크를 LLM에 주입해 대책 가이드 생성. 외부 지식베이스 API로 Dify Knowledge에 통합도 가능.
		- 작업량: dify 내 생성·오케스트레이션 / dify 외 코난 색인·검색
		- 복잡도: 중 — 대용량·검색품질을 코난에 위임, Dify는 생성에 집중
	- **방안 3. Dify Agent 노드 기반 다단계 검색**: Agent 노드가 코난 검색 Tool을 자율 호출(현상→유사원인 검색→해당원인 대책 검색)해 다단계로 근거 수집 후 대책 생성.
		- 작업량: dify 내 Agent + Tool / dify 외 코난 검색
		- 복잡도: 상 — 자율 다단계 검색은 강력하나 폐쇄망 모델 성능·제어 난이도 높음
	- **코난 솔루션 활용**: 7천~1만건 대량 대책서는 코난 RAG-X 색인(청킹/embedding-10/키워드+벡터)이 성패 핵심. 이슈타입·품명별 볼륨(vols)으로 검색 범위 조정, 동의어/형태소 사전으로 품질 향상, reranking/selector로 적합 청크 선별. Dify는 search API 결과로 생성만 수행.
	- **권장 방안**: 방안 2 — 7천~1만건 대용량과 검색품질 고도화(이슈타입·품명별 볼륨, 프롬프트)가 성패를 좌우하므로 검색은 코난, 생성은 Dify로 분담하는 것이 가장 안정적.
	- **권장 방안 (dify 단독)**: 방안 1 — Dify Knowledge Base에 메타데이터(형태/연도/사유)와 함께 적재 후 Knowledge Retrieval+IF/ELSE 분기로 RAG를 코난 없이 완결. 단 7천~1만건 대용량에선 Dify 단독 검색 성능·볼륨 관리 부담이 커 초기 PoC·소규모 우선 적용 권장.
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 영향 없음 — Knowledge Retrieval·IF/ELSE·LLM 기본 노드만 사용하므로 서드파티 라이브러리 불필요. 방안 1 그대로 유지.

## 과제 11: 컬러 사양표 자동 입력 및 품명 오타 보정
#중급 #퍼지매칭 #Levenshtein #텍스트유사도 #임베딩 #동의어사전 #TopK #NLP
- **비즈니스 배경**: 완성차 업체(현대차 등)는 차종별 내장 부품의 색상이 확정되면 '컬러 사양표(PPT·엑셀)'를 서연이화에 보내줍니다. 담당자는 이 표를 보고 부품별 컬러 값을 S-MLD 시스템에 일일이 입력해야 합니다. 그런데 고객사마다 부품명이 달라 어떤 부품과 매칭해야 할지 찾기가 까다롭고(예: 고객사 "DOOR TRIM LH" = 사내 "도어트림 좌측"), 심지어 오타까지 섞여 있어 수동 확인이 불가피합니다.
- **핵심사항**
	- 고객이 주는 비정형 컬러 사양표(엑셀, PPT)에서 부품별 컬러 값을 플랫폼에 자동 기입하는데, 고객사의 품명에 오타가 섞여 있어도 AI가 이를 보정하여 정확한 부품에 맵핑해 주어야 합니다.
- **액션 플랜**
	- 전처리 업체로부터 텍스트를 전달받아, 동의어 사전이나 단어 유사도 알고리즘을 적용해 오타를 매핑합니다. 유사도가 애매한 경우(예: 85%) 드롭박스를 통해 사용자가 최종 선택할 수 있도록 UI 옵션을 협의합니다.
- **dify 구현 방안**
	- **방안 1. Dify 유사도 매칭 Workflow (dify 중심)**: Start(OCR 텍스트) → Code(정규화·동의어 확장) → Knowledge Retrieval/Code(부품명 임베딩 유사도 TopK) → IF/ELSE(유사도 임계 분기: 고신뢰 자동확정 / 애매 시 TopK 후보 반환) → LLM(컬러-부품 매핑 정리) → HTTP(S-MLD 전송, 드롭박스용 후보 포함).
		- 작업량: dify 내 워크플로우 / dify 외 OCR·동의어 사전·S-MLD UI(드롭박스)
		- 복잡도: 중 — 유사도 임계 분기·TopK 후보·사용자 가중치 반영 로직 필요
	- **방안 2. 코난 검색 기반 매칭 (권장형)**: 부품 마스터를 코난에 색인, 동의어/형태소 사전으로 오타·약어 보정, 확장 부품명으로 코난 검색 TopK → Dify LLM이 컬러 매핑·후보 정리. 사용자 수정 데이터는 가중치로 반영.
		- 작업량: dify 내 LLM·분기 / dify 외 코난 색인·사전·S-MLD
		- 복잡도: 중 — 오타보정은 코난 형태소·동의어 사전이 강점, Dify는 매핑만
	- **방안 3. 로컬 유사도 API + Dify**: 부품명 매칭(RapidFuzz/임베딩)을 로컬 API로 구현, Dify는 호출·임계 분기·전송 담당.
		- 작업량: dify 내 적음 / dify 외 매칭 API
		- 복잡도: 중 — 유사도 알고리즘 튜닝을 코드로 관리
	- **코난 솔루션 활용**: 본 과제 핵심과 직결. 품명 오타·약어 보정에 코난 동의어/신조어/형태소 사전 + 유사도(키워드+벡터) 검색이 정통으로 부합. 부품 마스터를 코난 볼륨에 색인 후 v5/v6 search로 TopK 확보하고 relscore/threshold로 자동확정·후보제시 임계를 제어.
	- **권장 방안**: 방안 2 — 오타 보정·유사 매칭이 과제 핵심이며 코난 사전/검색이 이를 정통 지원. Dify는 임계 분기·매핑 정리·전송에 집중.
	- **권장 방안 (dify 단독)**: 방안 1 — Dify Code(RapidFuzz/임베딩 유사도)와 Knowledge로 부품 매칭·임계 분기를 코난 없이 구현하고 동의어 사전은 Code 내 dict 또는 Knowledge로 관리. 사전 규모가 커지면 코난 형태소·동의어 대비 관리 부담이 커지는 점만 유의.
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 변동 큼 — RapidFuzz를 못 쓰므로, ① 코난 방안 2(동의어/형태소 사전+유사검색)로 전환을 우선 권장, ② 코난 미사용 시 외부 유사도 API(방안 3), ③ 둘 다 불가하면 Code 노드에 순수 Python Levenshtein을 직접 구현(정확도·속도 제한 감수) + Knowledge 임베딩으로 보조. 의미 유사도는 Knowledge Retrieval로 가능하나 글자단위 오타 보정엔 임베딩이 약하므로 코난/외부 API 의존이 사실상 강제됨.

## 과제 12: 신규 프로젝트 금형 수축률 AI 추천
#고급 #회귀분석 #피처엔지니어링 #XGBoost #scikit-learn #교차검증 #모델해석 #SHAP #ML-API서빙 #Flask #콜드스타트
- **비즈니스 배경**: 플라스틱 부품(예: 도어트림)을 만들려면 금형을 설계해야 하는데, 플라스틱은 냉각될 때 수축하기 때문에 금형 설계 단계부터 '수축률'을 적용해야 합니다. 수축률을 잘못 잡으면 나중에 금형을 다시 깎아야 하는데 비용이 수천만 원에 달합니다. 지금은 숙련 엔지니어가 원소재 업체·재질·공장 등을 경험으로 판단해 수축률을 결정하지만, 신규 프로젝트마다 이 판단을 처음부터 반복해야 합니다.
- **핵심사항**
	- 원소재 업체, 재료, 생산 공장 등 과거 데이터를 기반으로 신규 프로젝트 시뮬레이션을 돌리기 전에 AI가 미리 최적의 금형 수축률을 추천해 주는 기능입니다.
	- 샘플 데이터: [[C:\Users\minji\Downloads\사양구성도 PNO_PNAME 조사_DR TRIM_정리.xlsx]]
- **액션 플랜**
	- 초기 양산 수축률뿐만 아니라 이후 품질 이슈로 인해 튜닝된 수축률 데이터까지 플랫폼에서 취합할 수 있는 방안을 기획하고, 이를 기반으로 추천 알고리즘을 적용합니다.
- **dify 구현 방안**
	- **방안 1. 검색+가중치 Workflow (dify 중심, 권장형)**: Start(아이템 메타 리스트) → Code(정규화) → HTTP/Knowledge(유사 수축률 이력 TopK 검색) → Code(품질이슈 평가결과·최신성 가중치 랭킹 보정) → LLM(수축률 추천+근거 생성) → HTTP(S-MLD). 검증완료 데이터는 별도 Workflow로 증분 적재.
		- 작업량: dify 내 워크플로우 + 가중치 Code / dify 외 수축률 이력 DB·S-MLD
		- 복잡도: 중 — 가중치 보정·증분 적재 로직이 핵심이나 표준 노드로 구성 가능
	- **방안 2. 코난 검색 + Dify 생성**: 수축률 이력을 코난에 색인(아이템 메타를 customfield), 유사 아이템 검색·필터는 코난, Dify는 가중치 보정 후 LLM 추천.
		- 작업량: dify 내 LLM·가중치 / dify 외 코난 색인·검색
		- 복잡도: 중 — 메타 기반 유사검색·customfield 필터를 코난이 지원
	- **방안 3. 로컬 ML 추천 API + Dify (데이터 축적 후)**: 데이터가 충분해지면 회귀/유사도 모델을 로컬 API로 학습·서빙, Dify는 호출·생성·전송 오케스트레이션.
		- 작업량: dify 내 적음 / dify 외 ML 학습·서빙 API
		- 복잡도: 상 — 데이터 축적·모델 학습 필요, 초기엔 과함
	- **코난 솔루션 활용**: 수축률 이력을 코난 RAG-X에 색인하고 타입·스펙·원소재업체 등을 customfield로 두어 유사 아이템 검색·userfilter 필터링 수행. 다만 정형 수치 위주라 벡터검색보다 메타 매칭·가중치 룰 비중이 큼. 추천 생성은 KonanLLM 모델로도 가능.
	- **권장 방안**: 방안 1 — 데이터가 정형 RDB이고 초기 볼륨이 적어 메타 매칭+가중치 룰이 가장 적합. 데이터 축적 후 방안 3(ML)으로 고도화하며, 검색단계는 코난 customfield 검색(방안 2)을 채택 가능.
	- **권장 방안 (dify 단독) [보정]**: 방안 3(외부 ML 결합) — 수축률은 본질적으로 수치 예측이므로 회귀 모델(scikit-learn/XGBoost)이 정답이며, Code 노드에서 학습·서빙이 어려워 외부 ML API가 필수. Dify는 아이템 메타를 정규화해 외부 ML API에 전달하고, 예측값을 받아 LLM으로 설명·근거를 생성한 뒤 S-MLD로 전송하는 오케스트레이터로 한정됨. → 'dify 단독'으로 예측 모델 자체를 구현하는 것은 부적절하며, 외부 ML과 결합하는 방식만 유효(외부 평가 표의 "회귀 모델 필요" 지적이 정당).
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 변동 큼(ML 단계) — 단순 가중치·통계 추천(콜드스타트)은 표준 Python(산술·정렬)만으로 Code 노드 구현 가능하나, 본격 ML 회귀(scikit-learn/XGBoost)는 Code 내 실행 불가하므로 방안 3(외부 로컬 ML API)이 필수화됨. 이 경우 Dify는 ML API 결과를 받아 LLM 설명·전송하는 오케스트레이터로 역할 한정.

- **비즈니스 배경**: 서연이화 설계팀에서는 같은 부품을 담당자마다 다르게 표기합니다(예: "DT K8 레프트", "도어트림K8좌측", "K8 Door Trim L"). 이렇게 제각각인 품명이 사양 구성도(S-SPC)에 쌓이면 검색·집계가 어렵고, 부품에 맞는 공법(조립 방식)을 추천하기도 어렵습니다. 표준 품명 규칙을 만들고 있지만 아직 20%만 완성됐고, 공법 데이터도 이제 막 쌓기 시작하는 단계입니다.
- **핵심사항**
	- 설계 담당자마다 다르게 텍스트로 치는 품명(예: DT K8 레프트)을 새롭게 제정할 표준 품명 규칙(예: K8_LH_V2)으로 자동 치환하고, 모호한 부품 공법 선택 기준을 과거 사용 빈도(예: 8대2 비율) 기반으로 추천합니다.
- **액션 플랜**
	- 고객사와 함께 현재 20%만 완성된 표준 품명 규칙을 확립하고 치환 엔진을 적용합니다. 공법 추천은 추후 상관 분석 및 회귀 분석을 통해 변수 가중치를 조절하는 방식으로 고도화를 검토합니다.
- **dify 구현 방안**
	- **방안 1. 사전+검색 정규화 Workflow (dify 중심)**: 13-1은 Start(입력 품명) → Code(약어/동의어 확장) → Knowledge/HTTP(정규 품명 마스터 유사검색 TopK) → LLM(표준 규칙 적용 정규품명 생성·설명) → HTTP(S-SPC). 13-2 공법은 검색+사용빈도 가중치 Code → LLM 추천.
		- 작업량: dify 내 워크플로우 / dify 외 품명·공법 마스터 DB·사전·S-SPC
		- 복잡도: 중 — 규칙 치환·유사검색·빈도 가중치 통계 결합 필요
	- **방안 2. 코난 검색 기반 (권장형)**: 정규 품명·공법 마스터를 코난 색인, 동의어/형태소 사전으로 입력 확장·키워드추출(kwdopt) 정규화, 유사검색 TopK + 사용빈도 customfield 가중치 정렬 → Dify LLM 정규화·추천.
		- 작업량: dify 내 LLM / dify 외 코난 색인·사전
		- 복잡도: 중 — 품명 정규화·동의어 처리가 코난 강점
	- **방안 3. 로컬 규칙엔진 API + Dify**: 표준 품명 규칙(정규식/매핑 테이블)을 로컬 API로 결정적 치환, 모호 케이스만 Dify LLM 보정.
		- 작업량: dify 내 적음 / dify 외 규칙 API
		- 복잡도: 중 — 규칙이 명확해지면 결정적 코드가 안정적
	- **코난 솔루션 활용**: 과제 11과 동일하게 동의어/형태소 사전+유사검색이 핵심. 정규품명·공법 마스터를 코난 볼륨에 색인하고 사용빈도 통계를 customfield로 두어 order by 가중치 정렬, 입력 품명은 코난 키워드추출(kwdopt)로 정규화.
	- **권장 방안**: 방안 2 — 표준 품명 규칙이 20%만 확립된 현 단계에선 동의어/유사검색(코난) 기반으로 시작하는 것이 현실적이며, 규칙이 확립되면 방안 3(결정적 치환)을 병행해 정확도를 높임.
	- **권장 방안 (dify 단독)**: 방안 1 — Dify Code(약어/동의어 확장)와 Knowledge 유사검색으로 정규화·공법 추천을 코난 없이 구현하고 사용빈도 가중치는 Code에서 통계 계산. 규칙 확립 후 방안 3(로컬 규칙 API)으로 결정적 치환 병행.
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 중간 변동 — 공법 통계(빈도·정렬)와 동의어 dict, 확립된 규칙의 정규식(re) 결정적 치환은 표준 Python으로 Code 노드 구현 가능. 다만 품명 퍼지매칭만 한계이므로 그 부분은 코난 방안 2(동의어/유사검색) 또는 Knowledge 임베딩 유사검색으로 대체.

## 과제 14: 원소재 업체 및 양산처 자동 맵핑
#중급 #HTML파싱 #LLM정보추출 #프롬프트엔지니어링 #구조화출력 #전자결재연동 #JSON
- **비즈니스 배경**: 도어트림에 쓸 원소재(원료 플라스틱 등)를 어느 협력사에서 살지가 확정되면, 그 결정 내용이 사내 전자결재 시스템에 HTML 형식의 짧은 승인 문서로 올라옵니다. 담당자는 이 문서를 보고 어떤 제품에 어떤 원소재 업체·양산 공장이 연결되는지를 직접 S-MLD 플랫폼에 입력합니다. 문서에 차종·품목·업체명이 조각조각 담겨 있어 정확히 어떤 제품과 매핑해야 할지 판단하기 쉽지 않습니다.
- **핵심사항**
	- 그룹웨어의 대내문(HTML) 제목과 간단한 표 정보만으로 어떤 제품의 원소재 공급 및 양산 업체인지를 추정하여 플랫폼에 자동으로 기입합니다.
- **액션 플랜**
	- 현재의 HTML 문서 내용만으로는 제품 매칭 정보가 부족할 위험이 크므로, 이메일 수신처나 추가 문맥 정보를 활용해 정확히 맵핑하는 규칙을 고객사와 심도 있게 사전 협의하여 확정합니다.
- **dify 구현 방안**
	- **방안 1. HTML 파싱 + LLM 추론 Workflow (dify 중심)**: Start(전자결재 조회조건) → HTTP Request(전자결재 API로 승인문서 조회) → Code(HTML 제목/본문/표 파싱) → LLM(차종·수신자·품목 종합해 협력사·양산처 매핑) → HTTP(S-MLD 전송).
		- 작업량: dify 내 워크플로우 + LLM / dify 외 전자결재 연동 API·S-MLD
		- 복잡도: 중 — HTML 파싱은 쉬우나 문맥 부족 보완·매핑 정확도 확보가 관건
	- **방안 2. RAG 보강 매핑 (권장형)**: 제품-업체 매핑 마스터·과거 승인문서를 코난/Knowledge에 색인, 대내문 키워드로 유사 과거사례 검색 후 LLM이 근거와 함께 매핑. 문맥 부족분을 검색으로 보강.
		- 작업량: dify 내 검색+LLM / dify 외 색인·전자결재 연동
		- 복잡도: 중 — 문맥 부족을 과거사례 검색으로 보완해 정확도 향상
	- **방안 3. 추출·분류 + 사용자 검증 루프**: Parameter Extractor/Question Classifier로 제목에서 차종·품목 추출 → 규칙 매핑 → 애매 시 S-MLD에서 사용자 검증.
		- 작업량: dify 내 추출·분류 / dify 외 검증 UI
		- 복잡도: 중 — 추출 정확도 한계로 사용자 검증 루프 필수
	- **코난 솔루션 활용**: 제품·원소재 업체 매핑 마스터와 과거 승인문서를 코난에 색인해 대내문 제목 기반 유사검색으로 매핑 후보·근거 제공. HTML 텍스트 추출은 코난 문서필터(DocAI)도 가능하나 단순 HTML은 Code 파싱으로 충분.
	- **권장 방안**: 방안 2 — 대내문(HTML)만으로는 정보가 부족한 것이 최대 리스크이므로 마스터·과거사례 검색으로 보강하는 RAG 방식이 정확도에 유리하며, 방안 3의 사용자 검증 루프를 결합해 오매핑을 방지.
	- **권장 방안 (dify 단독)**: 방안 1 + 방안 3 — Dify HTTP(전자결재 조회)→Code(HTML 파싱)→LLM(매핑)으로 코난 없이 완결하고, 문맥 부족 보완은 LLM 프롬프트와 사용자 검증 루프(방안 3)로 대체. 단 과거사례 검색 보강이 없어 매핑 정확도는 방안 2보다 낮을 수 있음.
	- **라이브러리 제약 시(Code 노드 설치 불가)**: 소폭 변동 — BeautifulSoup/lxml을 못 쓰므로 HTML 정밀 파싱 대신 ① 원문 HTML을 그대로(또는 re로 태그 제거한 텍스트를) LLM에 넣어 제품명·업체를 JSON으로 추출하거나 ② Parameter Extractor 노드로 추출. LLM 직접 추출 방식이라 오히려 라이브러리 의존이 낮아 영향이 작음.

**순위별 근거**
- **1위 · 과제 12**: LLM 프롬프트가 아닌 회귀 모델링(피처 엔지니어링·검증) 영역으로 유일하게 DS 스킬 요구. 데이터 성숙도에 종속(콜드스타트)되고 외부 ML API 결합이 필수라 dify 단독 불가. (외부표 2 M/M·고급)
- **2위 · 과제 6**: 7천~1만건 대용량이 성패 핵심 — 청킹 룰·메타데이터 볼륨·이슈타입/품명별 검색볼륨 설계가 난제. RAG 전반(색인→검색→재랭킹→생성) 설계 필요. (외부표 1.5 M/M·중고급)
- **3위 · 과제 3**: 100여 장 비정형의 분할요약→병합(맵리듀스)과 병합 시 품질 저하·환각 검증 부담. 전처리(OCR) 품질이 결과를 좌우하는 통제 밖 변수. 로직은 표준 노드로 가능하나 품질 안정화가 까다로움.
- **4위 · 과제 14**: 대내문(HTML)만으로 정보가 구조적으로 부족 → 매핑 정확도 확보가 본질적 난제. 문맥 추론·과거사례 검색 보강·사용자 검증 루프·고객 사전협의 의존.
- **5위 · 과제 11**: 핵심은 오타·약어 퍼지매칭 품질. 라이브러리 제약 시 코난/외부 의존으로 선회. 유사도 임계 분기·드롭박스 예외처리 UI 협의 필요.
- **6위 · 과제 13**: 표준 품명 규칙이 20%만 확립된 데이터 미성숙이 발목 — 규칙 확립이 선결. 품명 치환+공법 통계로 분해되어 개별 난이도는 중하.
- **7위 · 과제 2**: 반복 프로세스라 로직 난도는 낮으나 브라우저 자동화·OTP 로그인·사이트 변경 취약성 등 RPA 안정성이 변수(dify 밖 영역).
- **8위 · 과제 1**: 100% 룰베이스·LLM 불필요. 정책 6종+예외만 코드화하면 완결, 외부 의존은 권한통계 DB 조회뿐으로 가장 단순.

**난이도를 가른 3대 축**: ① AI 유형(룰<프롬프트<RAG<ML), ② 데이터 규모·성숙도(과제 6·12·13), ③ 통제 밖 외부 의존(과제 2 RPA, 3·6 OCR, 12 ML).

**순위별 근거**
- **1위 · 과제 12**: 뉴욕 택시비 예측(회귀)·생존 분석 실습이 수축률 회귀 모델과 직결된다. 피처 엔지니어링(원소재 업체·재질·공장·품질이슈 이력 결합)은 통계 전공 강점이 가장 강하게 발휘되는 구간이고, Flask 경험이 있어 ML 모델을 API로 서빙하는 외부 ML API 구축도 독립 수행 가능하다. "제조 도메인 수치 예측 ML"은 DA/DS 직군에서 희소하고 구체적인 포트폴리오가 된다. 단, 초기 데이터 부족(콜드스타트)이 리스크이므로 유사 이력 검색 방식을 병행하는 전략을 설계 단계에서 미리 잡아야 한다.
- **2위 · 과제 6**: 7천~1만 건 대용량의 청킹 전략·메타데이터 스키마·볼륨 분리가 성패를 좌우하는데, 이 데이터 설계 구간이 DA 배경이 직접 쓰이는 영역이다. RAG 파이프라인(색인→검색→생성) 전체를 Dify+코난으로 경험하므로 LLM·RAG 목표도 충족된다. 12(ML)와 6(RAG)를 함께 하면 DS 방향으로 전환할 때 두 가지 핵심 역량을 동시에 제시할 수 있다.
- **3위 · 과제 3**: Dify의 Document Extractor·Iteration·LLM·Knowledge 노드로 1~2일 내 설계 완료 가능. 분할요약 병합 패턴과 Knowledge 노드 구조를 여기서 익혀두면 복잡한 과제 6 설계 시간이 단축된다. 1주 4개 마감에서 가장 먼저 처리해야 할 워밍업 과제.
- **4위 · 과제 14**: HTML 파싱→LLM 추출의 단순한 흐름(HTTP Request→Code→LLM→HTTP)으로 Dify 노드 구성이 하루면 충분하다. ML·통계 강점이 살지 않아 커리어 가치는 낮지만, 1주 내 4개 과제 설계 완료를 위한 시간 완충 역할을 한다.
- **5위 · 과제 13**: 4번째 과제 후보. 공법 추천 단계의 빈도·상관분석에 통계 배경을 활용할 수 있어 14보다 커리어 가치는 높다. 단, 표준 품명 규칙 미완성(20%)이라는 고객사 의존 변수가 크고, 14에 비해 Dify 설계 복잡도도 높아 1주 마감이 빠듯해진다.
- **6위 · 과제 11**: 임베딩 유사도·퍼지매칭 NLP 경험이 가능하지만 4번째 과제로 선택 시 Dify 설계가 2~3일 소요되어 1주 마감을 위협한다. 또한 UI(드롭박스) 협의가 고객사 의존이라 설계 완결성이 낮을 수 있다.
- **7위 · 과제 2**: Dify 설계 자체는 단순하나 Playwright RPA·OTP 로그인이 실질 핵심 구현체다. Flask·Next.js 경험으로 개발 자체는 가능하지만, 완성 후에도 AI 포트폴리오로 보기 어렵고 ML·통계 강점이 전혀 쓰이지 않는다. 프로젝트 내 기여는 가능하나 커리어 연결성이 없다.
- **8위 · 과제 1**: 정책 1~6 룰베이스 엔진이라 LLM·ML이 없다. Dify 노드 구성이 가장 빠르지만(0.5일), 이력서에 AI 프로젝트로 기재할 수 없고 DA/DS 커리어와 가장 거리가 멀다.

**추천 순위를 가른 3대 기준**: ① 통계·ML 강점 활용도(회귀·피처 엔지니어링·데이터 설계 등 전공+실습 역량이 실제 작업에 쓰이는가), ② 포트폴리오 임팩트(제조 ML·대용량 RAG처럼 희소하고 구체적인 경험인가, 룰·RPA는 AI 경험으로 보기 어려움), ③ 1주 Dify 설계 완료 가능성(4개 과제 합산 노드 구성 시간이 5~7일 이내인가).

## 과제 12 준비 로드맵 (1주 선행 학습 권장)

### Step 1. 범주형 인코딩 + sklearn Pipeline ← 최우선 (Day 1~2)

```python
from sklearn.preprocessing import LabelEncoder, OneHotEncoder
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from xgboost import XGBRegressor

cat_cols = ['업체', '재질', '공법']   # 과제 12의 범주형 컬럼
num_cols = ['두께', '온도', '압력']   # 수치형 컬럼

preprocessor = ColumnTransformer([
    ('cat', OneHotEncoder(handle_unknown='ignore'), cat_cols),
    ('num', 'passthrough', num_cols)
])

pipeline = Pipeline([
    ('prep', preprocessor),
    ('model', XGBRegressor(n_estimators=300, max_depth=7))
])
pipeline.fit(X_train, y_train)
```

> **연습 방법**: 뉴욕 택시 데이터의 `passenger_count`, `dayofweek`을 일부러 범주형(`astype(str)`)으로 바꿔서 위 패턴을 적용해 보기.

### Step 2. K-fold CV (Python) ← R 경험 있으니 빠름 (Day 3)

```python
from sklearn.model_selection import cross_val_score, KFold

kf = KFold(n_splits=5, shuffle=True, random_state=42)
scores = cross_val_score(pipeline, X, y, cv=kf,
                         scoring='neg_mean_absolute_error')
print(f"CV MAE: {-scores.mean():.4f} ± {scores.std():.4f}")
```

> R의 `train(method='xgbTree', trControl=trainControl(method='cv', number=5))`와 동일한 개념 — 문법만 다름.

### Step 3. SHAP 모델 해석 (Day 4~5)

```python
import shap

# Pipeline에서 모델만 추출 후 SHAP
model = pipeline.named_steps['model']
X_transformed = pipeline.named_steps['prep'].transform(X_test)

explainer = shap.TreeExplainer(model)
shap_values = explainer(X_transformed)

shap.plots.waterfall(shap_values[0])   # 예측 1건 설명 (과제 12 핵심)
shap.summary_plot(shap_values, X_transformed)  # 전체 변수 중요도
```

> `plot_importance`는 "전체 학습에서 어떤 피처가 많이 쓰였나"이고,  
> SHAP는 "**이 예측값이 왜 X%인지**" 건별로 설명 — 과제 12의 LLM 설명 생성에 직결.

### Step 4. Flask API 서빙 ← 이미 경험 있음 (Day 6~7, 빠름)

```python
# 기존 Flask 경험 그대로 적용 — 구조만 추가
@app.route('/predict', methods=['POST'])
def predict():
    data = request.json                          # Dify HTTP Request 노드에서 호출
    df = pd.DataFrame([data])
    pred = pipeline.predict(df)[0]
    
    # SHAP 설명 추가
    X_t = pipeline.named_steps['prep'].transform(df)
    shap_val = explainer(X_t)
    top_features = sorted(
        zip(feature_names, shap_val.values[0]),
        key=lambda x: abs(x[1]), reverse=True
    )[:3]
    
    return jsonify({
        'prediction': round(float(pred), 4),
        'top_factors': [{'feature': f, 'impact': round(v, 4)}
                        for f, v in top_features]
    })
```

### Step 5. 콜드스타트·증분 적재 ← Dify 설계 병행 (설계 단계)

- **콜드스타트**: 신규 재질·업체 조합이면 → 코난 RAG로 유사 이력 검색 → 중앙값 디폴트값 fallback

- 이 두 가지는 코드 구현보다 **Dify 워크플로우 설계**에서 IF/ELSE 분기로 처리
