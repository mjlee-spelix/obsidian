# 서연이화 과제 업무로직 설계

> [!note] 이 문서의 레벨
> - **업무(비즈니스) 로직만** 적는다. 기술 스택·DB 스키마·알고리즘·라이브러리는 **쓰지 않는다** (아직 미정).
> - 목표는 "구현 명세"가 아니라 **"무엇이 정해져야 구현을 시작할 수 있는지 드러내기"**.
> - 모르는 건 억지로 채우지 말고 `❓`로 남긴다. **빈칸을 명확히 만드는 게 잘한 설계다.**
> - 스택·규칙이 정해지면 그때 별도 "구현 로직" 문서로 내려간다.

## 작성 템플릿 (과제마다 복제)

```
## 과제 N: (제목)
- **유형**: 룰베이스 / RPA / LLM·RAG / ML예측 / 유사도·통계  (중 하나)
- **한 줄 정의**: 무엇을 자동화/해결하는가

### 전제 · 범위 밖
- **전제**: 이 과제가 "참"이라고 가정하는 것 (예: 전처리 업체가 텍스트를 준다)
- **범위 밖**: 이 과제가 하지 않는 것 (예: OCR·문서 텍스트화는 우리 일이 아님)

### 흐름
- **입력**: 무엇이 들어오나
- **출력**: 무엇이 나가나

### 처리 단계
1. (단계) 무엇을 한다
2. (단계) 무엇을 한다
    - 이 단계에서 지킬 규칙·판단 (도메인 규칙이든 안전 결정이든 해당 단계 옆에)
3. ...
> 흐름이 두 갈래면 **[트랙 A]** / **[트랙 B]**로 나눠 각각 번호를 매긴다 (예: 적재/검색, 학습/추론).

### 공통 원칙 (전 단계 횡단)
- 특정 단계가 아니라 흐름 전체에 적용되는 안전 기본값 (멱등 · 격리 · 기록 · 롤백 등)

### 완료 기준
- 무엇으로 "잘 됐다"를 판단하나 (예: 오매핑률·검수 통과율·채택률 — 목표값은 고객사와 확정)

### 고객사 협의 사항
- [ ] 미정 항목 1
- [ ] 미정 항목 2
```

> **이 문서의 본체는 ① 처리 단계(단계별 흐름 + 단계 옆 규칙·결정), ② 공통 원칙, ③ 고객사 협의 사항.** 흐름·전제·완료 기준은 맥락용.
> - '공통 원칙'과 단계 옆 안전 결정은 전부 **"더 안전한 쪽 기본값"**(멱등·격리·기록)이라 규칙이 뭐가 되든 후회 없는 것만 적는다.
> - '전제·범위 밖'과 '완료 기준'은 세부는 고객 요청에 따라 바뀌지만, **경계와 평가 축을 미리 잡아두면 나중에 파악이 빠르다.**
> - 지금 정하지 말 것: 구체적 임계값, 고객사 규칙 내용, 기술 스택, 유형의 완결된 목록.

## 과제 1: 인사 정보 기반 권한 자동 맵핑  (예시)
- **유형**: 룰베이스 (AI 불필요)
- **한 줄 정의**: 인사 이동 정보를 받아 업무 시스템의 사용자 권한을 자동으로 바꿔준다.

### 전제 · 범위 밖
- **전제**: 그룹웨어가 인사 변동을 일배치로 안정적으로 내려준다 / 권한 부여 정책은 고객사가 정의해 제공한다
- **범위 밖**: 권한 정책 자체의 수립(고객사 몫), 인사 데이터의 생성·정정(그룹웨어 영역)

### 흐름
- **입력**: 그룹웨어의 인사 변동 정보 (입사 / 부서이동 / 승진 / 퇴사)
- **출력**: 업무 시스템 사용자 권한 변경 + 변경 내역 기록

### 처리 단계
1. 배치로 인사 변동 정보 수집 (마지막 처리 이후 증분만)
2. 사번·부서코드 검증
    - 처리 불가 데이터(부서코드 미존재·사번 불일치 등)는 버리지 말고 격리 후 사람 확인
3. 변동 유형 분류 (입사 / 이동 / 승진 / 퇴사 …)
    - 유형은 확장 가능하게, 모르는 유형이 오면 자동 변경 말고 보류
4. 정책표로 목표 권한 계산
    - 입사 → 부서 기본 권한 / 이동 → 이전 회수 + 신규 부여 / 승진 → 직급 권한 조정 / 퇴사 → 전체 회수
    - 정책은 표(데이터)로 외부화 — 규칙·예외가 와도 코드 수정 없이 행 추가
5. 업무 시스템에서 현재 권한 조회 → 목표와 Diff 산출 (목표 − 현재 = 부여/회수, 공통 권한은 안 건드림 → 순서 사고 방지·멱등)
6. 권한 변경 적용 — 부분 실패 시 성공분은 반영, 실패분만 재시도

### 공통 원칙 (전 단계 횡단)
- 모든 권한 변경은 전/후 값 + 적용 근거를 기록 (보안·감사 대상)

### 완료 기준
- 인사 변동과 실제 권한 상태가 일치 (미회수·오부여 권한 0건이 목표) / 모든 변경이 근거와 함께 추적 가능

### 고객사 협의 사항
- [ ] 부서·직급별 **권한 부여 기본 정책표** (이게 사실상 과제의 80%)
- [ ] 예외 케이스: 신설 부서, 1인 부서, 겸직, 같은 날 복수 발령(이동+승진) 등은 어떻게?
- [ ] 정보를 **받은 날**과 실제 **발령일**이 다를 때 어떻게? (받자마자 변경 vs 발령일에 맞춰 변경)
- [ ] 잘못된 변경이 났을 때 되돌리는 방법 / 책임 주체
- [ ] 인사 데이터를 **어떤 형태·경로**로 받나 (그룹웨어 연동 방식)

## 과제 2: 현대차 포털 단가 조회 자동화 (매크로)
- **유형**: RPA (웹 자동화)
- **한 줄 정의**: 매일 사람이 포털에서 단가 조회 → 엑셀 정리 → 업로드하는 반복 작업을 자동화.

### 전제 · 범위 밖
- **전제**: 포털 계정·접근 권한이 제공된다 / 미결 품목·단가가 포털에서 조회 가능하다
- **범위 밖**: 단가 협상·결정(우리는 조회·전달만), 포털 자체 운영

### 흐름
- **입력**: (자동화가 대신 수행할) 포털 로그인 → 미결 품목 조회
- **출력**: 자사 플랫폼에 단가 일괄 등록

### 처리 단계
1. 스케줄 트리거 (수동 재실행 진입점도 함께)
2. 포털 로그인 — 로그인 성공 확인 후에만 다음 단계 진행
    - 자격증명은 코드에 박지 않고 별도 안전 보관 (OTP 등 추가 인증 처리)
3. 미결 품목 조회 → 단가 스크래핑
    - 미결 품목만 대상
    - 화면에서 데이터를 읽는 기준(셀렉터)은 한곳에 모아 관리 — 화면 바뀌어도 한 곳만 수정
    - 추출 0건이면 "미결 없음"인지 "스크래핑 실패"인지 구분 — 애매하면 자동 진행 말고 알림
4. 파싱·정규화 (통화·단위·날짜 표기를 자사 기준으로 통일)
5. 검증
    - 이미 올린 품목(품번+조회일 기준)은 중복 제거, 단가 달라진 것만 갱신
    - 음수·비정상 자릿수 등 이상치는 등록 전 걸러내 따로 표시
6. 자사 시스템에 일괄 등록
7. 결과·예외 리포트 (실행 로그·실패 단계·증빙 스크린샷)

### 공통 원칙 (전 단계 횡단)
- 조용한 실패 금지 — 실패 시 즉시 알림 (RPA는 "조용한 실패"가 가장 위험)

### 완료 기준
- 수작업 대비 누락·오기 없이 자동 등록 / 사람 개입 시간 단축, 실패 시 100% 알림

### 고객사 협의 사항
- [ ] 포털 **로그인 방식** (OTP·추가 인증 있나?) ← 최대 난관
- [ ] 실행 **주기 / 시각**
- [ ] 단가 외에 같이 가져와야 할 항목은?
- [ ] 포털 화면이 바뀌면 누가 유지보수하나
- [ ] 실패 시 알림 대상·방법

## 과제 3: 기술 표준 문서 LLM 요약 및 비교
- **유형**: LLM
- **한 줄 정의**: 두꺼운 기술 표준 문서를 시험 항목 위주로 요약하고, 구버전↔신버전 차이를 비교.

### 전제 · 범위 밖
- **전제**: 전처리 업체가 문서를 텍스트로 변환해 준다 / 비교 대상 두 버전이 모두 확보된다
- **범위 밖**: OCR·문서 텍스트화(전처리 업체), 표준 문서 자체 작성

### 흐름
- **입력**: (전처리 업체가 텍스트화한) 기술 표준 문서
- **출력**: 요약된 시험 리스트 + 버전 차이 리포트

### 처리 단계
**[요약 — 문서 등록 시]**
1. 전처리된 문서 텍스트 수신
2. 긴 문서를 의미 단위(장/절·표 보존)로 분할
3. 각 부분에서 시험 항목을 구조화 추출 (시험명·기준·조건)
    - 자유 요약이 아니라 정해진 항목으로 뽑음
    - 각 항목이 원문 어디(페이지)에서 나왔는지 함께 표기 — 못 찾으면 "검토 필요"
4. 부분 결과 병합 → 시험 리스트 확정
5. 신뢰 낮은 항목은 자동 등록 말고 사람 검수로 분리

**[버전 비교 — 필요 시]**
> 두 버전 각각 [요약]을 거친 시험 리스트가 있다고 전제
1. 두 버전의 시험 항목을 항목명 기준으로 짝지음
2. 짝지어진 항목의 기준값 차이 분석
    - 한 버전에만 있으면 추가/삭제로 판정
    - 표현만 바뀐 것과 실제 기준값 변경을 구분 (표현 변경은 변경 아님)
3. 변경점 리포트 생성

### 공통 원칙 (전 단계 횡단)
- 어느 문서·버전을 언제 처리했는지 이력 기록

### 완료 기준
- 요약된 시험 항목이 원문과 일치(검수 통과율) / 버전 차이를 누락 없이 도출

### 고객사 협의 사항
- [ ] **요약 결과 항목 정의** (무엇을 뽑아야 "쓸모 있는 요약"인가)
- [ ] 전처리 업체(한국딥러닝) 텍스트 **품질·형식** 확인 (결과의 90% 좌우)
- [ ] 비교 단위: 문서 전체? 항목별?
- [ ] 틀린 요약이 섞이면 안 되는데, 사람 검수 단계를 둘 것인가

## 과제 6: 과거 대책서 기반 유사 사례 검색 및 대책 생성 (RAG)
- **유형**: LLM·RAG (데이터 규모 최대)
- **한 줄 정의**: 현상·원인을 입력하면 유사한 과거 대책서를 찾아 새 대책 보고서를 만들어준다.

### 전제 · 범위 밖
- **전제**: 과거 대책서가 텍스트로 전처리돼 있다 / 대책서 공통 구조(현상·원인·대책 등)가 합의돼 있다
- **범위 밖**: 대책의 실제 적용·실행, 전처리·OCR

### 흐름
- **입력**: 사용자가 입력한 "현상" + "원인"
- **출력**: 구조화된 대책 보고서 (근거 사례 포함)

### 처리 단계
**[사전 적재 — 일괄·주기적]**
1. 과거 대책서 텍스트 확보 (전처리 결과)
2. 현상/원인/대책 항목으로 분해 + 메타(품명·연도) 부착
    - 양식 일정하면 규칙 파싱, 불규칙하면 LLM 추출
3. 검색 단위로 쪼개 의미 벡터화 후 저장

**[검색·생성 — 매 요청]**
1. 사용자 현상·원인 입력
2. 동의어·약어 확장으로 질의 정제
3. 의미 + 키워드로 유사 사례 검색 → 상위 N건 선별
    - 원인 있으면 현상+원인으로 좁히고, 현상만 있으면 후보 원인 제시
    - 품명·이슈 타입으로 검색 범위를 좁힘
    - 검색 0건이면 자동 진행 말고 "없음" 반환
4. 선별 사례를 근거로 LLM이 대책 보고서 작성
    - 검색된 근거 안에서만 생성 (없는 얘기 지어내지 않기)
    - 참조한 과거 사례 ID를 함께 표기
5. 사람 검토·채택
    - 채택 여부 기록 → 향후 검색 품질 개선

### 공통 원칙 (전 단계 횡단)
- 외부 연동(수신·전송)은 재시도·멱등
- 초기 대량 적재와 이후 증분 적재를 분리

### 완료 기준
- 생성 대책의 사람 채택률 / 유사 사례 검색 적중률

### 고객사 협의 사항
- [ ] 대책서의 **공통 구조(현상/원인/대책 등)** 정의 ← 선행 과제
- [ ] 7천~1만 건 데이터의 **상태·품질** (얼마나 정형화돼 있나)
- [ ] "유사하다"의 기준 (품명별? 이슈 타입별로 나눠 검색?)
- [ ] 생성된 대책 보고서의 **출력 양식**
- [ ] 결과를 사람이 검토·채택하는 절차

## 과제 11: 컬러 사양표 자동 입력 및 품명 오타 보정
- **유형**: 유사도·정규화
- **한 줄 정의**: 컬러 사양표의 값을 자동 입력하되, 품명에 오타가 있어도 올바른 부품에 연결.

### 전제 · 범위 밖
- **전제**: 전처리로 사양표가 텍스트화돼 있다 / 사내 부품 마스터가 존재한다
- **범위 밖**: 부품 마스터 자체 관리, 컬러 값의 옳고 그름(정확성) 판단

### 흐름
- **입력**: (비정형) 컬러 사양표 + 사내 부품 마스터
- **출력**: 부품별 컬러 값 자동 기입 / 애매하면 사용자가 고를 후보 제시

### 처리 단계
1. 사양표 파싱 — "부품명 행 ↔ 컬러 열" 구조 인식
2. 품명 정규화 (대소문자·공백·약어·방향표기 통일)
    - 동의어·별칭 사전은 코드가 아닌 데이터로 외부화 (과제 13과 공유)
3. 부품 마스터와 매칭 → 후보 + 점수 산출
    - 오타는 글자 유사도로, 영↔한·약어 별칭은 의미 유사도로 — 둘 다 본다
4. 점수로 3분기: 고신뢰=자동 입력 / 애매(예: 85%)=후보 제시 / 저신뢰=보류
    - 오매핑 비용이 크므로 자동확정 기준은 보수적으로 시작
5. 컬러 값–부품 매핑 구성 (한 부품에 여러 컬러 오는 경우 예외 처리)
6. 시스템 기입 (애매분은 후보 리스트 동봉 → 사용자 선택)
7. 사용자 확정을 사전에 반영 → 다음부터 자동확정 (피드백 루프)

### 공통 원칙 (전 단계 횡단)
- 매핑 근거(점수·후보)를 함께 기록

### 완료 기준
- 부품 매핑 오매핑률이 목표 이하 / 자동확정 비율 대비 수작업 보정 비율

### 고객사 협의 사항
- [ ] **자동확정 / 사용자선택 / 보류**를 가르는 기준 (몇 %?)
- [ ] 사용자 선택 UI를 둘지, 둔다면 후보 몇 개·어떤 형태(드롭박스)?
- [ ] 사양표 **양식이 고객사마다 다른가**
- [ ] 동의어·별칭(영↔한 등) 정리 책임 주체

## 과제 12: 신규 프로젝트 금형 수축률 AI 추천
- **유형**: ML 예측 (회귀)
- **한 줄 정의**: 재료·업체·공장 등 과거 데이터로 신규 프로젝트의 최적 수축률을 추천.

### 전제 · 범위 밖
- **전제**: 과거 수축률 이력이 학습 가능한 형태로 확보된다 / 입력 변수가 정의돼 있다
- **범위 밖**: 실제 금형 설계·시뮬레이션(우리는 추천값 제공), 데이터 생성

### 흐름
- **입력**: 신규 프로젝트 조건 (원소재 업체·재질·공법·공장 등)
- **출력**: 추천 수축률 + 근거 설명

### 처리 단계
> ML은 트랙이 둘 — **학습(모델 만들기)** 과 **추론(모델 쓰기)**. 깊은 개발 디테일은 [[서연이화 과제12 ML 개발 프로세스.md]] 참고.

**[학습 / 오프라인 — 1회 + 주기적]**
1. 수축률 이력 수집 (초기 양산값 + 품질 튜닝값)
    - 품질 이슈로 튜닝된 값을 초기 양산값보다 신뢰도 높게 봄
2. 결측·이상치·표기 흔들림 정리
3. 입력 변수를 모델 입력 형태로 변환
4. 회귀 모델 학습
5. 검증 → 성능·변수 기여도 분석 (성능 미달이면 2~3단계로 돌아가 반복)
6. 기준 통과 시 배포

**[추론 / 온라인 — 매 요청]**
1. 신규 조건 입력
2. 학습과 동일하게 변수 변환
3. 학습 근거 충분하면 모델 예측 / 부족하면 유사 사례·통계 대체값
    - "모델 예측인지 대체값인지" 결과에 표기
4. 추천값 + 근거 변수 산출 (단일 값 아닌 범위/신뢰 구간과 함께)
5. LLM이 수치·근거를 엔지니어용 설명문으로 변환 (수치는 모델 결과 그대로)

**[재학습 루프]**
1. 트리거: 신규 데이터 누적 **또는** 예측 성능 저하(드리프트) 감지 시
2. 검증된 데이터만 학습에 투입 (라벨 신뢰·이상치 제거)
3. 신·구 모델을 **같은 검증 기준**으로 비교
4. 나아질 때만 교체 + 실전에서 나쁘면 롤백

### 공통 원칙 (전 단계 횡단)
- 모델 버전 관리: 어느 버전이 어떤 예측을 냈는지 기록

### 완료 기준
- 추천값과 실제 적용값의 오차 / 엔지니어 채택률

### 고객사 협의 사항
- [ ] 예측에 쓸 **입력 변수 목록** (무엇이 수축률에 영향을 주나)
- [ ] 과거 수축률 데이터를 **몇 건·어떤 형태로** 확보 가능한가 ← 모델 성패 좌우
- [ ] 튜닝된 수축률 데이터를 **앞으로 어떻게 모을지** (수집 경로 기획)
- [ ] "추천 근거"를 어디까지 보여줘야 엔지니어가 신뢰하나
- [ ] 데이터 부족 초기엔 어떻게 운영할지 (콜드스타트)

## 과제 13: 표준 품명 규칙 치환 및 공법 추천
- **유형**: 룰베이스 + 통계 (두 갈래)
- **한 줄 정의**: 제각각인 품명을 표준 규칙으로 치환하고, 모호한 공법 선택을 과거 빈도로 추천.

### 전제 · 범위 밖
- **전제**: 표준 품명 규칙이 (점진적으로) 확립된다 / 공법 사용 이력이 누적돼 있다
- **범위 밖**: 표준 규칙 제정 권한(고객사), 공법의 기술적 적합성 판단

### 흐름
- **입력**: 자유 표기 품명 (예: "DT K8 레프트") / 공법 선택 대상 부품
- **출력**: 표준 품명 (예: K8_LH_V2) / 추천 공법 + 비율 근거

### 처리 단계
**[품명 표준화]**
1. 입력 품명 정규화 (약어·동의어·방향표기 통일)
    - 정규화·동의어 사전은 과제 11과 공유
2. 확립된 표준 규칙에 맞으면 규칙대로 치환
    - 규칙(패턴→표준형)은 코드가 아닌 데이터로 둠 → 규칙 확립될수록 행 추가만
3. 규칙에 안 맞으면 정규품명 마스터와 유사 매칭 → 후보 제시 (자동 확정 아님)
4. 표준 품명 확정 + 변환 근거

**[공법 추천]**
1. 대상 부품(군) 식별 (표본 적으면 개별 부품 아닌 부품군 단위로 집계)
2. 유사 부품군의 공법 사용 이력 집계
3. 단순 빈도가 아니라 최근성·결과 양호 여부를 가중해 정렬
    - 빈도 가중치는 외부화 (나중에 상관·회귀로 고도화할 여지)
4. 상위 공법 추천 + 근거(비율·표본 수) 제시, 표본 적으면 "사례 N건 기준"
    - 추천은 강제 아닌 제안

### 공통 원칙 (전 단계 횡단)
- 사용자 선택을 이력에 적재 (피드백 루프)

### 완료 기준
- 표준 치환 정확도 / 공법 추천 채택률

### 고객사 협의 사항
- [ ] **표준 품명 규칙 확립** (현재 20%만 완성) ← 선행 과제
- [ ] 공법 추천에 쓸 **과거 사용 이력 데이터** 확보 여부
- [ ] 추천이지 강제가 아님 — 사용자가 다른 선택 가능한가
- [ ] 품명 정규화 사전을 과제 11과 공유할지

## 과제 14: 원소재 업체 및 양산처 자동 맵핑
- **유형**: LLM 추출 + 검증
- **한 줄 정의**: 전자결재 HTML 문서만 보고 제품의 원소재 업체·양산처를 추정해 자동 기입.

### 전제 · 범위 밖
- **전제**: 전자결재 대내문을 수신·조회할 수 있다 / 과거 제품–업체 매핑 데이터가 있다
- **범위 밖**: 업체 선정·계약(우리는 추정·기입만), HTML 외 정보원 수집

### 흐름
- **입력**: 그룹웨어 대내문 (HTML 제목 + 간단한 표)
- **출력**: 제품–원소재업체–양산처 매핑 (애매하면 사용자 검증)

### 처리 단계
1. 전자결재에서 대상 승인문서 조회 (문서 ID 기준 중복 처리 방지)
2. HTML 파싱 — 제목·표·본문 분리
3. 정보 추출: 차종·품목·원소재업체·양산처를 구조화
    - 문서에 없는 값은 비워둠(null) — "추출 실패"와 "정보 없음"을 구분, 지어내지 않음
4. 문맥 보강: 수신처·기안 부서·과거 매핑 이력으로 부족분 추정
5. 매핑 후보 + 신뢰도 산출
    - 후보가 여러 개면 신뢰도와 함께 모두 제시
6. 신뢰도 분기: 고신뢰=자동 기입 / 나머지=사람 검증
    - 정보 부족 리스크가 크므로 자동확정 기준 높게, 검증 루프 비중 크게 시작
7. 시스템에 기입
8. 사용자가 고친 매핑을 과거 매핑·보강 규칙에 반영 (피드백 루프)

### 공통 원칙 (전 단계 횡단)
- 추출·매핑 결과가 문서 어디(제목/표/수신처)에서 나왔는지 근거 표기

### 완료 기준
- 매핑 정확도(검증 후 수정률) / 자동확정 비율

### 고객사 협의 사항
- [ ] HTML 문서만으로 **정보가 충분한가** (가장 큰 리스크)
- [ ] 부족분을 보강할 **단서**(수신처·기안 부서·과거 매핑)를 쓸 수 있나 ← 핵심 협의 사항
- [ ] 자동확정 vs 검증 비율을 어떻게 시작할지
- [ ] 대상 문서를 어떻게 식별·수신하나
