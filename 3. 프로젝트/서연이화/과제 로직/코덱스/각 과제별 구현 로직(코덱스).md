# 각 과제별 구현 로직

## 작성 기준

- 개발 솔루션과 기술 스택이 확정되지 않은 상태를 전제로 작성한다.
- 특정 솔루션명, 특정 개발 언어, 특정 DB 제품명에 종속되지 않는 구조로 설계한다.
- 각 과제의 구현 로직은 `입력 수집 -> 전처리 -> 핵심 처리 -> 검증 -> 저장/전송 -> 운영 관리` 흐름을 기본 골격으로 한다.
- 코드블록 안의 `★`는 해당 과제의 핵심 구현 작업을 의미한다.
- 세부 설명에서는 핵심 구현 작업을 굵게 표시한다.

## 과제 1. 인사 정보 기반 권한 자동 맵핑

### 비즈니스 배경

직원이 입사, 퇴사, 부서 이동, 직무 변경을 할 때마다 담당자가 업무 시스템 권한을 수동으로 변경해야 한다. 이 작업이 지연되면 필요한 권한이 없는 직원과 더 이상 권한을 보유하면 안 되는 직원이 동시에 발생한다. 따라서 인사 변동 정보를 기준으로 권한을 자동 부여·회수하는 체계가 필요하다.

### 핵심사항

- 인사 변동 데이터를 일 단위 또는 이벤트 단위로 수집한다.
- 부서, 직급, 직무, 재직 상태, 예외 권한을 기준으로 권한 정책을 적용한다.
- 권한 변경 전후 이력을 남기고, 자동 처리 불가 건은 담당자 검토 대상으로 분리한다.

### 액션 플랜

- 인사 데이터 항목과 업무 시스템 권한 항목을 매핑한다.
- 권한 부여·회수 정책과 예외 케이스를 룰 테이블로 정의한다.
- 자동 권한 변경 로직, 검증 로직, 승인·감사 이력 로직을 구현한다.

### 전체 프로세스

```text
인사 변동 데이터 수집 -> 데이터 정합성 검증 -> 기존 권한 조회 -> ★ 권한 정책 룰 적용 -> 변경안 생성 -> 충돌·예외 검증 -> 권한 변경 실행 -> 변경 이력 저장 및 알림
```

### 단계별 구현 로직

1. 인사 변동 데이터 수집
   - 인사 시스템에서 신규 입사, 부서 이동, 직급 변경, 휴직, 퇴사 데이터를 수집한다.
   - 사번, 이름, 부서코드, 직급, 직무, 재직상태, 발령일자를 필수 항목으로 둔다.
   - 같은 사용자의 변동이 하루에 여러 번 발생할 수 있으므로 발령일자와 처리순서를 함께 관리해야 한다.

2. 데이터 정합성 검증
   - 사번 누락, 부서코드 미등록, 직급 코드 불일치, 퇴사자 재활성화 같은 오류를 검증한다.
   - 오류 데이터는 자동 처리하지 않고 별도 예외 큐에 적재한다.
   - 인사 데이터와 업무 시스템 사용자 마스터의 사용자 식별자가 다를 수 있으므로 식별자 매핑 테이블이 필요하다.

3. 기존 권한 조회
   - 현재 사용자가 보유한 메뉴 권한, 역할 권한, 임시 권한, 예외 권한을 조회한다.
   - 부서 이동 시 기존 부서 권한을 전부 회수할지, 공통 권한은 유지할지 정책을 구분해야 한다.

4. **권한 정책 룰 적용**
   - 부서·직무·직급별 기본 권한 룰을 적용한다.
   - 신규 입사자는 기본 권한 부여, 부서 이동자는 기존 부서 권한 회수 후 신규 부서 권한 부여, 퇴사자는 전체 권한 회수로 처리한다.
   - 1인 부서, 겸직, 프로젝트성 임시 권한, 임원 예외 권한은 별도 룰로 분리한다.
   - 룰은 코드에 하드코딩하지 않고 정책 테이블 또는 설정 파일로 관리해야 운영 중 변경이 쉽다.

5. 변경안 생성 및 충돌 검증
   - 현재 권한과 목표 권한을 비교해 추가 권한, 회수 권한, 유지 권한을 산출한다.
   - 동일 사용자가 상충되는 역할을 동시에 보유하는지 검증한다.
   - 고위험 권한은 자동 반영 전 승인 대상에 포함한다.

6. 권한 변경 실행
   - 업무 시스템 권한 변경 인터페이스를 통해 변경안을 반영한다.
   - 일부 권한 변경 실패가 전체 처리 실패로 번지지 않도록 사용자 단위 또는 권한 단위 재처리 구조를 둔다.

7. 변경 이력 저장 및 알림
   - 변경 전 권한, 변경 후 권한, 적용 룰, 처리자, 처리시간, 실패 사유를 저장한다.
   - 자동 처리 결과를 권한 담당자에게 요약 알림으로 제공한다.

## 과제 2. 현대차 업무 포털 단가 조회 자동화

### 비즈니스 배경

담당자가 외부 공급사 포털에 접속해 미결 품목의 단가를 조회하고, 결과를 정리해 사내 시스템에 업로드하는 반복 업무를 수행하고 있다. 품목 수가 증가할수록 수작업 시간이 늘고, 조회 누락이나 입력 오류가 발생할 수 있다.

### 핵심사항

- 외부 포털 로그인, 검색, 다운로드 또는 화면 조회 과정을 자동화한다.
- 조회 결과에서 품번, 품명, 단가, 적용일자, 상태값을 추출한다.
- 사내 시스템 업로드 전 중복·누락·형식 오류를 검증한다.

### 액션 플랜

- 포털 화면 흐름과 로그인 정책을 분석한다.
- 미결 품목 조회 조건과 결과 화면 또는 파일 형식을 표준화한다.
- 자동 조회, 결과 파싱, 검증, 업로드, 실패 재처리 로직을 구현한다.

### 전체 프로세스

```text
조회 대상 품목 수집 -> 포털 로그인 -> ★미결 품목 자동 조회·결과 수집 -> 파일/화면 데이터 파싱 -> 단가 데이터 정규화 -> 중복·누락 검증 -> 사내 시스템 업로드 -> 실행 로그 및 실패 재처리
```

### 단계별 구현 로직

1. 조회 대상 품목 수집
   - 사내 시스템에서 단가 미확정 품목 목록을 수집한다.
   - 품번, 업체코드, 차종, 프로젝트, 이전 조회일자, 현재 상태를 기준으로 조회 우선순위를 정한다.
   - 이미 확정된 품목이 다시 조회되지 않도록 상태값을 관리한다.

2. 포털 로그인 및 세션 관리
   - 계정 인증, 추가 인증, 세션 만료, 비밀번호 변경 안내 등 예외 화면을 처리한다.
   - 로그인 실패 횟수를 제한하고, 실패 사유를 별도 로그로 남긴다.
   - 외부 포털 화면 구조가 바뀔 수 있으므로 화면 요소 식별자를 설정화해야 한다.

3. **미결 품목 자동 조회·결과 수집**
   - 품번 또는 조회 조건을 입력해 미결 단가 정보를 조회한다.
   - 결과가 파일로 제공되면 다운로드하고, 화면 표로만 제공되면 화면 데이터를 추출한다.
   - 조회 결과가 여러 페이지로 나뉘는 경우 페이지 이동 로직과 마지막 페이지 판별 로직을 구현한다.

4. 파일/화면 데이터 파싱
   - 품번, 품명, 단가, 통화, 적용일자, 확정여부, 비고를 추출한다.
   - 금액의 쉼표, 통화 기호, 공백, 날짜 형식 차이를 정규화한다.
   - OCR이 필요한 화면 캡처 방식은 인식 오류가 생길 수 있으므로 신뢰도 점수와 원본 이미지를 함께 보관한다.

5. 단가 데이터 검증
   - 품번이 조회 대상 목록에 있는지 확인한다.
   - 단가가 0 또는 음수인지, 적용일자가 비정상인지, 동일 품번에 복수 단가가 있는지 검증한다.
   - 전일 조회 결과와 비교해 급격한 단가 변동이 있으면 검토 대상으로 분리한다.

6. 사내 시스템 업로드
   - 검증 완료 건만 사내 시스템에 전송한다.
   - 업로드 성공, 중복, 실패, 부분 성공 상태를 구분해 저장한다.
   - 동일 품번이 중복 업로드되지 않도록 멱등키를 사용한다.

7. 실행 로그 및 재처리
   - 조회 시작·종료 시간, 조회 건수, 성공 건수, 실패 건수, 실패 화면 캡처를 저장한다.
   - 포털 장애와 데이터 오류를 구분해 재처리 방식을 다르게 적용한다.

## 과제 3. 기술 표준 문서 요약 및 비교

### 비즈니스 배경

완성차 업체가 제공하는 기술 표준 문서는 문서당 분량이 많고 개정도 반복된다. 담당자는 시험 항목, 합격 기준, 변경 사항을 직접 읽고 정리해야 하므로 시간이 많이 걸리고 누락 위험도 크다.

### 핵심사항

- 비정형 문서에서 시험 항목, 기준값, 조건, 단위, 개정 이력을 구조화한다.
- 긴 문서를 한 번에 처리하지 않고 구간별 요약 후 최종 요약으로 병합한다.
- 이전 버전과 최신 버전의 변경점을 항목 단위로 비교한다.

### 액션 플랜

- OCR 또는 문서 추출 결과를 표준 텍스트 구조로 변환한다.
- 문서를 제목, 표, 시험 항목, 부록 단위로 분할한다.
- 요약·비교 결과를 검증 가능한 근거 위치와 함께 저장한다.

### 전체 프로세스

```text
문서 수집 -> 텍스트 추출·정제 -> 문서 구조 분석 -> ★청크 분할 및 항목별 요약 -> 요약 병합 -> 버전 간 변경점 비교 -> 근거 검증 -> 표준 결과 저장·전송
```

### 단계별 구현 로직

1. 문서 수집 및 메타데이터 등록
   - 문서명, 문서번호, 고객사, 차종, 부품군, 버전, 개정일자를 등록한다.
   - 동일 문서의 버전 관계를 추적할 수 있도록 원문 문서 식별자와 개정 식별자를 분리한다.

2. 텍스트 추출·정제
   - PDF, PPT, 이미지 문서에서 텍스트와 표 데이터를 추출한다.
   - 머리말, 꼬리말, 페이지 번호, 워터마크처럼 요약에 불필요한 반복 문구를 제거한다.
   - OCR 오류가 잦은 단위, 수치, 특수기호는 원문 좌표 또는 원문 이미지와 함께 보관해야 한다.

3. 문서 구조 분석
   - 목차, 제목, 소제목, 표 제목, 시험 조건, 판정 기준을 구분한다.
   - 표는 행·열 의미가 손상되면 요약 품질이 급격히 떨어지므로 텍스트 본문과 별도로 구조화한다.

4. **청크 분할 및 항목별 요약**
   - 문서를 시험 항목 또는 제목 단위로 분할한다.
   - 각 청크에서 시험명, 목적, 조건, 장비, 샘플 수, 기준값, 합격·불합격 조건을 추출한다.
   - 청크마다 원문 페이지, 제목, 표 번호를 함께 남겨 최종 결과의 근거 추적이 가능해야 한다.

5. 요약 병합
   - 청크별 요약을 시험 항목 기준으로 병합한다.
   - 같은 시험이 여러 곳에 반복되면 최신 기준 또는 더 구체적인 기준을 우선 적용한다.
   - 서로 충돌하는 수치 기준이 발견되면 자동 확정하지 않고 검토 대상으로 표시한다.

6. 버전 간 변경점 비교
   - 이전 버전과 최신 버전의 시험 항목을 매칭한다.
   - 신규 추가, 삭제, 기준값 변경, 조건 변경, 문구 변경을 구분한다.
   - 변경점은 "무엇이 바뀌었는지", "업무상 영향이 무엇인지", "확인해야 할 항목이 무엇인지"로 정리한다.

7. 근거 검증 및 저장
   - 요약·비교 결과마다 원문 위치를 연결한다.
   - 수치와 단위는 원문과 재대조하는 검증 단계를 둔다.
   - 최종 결과는 검색 가능한 구조화 데이터와 사용자용 요약 문서로 함께 저장한다.

## 과제 6. 과거 대책서 기반 유사 사례 검색 및 대책 생성

### 비즈니스 배경

품질 불량이 발생할 때마다 대책서가 작성되지만, 과거 사례가 많아 담당자가 유사 사례를 직접 찾기 어렵다. 현상과 원인을 입력하면 과거 대책서에서 유사 사례를 찾고, 이를 바탕으로 신규 대책서 초안을 생성하는 기능이 필요하다.

### 핵심사항

- 과거 대책서를 현상, 원인, 대책, 품명, 차종, 공정, 발생일자 등으로 구조화한다.
- 현재 입력된 현상·원인과 유사한 과거 사례를 검색한다.
- 검색된 근거를 바탕으로 신규 대책서 초안을 생성하되, 없는 사실을 임의로 만들지 않도록 제어한다.

### 액션 플랜

- 대책서 원문을 구조화하고 검색용 메타데이터 스키마를 정의한다.
- 유사도 검색 로직과 필터링 로직을 설계한다.
- 대책 생성 템플릿, 근거 표시 방식, 사용자 검토·수정 흐름을 구현한다.

### 전체 프로세스

```text
과거 대책서 수집 -> 텍스트·표 추출 -> 구조화 스키마 적재 -> ★현상·원인 기반 유사 사례 검색 -> 후보 재정렬 -> 대책서 초안 생성 -> 근거·환각 검증 -> 사용자 검토 및 최종 저장
```

### 단계별 구현 로직

1. 과거 대책서 수집 및 원문 관리
   - PPT, PDF, 이미지 형태의 대책서를 수집한다.
   - 원문 파일, 추출 텍스트, 이미지, 작성일자, 작성 부서, 품명, 차종을 함께 관리한다.
   - 원문과 추출 결과의 연결이 끊기면 근거 검증이 어려우므로 문서 ID를 일관되게 유지한다.

2. 구조화 스키마 설계
   - 현상, 원인, 임시조치, 근본대책, 재발방지, 품명, 공정, 설비, 불량 유형을 표준 필드로 정의한다.
   - 대책서마다 표현 방식이 다를 수 있으므로 필수 필드와 선택 필드를 구분한다.
   - 품명·불량유형·공정명은 표준 코드와 원문 표현을 함께 저장한다.

3. 검색 인덱스 구성
   - 현상 중심 검색 필드와 원인 중심 검색 필드를 분리한다.
   - 품명, 차종, 공정, 발생연도, 불량유형은 필터 조건으로 활용한다.
   - 긴 대책서는 의미 단위로 분할하되, 현상과 대책이 서로 다른 조각으로 분리되지 않도록 문맥 묶음을 유지한다.

4. **현상·원인 기반 유사 사례 검색**
   - 사용자가 입력한 현상과 원인을 정규화한다.
   - 현상만 입력된 경우 현상 중심으로 검색하고, 원인까지 입력된 경우 원인 유사도를 추가 반영한다.
   - 키워드 일치, 의미 유사도, 품명·공정 필터, 최신성, 조치 성공 여부를 종합해 후보를 산출한다.

5. 후보 재정렬
   - 단순 유사도 상위 결과를 그대로 쓰지 않고 업무 적합도 기준으로 재정렬한다.
   - 동일 불량 유형, 동일 공정, 동일 소재, 재발 방지 효과가 검증된 사례에 가중치를 부여한다.
   - 검색 후보가 부족하면 필터를 완화하되, 완화 조건을 결과에 표시한다.

6. 대책서 초안 생성
   - 검색된 과거 사례의 현상, 원인, 조치, 효과를 근거로 신규 대책서 초안을 생성한다.
   - 초안은 현상 요약, 추정 원인, 확인 필요 항목, 임시조치, 근본대책, 재발방지, 참고 사례로 구성한다.
   - 과거 사례에 없는 수치, 설비명, 책임부서, 일정은 임의 생성하지 않고 "확인 필요"로 표시한다.

7. 근거·환각 검증
   - 생성된 문장마다 참조한 과거 대책서 ID와 근거 문구를 연결한다.
   - 근거가 없는 문장은 자동 확정하지 않는다.
   - 사용자가 최종 수정한 내용은 향후 검색 품질 개선용 피드백 데이터로 저장한다.

## 과제 11. 컬러 사양표 자동 입력 및 품명 오타 보정

### 비즈니스 배경

고객사가 제공하는 컬러 사양표의 품명 표기가 사내 품명과 다르고, 오타나 약어도 포함되어 있어 담당자가 수작업으로 매칭해야 한다. 컬러 값을 자동 입력하려면 고객사 품명을 사내 표준 품명으로 정확히 보정하는 로직이 필요하다.

### 핵심사항

- 컬러 사양표에서 품명, 위치, 컬러 코드, 컬러명, 적용 차종을 추출한다.
- 고객사 품명을 사내 표준 품명으로 보정한다.
- 유사도가 낮거나 후보가 여러 개인 경우 사용자가 선택할 수 있도록 후보를 제공한다.

### 액션 플랜

- 품명 마스터, 고객사별 별칭, 약어, 오타 사례를 사전으로 구축한다.
- 텍스트 정규화, 유사도 계산, 임계값 분기 로직을 구현한다.
- 자동 확정 결과와 사용자 선택 결과를 학습 데이터처럼 누적해 매칭 품질을 개선한다.

### 전체 프로세스

```text
컬러 사양표 수집 -> 텍스트·표 추출 -> 품명·컬러 항목 정규화 -> ★품명 오타 보정 및 표준 품명 매칭 -> 유사도 임계값 분기 -> 컬러값 자동 입력안 생성 -> 사용자 검토 -> 최종 반영·피드백 저장
```

### 단계별 구현 로직

1. 컬러 사양표 수집 및 추출
   - 엑셀, PPT, PDF에서 표 데이터를 추출한다.
   - 품명, 부품 위치, 컬러 코드, 컬러명, 차종, 사양 구분을 필드로 분리한다.
   - 병합 셀, 다단 헤더, 주석에 컬러 정보가 숨어 있을 수 있으므로 표 구조 보존이 중요하다.

2. 텍스트 정규화
   - 대소문자, 공백, 특수문자, 좌우 표기, 약어를 표준 형태로 바꾼다.
   - 예를 들어 LH, LEFT, 좌측을 같은 의미 그룹으로 묶는다.
   - 정규화 전 원문도 보관해야 사용자가 결과를 검토할 때 추적 가능하다.

3. 매칭 기준 데이터 구축
   - 사내 표준 품명 마스터를 구축한다.
   - 고객사별 품명 별칭, 과거 매칭 이력, 오타 교정 이력을 별도 테이블로 관리한다.
   - 표준 품명 하나에 여러 고객사 표현이 연결될 수 있도록 1:N 구조를 허용한다.

4. **품명 오타 보정 및 표준 품명 매칭**
   - 정규화된 입력 품명과 표준 품명 마스터 간 문자열 유사도, 단어 유사도, 약어 일치도를 계산한다.
   - 완전 일치, 별칭 일치, 오타 교정 후보, 의미 유사 후보를 순서대로 평가한다.
   - 품명뿐 아니라 차종, 위치, 부품군이 일치하는지 함께 보아 오매칭을 줄인다.

5. 유사도 임계값 분기
   - 고신뢰 후보는 자동 확정한다.
   - 중간 신뢰 후보는 상위 후보 목록과 점수를 사용자에게 제공한다.
   - 낮은 신뢰 후보는 자동 입력하지 않고 신규 별칭 등록 또는 수동 확인 대상으로 분리한다.

6. 컬러값 자동 입력안 생성
   - 확정된 표준 품명에 컬러 코드와 컬러명을 매핑한다.
   - 동일 품명에 여러 컬러가 있는 경우 적용 위치나 사양 구분을 기준으로 분리한다.
   - 입력 전 기존 컬러값과 비교해 변경, 신규, 삭제 후보를 구분한다.

7. 피드백 저장
   - 사용자가 선택한 후보, 수정한 품명, 거절한 후보를 모두 저장한다.
   - 반복적으로 선택되는 후보는 다음 매칭에서 가중치를 높인다.
   - 잘못 자동 확정된 사례는 금지 매칭 또는 낮은 가중치로 관리한다.

## 과제 12. 신규 프로젝트 금형 수축률 AI 추천

### 비즈니스 배경

플라스틱 부품은 냉각 과정에서 수축하므로 금형 설계 단계에서 적정 수축률을 반영해야 한다. 잘못된 수축률은 금형 수정 비용과 일정 지연으로 이어진다. 현재는 숙련자의 경험에 의존하므로 과거 데이터를 기반으로 신규 프로젝트의 수축률을 추천하는 모델이 필요하다.

### 핵심사항

- 원소재 업체, 재질, 공법, 생산 공장, 품목, 과거 품질 이슈를 피처로 구성한다.
- 과거 수축률과 조정 이력을 학습해 신규 조건의 권장 수축률을 예측한다.
- 예측값만 제공하지 않고 추천 근거와 신뢰도를 함께 제공한다.

### 액션 플랜

- 수축률 이력 데이터와 품질 이슈 데이터를 통합한다.
- 초기에는 유사 사례 기반 추천을 병행하고, 데이터가 축적되면 회귀 모델로 고도화한다.
- 모델 학습, 검증, 배포, 모니터링, 재학습 로직을 구축한다.

### 전체 프로세스

```text
수축률·품질 이력 수집 -> 데이터 정제·피처 설계 -> 학습 데이터셋 생성 -> ★ML 회귀 모델 학습·검증 -> 모델 배포 -> 신규 프로젝트 수축률 예측 -> 추천 근거·신뢰도 생성 -> 검증 결과 적재 및 재학습
```

### 단계별 구현 로직

1. 데이터 수집
   - 과거 프로젝트의 품번, 품명, 차종, 원소재 업체, 재질, 공법, 생산 공장, 금형 수축률, 실제 양산 결과를 수집한다.
   - 초기 설계 수축률과 품질 이슈 이후 조정된 최종 수축률을 구분한다.
   - 불량 발생 여부, 치수 편차, 재작업 여부, 금형 수정 횟수 등 품질 결과를 함께 수집해야 추천값의 품질을 평가할 수 있다.

2. 데이터 정제
   - 동일 업체·재질·공법이 여러 표기로 입력된 경우 표준 코드로 정규화한다.
   - 수축률 단위, 소수점 자리수, 범위 오류를 정리한다.
   - 결측치가 많은 컬럼은 모델 피처로 쓸지, 별도 "미상" 값으로 처리할지 기준을 정한다.

3. 피처 설계
   - 범주형 피처: 업체, 재질, 공법, 공장, 부품군, 차종, 고객사.
   - 수치형 피처: 두께, 중량, 치수, 온도 조건, 압력 조건, 과거 평균 수축률, 품질 이슈 건수.
   - 파생 피처: 업체·재질 조합 평균 수축률, 공법별 조정 빈도, 최근 프로젝트 가중 평균, 유사 품목의 최종 수축률.
   - 신규 조합이 들어올 수 있으므로 미등록 범주 처리 전략이 필요하다.

4. 학습 데이터셋 생성
   - 목표값은 최종 확정 수축률로 정의한다.
   - 초기 수축률과 최종 수축률의 차이를 별도 목표값으로 두면 "권장 보정량" 모델도 만들 수 있다.
   - 같은 프로젝트의 중복 이력이 학습·검증 데이터에 동시에 들어가지 않도록 프로젝트 단위 분할을 고려한다.

5. **ML 회귀 모델 학습·검증**
   - 기본 모델은 평균·중앙값·유사 사례 기반 추천으로 만들고, 이를 기준선으로 사용한다.
   - 회귀 모델은 범주형 인코딩, 수치형 스케일링, 결측 처리, 모델 학습을 하나의 파이프라인으로 묶는다.
   - 데이터가 적으면 단순 모델부터 시작하고, 데이터가 충분해지면 비선형 회귀 모델을 비교한다.
   - 검증은 단순 1회 분할보다 교차검증을 사용해 과적합 여부를 확인한다.
   - 평가 지표는 평균절대오차, 허용오차 내 적중률, 고위험 오차 건수로 관리한다.

6. 모델 해석 및 추천 근거 생성
   - 전체 피처 중요도와 개별 예측 건의 주요 영향 요인을 산출한다.
   - 예를 들어 "동일 재질의 과거 평균", "특정 업체의 조정 이력", "동일 공법의 품질 이슈 빈도"가 추천에 어떤 영향을 줬는지 설명한다.
   - 설명은 모델 출력만 그대로 노출하지 말고 업무 담당자가 이해할 수 있는 문장으로 변환한다.

7. 모델 배포 및 예측
   - 신규 프로젝트 입력값을 받아 동일한 전처리 파이프라인을 적용한다.
   - 예측 수축률, 추천 범위, 신뢰도, 유사 과거 사례, 주요 근거를 반환한다.
   - 입력값이 학습 데이터 범위를 크게 벗어나면 자동 추천 대신 검토 필요로 분기한다.

8. 콜드스타트 대응
   - 신규 업체·신규 재질처럼 학습 이력이 부족한 경우 유사 사례 기반 추천과 중앙값 기반 추천을 병행한다.
   - 유사 사례가 부족하다는 사실을 결과에 명시해야 한다.
   - 초기에는 모델 예측보다 규칙·유사 이력·전문가 확인을 결합한 하이브리드 방식이 안정적이다.

9. 검증 결과 적재 및 재학습
   - 실제 양산 후 확정된 수축률과 품질 결과를 다시 적재한다.
   - 누적 데이터가 일정 건수를 넘거나 모델 오차가 커지면 재학습을 수행한다.
   - 재학습 전후 모델 성능을 비교하고, 성능이 악화되면 이전 모델로 되돌릴 수 있어야 한다.

## 과제 13. 표준 품명 규칙 치환 및 공법 추천

### 비즈니스 배경

같은 부품이 담당자마다 다른 이름으로 입력되면 검색, 집계, 사양 구성 관리가 어려워진다. 또한 부품에 맞는 공법을 선택할 때 과거 사용 이력과 표준 규칙을 참고해야 하지만 현재는 기준이 충분히 정리되어 있지 않다.

### 핵심사항

- 비표준 품명을 표준 품명 규칙으로 치환한다.
- 표준 규칙이 없는 경우 유사 품명 후보를 추천한다.
- 공법은 과거 사용 빈도와 조건 유사도를 바탕으로 추천한다.

### 액션 플랜

- 표준 품명 규칙, 약어, 동의어, 위치 표기, 차종 표기 기준을 정리한다.
- 품명 정규화 엔진과 공법 추천 엔진을 분리해 구현한다.
- 사용자 수정 결과를 반영해 규칙과 추천 가중치를 지속적으로 개선한다.

### 전체 프로세스

```text
입력 품명 수집 -> 텍스트 정규화 -> 규칙 기반 치환 -> ★표준 품명 후보 추천 -> 공법 이력 조회 -> ★공법 추천 점수 계산 -> 사용자 확정 -> 규칙·이력 업데이트
```

### 단계별 구현 로직

1. 입력 품명 수집
   - 사양 구성도, 설계 문서, 사용자가 직접 입력한 품명을 수집한다.
   - 입력 출처, 작성자, 작성일자, 차종, 부품군을 함께 저장한다.

2. 텍스트 정규화
   - 공백, 특수문자, 대소문자, 한글·영문 혼용, 좌우 표기, 버전 표기를 정규화한다.
   - 약어 사전을 적용해 DT, DR TRIM, DOOR TRIM 같은 표현을 같은 의미로 묶는다.
   - 차종 코드와 부품 위치가 품명 안에 섞여 있으므로 토큰 분해 로직이 필요하다.

3. 규칙 기반 치환
   - 이미 확정된 표준 품명 규칙이 있으면 결정적으로 치환한다.
   - 규칙은 우선순위를 가져야 한다. 예를 들어 차종+부품군+좌우 표기가 모두 맞는 규칙을 단순 부품군 규칙보다 우선한다.
   - 규칙 충돌이 발생하면 자동 치환하지 않고 후보로 반환한다.

4. **표준 품명 후보 추천**
   - 규칙으로 확정되지 않는 품명은 표준 품명 마스터와 유사도를 계산한다.
   - 문자열 유사도, 약어 일치도, 차종 일치도, 부품군 일치도, 과거 사용자 선택 빈도를 점수화한다.
   - 상위 후보와 점수를 함께 제공하고, 신뢰도가 높은 경우만 자동 확정한다.

5. 공법 이력 조회
   - 표준 품명, 부품군, 재질, 공장, 차종 기준으로 과거 공법 사용 이력을 조회한다.
   - 과거 공법이 여러 개면 사용 빈도, 품질 이슈 여부, 최신성을 함께 계산한다.

6. **공법 추천 점수 계산**
   - 공법별 추천 점수는 사용 빈도, 동일 조건 일치도, 최근성, 품질 문제 발생 여부를 반영한다.
   - 예를 들어 사용 빈도는 높지만 품질 이슈가 많았던 공법은 감점한다.
   - 데이터가 부족하면 확정 추천이 아니라 "후보 추천"으로 표시한다.

7. 사용자 확정 및 업데이트
   - 사용자가 최종 선택한 표준 품명과 공법을 저장한다.
   - 반복 선택되는 매핑은 규칙 승격 후보로 관리한다.
   - 잘못된 추천은 예외 규칙으로 등록해 재발을 막는다.

## 과제 14. 원소재 업체 및 양산처 자동 맵핑

### 비즈니스 배경

원소재 업체와 양산처가 전자결재 문서에 짧은 HTML 형태로 기록되지만, 담당자는 이를 읽고 관련 제품과 업체를 수동으로 매핑한다. 문서에 정보가 흩어져 있어 자동화하려면 HTML 파싱, 문맥 추론, 사용자 검증이 함께 필요하다.

### 핵심사항

- 전자결재 문서에서 차종, 품목, 원소재 업체, 양산처, 수신자, 결재 제목을 추출한다.
- 추출된 정보를 제품·업체 마스터와 매칭한다.
- 정보가 부족한 경우 사용자 검증 대상으로 분리한다.

### 액션 플랜

- 전자결재 문서 유형과 HTML 구조를 분석한다.
- 제품·업체 매핑 마스터와 과거 승인 이력을 정리한다.
- 자동 매핑, 신뢰도 판단, 사용자 검증, 최종 반영 로직을 구현한다.

### 전체 프로세스

```text
전자결재 문서 조회 -> HTML 제목·본문·표 파싱 -> 엔티티 추출 -> ★제품·업체·양산처 매핑 추론 -> 신뢰도 산정 -> 사용자 검증 분기 -> 최종 매핑 반영 -> 매핑 이력 저장
```

### 단계별 구현 로직

1. 전자결재 문서 조회
   - 결재일자, 문서 유형, 제목 키워드, 작성부서 기준으로 대상 문서를 조회한다.
   - 이미 처리한 문서는 중복 처리하지 않도록 문서 ID를 저장한다.

2. HTML 제목·본문·표 파싱
   - 제목, 본문, 표, 첨부파일명, 수신자, 참조자, 결재 라인을 분리한다.
   - HTML 태그 제거만으로 표의 의미가 사라질 수 있으므로 표 구조는 별도 추출한다.
   - 짧은 문서일수록 제목과 첨부파일명에 핵심 정보가 있을 가능성이 높다.

3. 엔티티 추출
   - 차종, 품목, 원소재 업체, 양산 공장, 프로젝트명, 적용일자를 추출한다.
   - 업체명 약칭, 법인명, 공장명은 마스터 데이터와 대조해 표준화한다.
   - 같은 문서에 여러 품목 또는 여러 업체가 포함될 수 있으므로 1:N 매핑을 허용한다.

4. **제품·업체·양산처 매핑 추론**
   - 추출된 차종, 품목, 업체명을 제품·업체 마스터와 대조한다.
   - 제목 정보, 본문 정보, 표 정보, 수신 부서 정보를 각각 점수화해 종합 매핑 점수를 계산한다.
   - 과거 승인 문서와 동일한 제목 패턴이나 유사 품목이 있으면 후보 점수를 높인다.

5. 신뢰도 산정 및 분기
   - 필수 정보가 모두 일치하고 후보가 하나이면 자동 확정한다.
   - 후보가 여러 개이거나 필수 정보가 누락되면 사용자 검증 대상으로 분리한다.
   - 신뢰도 점수와 판단 근거를 함께 제공해야 사용자가 빠르게 확인할 수 있다.

6. 최종 매핑 반영
   - 검증 완료된 제품, 원소재 업체, 양산처 정보를 사내 시스템에 반영한다.
   - 기존 매핑이 있는 경우 신규, 변경, 중복, 충돌 상태를 구분한다.
   - 충돌이 발생하면 자동 덮어쓰기를 하지 않고 승인 절차를 거친다.

7. 매핑 이력 저장
   - 문서 ID, 추출값, 최종 매핑값, 신뢰도, 사용자 수정 내역을 저장한다.
   - 반복적으로 수정되는 패턴은 매핑 규칙 개선 대상으로 관리한다.

## 공통 확인 필요사항

- 각 사내 시스템의 연동 방식: API, 파일 업로드, 배치 테이블, 수동 반영 중 무엇인지 확인 필요.
- 문서 전처리 범위: OCR, 표 추출, 이미지 추출을 누가 어디까지 수행하는지 확인 필요.
- 마스터 데이터 보유 여부: 품명, 업체, 공법, 권한, 부서, 재질 코드의 최신성과 관리 주체 확인 필요.
- 사용자 검증 UI 범위: 자동 확정이 불가능한 후보를 어디에서 누가 확정할지 확인 필요.
- 운영 기준: 자동 처리 실패 시 재처리 방식, 담당자 알림, 변경 이력 보관 기간, 권한 감사 기준 확인 필요.
