# 서연이화 과제별 구현 로직 (클로드코드)

> **작성 기준**
> - 개발 솔루션·기술 스택 미정 상태를 반영해 **완전 기술 중립**으로 작성합니다. 특정 제품(자동화 플랫폼·검색엔진 등)·개발 언어·DB 종류·라이브러리명을 명시하지 않고, **"무엇을 하는 구성요소인가(역할)"** 중심으로 기술합니다.
> - 솔루션이 확정되면 아래 **역할 매핑 가이드**의 역할명을 실제 제품/스택으로 치환하면 그대로 구현 설계가 됩니다.
> - 각 과제는 ① 배경·핵심 분석 ② 핵심 데이터 모델 ③ 양식 1(전체 프로세스 1줄) ④ 양식 2(단계별 세부·심화) 순으로 구성합니다.
> - 📍 = 해당 과제의 **핵심 구현 작업**(성패를 좌우하는 구간).

## 역할(구성요소) 매핑 가이드

| 역할명(본 문서)     | 하는 일                  | 솔루션 확정 시 대응 예시(미확정)   |
| ------------- | --------------------- | --------------------- |
| 배치 스케줄러       | 정해진 주기로 작업 트리거        | 크론/잡 스케줄러 류           |
| 워크플로우 오케스트레이터 | 단계 연결·조건 분기·재시도·로깅    | 워크플로우 엔진 또는 애플리케이션 코드 |
| 정형 데이터 저장소    | 구조화 데이터 영속 저장·조회      | 관계형/문서형 DB 류          |
| 의미 검색 인덱스     | 임베딩 기반 유사 검색 + 키워드 검색 | 벡터·검색 엔진 류            |
| 임베딩 생성기       | 텍스트를 의미 벡터로 변환        | 임베딩 모델                |
| LLM           | 요약·추출·생성·비교 등 자연어 처리  | 대규모 언어 모델             |
| 모델 서빙 API     | 학습된 예측 모델을 호출 가능하게 노출 | 추론 서비스 엔드포인트          |
| 브라우저 자동화 도구   | 사람 대신 웹 화면 조작·수집      | RPA/브라우저 제어 도구        |
| 룰엔진           | 결정적 정책·규칙 평가          | 규칙 평가 모듈(코드/엔진)       |
| 외부 연동 어댑터     | 사내·외부 시스템과 송수신        | API 클라이언트/커넥터         |

> ⚠️ 모든 과제 공통 전제: **OCR/문서 텍스트화 등 비정형→텍스트 전처리는 별도(전처리 업체) 영역**이며, 본 로직은 "텍스트가 확보된 시점" 이후를 설계 대상으로 한다. 또한 모든 외부 연동 단계는 **재시도·타임아웃·부분실패 롤백·멱등성(idempotency)**을 기본 요건으로 한다.

# 과제 1: 인사 정보 기반 권한 자동 맵핑

## 배경·핵심 분석
- **배경**: 입사·부서이동이 잦은데 권한 변경이 수작업이라, "필요 권한이 없는 직원"과 "이동·퇴사 후에도 권한이 남은 직원"이 동시에 발생한다.
- **핵심사항**: 인사변동 정보를 일배치로 수신해 업무 시스템 권한을 자동 변경하는 **규칙 기반(Rule-based)** 모델.
- **액션 플랜**: 권한 부여 기본 정책 + 예외 케이스를 분석해 룰엔진화하고 관리 도구와 연동.
- **유형 규정**: 100% **결정적 룰베이스 배치**. AI/ML 불필요. 난이도의 본질은 알고리즘이 아니라 **정책·예외 분기의 정합성**과 **멱등성·감사 추적**이다. 즉 "권한을 잘못/중복으로 바꾸지 않는 것"이 핵심.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 인사변동이벤트 | event_id, 사번, 변동유형(입사/이동/승진/퇴사), 이전부서, 신규부서, 직급, 발령일, 처리상태 | 그룹웨어 수신 |
| 권한정책 | policy_id, 부서코드, 직급, 부여대상(역할/메뉴/기능), 동작(grant/revoke), 우선순위 | 정책 1~6 + 예외 |
| 사용자권한현황 | 사번, 권한항목, 상태(활성/회수), 부여일, 부여근거(policy_id) | 현재 상태 스냅샷 |
| 변경이력(감사) | log_id, 사번, 변경전, 변경후, 적용룰, 처리시각, 결과(성공/실패/스킵) | 멱등·감사 |

## 전체 프로세스
```
배치 스케줄러로 인사변동 증분 수집 -> 정규화·검증(사번·부서코드 매핑, 무결성 체크) -> 변동유형 분류(입사/이동/승진/퇴사) -> 📍룰엔진 정책 평가(부서·직급→권한셋 산출, 신규/이동/신설부서/1인부서 예외 분기) -> 📍현재권한과 Diff 산출(부여·회수 대상 확정) -> 권한 변경 적용(업무시스템 반영, 멱등 처리) -> 📍감사로그 적재·결과 리포트 -> 실패건 재처리 큐 적재
```

## 단계별 세부 (심화)
1. **인사변동 증분 수집** — 배치 스케줄러가 일 1회 그룹웨어에서 변동 내역을 가져온다.
   - 구현: 마지막 처리 시각 이후의 **증분만** 조회(전체 재처리 방지). 수신 원본을 그대로 staging 영역에 적재 후 가공.
   - 유의: 외부 연동 어댑터의 **타임아웃·재시도** 필수. 수집 자체가 실패하면 그날 권한 변경이 통째로 누락되므로 **수집 성공/실패 알림**을 별도로 둔다.
2. **정규화·검증** — 사번·부서코드를 사내 마스터와 매핑하고 필수값을 검증한다.
   - 구현: 부서코드 미존재·사번 불일치 등은 처리 대상에서 격리(error 격리). 부서 구조는 **플랫(독립 부서)** 전제이므로 상위부서 상속 로직은 두지 않는다.
   - 유의: 한 사람의 동일 발령일에 복수 이벤트(예: 이동+승진)가 올 수 있어 **이벤트 병합/순서 정렬** 규칙을 정의해야 한다.
3. **변동유형 분류** — 입사/이동/승진/퇴사로 분기점을 만든다.
   - 유의: 퇴사는 "전체 회수", 이동은 "이전부서 권한 회수 + 신규부서 권한 부여"처럼 동작이 근본적으로 다르므로 유형 판별이 틀리면 권한 사고로 직결된다.
4. **📍룰엔진 정책 평가** — 부서·직급 조합으로 부여해야 할 권한셋을 산출하고 예외를 적용한다.
   - 구현: 정책을 **데이터(권한정책 테이블)로 외부화**해 코드 수정 없이 정책 변경이 가능하게 한다. 우선순위 필드로 정책 충돌을 해소한다. 신규입사·부서이동·신설부서·1인부서 등 예외는 별도 분기로 명시.
   - 유의: 정책이 코드에 하드코딩되면 유지보수가 불가능해진다. "정책 추가 = 데이터 한 줄 추가"가 목표. 결정적 로직이므로 **동일 입력 → 동일 출력**이 보장돼야 테스트 가능.
5. **📍현재권한과 Diff 산출** — 산출된 목표 권한셋과 현재 보유 권한을 비교해 실제 부여/회수 대상만 도출한다.
   - 구현: `목표셋 - 현재셋 = 부여`, `현재셋 - 목표셋 = 회수`. 이미 일치하는 권한은 건드리지 않는다.
   - 유의: 이 Diff 단계가 **멱등성의 핵심**. 같은 배치가 두 번 돌아도 이미 반영된 권한은 변경 0건이어야 한다.
6. **권한 변경 적용** — 업무시스템에 부여/회수를 반영한다.
   - 구현: 외부 연동 어댑터로 일괄 전송. **건별 결과**를 받아 성공/실패를 구분.
   - 유의: 부분 실패(10건 중 3건 실패) 대비 — 성공분만 커밋하고 실패분은 재처리 큐로. 전체 롤백이 맞는지/건별 처리가 맞는지는 업무 규칙에 따라 결정.
7. **📍감사로그 적재·결과 리포트** — 누가/무엇이/왜 바뀌었는지 전부 기록한다.
   - 구현: 변경 전후 값 + 적용 룰ID + 결과를 변경이력에 적재. 일배치 종료 후 요약 리포트(부여 N건/회수 M건/실패 K건).
   - 유의: 권한은 보안·감사 대상이므로 **추적 가능성이 기능 요건 자체**. "권한 설정 근거" 제시가 필요하면 적용 룰ID로 역추적할 수 있게 설계.
8. **실패건 재처리 큐** — 일시적 오류는 자동 재시도, 영구 오류는 담당자 알림.
   - 유의: 무한 재시도 방지를 위해 재시도 횟수 상한·백오프를 둔다.

# 과제 2: 업무 포털 단가 조회 자동화 (매크로)

## 배경·핵심 분석
- **배경**: 협력사 담당자가 매일 완성차 공급사 포털에 로그인해 '미결 품목' 단가를 조회·엑셀 정리·사내 업로드하는 반복 작업을 수행한다.
- **핵심사항**: 이 **로그인→조회→정리→업로드** 반복 작업을 자동화.
- **액션 플랜**: 웹 매크로로 미결 품목·단가를 스크래핑 → 엑셀 텍스트 파싱 → 자사 플랫폼 일괄 전송.
- **유형 규정**: **브라우저 자동화(RPA) + 텍스트 파싱**. AI 비중 낮음. 로직 난도는 낮으나 **로그인(OTP 포함)·포털 화면 변경 취약성·실행 안정성**이 실질 핵심이다.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 미결품목수집 | 수집ID, 품번, 품명, 단가, 통화, 조회일, 출처화면, 캡처경로, 상태(신규/중복/오류) | 스크래핑 결과 |
| 실행로그 | run_id, 실행시각, 로그인결과, 수집건수, 실패단계, 스크린샷경로 | 안정성 추적 |
| 전송결과 | 수집ID, 전송시각, 결과, 사유 | 사내 시스템 반영 |

## 양식 1 — 전체 프로세스
```
배치 스케줄러 트리거 -> 📍브라우저 자동화 로그인(자격증명·OTP 처리) -> 미결품목 목록 조회·페이지네이션 순회 -> 📍단가 데이터 스크래핑(표 추출, 텍스트화 안 되는 영역은 화면캡처→텍스트 인식 보조) -> 파싱·정규화(품번·품명·단가·통화·일자 정형화) -> 검증(중복·결측·이상치 필터) -> 📍자사 시스템 일괄 전송(멱등·중복 차단) -> 결과·예외 리포트 및 증빙 스크린샷 보관
```

## 양식 2 — 단계별 세부 (심화)
1. **스케줄 트리거**
	- 매일 정해진 시각 자동 기동. 수동 재실행 진입점도 함께 둔다.
2. **📍브라우저 자동화 로그인** — 자격증명 입력 + OTP/추가 인증 처리.
   - 구현: 자격증명은 **비밀 저장소에서 주입**(코드/스크립트에 평문 금지). OTP는 발급 방식(앱/SMS/이메일)에 따라 수신·입력 자동화 방식을 별도 설계.
   - 유의: **이 과제 최대 리스크.** 로그인 실패 시 이후 전 단계가 무의미하므로 로그인 성공 검증(특정 요소 등장 확인) 후에만 다음 단계 진행. 계정 잠금 방지를 위해 재시도 횟수 제한.
3. **미결품목 목록 조회·순회** — 조건 입력 후 결과 표를 끝까지 순회(페이지네이션).
   - 구현: 동적 로딩 화면 대비 **요소 등장 대기(wait)** 기반으로 안정화. 페이지 수가 가변이므로 "다음 페이지 없음"까지 반복.
   - 유의: 무한 루프 방지(최대 페이지 가드), 화면 응답 지연 시 타임아웃·재시도.
4. **📍단가 데이터 스크래핑** — 표에서 품번/품명/단가/통화/일자를 추출.
   - 구현: 가능한 한 DOM 표 구조에서 직접 추출(정규식·셀렉터). 텍스트로 안 잡히는 이미지성 영역만 화면캡처 후 텍스트 인식으로 보조하고 캡처본을 증빙으로 보관.
   - 유의: **포털 화면 구조 변경에 취약** — 셀렉터를 한곳에 모아 관리(변경 시 한 곳만 수정). 추출 0건이면 "정상(미결 없음)"인지 "스크래핑 실패"인지 구분하는 가드 필요.
5. **파싱·정규화** — 통화기호·천단위 콤마·날짜형식 등을 정형값으로 변환.
   - 유의: 단가의 통화·단위 혼재, 숫자 파싱 오류(쉼표/공백) 주의. 정규화 규칙을 명세화.
6. **검증** — 중복·결측·이상치(음수·비정상 자릿수)를 필터.
   - 유의: 이미 수집·전송된 품목과 **중복 제거**(품번+조회일 키). 이상치는 버리지 말고 별도 검토 상태로 분리.
7. **📍자사 시스템 일괄 전송** — 검증 통과분을 사내 시스템에 업로드.
   - 구현: 외부 연동 어댑터로 전송, 전송 키로 **중복 업로드 차단**(멱등).
   - 유의: 부분 실패 시 성공분/실패분 분리 기록 후 실패분 재시도.
8. **결과·예외 리포트** — 수집/전송 건수, 실패 단계, 증빙 스크린샷을 남긴다.
   - 유의: RPA는 "조용히 실패"가 가장 위험 → 실패 시 즉시 알림. 실행로그에 단계별 스크린샷을 남겨 원인 추적성을 확보.

# 과제 3: 기술 표준 문서 요약 및 버전 비교

## 배경·핵심 분석
- **배경**: 완성차사가 보내는 두꺼운(문서당 100여 장) 기술 표준 문서가 다수 존재하고 주기적으로 개정된다. 담당자가 시험 항목·합격 기준을 직접 뽑아 등록하고, 신·구 버전 차이도 직접 비교한다.
- **핵심사항**: 비정형 표준 문서를 **시험 리스트 위주로 요약**하고, **과거 버전 ↔ 최신 버전의 세부 차이를 비교**.
- **액션 플랜**: (전처리로 텍스트화된 뒤) 핵심 요약 + 연도별 변경점 도출 프롬프트 설계.
- **유형 규정**: **분할요약(Map-Reduce) + 버전 비교**. 긴 문서를 한 번에 못 넣으므로 청크 단위 요약 후 병합하는 구조가 핵심이며, **환각(없는 시험 기준 생성) 방지·근거 추적**이 품질 관건.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 문서 | 문서ID, 문서명, 버전, 발행연도, 원문위치 | 버전 관리 |
| 시험항목(요약결과) | 항목ID, 문서ID, 버전, 시험항목명, 합격기준, 단위, 시험조건, 페이지근거, 임베딩 | 구조화 추출 |
| 버전비교결과 | 비교ID, 기준버전, 대상버전, 항목명, 변경유형(추가/삭제/변경), 변경내용 | 차이 리포트 |

## 양식 1 — 전체 프로세스
### 3-1 요약
```
문서 텍스트 수신 -> 📍문서 구조 인식·청킹(장/절 단위, 표는 단위 보존) -> 📍청크별 LLM 요약(시험항목·합격기준·조건 구조화 추출) -> 병합·중복제거(Map-Reduce의 Reduce) -> 최종 구조화 요약 생성(시험 리스트) -> 📍근거 검증(추출값↔원문 페이지 매핑, 환각 필터) -> 정형 저장·시스템 등록
```
### 3-2 비교
```
비교 대상 두 버전 선택 -> 시험항목 단위 정렬·매칭(항목명 키 기반) 📍 -> 항목별 LLM 차이 분석(추가/삭제/기준값 변경 판정) 📍 -> 변경점 요약 리포트 생성 -> 등록·알림
```

## 양식 2 — 단계별 세부 (심화)
1. **문서 텍스트 수신** — 전처리로 텍스트화된 문서를 입력으로 받는다(OCR은 본 과제 범위 밖).
2. **📍문서 구조 인식·청킹** — 긴 문서를 의미 단위로 분할한다.
   - 구현: 무작정 글자수로 자르지 말고 **장/절/소제목 경계** 기준으로 청킹. **표는 잘리면 의미가 깨지므로** 한 단위로 보존. 각 청크에 출처 페이지를 메타로 부착.
   - 유의: 청킹 품질이 요약 품질을 좌우. 시험 기준은 보통 표에 있으므로 표 보존이 특히 중요.
3. **📍청크별 LLM 요약(Map)** — 각 청크에서 시험항목·합격기준·시험조건을 **구조화(JSON 등) 추출**.
   - 구현: 자유 요약이 아니라 **정해진 필드로 추출**하도록 프롬프트 설계(스키마 강제). 청크마다 독립 처리하므로 병렬화 가능.
   - 유의: "요약문"이 아니라 "구조화된 시험 리스트"가 목표임을 프롬프트에 명확히. 근거 페이지를 함께 출력하게 한다.
4. **병합·중복제거(Reduce)** — 청크별 결과를 합치고 중복 항목을 정리.
   - 유의: 같은 시험항목이 여러 청크에 걸쳐 나오면 통합. 병합 과정에서 정보 손실/왜곡이 생기지 않도록 키(항목명+조건) 기준 병합.
5. **최종 구조화 요약 생성** — 병합 결과를 등록용 시험 리스트로 확정.
6. **📍근거 검증(환각 필터)** — 추출된 각 기준값이 실제 원문에 존재하는지 페이지 근거로 확인.
   - 구현: 항목별 근거 페이지 텍스트와 추출값을 대조. 근거를 못 찾는 항목은 "검토 필요"로 플래그.
   - 유의: 기술 표준은 수치 한 자리 틀리면 큰 문제 → **자동 등록 전 검증이 필수**. 신뢰도 낮은 항목은 사람이 확인하도록 분리.
7. **정형 저장·등록** — 시험항목을 저장하고 시스템에 등록. 임베딩도 생성해 두면 비교·검색에 재사용.
8. **3-2 ① 버전 정렬·매칭** — 두 버전의 시험항목을 항목명 키로 1:1 정렬.
   - 유의: 항목명이 버전 간 미세하게 다를 수 있어(표기 변화) 유사도 보조 매칭 필요. 매칭 안 되는 항목이 곧 "추가/삭제" 후보.
9. **3-2 ② 항목별 차이 분석** — 매칭된 항목쌍의 기준값 변화를 LLM이 판정.
   - 구현: 추가/삭제/변경을 분류하고, 변경이면 무엇이 어떻게 바뀌었는지 서술.
   - 유의: "단순 표현 변경"과 "실제 기준값 변경"을 구분해야 함(노이즈 억제).
10. **변경점 리포트** — 변경 유형별로 정리해 담당자에게 제공.

# 과제 6: 과거 대책서 기반 유사 사례 검색 및 대책 생성

## 배경·핵심 분석
- **배경**: 불량 발생 시마다 작성된 '품질 대책서'가 7천~1만 건 이상 누적돼 있다.
- **핵심사항**: 사용자가 **현상·원인**을 입력하면 가장 유사한 과거 사례를 **검색(RAG)**하고, 새 대책 보고서 텍스트를 **구조화 생성**.
- **액션 플랜**: 대책서 스키마(현상·원인·대책 등)를 구조화하고, 이슈 타입·품명별로 검색 볼륨을 나눠 검색 품질·프롬프트 고도화.
- **유형 규정**: **대용량 RAG(검색증강생성)**. 8개 과제 중 데이터 규모가 가장 크다. 성패는 LLM이 아니라 **검색 품질**(청킹·메타데이터·하이브리드 검색·리랭킹)에서 갈린다.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 대책서(원본 구조화) | 문서ID, 현상, 원인, 대책, 품명, 이슈타입, 공정, 발생연도 | 전처리 후 분해 |
| 검색청크 | 청크ID, 문서ID, 청크텍스트, 임베딩, 메타(품명/이슈타입/연도) | 의미 검색 인덱스 적재 |
| 생성이력 | 요청ID, 입력현상, 입력원인, 참조문서ID[], 생성대책, 채택여부 | 피드백·품질 추적 |

## 양식 1 — 전체 프로세스
### 6-1 적재(색인)
```
구조화 텍스트 수신 -> 📍필드 분해(현상/원인/대책 등으로 파싱) -> 📍청킹 + 임베딩 생성 -> 메타데이터 부여(품명·이슈타입·연도) -> 의미 검색 인덱스에 적재(키워드+벡터 동시 색인)
```
### 6-2 검색·생성
```
현상·원인 입력 -> 입력 정규화·쿼리 확장(동의어·약어) -> (원인 유무) 조건 분기 -> 📍하이브리드 검색(키워드+벡터) + 메타 필터 -> 📍리랭킹·TopK 선별 -> 📍LLM 대책 보고서 생성(보고서 양식, 근거 사례 인용) -> 사용자 검토·채택 -> 생성이력 적재
```

## 양식 2 — 단계별 세부 (심화)
1. **구조화 텍스트 수신** — 전처리로 텍스트화된 대책서를 입력으로 받는다.
2. **📍필드 분해** — 자유 텍스트를 현상/원인/대책/품명/이슈타입/연도로 분해.
   - 구현: 양식이 일정하면 규칙 파싱, 불규칙하면 LLM 추출로 구조화. 고객사와 **DB 스키마(필드 정의)를 먼저 합의**하는 것이 선행 과제.
   - 유의: 이 스키마가 곧 검색 필터·생성 입력의 기준이 되므로 초기에 잘 잡아야 한다.
3. **📍청킹 + 임베딩 생성** — 검색 단위로 쪼개고 의미 벡터를 만든다.
   - 구현: 현상·원인·대책을 각각 검색 단위로 둘지, 한 문서를 한 단위로 둘지 설계. 7천~1만 건 규모라 **배치로 일괄 임베딩** 처리.
   - 유의: 청킹 전략(단위 크기·중복)이 검색 적중률을 좌우. 초기 대량 적재와 이후 증분 적재를 분리 설계.
4. **메타데이터 부여** — 품명·이슈타입·연도를 메타로 부착.
   - 유의: **이슈타입·품명별로 검색 범위를 좁히는 필터**가 대용량에서 정확도·속도의 핵심. 메타 설계가 곧 "검색 볼륨 분리" 전략.
5. **의미 검색 인덱스 적재** — 키워드 검색과 벡터 검색을 **둘 다** 가능하도록 색인.
   - 유의: 키워드(정확한 품번·용어)와 벡터(의미 유사) 각각의 강점이 달라 하이브리드가 필요.
6. **6-2 입력·정규화·쿼리 확장** — 현상·원인 입력을 정규화하고 동의어·약어를 확장.
   - 유의: 현장 용어 편차가 크므로 동의어 사전으로 쿼리를 보강해야 적중률이 오른다.
7. **조건 분기(원인 유무)** — 원인까지 입력됐는지에 따라 검색 전략을 달리.
   - 유의: 원인이 없으면 현상으로만 유사 사례 검색 → 후보 원인 제시, 원인이 있으면 현상+원인으로 좁힘.
8. **📍하이브리드 검색 + 메타 필터** — 키워드+벡터 결합 검색에 품명·이슈타입 필터를 적용.
   - 구현: 두 검색 결과를 점수 결합(가중합 등). 메타 필터로 무관 품명 사례를 배제.
   - 유의: 필터를 너무 좁히면 결과 0건, 너무 넓히면 노이즈 — 임계 튜닝 필요.
9. **📍리랭킹·TopK 선별** — 1차 검색 결과를 재정렬해 상위 N건만 생성 입력으로 사용.
   - 유의: 상위 정확도가 생성 품질을 결정. TopK 개수는 비용·품질 트레이드오프로 튜닝.
10. **📍LLM 대책 보고서 생성** — 선별된 과거 사례를 근거로 새 대책을 **보고서 양식에 맞춰** 생성.
    - 구현: 출력 구조(현상/원인/대책/주의)를 고정. **참조한 과거 사례 ID를 함께 인용**해 근거 추적.
    - 유의: 검색된 근거 안에서만 생성하도록 제약(환각 억제). 근거가 빈약하면 "유사 사례 없음"을 솔직히 반환.
11. **사용자 검토·채택 → 이력 적재** — 채택 여부를 기록해 향후 품질 개선·검색 가중치에 활용.

# 과제 11: 컬러 사양표 자동 입력 및 품명 오타 보정

## 배경·핵심 분석
- **배경**: 완성차사가 보내는 컬러 사양표의 부품별 컬러 값을 담당자가 수동 입력하는데, **고객사 품명이 사내 품명과 다르고(예: "DOOR TRIM LH" = "도어트림 좌측") 오타까지 섞여** 매칭이 까다롭다.
- **핵심사항**: 비정형 컬러 사양표에서 컬러 값을 자동 기입하되, **오타가 있어도 정확한 부품에 매핑**.
- **액션 플랜**: 동의어 사전·단어 유사도로 오타 매핑, 유사도 애매(예: 85%)면 드롭박스로 사용자 최종 선택.
- **유형 규정**: **퍼지 매칭 + 동의어 정규화**. 핵심은 "글자 단위 오타 보정"과 "의미 단위 별칭 매핑"을 함께 처리하고, **확신/애매를 임계값으로 갈라 자동확정 vs 후보제시**로 분기하는 것.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 부품마스터 | 부품ID, 표준품명, 표준품명_정규화, 임베딩 | 매칭 대상 |
| 별칭/동의어사전 | 원표현(고객사 표기), 표준표현, 출처, 신뢰도 | 학습 누적 |
| 컬러입력결과 | 행ID, 원품명, 매칭부품ID, 컬러값, 유사도점수, 상태(자동확정/후보제시/미매칭) | |
| 사용자확정이력 | 행ID, 선택부품ID, 확정자, 시각 | 피드백 학습 |

## 양식 1 — 전체 프로세스
```
컬러 사양표 텍스트 수신 -> 표 구조 파싱(부품 행·컬러 열 인식) -> 📍품명 정규화(대소문자·공백·약어·동의어 확장) -> 📍부품마스터 매칭(글자 유사도[편집거리] + 의미 유사도[임베딩] 결합, TopK 후보 산출) -> 📍임계값 분기(고신뢰=자동확정 / 애매=후보 제시 / 저신뢰=미매칭) -> 컬러값–부품 매핑 구성 -> 시스템 전송(애매 건은 드롭박스용 후보 동봉) -> 사용자 확정 피드백 수집·사전/가중치 갱신
```

## 양식 2 — 단계별 세부 (심화)
1. **텍스트 수신·표 파싱** — 사양표에서 "부품명 행 ↔ 컬러 열" 구조를 인식.
   - 유의: 고객사마다 표 양식이 달라 헤더 위치·병합 셀 처리 규칙이 필요. 컬러 값이 어느 열인지 식별 로직 필요.
2. **📍품명 정규화** — 매칭 전에 입력 품명을 표준형으로 다듬는다.
   - 구현: 대소문자 통일·공백/특수문자 정리·방향 약어 통일(LH/좌/Left → 좌측)·동의어 사전 확장.
   - 유의: 정규화가 곧 매칭 적중률의 절반. 사전은 데이터로 외부화해 지속 보강.
3. **📍부품마스터 매칭** — 정규화된 품명을 부품마스터와 대조해 후보를 뽑는다.
   - 구현: **두 종류 유사도를 결합** — (a) 글자 단위 **편집 거리**(오타·철자 흔들림에 강함), (b) **의미 임베딩 유사도**(별칭·번역 차이에 강함). 둘을 가중 결합해 TopK 후보와 점수 산출.
   - 유의: 오타는 글자 유사도가, 번역/별칭(영↔한)은 의미 유사도가 잡는다 — **한쪽만으로는 부족**하므로 결합이 핵심. 임베딩만으로는 미세 오타에 약하다.
4. **📍임계값 분기** — 점수로 처리 방식을 가른다.
   - 구현: 고신뢰(예: ≥상한)=자동확정, 중간(예: 85% 부근)=상위 후보를 사용자에게 제시(드롭박스), 저신뢰=미매칭으로 분리.
   - 유의: 임계값은 운영 데이터로 보정해야 함. 자동확정 임계를 너무 낮추면 오매핑, 너무 높이면 수작업 증가 — **오매핑 비용이 크므로 보수적으로** 시작.
5. **컬러값–부품 매핑 구성** — 확정된 부품에 컬러 값을 결합.
   - 유의: 한 부품에 복수 컬러, 동일 품명 중복 행 등 예외 처리.
6. **시스템 전송** — 자동확정분은 바로 기입, 애매분은 후보 리스트를 동봉해 사용자 선택 UI로.
   - 유의: 드롭박스 후보 개수·정렬(점수순) 등 UI 사양은 고객사와 협의 필요.
7. **사용자 확정 피드백 학습** — 사용자가 고른 매핑을 사전·가중치에 반영.
   - 구현: 확정된 "원표현→표준품명" 쌍을 별칭 사전에 추가해 **다음부터 자동확정**되게 한다.
   - 유의: 피드백 누적이 시스템을 점점 똑똑하게 만드는 선순환 — 이력 적재를 빠뜨리지 말 것.

# 과제 12: 신규 프로젝트 금형 수축률 AI 추천

## 배경·핵심 분석
- **배경**: 플라스틱은 냉각 시 수축하므로 금형 설계에 '수축률'을 반영해야 하고, 잘못 잡으면 금형 재가공 비용이 수천만 원. 지금은 숙련 엔지니어가 경험으로 결정한다.
- **핵심사항**: 원소재 업체·재료·생산 공장 등 과거 데이터로 신규 프로젝트의 **최적 수축률을 AI가 사전 추천**.
- **액션 플랜**: 초기 양산 수축률 + 품질 이슈로 튜닝된 수축률까지 취합해 추천 알고리즘 적용.
- **유형 규정**: 8개 중 유일한 **수치 예측(회귀) ML** 과제. 룰/검색이 아니라 **모델 학습·검증·서빙·설명**이 본질. 초기 데이터 부족(**콜드스타트**)과 **건별 근거 설명**이 두 난제.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 수축률이력 | 아이템ID, 원소재업체(범주), 재질(범주), 공법(범주), 공장(범주), 형상·치수(수치), 초기수축률, 튜닝수축률, 품질이슈여부, 적용일 | 학습 데이터 |
| 모델메타 | 모델버전, 학습일, 학습건수, 교차검증성능, 피처목록 | 재학습 추적 |
| 추천이력 | 요청ID, 입력메타, 예측수축률, 신뢰구간, 근거피처[], 콜드스타트여부, 채택여부 | 피드백 |

## 양식 1 — 전체 프로세스
### 학습(오프라인)
```
수축률 이력 수집·정제 -> 📍피처 구성(범주형 인코딩 + 수치형 결합, 파생변수) -> 📍회귀 모델 학습 + 교차검증(소량 데이터 대비) -> 성능 평가·피처 기여도 분석 -> 모델 서빙 API로 배포
```
### 추론(온라인)
```
신규 아이템 메타 입력 -> 정규화·학습과 동일한 피처 변환 -> 📍(데이터 충분) 모델 예측 / (콜드스타트) 유사 이력 검색·통계 fallback -> 예측값 + 건별 기여도 산출 -> LLM 근거 설명 생성 -> 시스템 전송 -> 📍검증완료 데이터 증분 적재 + 임계 초과 시 재학습 트리거
```

## 양식 2 — 단계별 세부 (심화)
1. **이력 수집·정제** — 과거 수축률 이력을 모아 결측·오타·이상치를 정리.
   - 유의: 제조 현장 데이터는 결측·표기 흔들림·범주값 오타가 흔함 → 정제 규칙이 모델 품질의 토대. **초기 양산값 + 품질 튜닝값**을 모두 취합하는 수집 경로를 기획에서 확보.
2. **📍피처 구성** — 범주형(업체·재질·공법·공장)과 수치형(치수 등)을 모델 입력으로 변환.
   - 구현: 범주형은 인코딩(원-핫/타깃 인코딩 등), 도메인 기반 파생변수 설계. **전처리+모델을 하나의 파이프라인으로 묶어** 학습·서빙 간 변환 불일치를 방지.
   - 유의: 학습 때와 추론 때 변환이 다르면 예측이 망가짐 → 파이프라인 일원화가 핵심. 미학습 범주값(신규 업체) 처리 정책 필요.
3. **📍회귀 모델 학습 + 교차검증** — 수축률(연속값)을 예측하는 회귀 모델 학습.
   - 구현: 데이터가 적으므로 단일 분할이 아닌 **교차검증(K-fold)**으로 안정적 성능 추정. 트리 기반 부스팅 회귀 등 비선형·혼합형 데이터에 강한 모델군이 적합.
   - 유의: 소량 데이터 과적합 경계. 성능 지표(MAE 등)와 잔차 분석으로 신뢰성 점검.
4. **성능 평가·기여도 분석** — 전체 성능 + 어떤 피처가 예측에 기여하는지 분석.
   - 구현: 전역 피처 중요도 + **건별 기여도**(개별 예측을 피처별로 분해)를 산출해 설명 생성에 활용.
   - 유의: "이 예측이 왜 이 값인가"의 건별 근거가 과제 요건이므로 전역 중요도만으로는 부족.
5. **모델 서빙 API 배포** — 학습된 파이프라인을 호출 가능한 추론 서비스로 노출.
   - 유의: 모델 버전 관리(어떤 버전이 어떤 예측을 냈는지 추적). 입력 스키마 검증.
6. **신규 메타 입력·피처 변환** — 추론 요청을 학습과 동일한 변환으로 처리.
7. **📍예측 / 콜드스타트 fallback 분기** — 데이터가 충분하면 모델 예측, 부족·미학습 조합이면 대체 전략.
   - 구현: 신규 재질·업체 조합 등 학습 근거가 약하면 **유사 이력 검색 → 중앙값/통계 기반 디폴트**로 fallback. 이 분기를 명시적으로 둔다.
   - 유의: 초기 운영은 대부분 콜드스타트일 수 있음 → fallback이 사실상 초기 주력. "모델 예측인지 통계 fallback인지"를 결과에 표기.
8. **건별 기여도 산출 → LLM 근거 설명** — 예측값과 함께 "어떤 재질·업체가 수축률을 올렸/내렸다"를 자연어로.
   - 구현: 건별 기여도 상위 피처를 LLM에 넘겨 엔지니어가 읽을 설명문 생성.
   - 유의: LLM은 **설명 문장화만** 담당하고 수치는 모델 결과를 그대로 인용(LLM이 수치를 지어내지 않게).
9. **시스템 전송** — 예측 수축률·신뢰도·근거를 시스템에 기입.
10. **📍증분 적재 + 재학습 트리거** — 검증 완료된 신규 이력을 누적하고, 일정량 쌓이면 재학습.
    - 구현: 신규 데이터 UPSERT, 누적 건수 임계(예: N건) 초과 시 재학습 파이프라인 기동.
    - 유의: 콜드스타트 탈출의 핵심 루프. 재학습 후 성능이 이전 모델보다 나아졌을 때만 교체(성능 가드).

# 과제 13: 표준 품명 규칙 치환 및 공법 추천

## 배경·핵심 분석
- **배경**: 같은 부품을 담당자마다 다르게 표기("DT K8 레프트", "도어트림K8좌측"…)해 검색·집계가 어렵고 공법 추천도 어렵다. 표준 품명 규칙은 20%만 완성, 공법 데이터도 초기 단계.
- **핵심사항**: 제각각 품명을 **표준 품명 규칙(예: K8_LH_V2)으로 자동 치환**하고, 모호한 공법 선택을 **과거 사용 빈도(예: 8:2) 기반으로 추천**.
- **액션 플랜**: 표준 규칙을 확립해 치환 엔진 적용, 공법 추천은 상관·회귀 분석으로 가중치 고도화 검토.
- **유형 규정**: 두 갈래 — (13-1) **규칙 기반 결정적 치환 + 미확립분 유사 매칭**, (13-2) **빈도·통계 기반 추천**. 최대 변수는 **표준 규칙이 20%만 확립된 데이터 미성숙**.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 품명규칙 | 규칙ID, 패턴(매칭조건), 표준형 템플릿, 적용범위, 버전 | 확립분 |
| 정규품명마스터 | 표준품명, 구성요소(차종·방향·버전 등), 임베딩 | 유사 매칭용 |
| 공법사용이력 | 부품군, 공법, 사용횟수, 최근사용일, 결과양호여부 | 빈도 통계 |

## 양식 1 — 전체 프로세스
### 13-1 품명 표준화
```
입력 품명 수신 -> 정규화(약어·동의어·방향표기 확장) -> 📍확립된 표준 규칙 결정적 치환(규칙 매칭 시) / 📍미해당 시 정규품명 마스터 유사 검색 보정 -> 표준 품명 생성 + 변환 근거 설명 -> 검증 분기(고신뢰 자동 / 애매 사용자 확인) -> 저장
```
### 13-2 공법 추천
```
부품(군) 식별 -> 📍유사 부품군의 공법 사용 이력 집계 -> 빈도·가중치 통계 산출(예: 8:2 비율, 최근성 가중) -> 공법 추천 + 근거(사용 비율) 제시 -> 사용자 선택 피드백 반영
```

## 양식 2 — 단계별 세부 (심화)
1. **입력 품명 수신·정규화** — 자유 표기 품명을 다듬는다.
   - 구현: 약어·동의어·방향표기(좌/LH/Left) 통일, 공백·구분자 정리.
   - 유의: 과제 11과 동일한 정규화 자산을 **공유**하면 효율적(동의어 사전 공통화).
2. **📍확립 규칙 결정적 치환** — 이미 확립된 표준 규칙에 매칭되면 규칙대로 치환.
   - 구현: 규칙을 데이터로 외부화(패턴→표준형 템플릿). 규칙 매칭은 **결정적**이라 정확·고속·검증 용이.
   - 유의: 규칙이 20%만 확립 → 적용 범위가 좁다. **"규칙 확립 = 데이터 추가"**로 점진 확대되는 구조로 설계해 규칙이 늘수록 결정적 치환 비율이 오르게.
3. **📍미해당 시 유사 검색 보정** — 규칙에 안 잡히는 품명은 정규품명 마스터와 유사 매칭.
   - 구현: 글자/의미 유사도로 가장 가까운 표준 품명 후보 제시(과제 11 매칭 로직 재활용).
   - 유의: 규칙이 미성숙한 현 단계에선 이 경로 비중이 큼. 규칙이 확립될수록 2번으로 이동.
4. **표준 품명 생성 + 근거** — 변환 결과와 "어떤 규칙/유사 매칭으로 변환했는지" 근거 동봉.
5. **검증 분기 → 저장** — 고신뢰는 자동, 애매는 사용자 확인 후 저장. 확정분은 규칙/마스터 보강에 활용.
6. **13-2 부품(군) 식별** — 공법 추천 대상 부품을 부품군으로 묶는다.
   - 유의: 공법 데이터가 초기 단계라 개별 부품 단위는 표본이 적음 → **부품군 단위 집계**로 표본 확보.
7. **📍유사 부품군 공법 사용 이력 집계** — 같은/유사 부품군에서 과거 어떤 공법을 얼마나 썼는지 집계.
   - 구현: 공법별 사용 횟수·비율 계산. 데이터가 적을 때를 대비해 유사 부품군까지 포함.
   - 유의: 표본 수가 적은 추천은 신뢰도 표기를 함께(예: "사례 5건 기준").
8. **빈도·가중치 통계 산출** — 단순 빈도에 **최근성·결과 양호 여부** 가중치를 더해 정렬.
   - 유의: 8:2 같은 비율을 그대로 보여주되, 향후 상관/회귀로 변수 가중치를 고도화할 여지를 남긴 구조(가중치 외부화).
9. **공법 추천 + 근거 제시** — 상위 공법을 비율 근거와 함께 추천.
10. **사용자 선택 피드백 반영** — 실제 선택을 이력에 적재해 다음 추천 정확도를 높임.
    - 유의: 데이터가 쌓일수록 통계 → (장기) 상관·회귀 기반 고도화로 자연 전환되도록 이력 설계.

# 과제 14: 원소재 업체 및 양산처 자동 맵핑

## 배경·핵심 분석
- **배경**: 원소재 구매처가 확정되면 그 내용이 사내 전자결재에 **HTML 형식 짧은 승인 문서**로 올라온다. 담당자가 이를 보고 어떤 제품에 어떤 원소재 업체·양산 공장이 연결되는지 직접 입력하는데, **정보가 조각조각**이라 판단이 어렵다.
- **핵심사항**: 대내문(HTML) **제목·간단한 표만으로** 제품의 원소재 공급·양산 업체를 추정해 자동 기입.
- **액션 플랜**: HTML만으론 정보가 부족할 위험이 크므로 **수신처·추가 문맥**을 활용한 매핑 규칙을 고객사와 사전 협의·확정.
- **유형 규정**: **HTML 정보 추출(LLM) + 문맥 보강 + 사용자 검증**. 난제는 추출 자체가 아니라 **정보 파편화로 인한 매핑 정확도**. 그래서 자동확정보다 **검증 루프**가 중요.

## 핵심 데이터 모델
| 엔터티 | 핵심 필드 | 비고 |
|---|---|---|
| 승인문서 | 문서ID, 제목, 본문HTML, 표데이터, 수신처, 기안일 | 전자결재 수신 |
| 제품–업체 매핑마스터 | 제품ID, 차종, 품목, 과거 원소재업체, 과거 양산처 | 문맥 보강·검증 기준 |
| 매핑결과 | 문서ID, 차종, 품목, 원소재업체, 양산처, 신뢰도, 근거, 상태(자동확정/검증대기) | |

## 양식 1 — 전체 프로세스
```
전자결재에서 대상 승인문서 조회 -> HTML 파싱·텍스트 추출(제목·표·본문 분리) -> 📍LLM 정보 추출(차종·품목·원소재업체·양산처 → 구조화 JSON) -> 📍문맥 보강(수신처·과거 매핑 이력 참조로 부족 정보 보완) -> 제품 매핑 후보 + 신뢰도 산출 -> 📍임계 분기(고신뢰 자동확정 / 애매 사용자 검증 루프) -> 시스템 전송 -> 검증 결과 피드백 적재
```

## 양식 2 — 단계별 세부 (심화)
1. **승인문서 조회** — 전자결재에서 대상 문서를 조건으로 가져온다.
   - 구현: 외부 연동 어댑터로 조회. 대상 문서 식별 조건(문서 종류·기간)을 정의.
   - 유의: 중복 처리 방지(문서ID 기준 멱등).
2. **HTML 파싱·텍스트 추출** — 제목·표·본문을 분리해 정리.
   - 구현: 단순 HTML이면 태그 제거·표 셀 추출로 충분. 정밀 파싱이 어려우면 정리된 텍스트를 다음 단계 LLM에 넘겨 추출을 맡길 수도 있다.
   - 유의: 표 구조(병합 셀 등)에서 항목–값 대응이 깨지지 않게 주의.
3. **📍LLM 정보 추출** — 텍스트에서 차종·품목·원소재업체·양산처를 **구조화(JSON)** 추출.
   - 구현: 출력 스키마를 고정하고, 값이 없으면 null로 명시하게 한다(없는 값을 지어내지 않게).
   - 유의: 이 과제는 입력 정보 자체가 적어 추출이 비어 있을 수 있음 → "추출 실패"와 "정보 없음"을 구분.
4. **📍문맥 보강** — 부족한 매핑 정보를 외부 단서로 보완.
   - 구현: **이메일 수신처·기안 부서** 등 메타와, **제품–업체 매핑 마스터(과거 사례)**를 참조해 "이 제목이면 보통 이 제품"을 추론·보강.
   - 유의: **이 과제 최대 리스크가 정보 부족**이므로 보강 단계가 정확도를 가른다. 보강 규칙은 고객사와 사전 협의해 확정(액션 플랜의 핵심).
5. **매핑 후보 + 신뢰도 산출** — 보강된 정보로 제품 매핑 후보와 신뢰도를 만든다.
   - 유의: 후보가 복수면 모두 신뢰도와 함께 제시.
6. **📍임계 분기(검증 루프)** — 신뢰도에 따라 자동확정 vs 사용자 검증.
   - 구현: 고신뢰만 자동 기입, 나머지는 후보를 제시해 사용자가 확정하는 검증 UI로.
   - 유의: 정보 파편화로 오매핑 위험이 크므로 **자동확정 임계를 높게** 두고 검증 루프 비중을 크게 가져가는 것이 안전. 초기엔 거의 검증 루프로 운영하다 정확도 확인 후 자동확정 확대.
7. **시스템 전송** — 확정된 매핑을 시스템에 기입.
8. **검증 결과 피드백 적재** — 사용자가 고친 매핑을 매핑 마스터/보강 규칙에 반영해 정확도를 누적 개선.
