## 배경

web-ui 리뉴얼에 로그인/세션 관리 기능을 추가해야 한다.
인증 모듈은 **Supabase Auth** 또는 **Keycloak(OIDC)** 중 선택 예정.
모듈 선택 전에도 로그인 UI와 라우트 보호 구조는 먼저 작업 가능하다.

## 인증 흐름 (공통)

```
사용자 → 로그인 UI → 인증 서버(Supabase/Keycloak) → 토큰 발급 → 쿠키 저장 → 세션 유지
```

- 로그인 시 인증 서버에 자격증명을 보내고, JWT 토큰을 발급받는다
- 토큰은 쿠키에 저장되어 요청마다 자동 전송된다
- Next.js middleware에서 토큰을 검증하고, 없으면 `/login`으로 리다이렉트한다

## 모듈 비교

| | Supabase Auth | Keycloak (OIDC) |
|---|---|---|
| **성격** | BaaS (DB + Auth 통합) | IAM 전용 서버 |
| **로그인 UI** | 직접 만든 폼 (이메일/PW) | Keycloak 페이지로 리다이렉트 |
| **세션 관리** | SDK가 쿠키(JWT) 자동 관리 | next-auth가 세션/JWT 관리 |
| **토큰 갱신** | SDK 자동 refresh | next-auth가 refresh_token으로 갱신 |
| **패키지** | `@supabase/supabase-js`, `@supabase/ssr` | `next-auth`, `@auth/core` |
| **난이도** | 쉬움 | 중간 (Keycloak 서버 세팅 필요) |
| **적합 케이스** | 빠른 프로토타입, Supabase DB 함께 쓸 때 | 기업 SSO, 역할 기반 접근제어 |

## 프론트엔드 구조 (모듈 무관)

```
frontend/
├── app/
│   ├── login/page.tsx        ← 로그인 페이지
│   ├── (main)/layout.tsx     ← 세션 체크 후 children 렌더
│   └── middleware.ts         ← 라우트 보호 (토큰 없으면 /login)
├── lib/
│   └── auth.ts               ← 인증 클라이언트 초기화/설정
```
