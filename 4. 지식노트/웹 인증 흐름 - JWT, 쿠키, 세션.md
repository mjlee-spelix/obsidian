# 웹 인증 흐름 - JWT, 쿠키, 세션

## 핵심
- 웹에서 "로그인 상태 유지"는 **토큰**(출입증)을 발급받아 매 요청마다 보여주는 것
- **인증 서버**가 토큰을 발급하고, **쿠키**가 토큰을 저장/운반하고, **세션**이 "이 사용자는 로그인됨"이라는 상태를 의미
- 로그인 → 토큰 발급 → 쿠키 저장 → 매 요청마다 쿠키 자동 전송 → 서버가 토큰 검증

## 상세

### 전체 흐름 (비유)

```
호텔 체크인에 비유하면:

1. 프론트 데스크(인증 서버)에 신분증(이메일/비밀번호)을 제출
2. 프론트 데스크가 확인 후 카드키(토큰)를 발급
3. 카드키를 지갑(쿠키)에 넣어둠
4. 방에 들어갈 때마다(페이지 요청) 카드키를 대면 문이 열림
5. 카드키가 만료되면 다시 프론트에서 갱신(토큰 리프레시)
```

### 인증 서버 (Authentication Server)

사용자의 신원을 확인하고 토큰을 발급해주는 서버.

- 직접 만들 수도 있지만, 보통 **전문 서비스**(Supabase, Keycloak, Auth0 등)를 사용
- 이메일/비밀번호, 소셜 로그인(Google, GitHub) 등 다양한 인증 방식을 처리
- 프론트엔드는 인증 서버의 API를 호출해서 로그인/로그아웃/회원가입을 수행

```
[프론트엔드]                    [인증 서버]
    │                              │
    ├── POST /login ──────────────→│  이메일+비밀번호 전송
    │                              │  DB에서 사용자 확인
    │←──── { token: "abc123" } ────┤  확인되면 토큰 발급
    │                              │
    ├── GET /api/data ────────────→│  요청 헤더에 토큰 포함
    │   (Authorization: abc123)    │  토큰 유효성 검증
    │←──── { data: [...] } ────────┤  유효하면 데이터 반환
```

### JWT (JSON Web Token)

토큰의 한 형태. 정보를 JSON으로 담아서 서명한 문자열.

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjoxMjN9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
│         헤더        │       페이로드        │           서명           │
```

3개 부분이 `.`으로 구분되어 있고:
- **헤더**: 토큰 타입, 암호화 알고리즘
- **페이로드**: 사용자 정보 (user_id, email, 만료시간 등)
- **서명**: 위변조 방지용 (서버의 비밀키로 생성)

**특징**:
- 서버가 DB를 조회하지 않고도 토큰만 보고 사용자를 확인할 수 있음 (서명 검증)
- 페이로드는 **암호화가 아닌 인코딩**이라 누구나 읽을 수 있음 → 비밀번호 같은 민감 정보는 넣지 않음
- 만료 시간이 있어서, 만료되면 **리프레시 토큰**으로 새 토큰을 발급받음

### 쿠키 (Cookie)

브라우저가 자동으로 저장하고, 매 요청마다 자동으로 서버에 보내주는 작은 데이터 조각.

```
[브라우저]                         [서버]
    │                               │
    │←── Set-Cookie: token=abc123 ──┤  서버가 "이거 저장해" 라고 응답
    │                               │
    │── Cookie: token=abc123 ──────→│  이후 모든 요청에 자동 포함
    │── Cookie: token=abc123 ──────→│  개발자가 별도 코드 안 써도 됨
    │── Cookie: token=abc123 ──────→│
```

**왜 쿠키를 쓰나?**
- `localStorage`에 토큰을 저장할 수도 있지만, 매번 직접 꺼내서 헤더에 넣어야 함
- 쿠키는 **브라우저가 알아서** 요청에 포함시켜줌
- `httpOnly` 쿠키는 JavaScript로 접근 불가 → XSS 공격으로부터 토큰 보호

### 세션 (Session)

"이 사용자는 현재 로그인된 상태"라는 정보 자체를 세션이라고 부름.

세션을 유지하는 방식은 크게 2가지:

| 방식 | 설명 | 장단점 |
|------|------|--------|
| **서버 세션** | 서버 메모리/DB에 세션 정보 저장, 쿠키에는 세션 ID만 저장 | 서버가 상태를 관리, 서버 재시작 시 세션 소멸 |
| **JWT 세션** | 쿠키에 JWT 자체를 저장, 서버는 상태를 저장하지 않음 | 서버 부담 적음, 토큰 만료 전 강제 로그아웃 어려움 |

Supabase와 next-auth 모두 **JWT 세션** 방식을 기본으로 사용.

### 리다이렉트 (Redirect)

사용자를 다른 URL로 자동 이동시키는 것.

인증에서 두 가지 상황에서 쓰임:

```
상황 1: 미인증 사용자 차단
  /dashboard 접속 시도 → 토큰 없음 → /login으로 리다이렉트

상황 2: 외부 인증 서버 사용 (Keycloak 등)
  "로그인" 버튼 클릭 → Keycloak 로그인 페이지로 리다이렉트
  → 로그인 성공 → 우리 사이트 /callback으로 리다이렉트 (토큰 포함)
```

### 토큰 리프레시 흐름

```
[Access Token]  ← 수명 짧음 (15분~1시간). 매 요청에 사용
[Refresh Token] ← 수명 김 (7일~30일). Access Token 갱신용

1. Access Token으로 API 호출
2. 만료됨 → 401 Unauthorized 응답
3. Refresh Token을 인증 서버에 보내서 새 Access Token 발급
4. 새 Access Token으로 다시 요청
```

- Supabase SDK, next-auth 모두 이 과정을 **자동으로** 처리해줌
- Refresh Token까지 만료되면 → 재로그인 필요
