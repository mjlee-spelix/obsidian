# 마트 설계 결정 (2026-05-14)

> 5/13 노트의 후속. 5개 컴포넌트(kpi-cards / kpi-drill-through / dept-objects / dept-activity / model-tokens) 한정으로 audit_events + RBAC 단일 SoT 마트를 재설계. 미결정 분기 3건 확정 + 채택/호출 기준 명확화.

## 1. 확정된 분기 3건

| # | 항목 | 결정 | 마트 영향 |
|---|---|---|---|
| a | "신규 X" 정의 | `resource_ownership.created_at` 단일 기준 (apps.created_at 분기 폐기) | KPI #1 증감률·dept-activity 신규 컬럼 단순화 |
| b | "호출 수" 부서 기준 | **owner 기준** 일관 (KPI #3, dept-activity 호출, drill-through 모두) | Layer 2에서 owner GROUP BY 기본 |
| c | api_call(nginx) 포함 여부 | **제외**, message_send + workflow_execute 두 액션만 | enriched action 화이트리스트 2개. 근거: [[0. Inbox/부서별 API 호출 집계 - api_call 대신 messages+workflow_runs 쓰는 이유.md]] |

> 레거시 앱 없음(결정 a의 부수효과) → `LEFT JOIN ro`를 **INNER JOIN ro**로 격상. "미배정" 버킷 폐기. NULL 발생 시 사고 신호로 모니터링.

### 1.1 RBAC JOIN 전략 — 옵션 B (사전 JOIN하되 ID만)

운영 RBAC 스케일 가정: departments 수십~백, department_members **만 단위 누적**, resource_ownership 수백~수천.

| 검토 옵션 | 결론 |
|---|---|
| A 사전 JOIN, name까지 박음 | 부서명 변경 즉시 반영 안 됨 + 저장 공간 복제 → 기각 |
| **B 사전 JOIN, ID만** | ✅ **채택** — 비싼 결합(audit × dept_members × ownership)은 refresh 시 1회로 흡수, 작은 departments는 컴포넌트 쿼리에서 매번 JOIN |
| C 완전 분리 (Layer 2에서 JOIN) | RBAC 만 단위 스케일에서 매 쿼리 hash build 부담 누적, 특히 drill 정확 users 카운트가 문제 → 기각 |
| D 이중 mat (normalized + enriched) | Layer 1 재사용성 좋지만 mat 비용 2배. 미래 보안/감사 화면 로드맵 확정 시 재검토 |

**옵션 B 핵심**:
- enriched MView에 `app_owner_dept_id`, `actor_dept_id` (ID만) 보존
- 부서명(`departments.name`)은 컴포넌트/Layer 2 쿼리에서 query-time JOIN
- 부서명 변경은 즉시 반영, ownership·membership 변동은 refresh 주기(5분) stale (모든 옵션 공통)

## 2. "채택" vs "호출"의 부서 기준 분리

5/14 정정 사항. KPI #2만 actor, 나머지 호출 메트릭은 owner.

| 컴포넌트 | 의미 | 부서 기준 |
|---|---|---|
| kpi-cards #2 부서별 채택 앱 수 (Breadth) | 우리 부서원이 실제로 쓰는 앱 종류 수 | **actor** |
| kpi-cards #3 API 호출 (Depth) | 우리 부서가 소유한 앱이 받은 호출량 | **owner** |
| kpi-cards #4 Top 앱 / drill-through | 동일 (호출량 기반) | **owner** |
| dept-activity 호출/토큰 컬럼 | 부서 소유 앱의 활동량 | **owner** |
| dept-activity 신규 a/k/t 컬럼 | 부서가 새로 보유한 자산 | **owner** (ownership.owner_dept) |

→ Layer 2 mat에 actor_dept_id, app_owner_dept_id **둘 다 GROUP BY 컬럼**으로 보존 (ID만, 이름은 query-time JOIN). 카디널리티 추정 — mock 5×5 부서 기준 45K행/월, 운영 N×N 부서로 확장 시에도 (일 30 × actor_dept × owner_dept × 앱 수 × app_mode) 폭이라 부서 수십 단위까지 백만 행 이내.

## 3. 마트 구조 (2계층)

```
[원본]    audit.audit_events (Generated Column 8개 보강)
           + rbac.{resource_ownership, departments, department_members}
              │
              ▼
[Layer 1] mart.v_audit_enriched               ← MView, 이벤트 1건 = 1행 (event-level)
[Layer 1] mart.v_resource_ownership_enriched  ← View, 자산 ↔ 부서 매핑 (state)
              │
              ▼
[Layer 2] mart.mv_kpi_calls_daily             ← MView, 호출 메트릭 공용 큐브
[Layer 2] mart.mv_model_tokens_daily          ← MView, 모델 코스트 전용 큐브
```

### 왜 2계층인가

- Layer 1만으로 5개 컴포넌트 다 쓸 수 있지만, **kpi-cards + drill-through는 동시 조회**라 같은 집계를 카드별로 4번 깎으면 비쌈
- Layer 2(daily roll-up mat)로 미리 day 단위까지 굴려두면 **카드·차트·표 모두 같은 mat을 다른 GROUP BY로 재사용** — 기간 필터는 `SUM` 한 번
- Layer 1은 "정규화된 이벤트 스트림"(추출/플래그 일관), Layer 2는 "비즈니스 큐브"(빠른 응답) — 역할 분리로 미래 진화 경로(incremental fact / 분석 DB)에서 Layer 2만 갈아끼우면 컴포넌트 코드 무수정
- 스테이징 layer 없음: `audit_events`가 이미 정규화된 이벤트 로그라 별도 정제 단계 불필요

### Layer 1을 굳이 따로 두는 진짜 이유

옵션 C(Layer 1 없이 Layer 2에서 RBAC JOIN)도 가능합니다. 굳이 Layer 1을 분리하는 핵심 이유:

- drill-through의 *정확* users 카운트는 daily mat 합산(중복 카운트 상한)이 아니라 `COUNT(DISTINCT actor_id)`가 필요 → **행 단위 데이터 다시 봐야 함**
- 옵션 C로 가면 매 drill 요청마다 `audit_events × RBAC JOIN`을 새로 함 (만 단위 dept_members hash build 반복)
- Layer 1을 분리하면 **행 단위 조회(drill)와 집계 조회(카드)가 같은 사전 JOIN 결과를 공유** — RBAC JOIN을 마트 어디서든 한 번만 함

### MView vs View 선택 기준 — 3축

`v_audit_enriched`는 MView, `v_resource_ownership_enriched`는 View로 형태가 다른 이유:

| 축 | View 유리 | MView 유리 |
|---|---|---|
| 원본 크기 | 작다 (수천 이하) | 크다 (수십만 이상) |
| 신선도 허용치 | 즉시 필요 | 분 단위 OK |
| 조회 빈도 (같은 결과 N번 보나) | 낮음 | 높음 |

- `audit_enriched`: 9백만 행 + 5분 stale OK + 5개 컴포넌트가 다 씀 → **3축 모두 MView 유리**
- `ownership_enriched`: 수천 행 + 즉시 반영이 자연스러움 + 조회 빈도 적당 → **3축 모두 View 유리**

### 3.1 객체별 비즈니스 의미

| 객체 | 형태 | 한 줄 의미 |
|---|---|---|
| `audit_events` Generated Column 8개 | 컬럼 | details JSONB 속 분기/필터 키를 컬럼으로 노출해 마트 쿼리가 인덱스 타고 H-DASH-01/03 방어를 일관 적용 |
| `mart.v_audit_enriched` | Materialized View | 감사 이벤트 1건 = 1행. actor·owner *부서 ID*, 디버그 여부, AppMode 정상 호출 여부 사전 결합된 *정규화 이벤트 스트림* — 모든 호출 메트릭의 단일 진실원 (부서명은 query-time JOIN) |
| `mart.v_resource_ownership_enriched` | View | 현재 시점의 자산(앱/KB/도구) ↔ 소유 부서 매핑 *state 스냅샷* — 누가 무엇을 보유했나 |
| `mart.mv_kpi_calls_daily` | Materialized View | (일 × actor부서ID × owner부서ID × 앱 × app_mode) 단위 호출/사용자/에러/토큰 *roll-up 큐브* — 채택은 actor, 호출은 owner, 양쪽이 같은 큐브에서 다른 GROUP BY로 나옴 |
| `mart.mv_model_tokens_daily` | Materialized View | (일 × 모델제공자 × 모델ID) 단위 토큰/호출 합계 — 모델 코스트 추세 분석 전용 큐브 (message_send만, workflow는 구조적 미가용) |

### 3.2 컴포넌트 → 마트 객체 의존

| 컴포넌트 | 사용 객체 | 기준 |
|---|---|---|
| kpi-cards #1 총 오브젝트 | v_resource_ownership_enriched | state |
| kpi-cards #2 채택 폭 | mv_kpi_calls_daily | actor |
| kpi-cards #3 API 호출 | mv_kpi_calls_daily | owner |
| kpi-cards #4 Top 앱 | mv_kpi_calls_daily + apps(name) | owner |
| kpi-drill-through 4구역 | mv_kpi_calls_daily + apps(name) + 정확 users는 v_audit_enriched | owner |
| dept-objects | v_resource_ownership_enriched | state |
| dept-activity 6컬럼 | mv_kpi_calls_daily + v_resource_ownership_enriched | 호출/토큰=owner, 신규=ownership.created_at |
| model-tokens | mv_model_tokens_daily | — |

## 4. DDL 핵심

### 4.1 audit_events Generated Column

```sql
ALTER TABLE audit.audit_events
  ADD COLUMN app_mode        TEXT  GENERATED ALWAYS AS (details->>'appMode')         STORED,
  ADD COLUMN model_provider  TEXT  GENERATED ALWAYS AS (details->>'modelProvider')   STORED,
  ADD COLUMN model_id        TEXT  GENERATED ALWAYS AS (details->>'modelId')         STORED,
  ADD COLUMN total_tokens    INT   GENERATED ALWAYS AS (NULLIF(details->>'totalTokens','')::int) STORED,
  ADD COLUMN error_text      TEXT  GENERATED ALWAYS AS (details->>'error')           STORED,
  ADD COLUMN invoke_from     TEXT  GENERATED ALWAYS AS (details->>'invokeFrom')      STORED,
  ADD COLUMN triggered_from  TEXT  GENERATED ALWAYS AS (details->>'triggeredFrom')   STORED,
  ADD COLUMN target_app_id   UUID  GENERATED ALWAYS AS (
    CASE
      WHEN target_type = 'app' THEN target_id::uuid
      WHEN details ? 'appId'   THEN (details->>'appId')::uuid
      ELSE NULL
    END
  ) STORED;
```

### 왜 Generated Column인가

- **마트 쿼리에서 `details->>'...'` 캐스팅 반복을 없애고, 인덱싱 가능 컬럼으로 만든다** — `WHERE app_mode='chat'` vs `WHERE details->>'appMode'='chat'`
- collector 코드가 의식하지 않아도 INSERT 시 PostgreSQL이 자동 계산 — collector는 details JSONB만 잘 박으면 됨
- 모든 이벤트 행에 컬럼 존재. 해당 키가 details에 없으면 NULL (정상). 마트 ETL은 `action IN ('message_send','workflow_execute')` 화이트리스트로 자연 필터링
- `STORED` 선택 사유: 디스크 약간 더 사용하지만 **인덱스 가능** (`VIRTUAL`은 매 쿼리 계산이라 인덱스 불가)
- collector별 채워지는 컬럼은 다르지만 (예: workflow_execute는 model_* NULL) 마트 쿼리 화이트리스트로 무관

### 적용 비용

- **현재 audit_events 데이터 없음** → `ALTER TABLE ... ADD COLUMN GENERATED`의 백필 lock 비용 0
- 마이그레이션 한 번에 적용 가능 (운영 트래픽 영향 없음)
- collector 보강 P0 완료 시점부터 신규 INSERT가 컬럼 자동 채움

### 왜 collector가 직접 컬럼에 박지 않고 details JSONB 거치나

collector 14종이 각자 다른 details 구조 — 어떤 건 `appMode` 박고, 어떤 건 `documentName` 박고, 어떤 건 `httpStatus` 박음.

| 방식 | 단점 |
|---|---|
| collector가 직접 컬럼 INSERT | 모든 collector에게 8개 컬럼 INSERT 강제 → 자기와 무관한 컬럼도 NULL로 강제. 새 컬럼 필요할 때마다 collector 14개 *모두* 수정. **audit_events 스키마와 collector 코드의 강결합** |
| **details JSONB + Generated Column** | collector는 알고 있는 키만 자유롭게 details에 박음. DB가 추출. 새 컬럼 필요 → ALTER TABLE 한 줄. collector 14개 안 고침. **스키마와 적재 로직 분리** |

추가 이점:
- 원본 보존 (details JSONB가 남아있어 향후 다른 컬럼 추출 가능 — 정보 손실 0)
- collector 자율성 (자유 형태 details OK, 표준 스키마 강제 X)

### 왜 audit_events 자체에 컬럼 추가하나 (enriched/JSONB index 대안 대비)

| 옵션 | 인덱스 | 쿼리 형태 | 단점 |
|---|---|---|---|
| **X. audit_events Generated Column** (채택) | 일반 B-tree, planner 항상 활용 | `WHERE app_mode='chat'` | audit_events ALTER 필요 (데이터 0건이라 비용 0) |
| Y. enriched에서만 추출 (audit_events 미수정) | enriched 컬럼 인덱스 가능, 단 enriched 거쳐야만 | enriched 안에서만 깨끗 | **다른 소비처(보안/운영/임시 분석)가 audit_events 직조회 시 매번 `details->>` 다시 씀**. enriched가 유일한 인터페이스 → 결합도↑ |
| Z. audit_events 미수정 + JSONB expression index | `CREATE INDEX ON ((details->>'appMode'))` 가능 | `WHERE details->>'appMode'='chat'` 형태 강제 | **expression index는 planner가 정확히 같은 표현식 매칭 필요** — 살짝만 달라져도 인덱스 안 탐. 타입 캐스팅 매번. `is_canonical_call` 같은 복합 boolean은 부자연. `\d` 출력에 안 보임 |

→ JSONB 인덱싱은 *가능*하지만 *불편*하고 *제한적*. Generated Column은 audit_events를 **모든 소비처의 공용 인터페이스**로 만든다 (마트 + 보안 + 운영 + 임시 분석 모두 깨끗한 컬럼 쿼리).

### 4.2 v_audit_enriched (옵션 B — ID만 박음)

```sql
CREATE MATERIALIZED VIEW mart.v_audit_enriched AS
SELECT
  ae.id, ae.occurred_at, ae.tenant_id,
  ae.action, ae.actor_type, ae.actor_id,
  ae.target_app_id, ae.app_mode,
  ae.model_provider, ae.model_id, ae.total_tokens,
  ae.invoke_from, ae.triggered_from, ae.error_text,
  ro.owner_department_id AS app_owner_dept_id,    -- ID만 (이름은 query-time JOIN)
  dm.department_id       AS actor_dept_id,         -- ID만
  (COALESCE(ae.invoke_from,'')='debugger' OR COALESCE(ae.triggered_from,'')='debugging') AS is_debug,
  (ae.app_mode <> 'advanced-chat' OR ae.action='message_send') AS is_canonical_call
FROM audit.audit_events ae
JOIN rbac.resource_ownership ro                 -- INNER (결정 a)
       ON ro.tenant_id=ae.tenant_id AND ro.resource_type='app' AND ro.resource_id=ae.target_app_id
LEFT JOIN rbac.department_members dm            -- LEFT (end_user는 부서 없을 수 있음)
       ON dm.tenant_id=ae.tenant_id AND dm.account_id=ae.actor_id AND dm.is_active=TRUE
WHERE ae.action IN ('message_send','workflow_execute');   -- 결정 c
```

### 왜 MView + 사전 JOIN (옵션 B)인가

- **`is_debug` / `is_canonical_call` 플래그 컬럼화** → 컴포넌트 쿼리가 H-DASH-01(AppMode 이중카운트)/H-DASH-03(디버깅 혼입) 방어를 빠뜨릴 수 없음. 마트 인터페이스에 방어를 강제로 흡수
- **부서명 컬럼 제거 (옵션 B 핵심)** — `departments`는 운영 스케일에서도 백 단위 → 컴포넌트 쿼리 query-time JOIN 무비용. 부서명 변경 즉시 반영
- **owner_dept INNER JOIN** → enriched에 들어온 행은 모두 부서 분류됨. NULL 발생 자체가 사고 신호로 모니터링 메트릭에 잡힘
- **actor_dept LEFT JOIN** → end_user/api 액터 보존 (외부 사용자 호출도 owner 부서로는 집계되므로 행 유실 X)
- **사전 JOIN의 의미**: audit × 대형 RBAC(dept_members 만 단위) 결합을 **refresh 시 1회만** 수행. 동시 N명 사용자가 매 쿼리에서 hash build 반복하는 옵션 C 방식의 누적 부담을 피함
- **MView 선택 사유**: View는 매 조회마다 audit×RBAC JOIN 풀스캔이라 동시 사용자 부하 위험. fact 테이블 + incremental ETL은 운영 데이터 양(< 1억 행) 기준 과잉. MView가 "100만~1억 행 + 동시 read-heavy" 워크로드의 sweet spot

### INNER vs LEFT JOIN 선택 의미

두 JOIN의 의미가 정반대입니다:

| JOIN | 의미 | 막는 것 / 보존하는 것 |
|---|---|---|
| INNER on `resource_ownership` | "매칭 *되어야 정상*" — 결정 a(레거시 없음)에 따라 모든 앱이 ownership에 등록되는 게 정상 | 매칭 안 되는 audit 행이 사라짐 → 모니터링 #3가 캐치 → **사고를 *드러나게* 하는 장치** |
| LEFT on `department_members` | "매칭 *안 될 수도 정상*" — actor_type이 end_user/api/system이면 dept 매핑 자체가 없는 게 자연 | 행은 보존(actor_dept_id=NULL) → **외부 액터 호출이 owner 기준 집계에서 누락 안 됨** |

비즈니스 약속의 차이가 JOIN 선택을 결정: "모든 앱은 부서가 있어야 한다"는 강한 약속이 있는 쪽은 INNER, "모든 액터가 부서 소속이어야 한다"는 약속이 없는 쪽은 LEFT.

### 플래그 컬럼화의 진짜 이유 — 시간이 지나며 사고가 누적되는 구조 차단

`is_debug` / `is_canonical_call`을 *컬럼*으로 박지 않고 매 컴포넌트 쿼리에서 `WHERE invoke_from != 'debugger' AND ...` 직접 쓸 수도 있음. 굳이 컬럼화하는 이유:

| 시점 | 컬럼화 안 했을 때 일어나는 일 |
|---|---|
| 지금 | 백엔드가 KPI #3 SQL 쓸 때 `CASE WHEN app_mode='advanced-chat' THEN action='message_send' ELSE TRUE END` 정확히 씀 |
| 3개월 후 | 다른 개발자가 KPI #4 SQL 추가. H-DASH-01 모름 → AppMode 분기 누락 → 카운트 2배 ❌ |
| 6개월 후 | 새 컴포넌트 추가. 또 누락 ❌ |
| 1년 후 | 한 군데만 고치고 다른 데 못 고침 → 컴포넌트 간 숫자 불일치 ❌ |

→ 컴포넌트 = N명 × N시간이 지남. 방어 코드를 매번 복사하라고 하면 어딘가에서 빠짐. **책임을 코드 한 곳에 모아서 누락 가능성을 0으로 만든다**가 본질. 마트 설계 황금 규칙: "비즈니스 규칙은 마트 안에 흡수하고, 컴포넌트는 그냥 SELECT한다".

추가 이점:
- 인덱스 가능 (`WHERE is_canonical_call` boolean에 인덱스 박을 수 있음)
- 자기문서화 (`is_debug`는 의미가 이름에 박힘. `invoke_from != 'debugger'`는 "이게 왜 들어가지?" 질문이 매번 발생)
- 일관성 ("디버깅이란 무엇인가" 정의가 한 줄로 박힘 — 정의 바뀌면 enriched 한 곳만 고침)

### 4.3 mv_kpi_calls_daily (옵션 B — ID만 박음)

```sql
CREATE MATERIALIZED VIEW mart.mv_kpi_calls_daily AS
SELECT
  tenant_id,
  date_trunc('day', occurred_at AT TIME ZONE 'Asia/Seoul') AS day,
  app_owner_dept_id,    -- ID만 (이름은 컴포넌트 쿼리에서 JOIN)
  actor_dept_id,         -- ID만
  target_app_id, app_mode,
  COUNT(*) AS calls,
  COUNT(DISTINCT actor_id) AS users,
  COUNT(*) FILTER (WHERE error_text IS NOT NULL) AS errors,
  SUM(total_tokens) AS tokens,
  MAX(occurred_at) AS last_seen
FROM mart.v_audit_enriched
WHERE NOT is_debug AND is_canonical_call
GROUP BY 1,2,3,4,5,6;
```

타임존: `Asia/Seoul` day 경계 (사용자 인지와 일치).

### 왜 daily roll-up인가

- 기간 선택기(`dashboard-controls`)가 항상 day 경계 → day까지 굴려두면 **기간/이전기간 모두 `SUM` 한 번으로** 끝남
- 카드 4종 + drill-through 4구역 + dept-activity + 이전기간 비교 = 같은 큐브를 다른 GROUP BY로 N회 재사용
- `(day × actor_dept × owner_dept × 앱 × app_mode)` 단위로 정밀도 유지 → 채택(actor)/호출(owner)/AppMode 분기 모두 큐브에서 자연 분리
- 시간(hour) 단위 차트가 필요해지면 별도 mat 추가 (현재 컴포넌트 요구 없음)

### actor_dept_id + app_owner_dept_id 둘 다 보존하는 이유

같은 호출 1건이 두 컴포넌트에서 *다른 부서로 분류*되기 때문. 시나리오:

> 마케팅팀 김대리가 IT팀이 만든 사내챗봇을 호출 1번

enriched 한 행에 두 부서가 동시에 박힘:

| 컬럼 | 값 |
|---|---|
| actor_id | 김대리 |
| **actor_dept_id** | **MKT** |
| target_app_id | 사내챗봇 |
| **app_owner_dept_id** | **IT** |

각 컴포넌트가 같은 행을 다르게 본다:

```sql
-- KPI #2 (채택): "MKT 부서원이 쓰는 앱 종류" → actor 기준 +1
SELECT COUNT(DISTINCT target_app_id) ... WHERE actor_dept_id='MKT';

-- KPI #3 / dept-activity (호출): "IT 부서가 만든 앱이 받은 호출" → owner 기준 +1
SELECT app_owner_dept_id, SUM(calls) ... GROUP BY app_owner_dept_id;
```

→ "마케팅 입장에선 IT챗봇이 우리 도구이고, IT 입장에선 자기 앱이 사용된 것" — 같은 데이터를 *다른 비즈니스 관점*으로 보는 게 정답. mat에 두 ID 다 보존해야 두 관점이 같은 큐브에서 다른 GROUP BY로 공존.

카디널리티: 부서 N개면 `actor × owner = N²` 조합. N=100이어도 1만 × day(30) × 앱(수십) × app_mode(3) = 백만 행 이내. 부담 없음.

**컴포넌트 쿼리 예 (부서명 query-time JOIN)**:
```sql
SELECT d.name AS dept, SUM(c.calls) AS calls, SUM(c.tokens) AS tokens
FROM mart.mv_kpi_calls_daily c
JOIN rbac.departments d ON d.id = c.app_owner_dept_id   -- 매번 JOIN, departments 작아서 무비용
WHERE c.tenant_id=:tid AND c.day BETWEEN :start AND :end
GROUP BY d.name;
```

### 4.4 mv_model_tokens_daily

```sql
CREATE MATERIALIZED VIEW mart.mv_model_tokens_daily AS
SELECT
  tenant_id,
  date_trunc('day', occurred_at AT TIME ZONE 'Asia/Seoul') AS day,
  COALESCE(model_provider,'미분류') AS model_provider,
  COALESCE(model_id,'미분류')       AS model_id,
  SUM(total_tokens) AS tokens,
  COUNT(*)          AS calls
FROM mart.v_audit_enriched
WHERE NOT is_debug AND action='message_send' AND total_tokens IS NOT NULL
GROUP BY 1,2,3,4;
```

workflow_execute는 모델 정보 구조적 미가용 → message_send만 집계 (H-DASH-02).

### 왜 별도 mat인가 (kpi_calls_daily와 분리)

- 그룹핑 차원이 완전히 다름 — calls는 (부서 × 앱), tokens는 (모델 provider × 모델 ID). 한 큐브에 합치면 카디널리티 폭증
- model-tokens는 model_provider/model_id가 필수, kpi_calls는 부서/앱이 필수 → 각자 인덱스/UNIQUE KEY 다름
- workflow_execute는 모델 정보 없으니 model mat에서 자연 제외 (`action='message_send'`만)

### 4.5 v_resource_ownership_enriched

```sql
CREATE VIEW mart.v_resource_ownership_enriched AS
SELECT
  ro.tenant_id, ro.resource_type, ro.resource_id,
  ro.owner_department_id, d.name AS owner_dept_name,
```

INNER JOIN (결정 a). 행이 빠진 ownership은 모니터링에서 잡음.

### 왜 MView가 아닌 View인가

- `resource_ownership`은 수백~수천 행 규모 (audit_events 9백만과 자릿수 다름) → View로도 풀스캔 비용 무시 가능
- View는 stale 없음 → **RBAC 변경(부서 이동, ownership 갱신) 즉시 반영**. KPI #1 총 오브젝트가 사용자 작업 직후 바로 보이는 게 자연스러움
- MView로 만들면 5분 stale + refresh cron 1개 추가 비용 — 작은 테이블에 굳이 들일 필요 없음

## 5. 새로고침 + 모니터링

### 5.1 pg_cron 5분 주기 + 의존 순서 체이닝

mat 간 의존 순서(`enriched → daily mat`)를 명시적으로 보장하기 위해 **단일 cron job 안에서 순차 실행**:

```sql
SELECT cron.schedule('mart_refresh_chain', '*/5 * * * *', $$
  REFRESH MATERIALIZED VIEW CONCURRENTLY mart.v_audit_enriched;
  REFRESH MATERIALIZED VIEW CONCURRENTLY mart.mv_kpi_calls_daily;
  REFRESH MATERIALIZED VIEW CONCURRENTLY mart.mv_model_tokens_daily;
$$);
```

### 왜 cron 체이닝인가

cron job을 mat별로 분리하면 (`*/5 * * * *` 3개) — 셋 다 *동시*에 시작 → daily mat이 enriched의 *이전* 결과를 기준으로 refresh됨 → mart lag에 5분 추가 누적 (collector 5분 + enriched 5분 + mat 5분 = 최악 15분).

체이닝하면 — enriched refresh 끝난 즉시 daily mat이 같은 cron tick 안에서 순차 실행 → **mat 단계 추가 지연 ~0분** (모든 mat이 *같은 enriched 스냅샷*을 기준으로 함).

→ 최악 지연이 10분 → ~6~7분으로 감소.

### 왜 INSERT trigger가 아니라 cron인가 (실시간 옵션 미채택 사유)

기술적으로는 `pg_trigger` AFTER INSERT → enriched에 행 1개 추가 (단 enriched가 MView가 아닌 *fact 테이블*이어야 함, MView는 전체 재계산이라 무의미). 또는 LISTEN/NOTIFY로 incremental ETL.

이걸 *현재 안 한 이유는 병목 분석*:

```
[Dify INSERT] → [collector 폴링 5분] → [chain refresh 5분] = 최악 10분
                       ↑
                  진짜 병목
```

**시스템 전체 lag = MAX(병목 단계)**. enriched만 실시간(0초)으로 만들어도 collector가 5분 폴링이라 사용자 입장에선 여전히 5분 lag. enriched 실시간화의 이득이 collector 단계에서 다 흡수됨.

→ 진짜 실시간이 필요하면 *collector도 함께 실시간화*(pg_trigger 또는 logical replication, § 7의 B/C 단계). 한쪽만 바꾸면 비용만 들고 효과 0. + incremental ETL은 멱등성/실패 재시도/ordering 비용 따라옴.

배치(cron)로 시작 → 운영 부하 보고 진화하는 것이 안전.

### 왜 5분 주기 + CONCURRENTLY인가

- **TanStack staleTime 5분과 정합** — 프론트가 어차피 5분 캐시하므로 더 자주 refresh해도 사용자 인지 차이 없음
- 대시보드는 분 단위 신선도면 OK (실시간 요구 X). 보안 알림처럼 초 단위 필요한 영역은 별도 마트로 분리 (현재 범위 밖)
- `CONCURRENTLY`로 refresh 중에도 SELECT 가능 → **다운타임 0** (전제: 각 mat에 UNIQUE INDEX)
- pg_cron 단일 인프라로 처리 — 별도 ETL 워커/스케줄러 도입 불필요
- 1분 주기 안 됨: chain 전체(enriched + 2 daily mat)가 그 자체로 수 분 걸리는데 주기 안에 끝나야 다음 cycle과 안 겹침. 5분 주기 + chain 전체 4분 임계 = 1분 여유

### RBAC 변경 stale의 두 시나리오

| 시나리오 | 변경 대상 | DB 시점 stale | 사용자 체감 stale | 이유 |
|---|---|---|---|---|
| 인사이동 (김대리 IT → MKT) | `department_members.department_id` | 최대 5분 | 최대 5분 | dept_members가 enriched MView에 박혀있어서 refresh 대기 |
| 부서명 변경 (IT → IT본부) | `departments.name` | **0초** | 최대 5분 (프론트 캐시만) | 옵션 B로 query-time JOIN이라 DB는 즉시. 프론트는 TanStack 5분 |

옵션 A(이름까지 박는 안)였다면 부서명 변경도 DB 시점 5분 stale이었을 것 — 옵션 B의 실질 이점.

> ⚠️ 인사이동 시 한계: refresh되면 **김대리가 IT 시절에 한 과거 호출도 MKT로 재분류**됨. SCD type 2 아니라서 시점 보존 안 됨. "현재 부서 기준 재집계"가 비즈니스 의도와 다르면 별도 작업 필요.

### 5.2 모니터링 메트릭 6개

lag는 *단계 분리*해서 진단 효율 확보 (어디서 막혔는지 즉시 식별).

| # | 메트릭 | 임계 |
|---|---|---|
| 1a | **collector lag**: `now() - max(occurred_at) FROM audit_events` | > 10분 (폴링 5분 + buffer 5분) |
| 1b | **mart lag**: `max(occurred_at FROM audit_events) - max(occurred_at FROM mv_kpi_calls_daily)` | > 7분 (chain refresh 5분 + buffer 2분) |
| 2 | chain REFRESH 소요 (pg_cron job_run_details) | > 4분 |
| 3 | enriched vs src 행수 차이 (대상 action 한정) | > 0 → ownership 누락 사고 |
| 4 | `resource_ownership.owner_department_id IS NULL` 카운트 | > 0 → 부서 누락 사고 |
| 5 | enriched의 actor_dept_id IS NULL & actor_type='account' 비율 | > 5% → department_members 동기화 사고 |

### lag 단계 분리 사유

호출 1건이 mat에 반영되기까지 누적 지연 (cron 체이닝 적용 후):

| 단계 | 최악 지연 | 누적 |
|---|---|---|
| Dify 호출 → messages INSERT | ~0 | 0 |
| dify-audit collector 폴링 (5분 주기) | 5분 | 5분 |
| chain refresh (enriched + daily mat 순차) | 5분 | **10분** |

cron 체이닝 덕분에 mat 단계 추가 5분이 사라짐. 단일 lag 메트릭(임계 10분)으로 보면 *어느 단계에서 막혔는지* 모름. collector와 mart 단계를 분리하면 경고 시 즉시 진단 가능 (collector면 `collector_state` 확인, mart면 pg_cron job 확인).

### 메트릭의 3단계 사고 캐치 메타

#3 / #4 / #5는 데이터 파이프라인의 *다른 단계*에서 다른 종류의 사고를 캐치:

```
[적재 단계]  audit_events에 이벤트 들어옴
   ↓
   #3 잡음: 이 이벤트의 target_app_id가 RBAC ownership 시스템에 아예 등록 안 됨
            → INNER JOIN으로 enriched에서 사라진 행을 src 행수와 비교해 감지

[등록 단계]  RBAC에 ownership 행 생성
   ↓
   #4 잡음: ownership은 등록됐는데 부서 컬럼이 NULL
            → enriched도 사라짐(같은 효과) + KPI #1 총 오브젝트에서 자산 누락

[동기화 단계]  RBAC dept_members가 Dify accounts와 매핑됨
   ↓
   #5 잡음: 자산은 다 OK인데, 사용자 부서 매핑이 누락
            → LEFT JOIN이라 enriched에 행은 남되 actor_dept_id NULL
            → KPI #2 채택 카드에서 그 사용자 활동이 분류 못 됨
```

세 메트릭이 합쳐서 **마트 건강 진단 체계**. 마트 객체 자체는 사고 나도 묵묵히 돌아가지만(사고 묻히기 쉬움), 메트릭이 옆에서 watching해서 *마트가 거짓말하는 순간*을 감지.

## 6. 실시간 확장 경로

```
[현재]  Postgres pg_cron 5분 (배치 MView)
   ↓ 부하 증가 / lag 5분 부족
[A]    각 mat에 incremental refresh (last_refreshed_at 컬럼)
   ↓ 실시간성 요구 (30초 이내 반영)
[B]    PG logical replication / pg_trigger → Redis Stream
            → 별도 fact 테이블 incremental upsert
   ↓ 글로벌 / 멀티테넌트 스케일
[C]    분석 DB 분리 (ClickHouse / TimescaleDB)
```

**핵심**: Layer 2가 컴포넌트의 인터페이스 — `mv_kpi_calls_daily`만 보면 아래 구현이 MView → incremental fact → 분석DB로 바뀌어도 컴포넌트 코드 무수정.

### 8.1 단계별 데이터 흐름

```
[T+0초]
```

### 8.2 사고 차단 지점 3개

| 차단 위치 | 막은 사고 | 효과 |
|---|---|---|
| Generated Column 자동 계산 | collector가 details만 INSERT하면 컬럼은 DB가 채움 | collector 코드 N개에 추출 로직 안 흩어짐 |
| enriched INNER JOIN | ownership 미등록 호출 차단 + 메트릭 #3가 캐치 | "ownership 없는 호출"이 묻혀서 누락되지 않음 |
| `is_canonical_call` 플래그 | advanced-chat의 message_send만 카운트 (workflow_execute 제외) | 컴포넌트가 H-DASH-01 모르고 SQL 짜도 이중카운트 발생 X |

→ 마트 인터페이스 단계마다 *방어를 흡수*해서, 컴포넌트는 그냥 `SUM(calls)`만 쓰면 자동으로 정확한 숫자가 나옴.

### 8.3 메트릭의 위치 — 흐름의 *옆*에서 watching

```
        [메인 흐름]                         [메트릭 watching]
                                            (주기적 실행, 옆에서 감시)
audit_events INSERT                ←──→ #1a collector lag
       ↓
v_audit_enriched (MView refresh)   ←──→ #1b mart lag, #2 refresh 소요
                                   ←──→ #3 행수 차이, #5 actor NULL
mv_kpi_calls_daily (MView refresh)
       ↓
컴포넌트 SELECT                    ←──→ #4 dept NULL (ownership 단계)
       ↓
KPI 카드 렌더링
```

- **정상 흐름 시**: 어떤 메트릭도 발동 안 함. 마트가 묵묵히 돌아감
- **사고 시** (예: IT챗봇이 ownership 미등록): enriched에 행 0건 진입 → KPI #3 +1 안 됨 ❌ → 메트릭 #3이 캐치 → 운영자가 ownership 등록 → 다음 refresh부터 정상

메트릭은 **마트의 "건강 검진"**이지 데이터 흐름의 일부가 아니다. 마트 객체 자체는 사고 나도 묵묵히 돌아가지만(그래서 사고가 묻히기 쉬움), 메트릭이 옆에서 watching해서 *마트가 거짓말하는 순간*을 감지한다.

### 8.4 같은 호출 1건의 다른 컴포넌트 분류

위 흐름의 행 A 1건은 동시에 여러 컴포넌트에 영향:

| 컴포넌트 | 분류 기준 | 결과 |
|---|---|---|
| KPI #2 채택 (사용자가 MKT 소속이면) | `actor_dept_id=MKT` 필터 | MKT 채택 앱 +1 (IT챗봇 종류) |
| KPI #3 API 호출 | 부서 무관 합계 | 총 호출 +1 |
| KPI #4 Top 앱 | `target_app_id=IT챗봇` GROUP BY | IT챗봇 호출 +1 |
| dept-activity (IT 행) | `app_owner_dept_id=IT` GROUP BY | IT 부서 호출 +1, 토큰 +350 |
| model-tokens | `model_provider, model_id` GROUP BY (`mv_model_tokens_daily`) | 해당 모델 토큰 +350 |
| drill-through 표 (IT챗봇 행) | `target_app_id=IT챗봇` | IT챗봇 호출/사용자/토큰 누적 |

→ 같은 큐브를 다른 GROUP BY로 N회 재사용 = 2계층 마트의 본질적 이점.
