# 대시보드 라우트 이동 - 3 어드민 게이트

> 배경: 대시보드를 설정 모달 탭 → 독립 라우트(`/admin/dashboard` 가정)로 이전 예정.
> 일반 사용자가 URL 직접 입력으로 들어왔을 때 차단할 게이트가 필요. 기존 패턴 식별 → 동형 적용이 목표.

---

## 기존 어드민 게이트 (있음 / 위치)

**부분적으로 있음. 백엔드 데코레이터 스택은 있으나 role 체크가 빠져 있고, 프론트는 admin 전용 가드가 아직 없음.**

### 백엔드 — `api/controllers/console/admin/dashboard.py:24-28`

```python
_DASHBOARD_DECORATORS = [
    account_initialization_required,
    login_required,
    setup_required,
]
```

- 모든 `/admin/dashboard/*` 라우트가 이 스택 적용 (`method_decorators = _DASHBOARD_DECORATORS`, 라인 46 등)
- **결함**: 로그인한 일반(`normal`) 사용자도 통과 → role 게이트 미적용

### 백엔드 — 별도 admin 패턴 (`api/controllers/console/admin/__init__.py`)

- `@admin_required` 데코레이터: `ADMIN_API_KEY` 헤더 검증 방식 (서버 간 호출용, 사람용 아님)
- `/admin/insert-explore-apps` 같은 운영 작업용 → **대시보드와 모델 다름** (참고만)

### 프론트 — `web/app/(commonLayout)/role-route-guard.tsx`

- 현재는 **dataset_operator → `/datasets` 리다이렉트 전용** (라인 9, 14, 17)
- admin 게이트 용도는 아니지만, `useAppContext()`에서 role 필드 읽어 redirect하는 **동형 패턴 템플릿**으로 활용 가능

## 권한 판별 채널

| 계층 | 출처 | 헬퍼 / 필드 |
|------|------|------------|
| DB | `accounts.role` 컬럼 (StrEnum) | `TenantAccountRole` (owner/admin/editor/normal/dataset_operator) — `api/models/account.py:19-49` |
| 백엔드 런타임 | `current_user.current_tenant_role` (flask_login 세션) | `TenantAccountRole.is_privileged_role(role)` → `owner` ∪ `admin` (account.py:38-42) |
| 프론트 API | `/console/api/account/profile` 응답의 `currentWorkspace.role` | `web/models/common.ts` |
| 프론트 훅 | `useAppContext()` | `isCurrentWorkspaceManager` (owner∪admin), `isCurrentWorkspaceOwner`, `isCurrentWorkspaceEditor`, `isCurrentWorkspaceDatasetOperator` |

→ **둘 다 같은 DB 컬럼이 진실 공급원.** Keycloak claim 별도 사용 안 함 (조사 범위 내).

## 게이트 위치 후보 비교

| 위치 | UX | 보안 | 구현 난이도 | 기존 패턴 부합 |
|------|----|------|----------|--------------|
| (A) `web/middleware.ts` (Edge middleware) | ◎ URL 진입 즉시 차단, 깜빡임 없음 | ◎ JS 다운로드 전 차단 | ✗ 현재 프론트에 middleware.ts 없음. role을 어디서 가져올지 새로 설계 (쿠키 파싱? edge에서 fetch?) | ✗ 선례 없음 |
| (B) page-level guard (`useAppContext`) | △ profile 로딩 후 1프레임 깜빡임 후 redirect | ○ (UI 진입은 되지만 데이터는 백엔드가 막음) | ◎ 5~10줄, `RoleRouteGuard`와 동형 | ◎ 기존 패턴 그대로 |
| (C) layout-level guard (`(commonLayout)/admin/layout.tsx`) | △ B와 동일 | ○ | ○ admin 라우트 여러 개 생길 경우 한 곳에서 일괄 | ◎ Next.js app router 정석 |
| (D) API 단 403만 (프론트 가드 없음) | ✗ UI 다 로드된 후 에러 토스트 — "왜 안 보이지" 혼란 | ◎ 백엔드만 신뢰 | ◎ 데코레이터 한 줄 추가 | ○ 백엔드만이라 절반 |

## 추천

**(C) layout-level 프론트 가드 + 백엔드 데코레이터 스택 확장 (이중 게이트).**

1. **프론트**: `web/app/(commonLayout)/admin/layout.tsx`에서 `useAppContext()`의 `isCurrentWorkspaceManager` 검사 → false면 `/apps` 등으로 `router.replace`. `RoleRouteGuard`(라인 13~33)와 동일한 골격(로딩 처리 + early return) 따라 작성. 향후 admin 라우트가 늘어도 자동 적용.
2. **백엔드**: `_DASHBOARD_DECORATORS` (dashboard.py:24)에 `admin_role_required` 데코레이터 추가. 내부에서 `TenantAccountRole.is_privileged_role(current_user.current_tenant_role)` 검사 후 403. 신규 데코레이터는 `api/controllers/console/wraps.py`에 정의 → 다른 admin 라우트에서도 재사용.

이중 게이트 근거: 프론트만 두면 API 직접 호출(curl/devtools)로 우회 가능하고, 백엔드만 두면 UX가 D처럼 깨짐. 두 계층 모두 같은 `TenantAccountRole` 진실 공급원을 보기 때문에 분기 정합성 위험은 낮음.
