# 앱별 통계 KPI 설계 작업

> 이사님 2차 미팅(2026-05-12 늦은 오후) 결정으로 **에러율 KPI → 앱별 통계 KPI 교체**. 처음부터 설계.

## 컨텍스트

- KPI 4종 새 구성:
  1. 총 오브젝트 (그대로)
  2. 부서별 사용
  3. API 호출
  4. **앱별 통계** ← 본 작업
- 영역 구성: 좌상(카드) / 좌하 / 우하 / 하단 표 + 차트 드로어 (KPI 드로어 좌하 차트 클릭 트리거)
- **데이터 소스 = audit 마트 단독 고정** (이사님 결정). OLTP/Dify endpoint 직접 호출 회피.
  - 단 검증 필요: audit details에 어떤 raw 메트릭이 들어오는지 (token, response_time, 만족도 등)

---

## Step 1. 어드민 핵심 질문 정의

**어드민이 앱 단위로 알고 싶은 게 무엇인가?**

후보:

| # | 어드민 질문 | 의사결정 |
|---|---|---|
| (a) | "어느 앱이 진짜 쓰이고 어느 앱이 죽어있나?" | 비활성 앱 정리, 거버넌스 |
| (b) | "어느 앱이 핵심(많이 쓰이는)인가?" | 자원 할당, 인기 앱 추적 |
| (c) | "어느 앱이 문제 있나(에러 많은)?" | 안정성 대응 — 이전 에러율 KPI 역할 흡수 가능 |
| (d) | "최근 만들어진 앱 / 오래된 앱은 뭔가?" | 라이프사이클 추적 |
| (e) | "앱별로 누가 만들고 누가 쓰나?" | 소유자/사용자 매핑 |

### 두 시나리오 병행 정리 (사용자 선택 대기)

| 시나리오 | 채택 질문 | 강조 신호 |
|---|---|---|
| **(a)+(c) 조합** | (a) 거버넌스 + (c) 안정성 | 활성/비활성 앱 + 에러 대응 |
| **B (모니터링 통합)** | (b) 인기 + (c) 안정성 + 모니터링 신호 종합 | 평균 사용 강도 + 앱별 다신호 |

**사용자 결정 (2026-05-13)**: **B 채택** — 이사님 의도 = "모니터링 + 차트/표 클릭 시 앱별 모니터링 화면 이동". 운영 초기 즉시 사용 가능 + 활성 임계값 결정 부담 회피.

## Step 2. 카드 헤드라인 숫자

### 시나리오 (a)+(c)

| 헤드라인 후보 | 의미 | 정보 중복 의문 |
|---|---|---|
| "활성 앱 N / 전체 M" | "11개 중 7개 활성" | ⚠️ 전체 M = 총 오브젝트 App 부분과 같음 |
| ⭐ **"활성률 N%" + 부제 "에러 K"** | 비율 + 안정성 신호 | 정보 중복 회피 가능 |
| "활성 N + 에러 K" | 두 신호 동시 | 약한 중복 |

→ **추천**: `활성률 N%` (대 헤드라인) + `에러 발생 K개` (부제)
→ **검증 필요**: 활성 정의 (Step 4)

**사용자 결정**:

### 시나리오 B

| 헤드라인 후보 | 의미 | audit 데이터 가능성 |
|---|---|---|
| "평균 호출/앱" | 사용 강도 평균 | ✅ audit 호출 이벤트로 자체 계산 |
| "평균 에러율 (앱 평균)" | 안정성 평균 | ✅ audit 에러 이벤트로 자체 계산 |
| ⭐ **"평균 호출/앱 + 부제 평균 에러율"** | 사용 + 안정성 | ✅ 둘 다 audit으로 계산 |
| "Top 앱 호출 N" | 1위 앱 강조 | ✅ audit 호출 집계 |
| "평균 TPS / 만족도" | Dify 모니터링 신호 | ⚠️ audit details에 raw 정보 있는지 검증 필요 |

→ **추천**: `평균 호출/앱 N` (대 헤드라인) + `평균 에러율 N%` (부제) — audit으로 둘 다 자체 계산 가능

**사용자 결정 (2026-05-13)**: **"Top 앱 호출 N" + 부제 "앱명"** — "평균 호출/앱"은 KPI 3번 "부서별 앱 호출 수"와 grain만 다른 동일 메트릭이라 의미 중복. 1위 앱 강조로 차별화. 부제는 앱명만(부서 제외 — 가독성 우선).

## Step 4. 활성 앱 정의 (시나리오 (a)+(c)만 필요)

### 시나리오 (a)+(c)
"활성 앱" 정의 필수 — 카드/좌하/표 활성도 컬럼의 기반.

| 정의 후보 | 데이터 검증 필요 |
|---|---|
| ⭐ 최근 7일 내 호출 ≥ 1 | ✅ 단기 활성 신호 |
| 최근 30일 내 호출 ≥ 1 | ✅ 중기 활성 신호 |
| 누적 호출 ≥ N (예: 100) | ⚠️ 작은 앱에 불리 |
| 사용자당 호출 ≥ N | ⚠️ 정의 복잡 |

→ **추천**: 최근 30일 내 호출 ≥ 1 (단 audit 90일 보존이라 90일 이전 정보는 없음 — 운영 초기엔 의미 약함)
→ **VSCode 위임**: 운영 데이터로 임계값 의미 검증 필요

**사용자 결정 (2026-05-13)**: **(a)+(c) 미채택으로 본 Step 불필요** — 시나리오 B 채택. 활성 임계값 결정 부담 회피한 게 B 선택의 주요 사유 중 하나.

### 시나리오 B
- 활성 앱 정의 **불필요** — 사용 강도 신호로 대체. (b) 인기 앱 / (c) 안정성 신호가 직접 답함.
- 단 표에 "마지막 사용일" 컬럼이 있어 어드민이 직접 판단 가능

## Step 5. 차트 드로어 트리거

이사님 결정: 좌하 차트 클릭 → 차트 드로어. 좌하 grain이 "앱별"이라 클릭 = 특정 앱 선택.

### 시나리오 (a)+(c) 공통
- 좌하 막대(특정 앱) 클릭 → 우측 드로어
- 드로어 내용: 그 앱의 audit 이벤트 로그 + 상세 (에러 분류 / 호출 추이 / 사용자 리스트)

### 시나리오 B 공통
- 동일 트리거
- 드로어 내용: 그 앱의 audit 이벤트 로그 + 모니터링 미니뷰 (호출 추이 / 에러 / 사용자)

→ **두 시나리오 차트 드로어 거의 동일**. 좌하 그 앱 클릭 시 디테일.
→ E 작업 (차트 드로어 4종 가치 검증)에서 다른 KPI 드로어와 함께 결정

## 최종 통합 — C 노트 v2에 박을 내용

> Step 1~5 결정 끝나면 시나리오 선택 → 아래에 정리. C 작업 세션이 v2 노트에 통합할 때 본 섹션 사용.

### 시나리오 (a)+(c) 채택 시
- **카드**: 활성률 N% + 에러 발생 K개
- **좌하**: 앱별 활성도 막대 (활성/비활성 색상 분리, hover에 마지막 사용일)
- **우하**: Top 에러 앱 (또는 에러 유형별 분포 — top-error-types 통합 검토)
- **하단 표**: 앱명 / 부서 / 활성도 / 에러율 / 마지막 사용 (5컬럼)
- **차트 드로어 트리거**: 좌하 앱 클릭 → 그 앱 상세 + 이벤트 로그
- **선결 조건**: 활성 앱 정의 (Step 4) + audit `targetAppId` 검증

### 시나리오 B 채택 (2026-05-13 확정)

**4영역 구성**
- **카드 헤드라인**: `Top 앱 호출 N` + 부제 `앱명` (옵션 4 — KPI 3번과 의미 중복 회피)
- **좌하**: 앱별 호출 수 **가로 막대 Top 10** (옵션 A)
- **우하**: Top 에러 앱 **가로 막대 Top 10** (옵션 a1) — 좌하/우하 둘 다 가로 막대지만 강조 차원 분리(분포 vs Top)
- **하단 표 (필수 6컬럼)**: 앱명 / 부서(소유) / 호출 수 / 사용자 수 / 에러율 / 마지막 사용일
- **하단 표 선택 컬럼 후보** (audit 검증 후 결정):
  - 앱 타입 (App/KB/Tool) — ✅ `resource_ownership.resource_type`로 가능
  - 평균 응답시간 — ⚠️ audit details raw 검증 필요
  - TPS — ⚠️ audit details raw 검증 필요
  - 만족도 — ⚠️ `message_feedbacks` collector 박힘 검증 필요

**표 행 클릭 동작 (신규 결정)**
- 클릭 영역: **행 전체** (앱명/호출/에러 등 어느 셀이든 클릭 가능)
- 이동 방식: **같은 탭**
- 이동 대상: Dify 앱별 모니터링 페이지 (`/app/{appId}/overview` 추정 — 라우트 분석 #1 결과 참조 필요)

**차트 드로어 + 표 클릭 역할 분리 확정 (2026-05-13 안 A)**
- 좌하 막대 클릭 → **차트 드로어** (지표 카드 추세 4종)
- 표 행 클릭 → Dify 모니터링 페이지 (`/app/{appId}/overview`)

**차트 드로어 KPI 4번 사양 (안 A — 공통 추세 지표)**
- 컨텍스트 헤더: 앱명 · 부서(소유) · 호출 · 기간 · 에러 포함
- 지표 카드 4개 (모두 추세/변화 표시 — AppMode 무관 공통):
  - 호출 N (+X% vs 지난 기간)
  - 사용자 수 N (+X명)
  - 에러율 N% (-X%)
  - 토큰 사용량 N (+X%)
- 로그: 그 앱의 호출·에러 audit 6건 (시간 역순)
- **표와의 차원 분리**: 표 컬럼(앱명/부서/호출/사용자/에러율/마지막 사용) = **현재 스냅샷**. 드로어 지표 = **추세/변화**. 정보 중복 없음.

**안 A 선택 사유 (2026-05-13)**
- 표 컬럼과 지표 중복 회피 (당초 안은 호출/사용자/에러율/마지막 사용으로 표와 100% 일치)
- 응답시간/만족도/모델 분포는 채팅형 전용 → AppMode 분기 spec 부담 → 공통 추세 지표가 단순
- KPI 4번 차트 드로어 가치 평가 ⚠️ 충돌 → ⭐⭐ 보통으로 격상 → E 작업 결과: 4종 다 살림 가능

**선결 조건**
- audit `targetAppId` 검증 (필수, 우선순위 2.5와 통합)
- TPS/만족도 raw 정보 검증 (선택 컬럼 채택 시)
