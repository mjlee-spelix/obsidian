# 화면 설계 검토 — 관리자 UX 가치 관점

> 이전 검토 노트(spec 정합성 위주)와 별개로, **"관리자가 이 화면을 보고 실제 무슨 결정을 내릴 수 있는가"** 관점에서 항목별 가치를 다시 검토.

## 시스템 본질과 사용자 정의

### 시스템
**기업 임직원이 Dify 기반 LLM 도구 플랫폼에서 앱/지식베이스/도구를 만들고 API 호출**하는 사내 시스템.

### 대시보드 사용자 = 관리자(어드민)
어드민이 답해야 할 핵심 질문 4가지:

1. **우리 회사 직원이 Dify를 잘 활용하고 있나?** — 도구 채택률
2. **어느 부서가 활발하고, 어느 부서가 안 쓰나?** — 부서별 활용도
3. **시스템 안정성에 문제 있나? 보안 이상은?** — 품질/안정성
4. **누가 핵심 기여자(앱/지식 생산자, 호출 사용자)인가?** — 핵심 인물 식별

→ 이 4가지 질문에 답할 수 있어야 화면이 가치 있음.

## KPI 4종 — SaaS/플랫폼 운영 표준 4축 패턴

| KPI | 축 | 의미 (관리자 관점) | 의사결정 |
|---|---|---|---|
| **총 오브젝트** | Volume (보유량) | "회사가 보유한 LLM 자산 양" | 자산 편중·미배정 정리, 거버넌스 |
| **활성 사용자** | Breadth (채택 폭) | "도구를 실제로 쓰는 직원 수" | 채택률 낮은 부서 교육, 도입 정착 판단 |
| **API 호출** | Depth (사용 강도) | "도구를 얼마나 자주 쓰나" | 모델 비용 관리, 인프라 사이징 |
| **에러율** | Quality (안정성·보안) | "서비스 품질 + 보안 이상" | 모델/API 이슈 대응, 침입 시도 감지 |

### 4축 패턴의 강점
- ✅ 의사결정 흐름과 직결 (Volume → Breadth → Depth → Quality 순으로 깊이 들어감)
- ✅ 4개 다 본질적으로 다른 정보, 중복 없음
- ✅ Breadth(폭) × Depth(깊이) 조합으로 "10명이 가끔? 5명이 폭주?" 구분 가능

### 약점/모호한 부분
1. **활성 사용자와 API 호출이 관리자에게 별개 신호로 읽히는가** — 둘 다 "사용 활동"이라 일반 사용자가 봤을 때 헷갈릴 수 있음
   - 권장: 카드 부제목으로 명시 — "활성 사용자(사람 수)" / "API 호출(호출 수)"
2. **모든 KPI의 기간 기준이 헤더 기간 따라가는지 명시 안 됨**
   - 권장: 카드에 미니 라벨 ("최근 7일")
3. **에러율이 호출+보안 통합 의미** — 사용자가 처음 보면 LLM 호출 에러만 생각함
   - 권장: hover tooltip 또는 부제목 ("LLM 에러 + 보안 이벤트")

## 신규/이탈 삭제 결정 — UX 관점 평가 ✅ 잘한 결정

### 왜 삭제가 맞는가
- "신규 임직원" = 입사 → **인사팀 영역**, Dify 관리자가 결정 내릴 일 없음
- "신규 활동(처음 호출)" → 출장/휴가/프로젝트 사이클 따라 변동 커서 패턴 추출 어려움
- "이탈(활동 끊김)" → 잠시 쉬는지 진짜 안 쓰는지 구분 어려움 + 임직원 평가 도구로 오용 위험

→ **변동성 큰 노이즈 신호**를 KPI에 박는 건 위험. 삭제 합리적.

### 대체 메트릭 후보 (관리자 의사결정 직결)
| 메트릭 | 의사결정 가치 |
|---|---|
| **Stickiness (DAU/MAU)** | 매일 쓰는 정착 정도 — 도입 성공 판단 |
| **사용자당 평균 호출 수** | 깊은 사용자/얕은 사용자 분포 |
| **Top 사용자 / Top 앱 변화** | 핵심 인물·자산 흐름 |
| **부서별 활용 순위 W-over-W** | 부서 활성도 변화 트렌드 |

## 차트별 관리자 가치 검토

### 메인 좌하 — 부서별 오브젝트 차트 (App/KB/Tool 스택)
- 의미: "어느 부서가 자산을 많이 만드나"
- 가치: ⭐⭐ 거버넌스 — 자산 편중, 미배정 발견
- 개선: ✅ "외부 막대" 삭제 결정 맞음 (오브젝트는 부서 소유 개념이지 사용자 개념 무관)

### 메인 우하 — 모델별 토큰 사용량 차트 ✅
- 의미: "어느 모델에 토큰(=비용 직결) 얼마 쓰나"
- 관리자 가치: ⭐⭐ 비용 분포 + 모델 채택 패턴 동시 신호 — 의사결정 직결
- **모델별 토큰량은 비용과 사실상 등가** (모델별 단가 × 토큰), 별도 비용 KPI 없어도 어느 정도 추론 가능
- 개선 검토 (가벼움):
  - 모델별 비용까지 직접 표시? (단가 곱하기) — 비용 KPI 부재 보완책
  - 또는 hover에 "추정 비용 $X" 표시

### 메인 하단 — 부서별 활동 테이블
- 의미: 부서 다차원 비교
- 가치: ⭐⭐⭐ 매우 높음 — 부서 간 활동 패턴 한 줄로 보임
- **"신규" 컬럼 = 신규 app/kb/tool (오브젝트 생성)** — 데이터로 계산 가능 + 의미 명확 → **유지**
- **사용자 신규/이탈만 삭제** (앞서 다룬 이사님 결정 — 사용자 활동 신규/이탈은 노이즈)
- **나중 고려용 대체/추가 컬럼 후보** (현재는 유지, 향후 검토):
  - **에러율** (안정성 — 어느 부서가 에러 많나)
  - **호출 추세 화살표 ↑↓** (이전 기간 대비)
  - 또는 컬럼 줄여서 단순화 (부서 / DAU / 호출 / 토큰 / 에러율 5컬럼)

## 차트 드로어 — 관리자 분석 경로 평가

### 시나리오 가치 ⭐⭐⭐ 매우 높음
"재무 14.5K 막대 클릭" → "재무 안에서 누가/언제/어떤 메시지로 그 14.5K 만들었나"

→ 집계 차트만으론 풀 수 없는 **이상치/특이 패턴 발견 경로**. 어드민이 가장 자주 쓰는 화면이 될 가능성.

### 미니 KPI 3종 (호출/활성/에러)
- 부서 단위 다차원 한눈에 — 좋음
- **컨벤션 정정 결정**:
  - **호출 / 활성 사용자**: 메인 KPI 카드와 표시 형식 통일 (예: 활성 사용자가 메인에서 사람 수면 드로어도 사람 수)
  - **에러**: 건수 + 비율 둘 다 표시 (예: "406건 / 2.8%")

### 활동 로그 행 (시간/사용자/내용/상태) ⭐⭐⭐ 핵심
- 어드민이 "누가 뭘 했나" 직접 볼 수 있는 유일한 화면
- 에러 행에 분류 라벨(model_timeout 등) + 색상 — 가치 큼
- 모범적 UX

### "더 많이 보기 → 감사 로그 풀뷰" ✅
- 미리보기 → 깊은 분석으로 자연스러운 경로
- 모범적 정보 아키텍처

## 컨텍스트 바 — drill-through 활성 상태 표시

> spec 출처: [[3. 프로젝트/spx-agent/hdd/specs/requirements/context-bar.md]]

### 역할
- KPI 카드 클릭으로 drill-through 활성 상태일 때만 노출 (종합 뷰엔 미렌더)
- 위치: KPI 섹션 바로 아래, 차트 영역 위
- 표시: `[메트릭: API 호출 ×]` 칩 1종 (선택된 메트릭만)
- × 클릭 → drill-through 해제 → 종합 뷰 복귀

### Slim 설계 (의도적으로 뺀 것)
PDF v0.3에는 기간/부서/URL/새로고침 칩이 있지만 우리 환경에선 중복이라 모두 제외:
- 기간 → DashboardControls (모달 헤더 우측)에 이미 있음
- URL 북마크 → 모달 환경 + 관리자 전용이라 불필요
- 새로고침 → DashboardControls에 있음
- 부서 → chart-drawer 자체 헤더에 표시

→ **활성 메트릭 칩 1종만**

### UX 가치
- ⭐ 유지 가치 있음 — drill-through 모드에서 "지금 무슨 메트릭 보고 있나" 시각화 + 해제 경로
- 작지만 모달 환경에서 길 잃기 쉬운 걸 막아주는 요소
- 단방향 뷰 원칙 (state는 drill-through 훅 단일 진실, 컨텍스트 바는 파생 뷰만)

## KPI 드로어 — 4영역 고정 레이아웃 평가

### 4영역 구성 (KPI별 — 사용자 확인)

| KPI | 좌상 (자기 카드) | 좌하 | 우하 | 하단 (표/그리드) |
|---|---|---|---|---|
| 총 오브젝트 | 카드 | 부서별 누적 오브젝트 | Top 소유자 | 부서별 신규 생성 |
| 활성 사용자 | 카드 | 부서별 DAU | 모델별 사용자 수 | 부서별 활성 사용자 |
| API 호출 | 카드 | 부서별 호출 | 모델별 호출 비중 | 부서별 호출 RPS (Top 앱/추세) |
| 에러율 | 카드 | 부서별 에러율 | Top 에러 유형 | 부서별 에러 |

→ **4영역 다 채워져 있음**. 빈 자리 없음.

### 4영역 고정의 장점
- ✅ 학습 비용 낮음 — 한 KPI 익히면 4종 다 익숙
- ✅ 시각적 일관성

### 각 항목 의미 평가

| KPI | 좌하 | 우하 | 하단 |
|---|---|---|---|
| **총 오브젝트** | 부서별 누적 ⭐⭐ 자산 분포 | Top 소유자 ⭐⭐ 핵심 기여자 식별 | 부서별 신규 생성 ⭐⭐ 거버넌스 추세 |
| **활성 사용자** | 부서별 DAU ⭐⭐ 부서별 활용도 | **모델별 사용자 수 🟡 가치 약함** | 부서별 활성 사용자 ⭐⭐ |
| **API 호출** | 부서별 호출 ⭐⭐ 사용 강도 | 모델별 호출 비중 ⭐⭐ 모델 분포 | 부서별 호출 RPS ⭐⭐ |
| **에러율** | 부서별 에러율 ⭐⭐ 안정성 신호 | Top 에러 유형 ⭐⭐⭐ 운영 핵심 | 부서별 에러 ⭐⭐ |

→ 12개 영역 중 11개는 의미 명확. **1개만 약함: 활성 사용자 KPI 드로어 우하 "모델별 사용자 수"**

### 약한 항목 — 활성 사용자 우하 "모델별 사용자 수"
- 의미: "GPT-4 쓰는 사람 30명, Claude 25명"
- 가치 약한 이유:
  - 사용자 수만으론 모델 선택/교체 의사결정 못 함
  - 다른 모델별 영역(메인 우하 "모델별 토큰", API 호출 우하 "모델별 호출 비중")과 정보 중복
- **대체안 (다른 KPI 드로어의 "Top XX" 패턴과 일관성)**:
  | 대체안 | 의사결정 가치 | 일관성 |
  |---|---|---|
  | **Top 사용자** (호출 많이 한 사용자) | 핵심 사용자 식별 — 어드민 핵심 질문 4번 직접 답 | ⭐⭐⭐ |
  | Stickiness (DAU/MAU 비율) | 정착 정도 | ⭐⭐ |
  | 활성 시간대 히트맵 | 인프라 부하 패턴 | ⭐ |
- **권장: Top 사용자** — 총 오브젝트의 "Top 소유자", 에러율의 "Top 에러 유형"과 패턴 일관

### 잠재적 검토 항목 — 비슷한 의미 영역 구분
- "부서별 DAU(좌하) + 부서별 활성 사용자(하단)" 처럼 **이름이 다른데 의미 비슷한 느낌** — 두 영역이 어떻게 다른지 사용자가 한눈에 구분되는지 UX 테스트
  - spec에 박힌 구분: 좌하 = 단순 가로 막대 (DAU 1종) / 하단 = 다컬럼 표 (DAU + WAU + 신규 + 이탈)
- "부서별 에러율(좌하) + 부서별 에러(하단)" 도 같은 케이스 — 율 차트(좌하) vs 다컬럼 표(에러/에러율/주원인/트렌드)로 spec에 박혀있음

### 하단 표 4종 — 컬럼 적절성 평가

> spec 출처: [[3. 프로젝트/spx-agent/hdd/specs/design/kpi-drill-through.md]] § 표 4종 컬럼 명세

#### objects 표 — 부서별 신규 생성 ✅
| 컬럼 | 평가 |
|---|---|
| 부서 / App / KB / Tool / 신규 | ⭐⭐ 의미 명확. App/KB/Tool 세분화는 디테일 조회 가치 |

→ **그대로 유지**

#### users 표 — 부서별 활성/신규 사용자 ⚠️ 컬럼 재설계 필요
| 현재 컬럼 | 변경 필요 사유 |
|---|---|
| 부서 (actor 기준) | 이사님 결정 → **앱 소유 부서로 변경** |
| DAU | 유지 |
| WAU | 유지 |
| 신규 | **삭제** (사용자 활동 신규/이탈 노이즈) |
| 이탈 | **삭제** |

**대체 컬럼 후보**:
| 후보 | 의사결정 가치 |
|---|---|
| **Stickiness (DAU/WAU 비율)** ⭐⭐⭐ | 도입 정착 신호 — 매일 쓰는 정도. DAU/WAU로 단순 계산 |
| **Top 사용자** (이름 1~3명) ⭐⭐ | 부서 내 핵심 사용자 식별 |
| 사용자당 평균 호출 ⭐⭐ | 깊은 사용자 vs 얕은 사용자 분포 |
| 활성 시간대 (피크 hour) ⭐ | 사용 패턴 |

→ **추천 신 컬럼 세트**: `부서 / DAU / WAU / Stickiness / Top 사용자` (5컬럼)

#### calls 표 — 부서별 호출/RPS 🟡 RPS 약함
| 컬럼 | 평가 |
|---|---|
| 부서 (owner) ✅ | ⭐⭐ |
| 호출 | ⭐⭐⭐ 핵심 |
| **RPS (평균)** | 🟡 **약함** — 평균 RPS는 매우 작은 수(예: 0.024 RPS)라 어드민 의사결정에 도움 약함 |
| Top 앱 | ⭐⭐ |
| 추세 | ⭐⭐⭐ |

**RPS 대체 후보**:
| 후보 | 의사결정 가치 |
|---|---|

## 추가로 검토해야 할 항목 (관리자 의사결정 관점에서 빠진 게 있는지)

### 비용 정보 — 후순위로 결정
- 토큰까진 audit + RBAC로 계산 가능: `audit_events.details->>'totalTokens'` + `modelId` 추출
- 비용 환산은 **별도 단가 테이블 필요**:
  - 모델 단가 정보가 현재 시스템(audit/RBAC)에 없음
  - 도입 부담: 단가 테이블 신설 + 운영자 단가 갱신 + historical 비용 계산 시 시점별 단가 적용
- **결론: 가치/노력 비례 낮아 후순위**. 모델별 토큰 분포로 "어느 모델에 많이 쓴다"는 신호는 이미 잡힘
- 향후 검토: 단가 테이블 도입 가치 충분히 클 때 (예: 비용 폭증으로 관리 요구 생기면)

### 사용자 Top 정보 — 활성 사용자 KPI 드로어 우하 대체안과 통합
- 위 KPI 드로어 평가에서 다룬 "활성 사용자 우하 → Top 사용자"가 이 항목과 같은 맥락
- 권장 통합: 활성 사용자 KPI 드로어 우하를 **모델별 사용자 수 → Top 사용자**로 변경하면 두 가지 목적 동시 해결

## 종합 평가 — 강점 / 약점

### 강점
1. ⭐ **SaaS 표준 4축 KPI** (Volume/Breadth/Depth/Quality) — 의사결정 흐름과 일치
2. ⭐ **3-tier 정보 구조** (메인 요약 → 드로어 부서 다차원 → 풀뷰 감사 로그) — 어드민이 깊이 자유 조절
3. ⭐ **컨텍스트 상속** — 부서/기간 잃지 않음
4. ⭐ **활동 로그 행 단위** — 어드민 핵심 화면
5. ✅ **신규/이탈 삭제** — 노이즈 신호 제거, UX 합리적

### 약점
1. **활성 사용자 KPI 드로어 우하 "모델별 사용자 수" 가치 약함** → Top 사용자로 교체 권장
2. **KPI 드로어 비슷한 의미 영역 구분 불명** (좌하 차트 vs 하단 표가 같은 메트릭처럼 보이는 케이스) — 영역별 시각화/필터 명세 필요
3. **메트릭 정의 모호** (기간 라벨 부재 / 툴팁으로 보완 필요)

### 의사결정 필요 (디자이너/PM 회의 5건)
1. **활성 사용자 KPI 드로어 우하 = 모델별 사용자 수 → Top 사용자로 교체** — 다른 KPI 드로어 Top XX 패턴과 일관
2. **users 표 신규/이탈 자리 → Stickiness + Top 사용자**
3. **calls 표 RPS → 피크 RPS 또는 Top 모델** (또는 제거하고 4컬럼 단순화)
4. **KPI 드로어 영역별 시각화/필터 명세 컨펌** — 좌하(차트) vs 하단(표) 명세 spec에 박혀있음, 디자이너 의도 일치 확인
5. **툴팁 보강** — KPI 카드 기간 라벨 / 활성·호출 신호 구분 / 에러 호출+보안 의미

### 자체 결정 완료 (컨펌만 받으면 됨)
- 에러 표시 컨벤션: 호출/활성은 KPI 카드와 통일, 에러는 건수+비율 둘 다
- 신규/이탈(사용자) 삭제 (이사님 결정)
- 메인 우하 = 모델별 토큰 사용량 (가치 명확)
- 부서별 활동 테이블 신규(app/kb/tool) 컬럼 유지
- 비용 KPI 별도 추가 후순위 (모델별 토큰으로 추론 가능)
- 컨텍스트 바 slim 설계 유지 (활성 메트릭 칩 1종만)
