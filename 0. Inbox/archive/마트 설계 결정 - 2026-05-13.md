## 결정 사항 7가지

### 1. 마트 입력 (이사님 5/12 확정)

**`audit_events` 단일 SoT + RBAC JOIN**
- audit collector 14종이 적재 (Dify DB 폴링 + nginx log + pg_trigger + self-audit)
- RBAC 4종 (`departments`, `department_members`, `resource_ownership`, `resource_permissions`)와 JOIN
- 단일 SoT 보장 (호출/에러/사용자 메트릭이 audit에서 일관)

### 2. 마트 형태 — **Materialized View로 시작 (Phase 1)**

| 형태 | 데이터 양 한계 | 응답 시간 | 우리 적합도 |
|---|---|---|---|
| View | < 100만 행 | < 1초 | ⚠️ 개발 환경만 |
| **Materialized View** | 100만 ~ 1억 행 | < 5초 | ✅ **프로덕션 시작점** |
| 별도 fact + ETL | > 1억 행 | 복잡 집계 | Phase 2 진화 시 |

**선택 사유 (프로덕션 환경 기준)**:
- 5/13 사용자 범위 = 로그인 사용자 전체 공개 → 동시 쿼리 부하 증가
- audit 90일 보존이라 max 데이터 양은 정해짐 (일 호출 수 × 90일)
- audit_events DB 부하 격리 효과 (스냅샷이라 collector 적재와 분리)
- View로 시작하면 사용자 늘었을 때 OLTP 풀스캔 위험

**단계별 진화 경로**:
```
Phase 0: View (개발 환경)
  ↓ 데이터 양 증가 / 사용자 부하
Phase 1: Materialized View (프로덕션 시작) ← 출발점
  ↓ 1억 행 초과
Phase 2: 별도 fact 테이블 + incremental ETL
  ↓ 멀티 테넌트 / 글로벌 스케일
Phase 3: 분석 DB 분리 (ClickHouse, BigQuery 등)
```

### 3. 구조 — **2계층, 스테이징 없음**

```
Layer 1: enrich MView (1개)
  - audit_events + RBAC JOIN + JSONB 추출
  - v_audit_enriched

Layer 2: 영역별 MView (선택)
  - 자주 쓰는 영역만 (KPI 카드 / 부서별 활동 표 등)
  - v_kpi_calls_daily, v_dept_activity_daily 등
```

**스테이징 불필요 사유**:
- `audit_events` 자체가 정규화된 이벤트 로그
- collector가 일관된 형식 적재
- JSONB 추출은 `audit_events`의 Generated Column으로 처리 → 별도 정제 layer 불필요

**시작은 Layer 1만**. Layer 2는 응답 시간 측정 후 필요한 영역만 추가.

### 4. JSONB 컬럼 추출 — **Generated Column**

`audit_events` 테이블에 generated column 직접 추가:

```sql
ALTER TABLE audit_events
  ADD COLUMN app_mode TEXT GENERATED ALWAYS AS (details->>'appMode') STORED,
  ADD COLUMN model_provider TEXT GENERATED ALWAYS AS (details->>'modelProvider') STORED,
  ADD COLUMN model_id TEXT GENERATED ALWAYS AS (details->>'modelId') STORED,
  ADD COLUMN total_tokens INT GENERATED ALWAYS AS ((details->>'totalTokens')::int) STORED,
  ADD COLUMN error_text TEXT GENERATED ALWAYS AS (details->>'error') STORED,
  ADD COLUMN invoke_from TEXT GENERATED ALWAYS AS (details->>'invokeFrom') STORED,
  ADD COLUMN triggered_from TEXT GENERATED ALWAYS AS (details->>'triggeredFrom') STORED,
  ADD COLUMN target_app_id UUID GENERATED ALWAYS AS ((details->>'targetAppId')::uuid) STORED;
```

**장점**:
- 자동 (collector가 details만 박으면 컬럼 자동 채워짐)
- 인덱싱 가능 (`CREATE INDEX ... ON audit_events (app_mode)`)
- 쿼리 단순 (`WHERE app_mode = 'chat'` vs `WHERE details->>'appMode' = 'chat'`)
- 디스크 약간 더 사용 (STORED 옵션)

**collector 보강과 같이 진행** — 사용자 작업 중. P0 보강(`appMode`, `triggeredFrom`, `invokeFrom`)이 끝나면 generated column 채워짐.

**대안**: VIRTUAL generated column (디스크 미사용, 매 쿼리 계산) — 인덱스 불가라 STORED가 권장.

### 5. 오브젝트 차트 — **마트 제외, `resource_ownership` 직접**

5/12 이사님 결정 + 5/12 VSCode 검증 (`references/objects-charts-feasibility.md`) 반영:
- 오브젝트는 **state**라 audit 본질 불가 (이벤트 로그로 현재 상태 못 표현)
- dept-cumulative / top-owners / dept-new-creations 3종 모두 **`resource_ownership` 직접 조회**로 구현 가능
- 마트 view 안 거침

**운영 방어**: `apps LEFT JOIN resource_ownership` 패턴 권장 (H-DASH-04 강화 — 레거시 앱 누락 방지)

### 6. RBAC JOIN — **enrich MView에 사전 JOIN**

```sql
CREATE MATERIALIZED VIEW v_audit_enriched AS
SELECT
  ae.id, ae.occurred_at, ae.action,
  ae.actor_id, ae.actor_type, ae.tenant_id,
  ae.target_id, ae.target_type,
  ae.app_mode, ae.model_provider, ae.model_id, ae.total_tokens,
  ae.error_text, ae.invoke_from, ae.triggered_from, ae.target_app_id,
  -- RBAC 사전 JOIN
  ro.owner_department_id AS app_owner_dept_id,
  d_owner.name AS app_owner_dept_name,
  dm.department_id AS actor_dept_id,
  d_actor.name AS actor_dept_name
FROM audit_events ae
LEFT JOIN resource_ownership ro
  ON ro.resource_id = ae.target_id
  AND ro.resource_type = 'app'
  AND ro.tenant_id = ae.tenant_id
LEFT JOIN departments d_owner
  ON d_owner.id = ro.owner_department_id
LEFT JOIN department_members dm
  ON dm.account_id = ae.actor_id
  AND dm.tenant_id = ae.tenant_id
  AND dm.is_active = true
LEFT JOIN departments d_actor
  ON d_actor.id = dm.department_id
WHERE ae.action IN (
  'message_send', 'workflow_execute', 'workflow_node_execute',
  'conversation_start', 'api_call', 'auth_failed'
);
```

**JOIN 시점 결정 사유**:
- RBAC 테이블이 작음 (부서 N개 ~ 수십, 멤버 수백 ~ 수천)
- 사전 JOIN 비용 적음
- 컴포넌트 쿼리에서 `WHERE owner_dept_id = :x` 같은 단순 필터로 단순화
- 보편 Kimball star schema는 매 쿼리 JOIN 권장하지만, 우리는 read-heavy + 단순화 우선

### 7. 새로고침 주기 — **5분 주기 (`pg_cron`)**

```sql
SELECT cron.schedule('refresh-mart-audit-enriched', '*/5 * * * *', $$
  REFRESH MATERIALIZED VIEW CONCURRENTLY v_audit_enriched;
$$);
```

**5분 사유**:
- TanStack staleTime 5분과 정합 (사용자가 새로고침 안 누르면 5분 캐시)
- 대시보드 = 분 단위 신선도면 OK (실시간 필요 X)
- `CONCURRENTLY` = 다운타임 0 새로고침

**REFRESH CONCURRENTLY 전제 조건**: UNIQUE INDEX 필요
```sql
CREATE UNIQUE INDEX ON v_audit_enriched (id);
```

## 컴포넌트별 쿼리 패턴

### KPI 1 — 총 오브젝트 (resource_ownership 직접, 마트 제외)

```sql
SELECT
  COALESCE(d.name, '미배정') AS dept,
  ro.resource_type,
  COUNT(*) AS cnt
FROM resource_ownership ro
LEFT JOIN departments d ON d.id = ro.owner_department_id
WHERE ro.tenant_id = :tenant_id
GROUP BY d.name, ro.resource_type;
```

### KPI 2 — 부서별 채택 앱 수 (enrich MView 사용)

```sql
SELECT
  actor_dept_name AS dept,
  COUNT(DISTINCT target_app_id) AS adopted_apps
FROM v_audit_enriched
WHERE tenant_id = :tenant_id
  AND occurred_at BETWEEN :start AND :end
  AND actor_dept_id IS NOT NULL
  AND target_app_id IS NOT NULL
  AND action IN ('message_send', 'workflow_execute')
  AND invoke_from != 'debugger'
  AND triggered_from != 'debugging'
  AND CASE WHEN app_mode = 'advanced-chat' THEN action = 'message_send' ELSE TRUE END  -- H-DASH-01
GROUP BY actor_dept_name;
```

### KPI 3 — API 호출 (enrich MView 사용)

```sql
SELECT
  app_owner_dept_name AS dept,
  COUNT(*) AS calls,
  COUNT(DISTINCT actor_id) AS users,
  COUNT(*) FILTER (WHERE error_text IS NOT NULL) AS errors
FROM v_audit_enriched
WHERE tenant_id = :tenant_id
  AND occurred_at BETWEEN :start AND :end
  AND action IN ('message_send', 'workflow_execute')
  AND invoke_from != 'debugger'
  AND triggered_from != 'debugging'
  AND CASE WHEN app_mode = 'advanced-chat' THEN action = 'message_send' ELSE TRUE END
GROUP BY app_owner_dept_name;
```

### KPI 4 — 앱별 통계 (Top 앱 호출)

```sql
-- 헤드라인: Top 앱 호출
SELECT
  ae.target_app_id,
  a.name AS app_name,
  COUNT(*) AS calls
FROM v_audit_enriched ae
LEFT JOIN apps a ON a.id = ae.target_app_id
WHERE ae.tenant_id = :tenant_id
  AND ae.occurred_at BETWEEN :start AND :end
  AND ae.action IN ('message_send', 'workflow_execute')
  AND ae.invoke_from != 'debugger'
  AND ae.triggered_from != 'debugging'
  AND CASE WHEN ae.app_mode = 'advanced-chat' THEN ae.action = 'message_send' ELSE TRUE END
GROUP BY ae.target_app_id, a.name
ORDER BY calls DESC
LIMIT 1;

-- 좌하 막대: 앱별 호출 수 Top 10 (위와 유사, LIMIT 10)
-- 우하 막대: Top 에러 앱 Top 10 (error_text IS NOT NULL 카운트)
-- 하단 표 6컬럼: 앱명/부서/호출/사용자/에러율/마지막 사용
```

### 모델별 토큰 (enrich MView)

```sql
SELECT
  model_provider,
  model_id,
  SUM(total_tokens) AS tokens
FROM v_audit_enriched
WHERE tenant_id = :tenant_id
  AND occurred_at BETWEEN :start AND :end
  AND action = 'message_send'  -- workflow는 model 정보 없음 (P1 보강 후 확장)
  AND invoke_from != 'debugger'
GROUP BY model_provider, model_id;
```

### 부서별 활동 (dept-activity 6컬럼 표)

```sql
WITH calls AS (
  SELECT
    app_owner_dept_name AS dept,
    COUNT(*) AS calls,
    SUM(total_tokens) AS tokens
  FROM v_audit_enriched
  WHERE tenant_id = :tenant_id
    AND occurred_at BETWEEN :start AND :end
    AND action IN ('message_send', 'workflow_execute')
    AND invoke_from != 'debugger'
    AND triggered_from != 'debugging'
  GROUP BY app_owner_dept_name
),
new_objects AS (
  SELECT
    COALESCE(d.name, '미배정') AS dept,
    ro.resource_type,
    COUNT(*) AS cnt
  FROM resource_ownership ro
  LEFT JOIN departments d ON d.id = ro.owner_department_id
  WHERE ro.tenant_id = :tenant_id
    AND ro.created_at BETWEEN :start AND :end
  GROUP BY d.name, ro.resource_type
)
SELECT
  c.dept,
  COALESCE((SELECT cnt FROM new_objects WHERE dept = c.dept AND resource_type = 'app'), 0) AS new_apps,
  COALESCE((SELECT cnt FROM new_objects WHERE dept = c.dept AND resource_type = 'dataset'), 0) AS new_kbs,
  COALESCE((SELECT cnt FROM new_objects WHERE dept = c.dept AND resource_type = 'tool'), 0) AS new_tools,
  c.calls,
  c.tokens
FROM calls c;
```

## 운영 모니터링 (3개 메트릭)

1. **쿼리 응답 시간** — 각 endpoint별 p95, p99 (Datadog/Prometheus)
2. **MView 새로고침 시간** — `REFRESH CONCURRENTLY` 소요 시간
3. **마트 lag** — audit 적재 시각 vs MView 반영 시각 (5분 주기인데 더 벌어지면 경고)

알림 임계:
- 응답 시간 p95 > 3초 → 경고
- 새로고침 시간 > 4분 → 경고 (5분 주기인데 4분 걸리면 임계)
- lag > 10분 → 경고

## 미결정 사항 / PM 확인 후보

| 항목 | 확인 필요 | 영향 |
|---|---|---|
| 운영 데이터 양 추정 | 회사 일 호출 수 / 사용자 수 | MView vs 별도 fact 결정에 직결. 일 5~10만건 가정 시 MView 충분 |
| audit DB 부하 격리 | Read Replica 도입 여부 | 데이터 양 < 1천만 행이면 같은 DB OK |
| dept-new-creations 신규 정의 | 소유권 등록 시점 vs 앱 생성 시점 | resource_ownership.created_at 의미 확정 |
| api_call (nginx) 부서 분류 | URI로 앱 특정 불가 → 마트 포함 여부 | KPI 3 호출수 메트릭에 nginx 이벤트 포함할지 |
| dbt 도입 | SQL 모델링 표준화 | Phase 1에서 도입 시 운영 안정성↑, 학습 비용 발생 |
