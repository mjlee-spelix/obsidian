# 대시보드 추가 위젯 후보 10개

화면 설계([[(화면 설계) 대시보드.png]])에 이미 있는 KPI 4종·부서별 오브젝트·모델별 토큰·부서별 활동 테이블 외에, 추가로 들어가면 의미 있을 후보들.

데이터 출처는 RBAC 테이블([[0. Inbox/테이블추가_설명_DDL_Claude.md]])과 Dify 통계 테이블([[4. 지식노트/Dify - 통계·토큰 DB 스키마 구조.md]]) 기준.

## 후보 목록

| #   | 위젯                   | 형태                   | 데이터 출처                                                                                                  | 인사이트                                                              |
| --- | -------------------- | -------------------- | ------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 1   | **일별 호출/토큰 추이**      | 듀얼 라인 차트 (30일)       | `messages.created_at` + `workflow_runs.created_at` GROUP BY DATE                                        | KPI 카드의 "증감 %"를 풀어서 보여주는 시계열. 트래픽 급증/급감 포착                        |
| 2   | **앱 모드 분포**          | 도넛/파이                | `apps.mode` (chat / agent-chat / workflow / completion) COUNT                                           | 어떤 유형의 앱이 주력인지 파악 — 모드별 통계 분기가 필요한 만큼 비중 보고도 자연스러움                |
| 3   | **성공/실패율 추이**        | 100% 스택 영역 차트        | `messages.status` (normal/error), `workflow_runs.status` (succeeded/failed/stopped), `exceptions_count` | 운영 안정성 모니터링 — 모델 장애·플로우 결함 조기 감지                                  |
| 4   | **모델 응답 지연 p50/p95** | 수평 막대 또는 라인          | `messages.provider_response_latency` GROUP BY `model_id`                                                | 모델별 토큰량 옆에 두면 "비용은 적은데 느린 모델" 같은 의사결정에 직결                         |
| 5   | **앱 사용량 Top N 테이블**  | 표 (호출수, 토큰, 부서, 소유자) | `messages` / `workflow_runs` GROUP BY `app_id` JOIN `sp_object_ownership` JOIN `apps`                   | "부서별 활동" 한 단계 아래의 드릴다운 — 어떤 앱이 가장 많이 쓰이나                          |
| 6   | **활성 사용자 Top N**     | 표 또는 막대              | `messages.from_end_user_id` COUNT (또는 `sp_object_ownership.owner_user_id`로 "오브젝트 생산자 Top")              | KPI "활성 사용자 87명"의 구성 보여주기. 헤비 유저 식별                               |
| 7   | **권한 부여 현황**         | 누적 막대 또는 KPI 미니카드    | `sp_object_permissions` GROUP BY `level`, `grantee_type`                                                | viewer/editor 비율, user-grant vs department-grant 비율 → 권한 통제 정책 점검 |
| 8   | **시간대 사용 히트맵**       | 7×24 히트맵 (요일×시간)     | `messages.created_at`, `workflow_runs.created_at`                                                       | 피크 시간 식별 → 모델 풀/리소스 산정, 정기 작업 스케줄 근거                              |
| 9   | **비용(USD) KPI + 추이** | KPI 카드 1개 + 미니 라인    | `messages.total_price` SUM (+ workflow는 노드별 `execution_metadata.total_price`)                           | 토큰 수만으로는 가려지는 실제 지출. 모델 단가 차이가 큰 만큼 토큰 ≠ 비용                       |
| 10  | **워크플로우 노드 유형 분포**   | 스택 막대 (앱별 또는 전체)     | `workflow_node_executions.node_type` (llm/tool/code/...) COUNT + 토큰 합                                   | 워크플로우 모드의 모델 분리가 어렵다는 한계를 우회 — "어디서 토큰을 쓰나"를 노드 단위로 보여줌           |

## 추천 우선순위

1 → 9 → 5 → 3 → 8 — 시계열·비용·앱별 Top·에러·시간대는 운영 대시보드의 정석이라 윗선 보고에서도 안 빠짐.

- **7번**은 권대리님 RBAC 영역과 자연스럽게 엮임
- **10번**은 WORKFLOW 모델별 토큰 분리가 안 되는 한계를 보완하는 카드라 화면 설계 공유 자리에서 명분으로도 좋음
- 화면 설계 공유 회의에서 추가 제안할 거면 **1·3·9** 정도가 데이터 부담 적고 임팩트 커서 무난
