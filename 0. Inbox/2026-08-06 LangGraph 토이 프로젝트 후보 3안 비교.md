# LangGraph 토이 프로젝트 후보 3안 비교

> Three candidate topics for the next LangGraph toy project, compared by graph shape,
> LangGraph surface exercised, verifiable invariant, and size. Written 2026-08-06 to
> pick one. Baseline for "what is already learned" is `~/Projects/salesbot-lg`.

## Baseline — salesbot-lg 가 이미 소진한 것

새 주제의 가치는 "LangGraph 를 쓰느냐"가 아니라 **salesbot 에서 못 써본 표면을 쓰느냐**로
정한다. done.md 기준 이미 다룬 것:

```yaml
already_used:
  - create_agent 상위 + nl2sql 서브그래프 (경계를 state 필드로 정의)
  - 조건부 엣지로 상태 분기 (Dataset.status 6종)
  - 사이클 (gen_sql ⇄ repair, MAX_ATTEMPTS 상한 + recursion_limit 이중 안전망)
  - 커스텀 리듀서 (merge_datasets — id 누적 + 최근 5개만 rows 유지)
  - 체크포인터 SqliteSaver + thread_id (스레드 단위 후속질문)
  - HITL — HumanInTheLoopMiddleware interrupt/resume (approve/edit/reject)
  - 미들웨어 — ModelCallLimit / ToolCallLimit / ToolError
  - response_format 으로 최종 답변 스키마 고정
  - stream(stream_mode="updates") + 골든셋 evals
```

안 써본 표면 (이번 주제 선정의 실제 기준):

```yaml
untouched:
  multi_agent:   Command(goto=..., graph=PARENT) 핸드오프    # salesbot "안 함" 목록이었음
  send:          Send 병렬 분해 + fan-in 리듀서              # Phase 7 미완
  time_travel:   get_state_history / update_state / fork    # Phase 7 미완
  store:         BaseStore — 스레드를 넘는 장기기억          # 아예 없음
  streaming:     messages / custom(StreamWriter) 토큰 스트림 # updates 만 써봄
  durability:    백그라운드 run, 며칠 걸리는 interrupt, cron 재개
  perf:          노드 캐시(CachePolicy), retry 정책, deferred 노드
```

**이식할 규율 하나** — salesbot 을 성립시킨 건 기능이 아니라 불변식이었다("모든 숫자는 코드가
만든다"). 후보 3안 모두 **코드가 판정하는 진실**을 하나씩 갖도록 설계했다. 그게 없으면
"LLM 이 글을 쓴다, 그럴듯하다"로 끝나고 evals 가 감시할 대상이 사라진다.

## Option 1 — 분기 서사 게임 / 협상 시뮬레이터

되돌리기와 "다른 선택 해보기"가 부가기능이 아니라 **제품 그 자체**인 주제.

### 그래프 골격

```
                      ┌─────────────────────────────────┐
  player_input ─→ parse_action ─→ resolve (순수 함수)   │
                                      │  세계 상태 전이  │
                                      ↓                 │
                              Send ──┬─→ npc_a (subgraph)
                                     ├─→ npc_b (subgraph)   병렬 반응
                                     └─→ npc_c (subgraph)
                                      │
                                  fan-in 리듀서 (events 병합)
                                      ↓
                                  narrate (LLM — 묘사만)
                                      ↓
                              [interrupt] 되돌리기/분기 지점 ─┘

  별도 경로: get_state_history → 과거 checkpoint 선택 → update_state → fork 실행
```

### 쓰는 LangGraph 표면

| 표면 | 어디서 | 신규? |
|---|---|---|
| `get_state_history` / `update_state` / fork | 되돌리기·분기 타임라인 = 핵심 기능 | ★ 신규 |
| 멀티에이전트 핸드오프 `Command(goto)` | NPC 가 대화 주도권을 넘겨받음 | ★ 신규 |
| `Send` 병렬 fan-out | 한 행동에 NPC 여럿이 동시 반응 | ★ 신규 |
| 커스텀 리듀서 | 동시 반응 이벤트 병합 (순서 결정 규칙 필요) | 재사용 |
| `interrupt` | 선택지 제시 = HITL 의 자연스러운 형태 | 재사용 |
| custom 스트리밍 | 묘사를 토큰 단위로 흘림 | ★ 신규 |

### 검증 가능한 진실

**세계 상태(소지금·인벤토리·호감도·플래그)는 전부 `resolve` 순수 함수가 계산한다. LLM 은
그 결과를 묘사만 한다.** salesbot 불변식의 직계 이식이다.

- 상태 전이가 순수 함수 → 모델 없이 단위 테스트
- evals 가 잡는 것: 묘사에 등장한 수치가 상태에 없는 값이면 실패 (salesbot 의
  `test_rendered_table_matches_the_database` 와 같은 형태)
- fork 검증: 같은 checkpoint 에서 두 갈래로 갈라 **양쪽 상태가 서로 오염되지 않음**을 단언

### 규모 / 리스크

```yaml
size:  저녁 작업 2~3주. 게임 콘텐츠(시나리오)를 최소로 잡는 게 관건
risk:  콘텐츠 만들다 LangGraph 학습이 뒷전이 될 수 있다
       → 방어: 시나리오는 YAML 한 장 고정, 코드는 그 YAML 을 해석만
fail_mode: "재미없다"고 느끼는 순간 동력이 끊긴다. 실사용 가치가 0인 유일한 안
```

## Option 2 — Obsidian 볼트 장기기억 비서

`BaseStore` 를 중심에 놓는 안. **스레드가 끝나도 남는 기억**이 주제.

### 그래프 골격

```
  대화 그래프 (foreground)
    user ─→ agent ─┬─→ tool:search_memory   (store.search — 임베딩)
                   ├─→ tool:search_vault    (볼트 파일 검색)
                   └─→ tool:remember  ──[interrupt] "이걸 기억할까요?"
                          ↓ 승인 시 store.put(namespace, key, value)

  정리 그래프 (background / cron — 대화와 분리된 별도 그래프)
    scan_recent ─→ Send ─┬─→ dedupe   (같은 사실 병합)
                         ├─→ conflict (모순 기억 판정 → 최신 채택 + 폐기 로그)
                         └─→ promote  (반복 등장 = 승격)
                              ↓
                          store.put / store.delete
```

### 쓰는 LangGraph 표면

| 표면 | 어디서 | 신규? |
|---|---|---|
| `BaseStore` + 임베딩 semantic search | 기억의 저장/회수 전부 | ★ 신규 |
| namespace 설계 (user/topic/scope) | 기억 격리 — 스레드 간 공유의 단위 | ★ 신규 |
| 백그라운드 run / cron 재개 | 정리 그래프가 대화와 따로 돈다 | ★ 신규 |
| 그래프 2개 분리 + Store 공유 | 대화 ↔ 정리의 유일한 접점이 Store | ★ 신규 |
| `Send` | 정리 대상 기억들 병렬 처리 | ★ 신규 |
| `interrupt` | "기억할까요?" 승인 | 재사용 |

**time-travel·멀티에이전트는 거의 안 쓰게 된다** — 이 안의 유일한 큰 구멍.

### 검증 가능한 진실

**모든 기억은 출처(볼트 파일 경로 + 원문 span 또는 대화 thread_id/turn)를 갖는다. 출처 없는
기억은 저장 자체가 거부된다.**

- 회수 정확도: 질문 → 기대 기억 골든셋 (실제 볼트로 만들 수 있다)
- 모순 처리: 일부러 모순 기억 2개를 심고 정리 그래프가 한쪽을 폐기하는지
- 오염 검증: namespace 가 다르면 회수되지 않음
- evals 가 잡는 것: 답변에 인용된 볼트 내용이 실제 파일에 문자열로 존재하는지

### 규모 / 리스크

```yaml
size:  저녁 작업 2주 + 볼트 인덱싱 튜닝이 꼬리처럼 붙는다
risk:  임베딩 모델·벡터 저장소 선택에서 시간이 샌다 (LangGraph 밖 문제)
       → 방어: 1주차는 InMemoryStore + 로컬 임베딩으로 끝내고 영속화는 그 다음
utility: 3안 중 유일하게 매일 쓰게 될 물건. 볼트가 이미 있다
```

## Option 3 — 다중 소스 리서치 / 감사 파이프라인

`Send` map-reduce 와 loop-until-dry 를 정면으로 쓰는 안.

### 그래프 골격

```
  question ─→ plan (조사 축 N개로 분해)
                 ↓
              Send ──┬─→ research (subgraph: 검색→읽기→주장 추출)  ← 노드 캐시
                     ├─→ research
                     └─→ research  … N개 병렬, 부분 실패 허용
                     ↓
                fan-in 리듀서 (주장 누적 + 중복 제거)
                     ↓
                verify (주장별 원문 span 매칭 — 코드)
                     ↓
                critic ("빠진 축이 뭔가") ──있으면──→ plan 으로 되돌아감 (loop-until-dry)
                     │ 없으면
                     ↓
                 synthesize
```

### 쓰는 LangGraph 표면

| 표면 | 어디서 | 신규? |
|---|---|---|
| `Send` map-reduce + fan-in | 조사 축 병렬 분해 | ★ 신규 |
| loop-until-dry 사이클 | critic 이 빈틈 없다 할 때까지 | 형태는 repair 와 유사 |
| 노드 캐시 `CachePolicy` | 같은 소스 재조회 방지 | ★ 신규 |
| retry 정책 / 부분 실패 허용 | 소스 하나 죽어도 전체는 산다 | ★ 신규 |
| deferred 노드 | 모든 축이 끝난 뒤에만 synthesize | ★ 신규 |
| 멀티에이전트 | 안 씀 (역할 분리는 노드로 충분) | — |

### 검증 가능한 진실

**모든 주장은 원문 span 과 문자열 단위로 매칭돼야 한다. 매칭 실패한 주장은 폐기된다** —
요약도, 완화도 없다. salesbot 불변식의 텍스트판.

- evals 가 잡는 것: 최종 리포트의 모든 문장이 span 을 갖는지, span 이 원문에 실제로 있는지
- loop 종료 보장: critic 이 계속 "빠졌다"고 해도 상한에서 멈추는지 (salesbot MAX_ATTEMPTS 와 동형)

### 규모 / 리스크

```yaml
size:  저녁 작업 1.5~2주 — 3안 중 가장 짧다
risk:  주제가 흔하다. 그리고 골격이 "조회 → 근거 → 요약"이라 salesbot 과 형태가 겹친다
       (병렬이 붙었을 뿐 배운 패턴의 재연습에 가까울 수 있다)
```

## Recommendation — 1안, 단 조건부

**1안(분기 서사 게임)을 추천한다.** 이유는 커버 개수가 아니라 **강도**다.

- time-travel 과 멀티에이전트는 salesbot 에서 두 번 다 미룬 항목이고(Phase 7 미완 / "안 함"
  목록), 억지로 붙이면 또 미뤄진다. 게임에서는 **그 기능이 없으면 제품이 성립하지 않는다** —
  미룰 수가 없는 구조가 학습을 강제한다.
- 검증 축이 salesbot 불변식의 직계라서, 세운 규율을 버리지 않고 이어간다.
- 3안은 커버 개수는 같지만 골격이 salesbot 과 겹친다. 새 표면 학습보다 재연습에 가깝다.

**뒤집을 조건**: "재미"보다 "매일 쓸 물건"이 우선이면 2안. 1안은 3안 중 유일하게 실사용
가치가 0이고, 그게 유일한 실패 원인이 될 수 있다.

**절충안도 있다** — 2안을 먼저 2주에 끝내고(실사용 물건 확보), time-travel/멀티에이전트는
1안으로 그 다음에. 순서만 바꾼 것이고 둘 다 남는다.
