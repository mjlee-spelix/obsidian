## TL;DR (5/11 최종, 12종 추론 + 드로어 + audit 비교 반영)

> **OLTP 기반 마트 3개 확정**: `fact_call_daily`, `fact_user_activity_daily`, `fact_objects_snapshot_daily`. 차트 ①~⑱ 커버.
> **audit 활용 방식은 보류** — top-error-types(차트 ⑲)와 드로어용 audit 활용은 옵션 C(audit 보강)/D(정규식 분류)/E(절충) 중 **audit collector 실제 동작 확인 후 결정**. 현재 audit 컨테이너 본인 브랜치에 없어서 확인 불가, dev 머지 후 재개.
> 현재 10초 응답 시간은 마트 무관 — 백엔드 non-DB fix 별개 트랙.

## ① "어느 테이블에서 가져올까?" (변동 없음)

**기본 OLTP**. 15개 엔드포인트 전부 Dify OLTP 테이블(messages, workflow_runs, apps, datasets, accounts) + 우리 RBAC 테이블(resource_ownership, departments, department_members) 직접 조회.

| 영역 | 테이블 | 사용 서비스 수 |
|------|--------|--------------|
| OLTP | messages | 7 |
| OLTP | workflow_runs | 5 |
| OLTP | apps | 5 |
| OLTP | datasets | 2 |
| OLTP | accounts | 1 |
| RBAC | resource_ownership | 6 |
| RBAC | departments | 6 |
| RBAC | department_members | 2 |

별도 audit/로그 테이블 사용 없음. 모든 집계가 OLTP 실시간 쿼리.

## ② "마트 필요한 부분 + 유형별 스키마" (설계만, 구현 보류)

### 4-fact 설계 (이사님 5/8 컨펌 반영)

[[0. Inbox/마트 설계 초안 - 4 fact 구조]] 참조 — OLTP 3 + audit 1 + RBAC dim:

| Fact | 출처 | 보존 | 커버 차트 |
|------|------|------|-----------|
| `fact_call_daily` | OLTP (messages+workflow_runs) | 영구 | KPI 호출/에러율, model-tokens, model-call-share, dept-call-count, dept-call-rps, dept-error-rate, dept-error-table |
| `fact_user_activity_daily` | OLTP | 영구 | KPI 활성사용자, dept-dau, dept-user-activity, model-users |
| `fact_objects_snapshot_daily` | OLTP (apps+datasets+RBAC) | 영구 | KPI 오브젝트, dept-cumulative, dept-new-creations, top-owners |
| `fact_audit_event_daily` | audit.audit_events | 90일 자연 cap | top-error-types + 향후 거버넌스/보안 차트 |

RBAC(부서)는 별도 fact 없이 ETL 시점에 fact 행에 dept_id 박음.

### 마트로 풀리는 것 vs 안 풀리는 것

**마트로 풀림** (사전 집계 → 단순 SUM/GROUP BY):
- KPI 호출 수, 에러율 → `fact_call_daily` SUM
- 부서별 활동 테이블 → `fact_call_daily` GROUP BY dept_id
- 모델별 토큰 → `fact_call_daily` GROUP BY model_id

**마트로 안 풀림** (실시간 조인/윈도우 필수):
- Top 소유자 10명 (#9) — LIMIT + 실시간 accounts JOIN
- 부서별 사용자 활동 상세 (#13) — 신규/이탈 NOT EXISTS + 이전 기간 대조
- 부서별 에러 테이블 (#18) — 최다 에러 원인 ROW_NUMBER (m.error 텍스트 집계)

## ③ "마트로 12종 다 그릴 수 있나?" — **결론 뒤집힘 (5/11 측정 후)**

### 5/8 가설 → 5/11 측정 결과

| 항목 | 5/8 가설 | 5/11 실측 |

| 마트 가치 | 8/15 엔드포인트 단축 | **0% 단축** (현 데이터 양) |

### 측정 결과 — Phase 2 drill-through (가장 무거운 4개)

| 엔드포인트 | 전체 응답 | DB (EXPLAIN ANALYZE) |
|------------|----------|---------------------|
| #18 dept-error-table (9-CTE, 최복잡) | 0.54s | **1.5ms** |
| #16 dept-call-rps (7-CTE) | 1.04s | 1.6ms |
| #7 dept-activity (6-CTE) | 2.72s | 1.4ms |

### 4-레이어 시간 분해

```
Phase 1 엔드포인트 1건 = 2.7초
├─ Network                  : ~0.001초  ( 0.04%)
├─ DB (EXPLAIN ANALYZE)     :   0.002초 ( 0.07%)
└─ 백엔드 non-DB            :   2.7초   (99.9%)
    │  Auth (Keycloak JWT 검증)
    │  RBAC permission check
    │  SQLAlchemy ORM 오버헤드
    │  JSON serialization
    │  Flask middleware chain
```

→ **DB는 무죄**. 9-CTE 최복잡 쿼리도 1.5ms. 마트로 줄일 시간은 ms 단위 — 사용자 체감 무변화.

### 결론: 두 트랙 분리

**트랙 A — 마트 (장기 보험)**: 진행
- 운영 데이터 양 증가는 기정 사실 (mockup 375건 → 운영 100만+)
- 운영 들어간 후 만들기 시작 = 사용자 응답시간 한참 느려진 후 fix 시작 = 피해
- 미리 설계 + 구현해두면 데이터 양 늘어나는 대로 자연스럽게 효과
- **단 현재 10초 문제 해결은 아님**

**트랙 B — 백엔드 non-DB fix (단기 응답시간)**: 별도 트랙
- 측정 결과 DB 0.07% / 백엔드 non-DB 99.9%
- 부수 발견: 1요청당 JWT 검증 + account/tenant 조회가 **59번 redundant 실행** (Flask-Login 캐시 미작동)
- 별도 분석 노트 참조 → [[4. 지식노트/Dify - 대시보드 API 백엔드 2.7초 병목 분석 (Flask-Login 캐시 미작동).md]]
- 원인 추적은 신입 단독 fix 영역 아님 (Dify upstream + keycloak patch + ssp RBAC 결합)
- 김이사님/팀 결정 영역

→ **두 트랙은 분리된 문제**. 한쪽이 다른 쪽을 막지 않음. 마트 가치는 데이터 양에서, 응답시간 개선은 백엔드 fix에서.

### 마트 설계 — OLTP 3-fact 확정 + audit 활용 방식 보류

**확정: OLTP 기반 3개 (차트 ①~⑱ 커버)**
```
fact_call_daily              (호출/토큰)        ← ②③④⑥⑦⑭⑮⑯⑰⑱
fact_user_activity_daily     (활성 사용자)      ← ⑪⑫⑬
fact_objects_snapshot_daily  (오브젝트 누적)    ← ①⑤⑧⑨⑩
```

**보류: audit 활용 방식 (차트 ⑲ top-error-types + 드로어)**

다음 3옵션 중 결정 필요, audit collector 실제 동작 확인 후:

| 옵션 | 어떻게 | 채택 조건 |
|---|---|---|
| C | audit collector에 본문 보강 요청 + audit 직접 쿼리 (top-error-types) + audit + RBAC JOIN (드로어) | audit.action에 정규화 에러 라벨 있을 때 |
| D | OLTP messages.error 정규식 분류로 error_type 박기 (top-error-types도 OLTP 마트화) | audit collector 신뢰 어렵거나 보안 이벤트 차트에 안 보여줘도 될 때 |
| E (절충) | 호출 에러는 OLTP 정규식, 보안 이벤트는 audit 직접 | 화면이 호출 에러 + 보안 이벤트 둘 다 보여주는 경우 |

**확인 필요한 것**:
```bash
# audit 가동 환경에서:
SELECT DISTINCT action FROM audit.audit_events ORDER BY action;
SELECT details FROM audit.audit_events WHERE status='failed' LIMIT 5;
```
→ action에 `model_timeout` 같은 에러 라벨 있나? details에 errorType 정규화 라벨 있나, raw 텍스트만 있나?

이 두 쿼리 결과로 C/D/E 자동 결정.

### 결정 논리 — Silver fact_event를 안 만든 이유 (회의 설명용)

**처음 가설**: 드로어 한 행 그리려면 5 테이블 JOIN. 매번 비싸니까 ETL로 미리 합쳐서 `fact_event` Silver layer 만들자.

**재검토 후 뒤집힘**:

| 검토 | 결론 |
|---|---|
| audit이 이미 메시지 1건 단위 적재 중 | 사실상 fact_event 역할의 80%를 audit이 함 |
| audit에 빠진 건 메시지 본문만 | collector에 `queryPreview` 200자 추가 요청이면 끝 |
| 부서 매핑은 audit이 RBAC 모름 | 화면 JOIN 2개로 처리 (드로어 LIMIT 6라 부담 작음) |
| 5/11 측정 결론과 일관성 | "마트화 즉시 효과 0% (현 데이터 양)" → Silver도 같은 논리 |
| 우리 작업량 | Silver = 우리 ETL 코드 + 모니터링 부담 / audit 보강 = audit 팀 협의 한 번 |

→ **있는 자원(audit) 활용** > **새 ETL 시스템 추가 운영**

**회의에서 한 줄로 설명**:
> "드로어 그리려고 추가 마트(Silver)를 만들지, 이미 있는 audit을 활용할지 검토했는데, audit 쪽이 우리 운영 부담이 적어서 audit 활용 + RBAC JOIN 2개로 가기로 했습니다. 단 audit collector의 에러 분류 방식 확인 후 옵션 C/D/E 중 최종 결정."

## 회의에서 받을 가능성 있는 후속 질문

### Q: "마트 만들 이유는?"
A: 현재 mockup 양에선 효과 0이지만 운영 데이터 양 도달 시 효과 발생. 운영 진입 후 만들기 시작 = 사용자 피해. 미리 설계·구현해두는 게 합리적.

### Q: "그럼 지금 10초 문제는?"
A: 마트로는 안 풀림. 백엔드 non-DB가 99.9% 차지. 별도 트랙 — Flask-Login 캐시 미작동으로 redundant load 발생. Dify upstream + 우리 patch 결합 영역이라 신입 단독 fix는 risk. 팀 결정 필요.

### Q: "그럼 응답 시간 개선 일정은?"
A: 백엔드 fix 트랙의 우선순위/담당자 결정되어야 답 가능. 마트 트랙은 분리되어 진행.

### Q: "드로어(차트 클릭 상세) 화면도 마트가 필요한가?"
A: **마트 추가는 안 만듭니다.** audit이 이미 메시지 1건 단위로 적재 중이라, audit collector에 메시지 본문 200자만 보강 요청하면 audit + RBAC JOIN 2개로 끝남. Silver fact_event 만들기는 우리 운영 부담만 늘어남.

### Q: "audit 보강 요청은 누가 누구에게?"
A: `dify-audit` 컨테이너의 collector 코드 담당 팀(또는 승랑님 트랙). messages.ts에 `queryPreview` 200자 trim 필드 추가 + workflow-runs.ts의 5필드만 비대칭(5/8 발견) 같이 보강 요청. 큰 변경 아니지만 외부 협의 필요.
