## After — 탐색 메뉴 좌측 라우트
```
┌──────┬────────────────────────────────┐
```

## 가치 판단
- 모달 제약 전면 해제 → drill-through deep link, ESC 활용 등 UX 개선 가능
- 로그인 디폴트 페이지 = 대시보드 노출도 자연 증가

## 의견 수렴 포인트
- 디폴트 페이지로 박는 게 맞는지 (기존 디폴트 `/apps`와 공존 vs 완전 대체)

### 각 KPI 차트 드로어 — 상세 평가 근거

#### 1. 총 오브젝트 — ⭐⭐ 보통
- **어떤 의사결정에 도움?**: "어느 부서가 뭘 가지고 있나" 자산 인벤토리 파악
- **드로어 추가 정보**: 카드("총 234")만으로는 분포 안 보임. 드로어는 부서별 App/KB/Tool 세부 + 생성·삭제 이벤트 로그
- **대체 가능?**: ✅ dept-cumulative 차트가 부서별 분포 이미 보여줌. 드로어는 "어느 시점에 누가 만들었나" 로그만 추가
- **사용 빈도**: 낮음 — 자산 변동 추적은 일상 업무 아님 (분기별 검토)
- **결론**: 같은 정보를 다른 차트에서 80% 얻을 수 있어 가치 평범

#### 2. 부서별 사용 — ⭐⭐⭐ 강함
- **어떤 의사결정에 도움?**: "어느 부서가 활발하고 어느 부서가 안 쓰나" — 도입 검토, 부서별 활용도 평가
- **드로어 추가 정보**: 카드(총 사용 건수 평균)는 분포 안 보여줌. 드로어는 부서 멤버의 사용자 수, 사용 앱 종류, 가장 많이 쓴 앱, 시간대 추이
- **대체 가능?**: ❌ 같은 grain의 정보를 다른 곳에서 못 얻음 — drill-down이 유일 채널
- **사용 빈도**: 높음 — 부서장/임원이 "우리 부서 어떻게 쓰고 있나" 주간 확인
- **결론**: KPI 2번의 핵심 drill-down. 유지 필수

#### 3. API 호출 — ⭐⭐⭐ 강함
- **어떤 의사결정에 도움?**: 운영 모니터링 핵심 — 호출량 추이 + 에러 빈도 = 안정성·비용 관리 직결
- **드로어 추가 정보**: 카드(호출 N + 에러율 N%)는 평균만. 드로어는 부서별 호출/에러 분포, 에러 유형 breakdown, 시간대 패턴, 실제 에러 로그
- **대체 가능?**: ❌ Dify 자체 모니터링은 **앱 단위**만 보여줌. **부서별** 호출/에러 분석은 우리만 제공
- **사용 빈도**: 매우 높음 — 운영 담당자 매일 확인, 에러 알림 후 원인 추적 일상
- **결론**: 운영 관점 핵심 drill-down. 유지 필수

#### 4. 앱별 통계 — ⭐⭐ 보통 (2026-05-13 격상)
- **어떤 의사결정에 도움?**: 앱 단위 호출/에러/토큰 사용량의 **변화 추이** 파악
- **드로어 추가 정보**: 호출 추세(+12%) / 사용자 추세(+5명) / 에러율 변화(-0.1%) / 토큰 사용량 추세(+18%) — **모두 추세/변화 지표** (표는 현재값만)
- **대체 가능?**: ❌ Dify 모니터링 페이지는 디테일 위주, 추세 변화율은 우리 드로어만 제공
- **사용 빈도**: 보통 — 앱별 추세 점검 시 유용
- **결론**: **안 A(공통 추세 지표) 채택**으로 표(스냅샷)와 드로어(추세) **차원 분리** 성립. 좌하 클릭 = 차트 드로어 / 표 클릭 = Dify 모니터링 페이지로 **두 액션 의미 명확** ✅
- **선택 사유 (당초 충돌→해소)**: 당초 안(호출/사용자/에러율/마지막 사용)은 표 컬럼과 100% 일치 → 의미 없음. 응답시간/만족도/모델 분포는 채팅형 전용이라 AppMode 분기 spec 부담 → 공통 추세 지표(안 A)가 단순하면서 차원 분리 성립
