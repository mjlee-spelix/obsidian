# 대시보드 라우트 이동 - 2. 디폴트 라우트 분기

> **결론 한 줄**: 로그인 후 디폴트는 `/apps`로 **하드코딩**(여러 곳에 분산), 별도 미들웨어/서버 분기 없음. "전 사용자 → /dashboard" 변경은 **5~6개 호출 지점의 fallback 문자열을 단일 상수로 교체**하면 됨. 분기 자체가 사라지므로 추가 분기 로직은 불필요.

---

## 현재 로그인 후 redirect 경로 (파일 + 라인)

`/apps`로 보내는 호출 지점은 **모두 클라이언트 사이드**에 있고, 서버 미들웨어(`web/middleware.ts`)는 **존재하지 않음**.

| # | 시나리오 | 파일:라인 | 호출 |
|---|----------|-----------|------|
| 1 | 이메일/비밀번호 로그인 성공 | `web/app/signin/components/mail-and-password-auth.tsx:88-89` | `router.replace(redirectUrl \|\| '/apps')` |
| 2 | 이메일 코드 로그인 성공 | `web/app/signin/check-code/page.tsx:54-55` | `router.replace(redirectUrl \|\| '/apps')` |
| 3 | OAuth/소셜 로그인 성공 | `web/app/signin/normalForm.tsx` (around line 45) | `router.replace(redirectUrl \|\| '/apps')` |
| 4 | 초대 멤버 활성화 완료 | `web/app/signin/invite-settings/page.tsx:59-60` | `router.replace(redirectUrl \|\| '/apps')` |
| 5 | 회원가입 비밀번호 설정 완료 | `web/app/signup/set-password/page.tsx:83` | `router.replace('/apps')` (fallback 없음) |
| 6 | 최초 설치 완료 (관리자) | `web/app/install/installForm.tsx:73` | `router.replace('/apps')` (fallback 없음) |
| 7 | "한 단계 더" 초대 코드 입력 후 | `web/app/signin/one-more-step.tsx:69` | `router.push('/apps')` (fallback 없음) |

핵심 스니펫 — `mail-and-password-auth.tsx:80-91`:

```ts
if (isInvite) {
  router.replace(`/signin/invite-settings?${searchParams.toString()}`)
}
else {
  const externalReturn = safeReturnTo(searchParams.get('return_to'))
  if (externalReturn) {
    // 다른 도메인(예: dify-audit) SSO 핸드오프
    window.location.replace(externalReturn)
  }
  else {
    const redirectUrl = resolvePostLoginRedirect()
    router.replace(redirectUrl || '/apps')   // ← 여기 디폴트
  }
}
```

핵심 스니펫 — `web/app/components/app-initializer.tsx:80-97` (앱 진입 시 동작):

```ts
const isFinished = await isSetupFinished()
if (!isFinished) {
  router.replace('/install')           // 셋업 미완료 → 설치 화면
  return
}

const redirectUrl = resolvePostLoginRedirect()
if (redirectUrl) {
  location.replace(redirectUrl)        // OAuth 등 임시 저장된 복귀 URL이 있으면 우선
  return
}

// ... 실패 시
router.replace('/signin')              // 프로필 조회 실패 = 비로그인 → /signin
```

`resolvePostLoginRedirect()` (`web/app/signin/utils/post-login-redirect.ts`)는 **모듈 변수에 저장된 일회용 redirect URL**(주로 OAuth 인증 흐름에서 `setPostLoginRedirect()`로 미리 저장)이 있으면 반환하고 비우는 역할. 평소엔 `null` → `'/apps'` fallback이 그대로 적용됨.

## 현재 디폴트 경로 식별

- **값**: `'/apps'`
- **방식**: **하드코딩 문자열 리터럴**, 7곳에 분산. 환경 변수/설정 분리 없음.
- **공통 상수도 없음** (검색 결과 `DEFAULT_LANDING_PATH` 같은 상수 부재).
- **사용자별/역할별 디폴트 분기 없음**: 모든 시나리오가 동일하게 `/apps`. 단 로그인 *이후* `RoleRouteGuard`가 `dataset_operator` 역할이면 `/datasets`로 강제 이동(`web/app/(commonLayout)/role-route-guard.tsx:9, 22`).

```ts
// role-route-guard.tsx:9-22
const datasetOperatorRedirectRoutes = ['/apps', '/app', '/explore', '/tools'] as const
// ...
useEffect(() => {
  if (shouldRedirect)
    router.replace('/datasets')
}, [shouldRedirect, router])
```

→ 즉 "관리자 vs 일반"으로 갈라지는 코드는 **없음**. 대신 "`dataset_operator`만 분기"되는 단일 가드만 존재.

## 변경 위치 후보 (1~2곳, 핵심 스니펫)

사용자 요구사항이 "전 로그인 사용자 디폴트 = 대시보드"이므로 분기 추가 없이 **fallback 문자열 교체**가 깔끔함. 두 가지 전략:

### 후보 A — **단일 상수 도입 (권장)**

새 모듈을 추가하고 7곳 모두 거기로 import. 디폴트가 한 곳에 모이고 향후 변경/A-B 테스트도 쉬움.

```ts
// web/app/signin/utils/post-login-redirect.ts (확장)
export const DEFAULT_POST_LOGIN_PATH = '/dashboard'   // ← 단일 진실
```

각 호출 지점:

```ts
// before
router.replace(redirectUrl || '/apps')
// after
router.replace(redirectUrl || DEFAULT_POST_LOGIN_PATH)
```

장점: 분기점 7곳이 동일 의미를 공유함을 코드로 표현. 단점: import 라인 7개 추가.

### 후보 B — **`AppInitializer`에서 일괄 처리**

각 로그인 폼은 `router.replace('/')`처럼 중립 경로로 보내고, 진입점인 `AppInitializer`가 *항상* `/dashboard`로 redirect. 단점은 `AppInitializer`가 `(commonLayout)`만 감싸므로 `/apps` 직접 진입 시 적용 안 됨 → 추가 가드 필요. **분기점이 이미 7곳에 흩어져 있어 후보 A가 더 단순**함.

---

## 의사코드 (변경 예시만, 실제 변경 X)

```ts
// 1) web/app/signin/utils/post-login-redirect.ts
export const DEFAULT_POST_LOGIN_PATH = '/dashboard'

// 2) 모든 로그인 성공 핸들러에서
import { DEFAULT_POST_LOGIN_PATH, resolvePostLoginRedirect } from '...'
const redirectUrl = resolvePostLoginRedirect()
router.replace(redirectUrl || DEFAULT_POST_LOGIN_PATH)

// 3) /apps로 직접 보내던 곳 (set-password, installForm, one-more-step)도 통일
router.replace(DEFAULT_POST_LOGIN_PATH)
```

### 기존 `/apps`와 공존 시나리오 (참고)

만약 미래에 "사용자가 디폴트 화면을 선택" UX가 필요하면:

```ts
// 사용자 프로필에 default_landing 필드를 두고
const profile = await fetchProfile()
const fallback = profile.default_landing || DEFAULT_POST_LOGIN_PATH  // '/dashboard' | '/apps' | ...
router.replace(redirectUrl || fallback)
```

→ 현재 단계에서는 불필요. **요구가 "전 사용자 → 대시보드"로 이미 단순화**된 만큼 후보 A로 충분.

## 추가 고려사항 (비로그인 가드 + 라우트 미생성 시 404)

### 비로그인 가드

- **서버 미들웨어 없음** (`web/middleware.ts` 부재 확인). Next.js 라우트 자체는 누구나 접근 가능.
- 실질 가드는 **`AppInitializer` (`web/app/components/app-initializer.tsx`)** 에서:
  - `fetchSetupStatusWithCache()` 실패 → `catch` 블록에서 `router.replace('/signin')` (line 96)
  - 즉 *프로필/셋업 상태 조회 API가 401* 이면 자동으로 `/signin` 이동
- `(commonLayout)` 레이아웃이 `AppInitializer`로 감싸져 있어(`web/app/(commonLayout)/layout.tsx:25-46`), 그 하위 모든 페이지(`/apps`, `/datasets`, 신설할 `/dashboard`)는 동일 가드 혜택. → **신규 `/dashboard`를 `(commonLayout)` 하위에 만들면 가드는 자동 적용**.
- `Splash` 컴포넌트(`web/app/components/splash.tsx`)는 주석에 "would auto redirect"라고 적혀 있지만 실제 코드는 **로딩 오버레이만 표시하고 redirect 안 함**. 진짜 가드는 `AppInitializer` 쪽이 담당.

### 대시보드 라우트 미생성 상태에서 디폴트 변경 시 404

- `/dashboard` 페이지 파일(`web/app/(commonLayout)/dashboard/page.tsx`)이 없는 상태에서 fallback만 바꾸면 **모든 로그인 직후 404**. 배포 순서가 매우 중요함.
- 안전한 순서:
  1. `web/app/(commonLayout)/dashboard/page.tsx` 신설 (현재 모달 안 마운트된 컴포넌트 재활용)
  2. 동작 확인 (수동 `/dashboard` 진입)
  3. **그 다음에** fallback을 `/dashboard`로 교체
- 임시 방어책으로 `DEFAULT_POST_LOGIN_PATH` 도입 + ENV 토글(`NEXT_PUBLIC_DEFAULT_LANDING`)을 두면 페이지 신설 전엔 `/apps`, 신설 후 ENV로 전환 가능. 다만 요구가 단순하므로 굳이 필요 없으면 생략.
- 마운트 환경 주의 (CLAUDE.md 발췌): 현재 대시보드는 *설정 모달의 탭*으로만 존재. 일반 라우트로 이전 시 페이지 자체 헤더/제목, URL 동기화 등을 새로 설계해야 함(현재는 모달이 제목·ESC 닫기 담당).
- `RoleRouteGuard`의 `datasetOperatorRedirectRoutes` 배열(`role-route-guard.tsx:9`)에 `/dashboard`를 포함할지 결정 필요. **포함 안 하면** dataset_operator 사용자도 `/dashboard` 접근 가능. 요구가 "전 사용자 디폴트"이므로 포함하지 않는 것이 자연스러움.

## 참고: 미체크 항목

- 백엔드(`api/`)에는 로그인 redirect 분기가 없음을 가정 (Dify는 토큰만 발급, redirect는 프론트가 결정). 필요 시 별도 확인.
- `/apps`로 보내는 다른 부수 호출(헤더 로고 클릭 → `account/(commonLayout)/header.tsx:17`, 앱 삭제 후 `app/[appId]/layout-main.tsx:145` 등)은 **로그인 직후 디폴트와는 무관**하므로 본 변경 범위에서 제외 가능. 단 통일성을 위해 같이 바꿀지 별도 결정.
